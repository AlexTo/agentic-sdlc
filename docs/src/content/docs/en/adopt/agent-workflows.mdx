**You'll end with:** workflows that open issues from specs, send the agent back on red CI or a
"changes requested" review, and archive a spec once every task is ticked.

<Steps>

1. **Copy the four workflows** from this repository's `.github/workflows/`: `agent-issues.yml`,
   `agent-ci.yml`, `agent-review.yml`, and `agent-status.yml`, which holds the steps the two status
   workflows share. Change the `@agentic-sdlc/` scope in them. Their triggers and permissions are
   listed in [Reference: workflows](../../reference/workflows/).

2. **Check the `if:` conditions match your decisions.** If you changed the branch prefix or the
   labels, change them here too:

   ```yaml
   # agent-issues.yml
   if: >-
     github.event_name == 'workflow_dispatch' ||
     (github.event.pull_request.merged == true &&
     ((github.event.action == 'closed' &&
     (contains(github.event.pull_request.labels.*.name, 'spec-ready') ||
     startsWith(github.event.pull_request.head.ref, 'openhands/'))) ||
     (github.event.action == 'labeled' &&
     github.event.label.name == 'spec-ready')))

   # agent-ci.yml
   if: >-
     github.event.workflow_run.event == 'pull_request' &&
     startsWith(github.event.workflow_run.head_branch, 'openhands/') &&
     (github.event.workflow_run.conclusion == 'failure' ||
     github.event.workflow_run.conclusion == 'timed_out')

   # agent-review.yml
   if: >-
     startsWith(github.event.pull_request.head.ref, 'openhands/') &&
     github.event.pull_request.head.repo.full_name == github.repository &&
     contains(github.event.review.body, 'CHANGES REQUESTED')
   ```

3. **Keep the permissions and the checkout exactly as copied.** Each workflow asks only for what
   it writes. `pull-requests: write` looks spare but isn't: labels and comments on a PR go through
   the issues API, which refuses the workflow token without it.

   The two status workflows check out the **default branch**, in `agent-status.yml`. Agent Issues checks out the
   **merge commit**, so it sees the ticks the merged PR made. Never change either to check out the
   PR's head: these jobs hold a token that can write.

4. **Keep the lock before the label.** Agent Issues opens each issue without its `openhands`
   label, locks its conversation so only collaborators can comment on what the agent reads, and
   only then adds the label. If the lock fails, the label is never added and the run fails, naming
   the issue to lock by hand. The code is `helpers/conversation-lock.ts`.

5. **Keep the concurrency groups.** Each is per PR or per branch, with `cancel-in-progress: false`.
   That way two events for one PR can't each count an attempt, and merges of different PRs never
   cancel each other.

6. **Copy `archive-specs.yml`**, if you want finished specs moved out of the way. When a push to
   `main` changes a live `specs/*/tasks.md`, it prepares a PR on branch `archive-spec/<folder>`
   for each spec with every task ticked, **(human)** ones included. The PR moves the folder to
   `specs/_archive/` and rewrites the links to and from it. Agent Issues skips `specs/_archive/`,
   and `Tasks format` fails if an archived `tasks.md` has an unticked task.

   It skips a spec with an open agent issue, and one that already had an archive PR. Close that
   PR unmerged to keep the spec live.

   <Aside type="caution">
   Leave the repository setting "Allow GitHub Actions to create and approve pull requests" off,
   as `scripts/setup-repository.sh` does: it would also let a workflow approve a PR. The
   workflow then pushes the branch and its run warns with a link that opens the PR, title and
   body filled in, for you to submit. A PR you open starts PR Checks by itself. Until someone
   does, each run pushes the branch again and repeats the warning.
   </Aside>

</Steps>

## Check it worked

The workflows appear under the repository's **Actions** tab after they reach `main`. Open
**Actions → Agent Issues → Run workflow**, and enter a spec folder that doesn't exist, such as
`does-not-exist`.

The run succeeds with a notice: `No issue created: no spec folder with a tasks.md was found`.

<Aside type="note">
`workflow_run` and `pull_request_review` workflows only run from the version on the default branch.
Changes to them take effect once they are merged. That is also why an agent can't change them in its
own PR.
</Aside>
