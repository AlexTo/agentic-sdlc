import { Steps, Aside } from '@astrojs/starlight/components';

**You'll end with:** a Trivy scan on every push to `main`, a Deploy workflow that ships each green
`main` to a development stage, production deploys that wait for a person, and, if you want it, a
Tester agent that tests each merged change on the development stage.

This repository ships the workflows, off: `deploy.yml` runs only by hand or once
`AUTO_DEPLOY_STAGE` is set, and `post-merge-verify.yml` runs only after a deploy. The notes app has
no cloud infrastructure, so the part to write is yours. The steps say AWS and CDK, as Discava uses,
but the shape works for any cloud.

<Steps>

1. **Add a `trivy` target** to the projects you want scanned (the root `pnpm trivy` runs
   `nx run-many --target trivy --all`). The `trivy` job in the copied `ci.yml` runs it on every
   push to `main`, as a separate job from `build`, so a newly published CVE flags `main` without
   blocking anything else. Record accepted findings, one ID per line, in `.trivyignore`.

2. **Add your infrastructure** as a CDK app at `packages/infra`, with a stage per environment in
   its `src/main.ts`:

   ```bash
   pnpm nx g @aws/nx-plugin:ts#infra --name=infra
   ```

   Its `deploy-ci` target is what the Deploy workflow runs. The constructs for the notes website
   are already in `packages/common/constructs`.

3. **Set up keyless cloud access** for each stage: the GitHub OIDC provider, a deploy role
   trusted only for `repo:owner/repo:environment:<stage>`, a CloudFormation execution role with a
   permissions boundary, the CDK bootstrap, and a GitHub environment named after the stage with
   the variables `AWS_REGION`, `AWS_DEPLOY_ROLE_ARN` and `AWS_EXECUTION_ROLE_ARN`. Discava's
   [`scripts/setup-stage.sh`](https://github.com/AlexTo/discava/blob/main/scripts/setup-stage.sh)
   does all of it for its stages; read it before adapting it. Don't store access keys.

4. **Copy `.github/workflows/deploy.yml`**, if you aren't working in a fork, and change its
   `@agentic-sdlc/` scope and the default stage name. It checks out the commit CI verified, stops
   early with a clear error if `packages/infra` or the environment's variables are missing, runs
   Trivy, synthesizes, and deploys only if the commit is still `main`'s latest. That freshness
   check sits *inside* the job's concurrency slot, so it reflects `main` right before the deploy,
   even if the run waited behind another one.

5. **Turn on automatic deploys** for the development stage. Under **Settings → Secrets and
   variables → Actions → Variables**, add a repository variable `AUTO_DEPLOY_STAGE` with your
   development stage's name.

6. **Protect production.** Under **Settings → Environments**, open your production stage's
   environment and add **Required reviewers**. To deploy it, open **Actions → Deploy → Run
   workflow** and enter the production stage. The job then waits for approval.

7. **Add the Tester agent**, if you want each deployed change tested (gap 11). From this
   repository you already have its glue (`post-merge-test/` in step 5), its issue template (step
   4), and `.github/workflows/post-merge-verify.yml`, which opens a test issue for each pull
   request a Deploy run put on the test stage. It tests on `TEST_STAGE`, a repository variable
   that defaults to `AUTO_DEPLOY_STAGE`.

   On the OpenHands side, add a `tester` agent profile and an automation that polls for issues
   labelled `openhands-test`. There is no catalog template for it. Discava's worker and its prompt
   are described on [OpenHands setup](../../discava/openhands-setup/#tester-github-issue-tester)
   and [The agents' prompts](../../discava/agent-prompts/#tester). Give the Tester:

   - a cloud CLI signed in to the development account, with as little access as testing needs
   - one test user per role in your app, stored as OpenHands secrets
   - a browser it can drive, such as Playwright with Chromium

   <Aside type="caution" title="Public repository? Limit comments to collaborators first">
   The Tester reads issues, pull requests and their comments while holding those credentials. If
   your repository is public, a stranger's comment can carry instructions to it.
   `scripts/setup-repository.sh` limits interactions to collaborators, for at most six months, so
   run it again before the limit ends. Also keep the locking in `helpers/conversation-lock.ts`,
   keep the "how to test" in the automation's own prompt instead of the issue, and never point it
   at a stage whose data matters.
   </Aside>

</Steps>

## Check it worked

Merge any PR. CI runs, then **Deploy** starts by itself with the development stage. Run CI again
by hand on an older commit: Deploy logs `Skipping deploy: no longer main's latest commit` and
ships nothing.

With the Tester set up: after that deploy, **Post-merge Verify** opens a locked issue titled
`test(post-merge): verify #<pr> …`, labelled `openhands-test`. Within one poll, the Tester starts,
and its report appears as a comment on the issue.

<Aside type="note">
No agent deploys, and none sees these roles. The Developer and the Reviewer need only the GitHub
token. The Tester's access to the development account is separate from the deploy role, which is
assumed only by a workflow running from `main`, in the stage's environment.
</Aside>
