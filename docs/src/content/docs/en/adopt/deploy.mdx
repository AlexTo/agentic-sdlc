import { Steps, Aside } from '@astrojs/starlight/components';

**You'll end with:** a Trivy scan on every push to `main`, a Deploy workflow that ships each green
`main` to a development stage, production deploys that wait for a person, and, if you want it, a
Tester agent that tests each merged change on the development stage.

This step is Discava-specific in its details (AWS, CDK), but the shape works for any cloud. The
example notes app in this repository has no deploy, so copy from
[Discava's `deploy.yml`](https://github.com/AlexTo/discava/blob/main/.github/workflows/deploy.yml).

<Steps>

1. **Add a `trivy` target** to the projects you want scanned (the root `pnpm trivy` runs
   `nx run-many --target trivy --all`). Add the `trivy` job to `ci.yml`, as in this repository. Keep
   it a separate job from `build`, so a newly published CVE flags `main` without blocking anything
   else. Record accepted findings, one ID per line, in `.trivyignore`.

2. **Set up keyless cloud access.** On AWS, Discava's `scripts/setup-stage.sh` creates, per stage:
   the GitHub OIDC provider, a deploy role trusted only for
   `repo:owner/repo:environment:<stage>`, a CloudFormation execution role with a permissions
   boundary, and the GitHub environment's variables (`AWS_REGION`, `AWS_DEPLOY_ROLE_ARN`,
   `AWS_EXECUTION_ROLE_ARN`). Use your cloud's OIDC federation for GitHub Actions the same way.
   Don't store access keys.

3. **Add the Deploy workflow**, triggered by CI completing on `main` and by hand:

   ```yaml
   on:
     workflow_run: { workflows: [CI], types: [completed], branches: [main] }
     workflow_dispatch:
       inputs: { stage: { type: string, required: true } }

   jobs:
     deploy:
       if: ${{ github.event_name == 'workflow_dispatch' ||
               (github.event.workflow_run.conclusion == 'success' && vars.AUTO_DEPLOY_STAGE != '') }}
       environment: ${{ inputs.stage || vars.AUTO_DEPLOY_STAGE }}
       concurrency: { group: 'deploy-${{ inputs.stage || vars.AUTO_DEPLOY_STAGE }}', cancel-in-progress: false }
       steps:
         - uses: actions/checkout@<sha>
           with: { ref: '${{ github.event.workflow_run.head_sha || github.sha }}' }
         # init, then: pnpm trivy, configure credentials (OIDC), synth
         - name: Check commit is still main's latest
           id: freshness
           if: ${{ github.event_name == 'workflow_run' }}
           run: |
             main_sha="$(git ls-remote --exit-code origin refs/heads/main | cut -f1)"
             if [[ "$main_sha" == "$(git rev-parse HEAD)" ]]; then
               echo "current=true" >> "$GITHUB_OUTPUT"
             else
               echo "::notice::Skipping deploy: no longer main's latest commit"
               echo "current=false" >> "$GITHUB_OUTPUT"
             fi
         - name: Deploy
           if: ${{ github.event_name != 'workflow_run' || steps.freshness.outputs.current == 'true' }}
           run: pnpm nx run @your-scope/infra:deploy-ci "$STAGE/*" --role-arn "$AWS_EXECUTION_ROLE_ARN"
   ```

   The freshness check sits *inside* the concurrency slot, so it reflects `main` right before the
   deploy, even if the run waited behind another one.

4. **Turn on automatic deploys** for the development stage. Under **Settings → Secrets and
   variables → Actions → Variables**, add a repository variable `AUTO_DEPLOY_STAGE` with your
   development stage's name.

5. **Protect production.** Under **Settings → Environments**, open your production stage's
   environment and add **Required reviewers**. To deploy it, open **Actions → Deploy → Run
   workflow** and enter the production stage. The job then waits for approval.

6. **Add the Tester agent**, if you want each deployed change tested (gap 11). This is the newest
   piece, and it lives in Discava, not in this repository. Copy from there:

   - `packages/tooling/agent/src/post-merge-test/` and `src/helpers/`, with the Nx target
     `post-merge-test`
   - `.github/workflows/post-merge-verify.yml`
   - `.github/ISSUE_TEMPLATE/test-deployed-pr.md`, for opening a test issue by hand

   Then set the stage name (`TEST_STAGE`), and the paths that never reach a deployed stack
   (`NOT_DEPLOYED` in `plan.ts`), to match your repository.

   On the OpenHands side, add a `tester` agent profile and an automation that polls for issues
   labelled `openhands-test`. There is no catalog template for it. Discava's worker and its prompt
   are described on [OpenHands setup](../../discava/openhands-setup/#tester-github-issue-tester)
   and [The agents' prompts](../../discava/agent-prompts/#tester). Give the Tester:

   - a cloud CLI signed in to the development account, with as little access as testing needs
   - one test user per role in your app, stored as OpenHands secrets
   - a browser it can drive, such as Playwright with Chromium

   <Aside type="caution" title="Public repository? Limit comments to collaborators first">
   The Tester reads issues, pull requests and their comments while holding those credentials. If
   your repository is public, a stranger's comment can carry instructions to it. Before you turn
   it on, open **Settings → Moderation options → Interaction limits** and choose **Limit to
   repository collaborators**. The limit lasts at most six months, so note when to renew it.

   Also keep the locking in `helpers/conversation-lock.ts`, keep the "how to test" in the
   automation's own prompt instead of the issue, and never point it at a stage whose data matters.
   </Aside>

</Steps>

## Check it worked

Merge any PR. CI runs, then **Deploy** starts by itself with the development stage. Run CI again
by hand on an older commit: Deploy logs `Skipping deploy: no longer main's latest commit` and
ships nothing.

With the Tester set up: after that deploy, **Post-merge Verify** opens a locked issue titled
`test(post-merge): verify #<pr> …`, labelled `openhands-test`. Within one poll, the Tester starts,
and its report appears as a comment on the issue.

<Aside type="note">
No agent deploys, and none sees these roles. The Developer and the Reviewer need only the GitHub
token. The Tester's access to the development account is separate from the deploy role, which is
assumed only by a workflow running from `main`, in the stage's environment.
</Aside>
