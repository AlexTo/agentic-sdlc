**You'll end with:** `pnpm dev` starting the whole app with local stand-ins, a Playwright suite CI
runs on every PR, screenshots posted on the PR, and invariants checked after each test.

This is the step that depends most on your stack. It is also what lets CI give the agent real
feedback without cloud credentials.

<Steps>

1. **Give every cloud service a local stand-in**, started by a `dev` target, so `pnpm dev` runs
   everything. This repository's `packages/tooling/local-dev/` starts DynamoDB local in Docker for
   the notes table. [Discava's stand-ins](../../discava/local-stack/#what-runs-locally) also cover
   S3, SQS, OpenSearch and Cognito, plus an "event runner" process that calls the same handlers
   that Lambda triggers, streams and EventBridge call in the cloud.

   Switch backend code on one flag (`LOCAL_DEV=true`), with the endpoints in one shared module.
   List what still only runs in the cloud in your contributing guide, and mark tasks that need it
   **(human)**.

2. **Copy the e2e project** from this repository, `packages/e2e/`, and replace its scenario with
   yours, one file per user flow. What to keep:

   <FileTree>
   - packages/e2e/
     - playwright.config.ts reads `E2E_SHARD` so the CI matrix can split the suite, starts `pnpm dev`, one worker, retries only in CI
     - src/helpers/
       - screenshots.ts `screenshot(page, 'name')`, which saves the pictures the PR Checks `e2e` job uploads
       - table-invariants.ts a Playwright `test` that checks invariants after every scenario
   </FileTree>

   Each scenario makes its own users and uniquely named data, and none resets local data, so they
   run in any order. Call `screenshot` where a person would look, after an `expect` on what shows:

   ```ts
   await expect(page.getByRole('heading', { name: 'Reviews' })).toBeVisible();
   await screenshot(page, 'reviews section with three reviews');
   ```

3. **Copy the invariants** from `packages/notes-table/src/helpers/invariants/` into the package
   that owns your table. For each rule that spans records written by different code (counters,
   aggregates, ordering), write a check that scans a snapshot of the data and returns violations,
   with a unit test that breaks it. `packages/notes-table/README.md`, "Rules that span records",
   walks through adding one.

   Scenarios take `test` from `table-invariants.ts` instead of `@playwright/test`. After each
   one, it fails the scenario if the table has a violation it didn't have before. Only *new*
   violations count, so old local data never fails a run, and `expect.poll` gives background work
   (stream handlers, recalculation) time to catch up.

4. **Generate the writer map, and copy the pre-push hook.** Run
   `pnpm nx run @your-scope/tooling-agent:entity-writers` and commit the `entity-writers.json` it
   writes. Copy `.husky/pre-push` from this repository, with its `MAP` and `PATHS` pointed at
   yours: when a branch changes code that could write the table, it regenerates the map and stops
   the push if it changed. The `Invariant coverage` PR check then compares the map with the base
   branch's, and holds a PR that adds a writer until the invariants name the entity.

5. **Add concurrency tests** for writes two users could race on: fire the same API requests at
   the same moment with `Promise.all`, then assert on the result and the invariants.

</Steps>

## Check it worked

```bash
pnpm nx e2e @your-scope/e2e
ls dist/packages/e2e/screenshots/*/
```

Then open a PR that changes a page and adds one `screenshot(` call. When PR Checks finishes, the PR
has a comment headed **E2E screenshots** that lists the new picture under "Added by this pull
request".

<Aside type="tip">
If your app can't run fully locally yet, start with what can. Even a suite that covers only the
API and the database catches most agent mistakes. Add stand-ins one service at a time, and keep
the rest as **(human)** tasks until then.
</Aside>
