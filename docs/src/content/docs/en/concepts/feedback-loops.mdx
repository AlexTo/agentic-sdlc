**The short version:** when something fails, a workflow marks the PR's head commit with a failing
status. The OpenHands worker sees it on its next poll and asks the same Developer conversation to
fix the same PR. Each loop has a counter in a label, and stops at five. A third loop starts after
the merge: the Tester agent tests the change on the deployed stage.

## The two loops

```d2
direction: right

pr: Developer agent pushes {shape: page}
checks: PR Checks
review: Reviewer agent
you: human review

actions: GitHub Actions {
  style.stroke-dash: 3
  ci: Agent CI Status
  rv: Agent Review Status
}

status: "software-factory/review\n= failure" {shape: document}
worker: "issue-to-PR worker\n(next poll)"

pr -> checks
checks -> review: all finished
checks -> actions.ci: failed
review -> actions.rv: changes requested
review -> you: approved
actions.ci -> status: ci-fix-N
actions.rv -> status: review-fix-N
status -> worker
worker -> pr: revise the same PR
```

| | CI loop | Review loop |
| --- | --- | --- |
| Triggered by | The PR Checks workflow finishing with `failure` or `timed_out` | A review on the PR that the Reviewer agent wrote, ending `🔄 CHANGES REQUESTED` |
| Workflow | Agent CI Status | Agent Review Status |
| Counter labels | `ci-fix-1` … `ci-fix-5` | `review-fix-1` … `review-fix-5` |
| When it gives up | `ci-fix-exhausted`, plus a comment | `review-fix-exhausted`, plus a comment |
| Status description | `CI failed (fix attempt 2 of 5): E2E tests (3/4)` | `Review requested changes (fix attempt 1 of 5): see the review` |

A passing run posts nothing. The next commit starts with no status, so the worker leaves the PR
alone.

## The checks before sending the agent back

Each script refuses to act unless all of these hold:

1. The branch is an agent's: one segment under `openhands/`, such as `openhands/issue-308` or
   `openhands/test-fix-782`. The Developer's worker only revises `openhands/issue-<n>` exactly.
   On any other agent branch the status and labels still mark the PR as sent back, so a person
   sees it.
2. The PR is open.
3. The run or review is for the PR's **current** head commit. An older run is stale.
4. That commit hasn't already been sent back. A re-run of the same checks must not use another
   attempt.
5. For reviews: the review carries the Reviewer's hidden run marker and comes from an account with
   write access or from the agents' own GitHub App, so a person quoting the verdict doesn't
   trigger it.
6. Fewer than five attempts have been used.

The label goes on **before** the status is posted. If posting the status then fails, the next
failure counts one more attempt instead of repeating this one forever.

## Why five

One retry fixes most mistakes: a flaky locator, a missed type, a lint rule. The next few cover a fix
that uncovered a second problem, or a CI run and a review that each ask for something different. By
the fifth failure, the agent is usually stuck on something it can't see, and more attempts cost
money without converging. Discava started with a cap of three and raised it to five.

Of Discava's first 67 merged agent PRs, 42 carry no fix label (some predate the fix-up workflows),
17 needed exactly one round, and only one ran a loop to exhaustion.

<Aside type="caution">
When a loop is exhausted, read the last failure before you fix anything. Repeated failure often
means the spec or plan was ambiguous, and the agent was trying to satisfy two readings at once. Fix
the spec, then let the agent try again.
</Aside>

To give the agent another round afterwards, see
[Resetting a loop](../../reference/labels/#resetting-a-loop).

## After the merge: the test loop

The two loops above end at the merge. Everything they checked ran on a local stack, so one
question is still open: does the change work where it is deployed? When the repository deploys
`main` to a development stage, a third loop answers it.

```d2
direction: down

deploy: "Deploy\n(merged PRs reach the development stage)"
verify: "Post-merge Verify\n(GitHub Actions)"
issue: "test issue\nopenhands-test" {shape: page}
tester: Tester agent
stage: development stage {shape: cylinder}
report: report on the issue {shape: document}
you: a person

deploy -> verify: deployed
verify -> issue: one per PR
issue -> tester: next poll
tester -> stage: "UI, APIs, stored data"
tester -> report
report -> you: left open on a fail
```

| | Test loop |
| --- | --- |
| Triggered by | A deploy of `main` to the development stage finishing |
| Workflow | Post-merge Verify opens one test issue per merged PR that changed something deployed |
| Agent | The Tester: it clicks through the change in a real browser, calls the APIs, and then verifies what was written to storage (database records, stored files, search documents) and the logs |
| On a pass | A report with every check and its evidence, and the issue is closed |
| On a fail | The same report with steps to reproduce, and the issue stays open. If the cause is clear and the fix small, the Tester also opens a fix PR, which goes through the same checks, Reviewer and human review as any other |

This loop has no counter, because nothing is sent back by itself. A failed test ends with a person:
they read the report and decide whether to merge the fix PR, write a new task, or change the spec.
To test again, remove and re-apply the `openhands-test` label.
