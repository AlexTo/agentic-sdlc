Everything in this workflow follows from one move: **take the developer out of the loop and put
them at its two ends.** Humans decide *what* to build and *whether it is good*. Agents do
everything in between, through the normal GitHub process.

The rest of this guide refers back to these principles by number.

<Aside type="tip" title="Verification matters most">
Verification is the most important step. An agent that can't run the app and see what it built
is guessing, and every other principle only organises the guesses.
</Aside>

## 1. The spec is the source of truth

A feature starts as `spec.md`, `plan.md` and `tasks.md`, reviewed like code. The agent builds from
them. To change behaviour, change the spec and regenerate the plan and tasks. Don't patch the code
by hand and let the spec go stale.

## 2. Every step leaves an artifact

Intent lives in the spec, scope in the issue, history in the pull request, and the reason a run
stopped in a label or a comment. Nothing lives only in a chat window or in someone's head, so a new
teammate or a new agent can pick up where the last one stopped.

## 3. Small, scoped units of work

A spec splits into phases. Each group of phases is one issue and one pull request, with a task
range the agent must not leave. Small PRs are cheap to review and cheap to throw away.

## 4. Verification is the most important step: give the agent hands and eyes

Code that compiles and passes its unit tests can still fail the user. The agent has to **run what
it built and interact with it, from the back end to the front end**, the way a person would:

- **Hands:** start the whole app on a local stack with no cloud account, call the API, sign in as a
  user, click through the flow in a real browser, and trigger the background work behind it.
- **Eyes:** read what comes back: responses, logs, the data left in the database, and screenshots
  of every state a reviewer would want to see.

The agent doesn't need to do this on its own machine. In this workflow it writes the e2e scenarios,
and GitHub CI runs them on every PR against a fresh local stack. The results, invariant failures
and screenshots come back on the PR for the agent to read, so its own environment stays simple.

Without hands and eyes the agent writes code it has never seen work, and a person has to pull the
branch to find out. With them, the agent catches its own mistakes and every PR arrives with
evidence. Build for this from day one: every cloud service needs a local stand-in, every user flow
an e2e scenario, and every UI state a screenshot. Anything the agent can't run locally is a task a
person has to verify.

## 5. Automated gates give the feedback, not you

Lint, typecheck, unit tests, invariants, e2e tests, concurrency tests, screenshots and an agent
reviewer run on every PR. A red result goes straight back to the agent that wrote the change.
Nobody pastes an error message.

## 6. Bounded autonomy

The agent can't merge, can't edit workflows, can't touch cloud credentials, and can't weaken a test
to get green. Each fix-up loop is capped at five attempts. Then it stops and asks a person.

## 7. Humans keep the two decisions that matter

1. **Approve the spec.** Merging the spec PR with the `spec-ready` label is the go signal.
2. **Approve the result.** A person does the final review and merges each PR.

## 8. The glue is code, not prompts

Anything that decides *what happens next* (which issue opens, whether the agent goes back, when to
stop) is a deterministic script with unit tests, run by a workflow. The agent is only asked to do
what needs judgment: write the code, and review it. A prompt can be ignored. A workflow can't.

## 9. Make rules and skills deterministic

Principle 8 covers the glue between steps. This one covers the rules and skills the agent follows
inside a step. A rule written only in `AGENTS.md` or the constitution is a request. The agent may
miss it, read it two ways, or forget it in a long session. Wherever a rule can be checked by a
script, write the script, run it in a hook or a PR check, and keep the prose as the explanation.
A failed check tells the agent exactly what is wrong and where, and it goes back through the same
feedback loop as any other red result.

Discava does this throughout:

- **Task format.** The agent workflow reads `tasks.md` with a parser. A file that strays from the
  format isn't refused; its phases are silently skipped. So the `Tasks format` PR check runs a
  validator on every `tasks.md`, and the workflow that opens issues refuses a file that fails it.
- **Screenshots of UI changes.** The constitution says a change to what a user sees must take
  screenshots in its e2e scenario. The `UI Screenshots` check reads the PR's diff and fails if a
  portal's markup or styles changed but no scenario gained a `screenshot(` call. A maintainer can
  waive it with the `no-ui-screenshots` label.
- **Invariants for shared records.** The constitution says a rule that spans records needs a check
  in `invariants.ts`. The `Invariant coverage` check scans which code writes the core table, and
  fails if a new writer arrives without an invariant naming its entity. A pre-push hook regenerates
  the writer map, so the agent finds out before CI does.
- **Commits.** Conventional Commits are enforced by commitlint in a `commit-msg` hook, and
  `git-secrets` runs on every commit.
- **Skills that call scripts.** The Speckit skills don't describe how to create a feature branch or
  commit a step. They run `create-new-feature.sh` and `auto-commit.sh`, and Speckit's extension
  hooks run them before and after each command, whether or not the agent remembers to.

Leave the judgment to the agent and move everything checkable into code. If you write the same
correction in a review twice, it's probably a missing check.
