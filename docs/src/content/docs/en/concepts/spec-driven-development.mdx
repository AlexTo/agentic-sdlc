**The short version:** a person and an agent write down what to build, how, and in what order,
before any code exists. The written result is reviewed like code and merged. From then on every
agent run reads the same files, so the result doesn't depend on who phrased the prompt.

## Why not just prompt?

A prompt is gone once the chat ends. It can't be reviewed, it differs every time someone types it,
and the agent forgets it halfway through a long task. A spec in the repository fixes all four
problems:

| A prompt | A spec |
| --- | --- |
| Lives in one person's chat history | Lives in `specs/`, under version control |
| Nobody reviews it before work starts | Goes through a pull request |
| Re-typed for every run, slightly differently | Read, word for word, by every run |
| Says what to build, rarely why | States user stories, requirements and acceptance criteria |

## The four documents

[Speckit](https://github.com/github/spec-kit) is a set of agent commands and templates that
produce these, one step at a time:

| Command | Writes | Answers |
| --- | --- | --- |
| `/speckit-constitution` | `.specify/memory/constitution.md` | The rules every plan must obey, for the whole project. Written once, amended by PR |
| `/speckit-specify` | `spec.md` | **What and why.** User stories, functional requirements, acceptance scenarios. No technology |
| `/speckit-clarify` | updates `spec.md` | Up to five targeted questions, with answers written back into the spec |
| `/speckit-plan` | `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md` | **How.** The technical approach, checked against the constitution |
| `/speckit-tasks` | `tasks.md` | **In what order.** Checkable tasks, grouped into phases |
| `/speckit-analyze` | a report | Requirements with no task, tasks with no requirement, contradictions between the files |

Each feature gets its own folder, for example `specs/20261116-013307-course-reviews/`.

## The constitution

The constitution is the most underrated piece. It holds the project's non-negotiable rules,
written so a plan can be checked against them: "a feature MUST work under `pnpm dev` with no cloud
account", "a failing test MUST be fixed in the code, not by weakening the test". Every
`/speckit-plan` run fills in a **Constitution Check** section and must justify any violation.

Because every agent reads it before it writes code, the constitution is where you put the rules
that make agent output trustworthy. See
[Discava's constitution](../../discava/constitution-and-guidance/) for a full example.

<Aside type="tip">
When a reviewer keeps making the same comment on agent PRs, that comment belongs in the
constitution or in `AGENTS.md`. Then the next agent follows it instead of being caught by it.
</Aside>

## `tasks.md` is a contract with the automation

Speckit treats `tasks.md` as a document for people. In this workflow, a script also reads it, to
decide which tasks the agent gets next. So its format is fixed and checked on every PR:

```markdown
## Phase 1: Setup
- [ ] T001 Create the review entity in packages/databases/core-table/src/entities/review.ts

## Phase 3: User Story 1 - Leave a rating (Priority: P1) 🎯 MVP
- [ ] T010 [P] [US1] Unit tests for rating rules
- [ ] T011 [US1] review.upsert procedure
- [ ] T012 (human) Check the layout on a phone-width window
```

- Phases are `## Phase <n>: <title>`, numbered upwards.
- The first `User Story` phase ends the first issue. Setup, foundations and the MVP story ship
  together. Every later phase is its own issue.
- Tasks are `- [ ] T<3 digits> ...`, ticked in place, never renumbered.
- **(human)** marks a task the agent skips and lists in its PR for the reviewer.

The full rules are in [Reference: tasks.md format](../../reference/tasks-format/).

## Change the spec, not the code

When behaviour has to change, go back to the spec, update it, and regenerate the plan and tasks.
New tasks take the next unused ID, so the automation opens an issue for them like any other. If you
fix the code by hand instead, the spec stops describing the product, and the next agent that reads
it builds the old behaviour back.
