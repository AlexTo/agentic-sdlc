**The short version:** OpenHands runs three scheduled automations against your repository, one per
agent role. The **Developer** implements labelled issues and revises pull requests that have been
marked as failing. The **Reviewer** reviews pull requests once their checks finish. The **Tester**
tests each merged change on the deployed development stage. Each starts an ordinary coding agent
with a fixed prompt. None needs you to open a chat.

## The three roles

| Role | Automation | Starts from | Leaves behind |
| --- | --- | --- | --- |
| **Developer** | GitHub issue to PR | An issue labelled `openhands`, or a failing `software-factory/review` status on its own PR | A pull request on `openhands/issue-<n>`, and its revisions |
| **Reviewer** | GitHub code review | A PR labelled `openhands-review`, once every check has finished | A review ending `✅ APPROVED` or `🔄 CHANGES REQUESTED` |
| **Tester** | GitHub issue tester | An issue labelled `openhands-test`, opened after a deploy | A test report on the issue, with evidence from the UI, the APIs and the stored data, and sometimes a small fix PR |

The Developer and the Reviewer are all a repository needs to run the loop up to the merge. The
Tester needs somewhere deployed to test, so it comes with [automatic deploys](../../adopt/deploy/).
The example app in this repository has no deploy, so a fork runs the first two.

```d2

```

## The parts

| Part | What it is |
| --- | --- |
| **Agent Canvas** | The OpenHands app you run yourself (`npx @openhands/agent-canvas`). It bundles the agent server, the automation backend and a web UI |
| **Agent profile** | Which agent runs, and with which model. A profile can be OpenHands' own agent with any LLM, or an external coding agent over ACP (the Agent Client Protocol) |
| **Automation** | A small Python worker that runs on a cron schedule. It reads GitHub, decides what to do, and starts or resumes agent conversations. Installed from the Agent Canvas catalog |
| **Secret** | A named credential, such as the GitHub token. A conversation is handed only the secrets on its allow-list |

## The three automations

### Developer: GitHub issue to PR

On every poll, for each repository it watches, the worker:

1. Finds open PRs on `openhands/issue-<n>` branches whose head commit carries a commit status named
   `software-factory/review` in state `failure` or `error`. For each one it sends a **revise** turn
   to that issue's conversation: read the reviews, comments and failing checks, fix them, and push
   to the same branch.
2. Finds open issues with the trigger label (`openhands`) that have no PR yet, and starts an
   **implement** turn: clone, create `openhands/issue-<n>`, implement, test, push, open the PR, and
   add the `openhands-review` label.

Each issue is one *subject* with a stable conversation. A revise goes to the same conversation as
the original implementation, so the agent keeps its context.

### Reviewer: GitHub code review

On every poll, it looks for PRs that carry the `openhands-review` label, have a pending review
request for its account, or are open, non-draft, unrequested and unreviewed. For each, it waits
until **every check on the head commit has finished**, then starts a review of that exact commit.
The review ends with a verdict on its own line: `✅ APPROVED` or `🔄 CHANGES REQUESTED`.

<Aside type="caution">
The issue-to-PR worker only revises a PR when it sees the failing `software-factory/review` status.
Neither a red CI run nor the Reviewer's "changes requested" sets that status by itself. Closing
that gap is two pieces of the [missing glue](../the-missing-glue/).
</Aside>

### Tester: GitHub issue tester

The first two automations come from the Agent Canvas catalog. This one is written by hand, and it
is small: a worker of about a hundred lines, on top of the catalog's GitHub helpers, and a prompt
file.

On every poll, it looks for open issues with the trigger label (`openhands-test`) that were opened
by the workflow's own account, `github-actions[bot]`. For each, it starts a **test** turn: clone
the repository at the commit the stage runs, work out what the merged pull request changed, test
it on the deployed stack, and comment the result on the issue.

The test has three parts, and the third is what sets it apart from clicking through a page:

1. **The UI**, in a real browser, signed in as a test user.
2. **The APIs** behind those screens, called with the test user's token, including the cases that
   should be refused.
3. **The stored data.** After each action, the Tester reads what the change should have written
   and checks it: the database records, the files in storage, the search index, and the logs. In
   Discava that is DynamoDB, S3, OpenSearch and CloudWatch.

Three details keep it safe and quiet:

- **The issue says only what to test.** How to test it (the tools, the test users, the checks, the
  report) is the automation's own prompt, on the machine. Nobody who can edit an issue can change
  it.
- **An issue opened by anyone else is skipped**, because its body would become the agent's
  instructions.
- **One test per labelling.** Each time the label is applied counts once, so the Tester's own
  comments never start a second test. Remove and re-apply the label to test again.

Nothing opens these issues by default. A workflow that opens one for each deployed pull request is
the last piece of the [missing glue](../the-missing-glue/). Discava's is on
[Post-merge verify](../../discava/post-merge-verify/).

## Why polling, not webhooks

The automations poll (every 5 minutes in Discava, every 15 by default), so Agent Canvas can run on
a laptop or a home server with no public URL and no webhook secret. The cost is up to one poll
interval of latency, which is small next to the time the agent takes to work.

## Memory that outlives the run

A conversation keeps its context for one issue. The agents also keep a memory that outlives it.
OpenHands stores it on the machine that runs Agent Canvas, and all three roles read it and write to
it. What one run learns, such as a quirk of the local stack, a check that keeps failing for the
same reason, or a convention the Reviewer keeps asking for, is there for every later run, whatever
the role, the issue or the person who asked for it.

That is the difference from an agent in an editor, where what it learns stays on one developer's
workstation. Here the memory belongs to the runtime, so it builds up across every task the team has
given the agents, not only the tasks one person ran.

<Aside type="caution">
The agents write to the memory directly, and nobody reviews it. A wrong lesson is repeated until
someone removes it, and text an agent read in an issue or a comment can end up in it, which is one
more reason only collaborators may comment. Read the memory now and then. A lesson that is really a
rule belongs in `AGENTS.md`, or better, in a check that enforces it. The memory lives on one
machine, so back it up with the rest of Agent Canvas's state.
</Aside>

## What the agent can and can't reach

The Developer's and the Reviewer's prompts name one secret, the GitHub token, so the Developer can
read the issue and push its branch and the Reviewer can publish its review. Neither needs cloud
access: everything they run, runs on the local stack.

The Tester is the exception. It has to reach the deployed stage, so it works with a cloud CLI
signed in to the development account, which its prompt tells it to use read-only, and a test user
for each role in the app. It never gets the deploy roles, and its prompt forbids changing
infrastructure, deploying, or touching another stage. Because it reads
issues and pull requests while holding those credentials, nobody without write access may comment
on them. On a public repository, that means setting GitHub's interaction limit to collaborators
only.

What else agents may never do, and what enforces each limit, is on
[Human gates](../human-gates/#what-agents-may-never-do).

## Choosing agents

Discava runs all three on **Claude Code over ACP**, each with its own agent profile: Sonnet for
the Developer, Opus for the Reviewer and the Tester. A stronger model for review is deliberate: the
Reviewer is the last check before a person, and it reads far less code than the Developer writes.
The Tester gets the same model because its job is judgment too: deciding what a change should do,
and whether what it sees on the stage, and finds in its storage, is right. Any ACP agent, or OpenHands' own agent with any
LLM, plugs into the same profiles.

The prompt each role runs with is on [The agents' prompts](../../discava/agent-prompts/).
