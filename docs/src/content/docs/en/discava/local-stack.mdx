Gap 8: the agent can't run the real stack without cloud access, and you don't want to give it
cloud access. Discava's answer is constitution principle III: every AWS service has a local
stand-in, and `pnpm dev` starts all of them with Docker.

## What runs locally

| Service | Port | Stands in for |
| --- | --- | --- |
| Student, instructor and admin portals | 4201, 4200, 4202 | CloudFront |
| core-api, instructor-api | 2022, 2023 | API Gateway and Lambda |
| DynamoDB local | 8001 | DynamoDB |
| S3Mock | 9090 | S3 |
| ElasticMQ | 9324 | SQS |
| OpenSearch (Docker) | | OpenSearch Serverless |
| Event runner | 2024 | DynamoDB streams and the stream router, MediaConvert (ffmpeg), Transcribe (a placeholder track), SES (an inbox page), EventBridge, Scheduler, Cognito triggers |
| Local OIDC server | 9400 | Cognito |

Backend code switches on `LOCAL_DEV=true`. The shared settings are in one package
(`common-server-utils/local-dev`), so every Lambda resolves endpoints the same way. Each stand-in
is an Nx target in `packages/tooling/local-dev`, which pulls and starts its container.

The local sign-in page offers fixed users (an instructor, two students, an admin) and a
"Someone else" form for any claims. No passwords, no Cognito.

## Who runs it

The **implementing agent doesn't**. Its issue says not to use `pnpm dev`, Docker or the e2e runner.
It writes the scenarios, and **PR CI** runs them: each e2e shard starts its own `pnpm dev` on a
fresh runner. The agent's machine stays simple, and the result it reads is always from a clean
stack.

People run it for **(human)** tasks, and to reproduce a failure.

## E2E scenarios

`packages/e2e` has one `src/scenarios/*.e2e.ts` per user flow, built from shared helpers.
The rules that make them safe to run in any order, on a shared stack:

- Each scenario makes its own users and uniquely named data.
- No scenario resets local data.
- One worker, one retry on CI, two-minute timeout. Flows wait on background work such as progress
  recalculation.

## Invariants after every test

`packages/databases/core-table/src/helpers/invariants/` holds checks over the whole table, one file
per topic (curriculum, student activity, media, analytics and so on): "a course has an instructor", "a student's activity count matches the students who used the
item", "sibling order is unique", and more than forty others.

A Playwright fixture (`packages/e2e/src/helpers/table-invariants.ts`) runs them **after every e2e
test**. It records the violations that already existed before the test and fails only on new ones,
so old local data can't fail a run. The message names the invariant and the offending record. An
agent that writes a counter wrongly finds out in the test that wrote it, not three features later.

Every rule that spans writers is written through one shared helper that every writer calls (for
example `studentActivityWrites`), and has an invariant and a test that breaks it.

The **Invariant coverage** PR check keeps this honest. `core-table`'s `entity-writers.json` maps
each entity to the files in each package that write it, generated from the code with the
TypeScript compiler. Compared with `main`, the check fails a PR when:

- an entity gains a writing package beside the ones it had,
- a file outside the `core-table` package starts writing an entity that several packages write, or
- a new entity appears.

It passes again once the lines the PR adds under `helpers/invariants/` (tests and fixtures don't
count) name each of those entities or its `TableSnapshot` key, such as `snapshot.enrolments`. The
check also fails while `entity-writers.json` is out of date. A pre-push hook regenerates it and
stops the push if it changed, so the agent finds out before CI does.

### Waiving the check

The check only sees that the set of writers changed. It can't tell whether a rule now spans them,
so a maintainer can waive it: add the `no-new-invariant` label to the PR and re-run the job.

Use the label when the writes moved or were split, but no new rule is at stake. The usual case is a
refactor. When Discava moved helpers out of its API procedures into their own files, existing
writes showed up in new files and tripped the check, but the rules they keep were already covered.

Don't use it to get a feature through. If a new writer means another API or handler now depends on
a record being right, the rule belongs in a `core-table` helper every writer calls, with a check in
`helpers/invariants/`. The label is for a human to apply, not the agent: deciding that no rule is at
stake is the judgment the check exists to force.

## Concurrency tests

`packages/e2e/src/concurrency/` fires API requests at the same moment, straight at the APIs, for
writes two users could race on: issuing a certificate, attaching a caption, the analytics counters.
They run in the same e2e job.

## What still only runs on a deployed stage

The stand-ins aren't perfect, and `CONTRIBUTING.md` lists exactly where they fall short: CloudFront signing,
MediaConvert's exact output, real Transcribe, Cognito Managed Login, EventBridge retries and the
failure queues. Tasks that depend on those are **(human)** tasks, checked on `discava-development`
after deploy.
