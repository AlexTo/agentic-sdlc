Gaps 1 and 7: nothing turns a finished spec into work for the agent, and merging the agent's PR
doesn't start the next phase. Discava fills both with one workflow, **Agent Issues**, and the
script behind it.

## When it runs

`.github/workflows/agent-issues.yml` listens for pull requests to `main` being `closed` or
`labeled`, plus a manual `workflow_dispatch` with a `spec_folder` input. The job runs only when:

| Event | Condition | Meaning |
| --- | --- | --- |
| PR closed | merged, and labelled `spec-ready` | A spec was approved: open the first issue |
| PR closed | merged, and the branch starts with `openhands/` | An agent PR landed: open the next issue |
| PR labelled | merged already, and the label is `spec-ready` | Someone forgot the label before merging |
| Manual run | a spec folder name | Restart a chain by hand |

Any other merged PR is ignored, [even one that touches `specs/`](../../concepts/one-phase-at-a-time/#what-opens-the-next-issue).

The job checks out the **merge commit**, so it sees the ticks the PR just made. Its concurrency
group is per PR, never global: a global group keeps only the newest pending run, so two merges
close together would cancel each other.

## What the script does

```d2
direction: right

merged: merged PR {shape: page}
gate: "agent branch,\nor spec-ready?" {shape: diamond}
ignore: ignore
folder: find the spec folder
valid: "tasks.md valid?" {shape: diamond}
fail: fail the run
next: "next group with\nagent tasks left?" {shape: diamond}
done: done
exists: "issue for it\nalready exists?" {shape: diamond}
stalled: comment on the PR
open: open the issue {shape: page}

merged -> gate
gate -> ignore: no
gate -> folder: yes
folder -> valid
valid -> fail: no
valid -> next: yes
next -> done: no
next -> exists: yes
exists -> stalled: yes
exists -> open: no
```

`pnpm nx run @discava/tooling-agent:agent-issue`, in `src/agent-issues/`:

1. **Gate** (`gate.ts`). `decide()` classifies the PR as `spec`, `implementation` or `ignore`.
2. **Find the spec folder** (`discover.ts`). For an agent PR, it reads the issue that the PR closes
   and takes the folder from that issue's hidden marker. Otherwise, it uses the `specs/<folder>/`
   paths the PR changed.
3. **Validate** (`validate.ts`). A `tasks.md` that fails the format check fails the run, rather
   than handing the agent the wrong tasks.
4. **Group the phases** (`tasks.ts`): everything up to and including the first `User Story` phase,
   then each later phase on its own.
5. **Pick the next group**: the first one with an unticked task that isn't **(human)**.
6. **Check for an existing issue.** Every issue body starts with a marker such as
   `<!-- agent-issue spec:20261116-013307-course-reviews group:3 -->`. If an issue for this group
   already exists (open or closed), the script doesn't open another. A marker counts only in an
   issue opened by the workflow or by someone with write access, so a stranger's issue can't stall
   a spec's chain. It comments on the PR
   instead, for example:

   > The next implementation issue for `specs/…/` was not opened: an issue for "Ratings in search"
   > already exists, and these tasks in its `tasks.md` are not ticked: T017, T018.

7. **Render and create the issue** (`issue.ts`), without a label.
8. **Lock it, then label it** (`helpers/conversation-lock.ts`). The issue is locked, so only people
   with write access can comment on what the Developer agent will read, and only then gets the
   `openhands` label. If the lock fails, the label is never added and the run fails, naming the
   issue to lock and label by hand.

## The issue it opens

A real one, [#466](https://github.com/AlexTo/discava/issues/466):

```markdown
<!-- agent-issue spec:20261116-013307-course-reviews group:3 -->

## Spec

- Spec folder: `specs/20261116-013307-course-reviews/` (read `spec.md`, `plan.md`, `tasks.md`,
  `data-model.md` and `contracts/`)
- Parent issue: #279

## Scope

Tasks `T015` to `T019` of `tasks.md`: every task under Phase 4: Ratings in search (PR 4). Do not
start tasks outside these phases.

## Instructions for the agent

- Read `AGENTS.md`, `.specify/memory/constitution.md` and the spec folder first.
- …the rest of the template's bullets, with `#<parent>` filled in as `#279`
```

The title is a Conventional Commit header built from the folder and the phase:
`feat(course-reviews): ratings in search (PR 4)`. It has a lower-case subject and at most 100
characters, so the agent can reuse it for its PR without failing commitlint. The first group adds
` (with setup and foundations)`.

<Aside type="note">
The standing instructions are read from the issue template at run time, so there is one place to
change them. Editing `.github/ISSUE_TEMPLATE/implement-phase.md` changes every future issue.
</Aside>

## Dry run

```bash
DRY_RUN=true GITHUB_REPOSITORY=owner/repo GITHUB_EVENT_NAME=workflow_dispatch \
  SPEC_FOLDER=20261116-013307-course-reviews \
  pnpm nx run @discava/tooling-agent:agent-issue
```

This prints the title and body of the issue it would open. It still reads existing issues through
`gh`, so you need to be signed in.

## Archiving a finished spec

A second workflow, **Archive Specs** (`.github/workflows/archive-specs.yml`), closes the chain. It
runs on a push to `main` that changes a live `specs/*/tasks.md`, and by hand. It needs its own
trigger because the last tick is usually a **(human)** task, in a PR that Agent Issues ignores.

`pnpm nx run @discava/tooling-agent:archive-specs`, in `src/agent-issues/archive-specs.ts`:

1. Finds each live spec with every task ticked, **(human)** ones included.
2. Skips a spec with an open agent issue, and one that already had an archive PR. Closing that PR
   unmerged keeps the spec live.
3. Pushes branch `archive-spec/<folder>`, which moves the folder to `specs/_archive/` and
   rewrites the links to and from it, and opens its PR.

Agent Issues skips `specs/_archive/`, so an archive PR never opens an issue. The `Tasks format`
check reads archived `tasks.md` files too, and fails if one has an unticked task.

<Aside type="caution">
Discava keeps the repository setting "Allow GitHub Actions to create and approve pull requests"
off, because it would also let a workflow approve a PR. So the workflow's token can push the
branch but not open the PR. The run warns with a link that opens it, title and body filled in,
and a maintainer submits it. A PR a person opens starts PR Checks, which one opened with the
workflow's token wouldn't. Until someone submits it, each run pushes the branch again and repeats
the warning.
</Aside>
