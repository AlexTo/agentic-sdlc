[How it works](../how-it-works/) describes the loop. This page shows it running once, on a real
pull request in [Discava](https://github.com/AlexTo/discava): what a student sees after asking
for a refund on a course they bought.

Every quote, number and link is from GitHub. Times are Sydney time (AEDT, UTC+11), on 25 and 26
November 2026.

From the pull request opening to its merge: four fix rounds, three from CI and one from review,
and one action by a person. Then the Tester found two problems that neither CI nor review could
have seen.

## 1. The issue

A student who asks for a refund sees "Refund requested" while Stripe processes it, and the course
page checks every 2 seconds whether it has gone through. [#1166](https://github.com/AlexTo/discava/issues/1166)
says what was wrong with that:

> While a student's refund is pending, the course page refetches `course.myEnrolment` and
> `payment.myOrder` every 2 s, and never stops. If the refund fails at Stripe or its event never
> arrives, the order stays `paid` with a refund requested, the page keeps polling for as long as
> it is open, and the student isn't told anything has gone wrong.

Its acceptance criteria are two lines: polling stops after a limit, and a failed refund, simulated
in the Stripe stand-in, ends the pending state with a clear message.

This issue didn't come from a spec. The Reviewer agent raised it while reviewing the PR that let
a student ask for a refund, as a problem outside that PR's scope, and it became an issue of its
own. (#1166 is a
copy: the agents' old machine account was flagged by GitHub, which hid everything it had opened,
and the open issues were [opened again](../../discava/openhands-setup/#the-github-app) by the
GitHub App the agents use now.)

## 2. The Developer agent opens the PR

The Developer agent picked the issue up and opened [#1195](https://github.com/AlexTo/discava/pull/1195)
on `openhands/issue-1166`. The change runs through four packages: a 2-minute limit and a "Check
again" button on the course page, a webhook handler for Stripe's failed-refund events, a
`refundFailedAt` field on the order with an invariant that a failure must follow a request, and
"Your refund failed" on the course page. The description ended with what it had and hadn't run:

> Unit tests cover the helper, the webhook, the invariant and the UI (poll limit, check again,
> failure message). [...] I did not run the e2e tests or try the stand-in control in a browser.

## 3. CI sends it back, three times

**`ci-fix-1`: no screenshots, and lines without tests.** The PR changed what a student sees but
took no screenshot, so [**UI Screenshots** failed](https://github.com/AlexTo/discava/actions/runs/45619342535/job/139224403383).
**codecov/patch** failed too: new lines had no test. **Agent CI Status** added `ci-fix-1` and
sent the Developer agent back. Its [reply](https://github.com/AlexTo/discava/pull/1195#issuecomment-7164484931)
shows it found a problem in its own first attempt on the way:

> **UI Screenshots:** added a `learner-refund` e2e scenario for a failed refund, with
> `screenshot(student, 'refund-failed')`. For this the Stripe stand-in has a new
> `fail-next-refund` control. [...] This replaces the `refund-fail` control from the first push,
> which the scenario could not use, because the stand-in completed the refund before it could
> fail.

**`ci-fix-2`: a failure that wasn't its own.** The next run failed in **Checks (build)**, in a
CDK synth test in the infrastructure package. The agent read the log and
[didn't change any code for it](https://github.com/AlexTo/discava/pull/1195#issuecomment-7165688653):

> the one failure was `@discava/infra` `instructor-api-stack.test.ts` [...], which hit its 30s
> timeout while the sibling CDK synth tests in that file took 22–31s. This PR doesn't touch infra
> or anything the stack synthesises [...], so I made no code change for it. The push below
> re-runs the build.

It covered the one partial line codecov still reported, and the push reran the build, which
passed. An agent that "fixes" a failure by changing code it doesn't understand is worse than one
that says the failure isn't its own and why.

**`ci-fix-3`: its own new test was wrong.** After the review (next section) the agent added an e2e
scenario for the 2-minute limit, and it failed in [**E2E tests (11/12)**](https://github.com/AlexTo/discava/actions/runs/45685812586/job/139458011986).
Five minutes later, [the cause](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172674824):

> the new `a pending refund stops polling and offers to check again` scenario failed with a
> Playwright strict-mode violation, not a product bug. `getByText('Still being processed')` also
> matched the alert's description ("Your refund is still being processed…"), so it resolved to two
> elements. The page did reach the timed-out state. I now match the title with `{ exact: true }`.

The agent hadn't run any e2e scenario locally; it said so each time. PR CI is where they first
run, and the [E2E screenshots comment](https://github.com/AlexTo/discava/pull/1195#issuecomment-7163204279)
lists the two screens the run captured: `learner-refund/01-refund-failed.png` and
`learner-refund/01-refund-still-being-processed.png`.

## 4. The Reviewer agent finds what CI couldn't

Once every check on the head had finished, the Reviewer agent read the diff against the issue. It
found the payments code right, reran 361 focused tests itself, and still
[blocked the merge](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6063632214):

> 1. **The branch carries another open PR's change.** Commit `e7cb9bc9`, "fix(student-portal):
>    surface completions and progress load errors on start route", is the change from open PR
>    #1188, not part of #1166. [...] Merging this PR would ship #1188's start-route error behaviour
>    under a payments title, before #1188 is reviewed.
> 2. **Live evidence is missing for the "Still being processed" / "Check again" state.** [...] The
>    new timed-out state [...] has only unit tests, and no capture from the running app.
>
> 🔄 CHANGES REQUESTED

The first point is the kind of thing that gets past every check. The extra commit compiled and
its tests passed; it just didn't belong. The agent's checkout had started from a branch that
already had it. The second point is the screenshot rule again, applied by a reader: CI checks that
a PR adds a screenshot, and the Reviewer checks that every new state has one.

**Agent Review Status** added `review-fix-1`. Eight minutes later the Developer agent
[had](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172386579) rebased its own four
commits onto `main` without the other two, and added a stand-in control that holds a refund
pending and an e2e scenario that installs Playwright's fake clock and fast-forwards 125 seconds.
That is the scenario `ci-fix-3` then corrected.

On the final head the Reviewer [confirmed](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066801083)
both points were resolved, that all 12 e2e shards had passed, and named the two screenshots:
"No material findings [...] ✅ APPROVED".

## 5. A person approves

At 11:33 the maintainer [approved](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066944326)
and merged. That was the only thing a person did on this PR. What they had in front of them: a
description that said what was and wasn't run, the two screenshots from CI, a green check list,
and a trail of four revisions, each with the reason for it.

## 6. The merge is deployed, and a test issue opens

On Discava, `main` deploys by itself to a development stage. The [deploy](https://github.com/AlexTo/discava/actions/runs/45734764281)
carrying this merge finished at 12:28, and a minute later **Post-merge Verify** opened
[#1240](https://github.com/AlexTo/discava/issues/1240). It lists the 12 deployed files the PR
changed and says what kind of test to run:

> Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
> through the flow with Playwright, then call the APIs behind it and check the stored data.

## 7. The Tester agent tests the deployed stage

The Tester agent doesn't rerun the test suite, and it doesn't use the Stripe stand-in. It uses the
deployed product the way a person would, with real Stripe in sandbox mode. Its
[report](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815) lists every step:

1. As a test instructor, through the API, it created two courses at $19.99.
2. As a test student, in a real browser, it signed in and bought each one on Stripe Checkout,
   using Stripe's test cards for "refund fails" and "refund pending".
3. It requested a refund on each from the course page.
4. After each step it called the APIs, read the orders and enrolments in DynamoDB, and read the
   webhook and API Lambda logs.

That is the wrong ending. This card's refund fails, but Stripe first reports it as succeeded, so
the order was marked `refunded` and the enrolment ended within about three seconds. The failure
came later, and nothing arrived for it. The Tester went looking for why, and found two separate
causes (next section).

Real Stripe couldn't hold a refund pending or record a failed one on this stage. So, to check the
new screens in the deployed bundle, the Tester rewrote the `payment.myOrder` response in the
browser, then checked the real API responses and the stored data separately. It timed the limit:
"Still being processed" appeared **120.2 s** after the pending refund showed, and no request
followed in the next 20 seconds (`13-still-being-processed-after-2-minutes.png`):

"Request a refund" button is gone and polling stops:

The report has 22 checks. Seventeen passed, including these:

| Check | Result |
| --- | --- |
| Polling stops after 2 minutes | 120.2 s, then 0 requests in the next 20 s |
| "Check again" starts polling again | 4 requests in the next 8 s, and the notice is gone |
| `payment.myOrder` without a token | Refused: 401 |
| `payment.myOrder` as a user who didn't buy | 200 with `null`: no one else's order |
| `payment.requestRefund` on an order already refunded | Refused: 412, "No purchase to refund" |

## 8. The Tester leaves the issue open

Three checks failed, and two ended in a state the PR didn't expect. The
[verdict](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815):

> **Verdict: the student-facing UI and `payment.myOrder` work as the PR describes. The
> failed-refund path does not work end to end on the deployed stage.**

It found two causes, both outside anything the PR's tests could reach:

1. **The stage's Stripe webhook never gets the new events.** The PR added `refund.failed` and
   `charge.refund.updated` to the list of events, but that list is only sent to Stripe when an
   administrator first connects it. The stage was connected six days earlier. The Tester counted
   exactly four webhook invocations in the half hour, none of them for a failure.
2. **With real Stripe, a failed refund arrives after the order is already `refunded`.** Stripe
   sends `charge.refunded` as soon as a refund is created, even one that is pending or will fail.
   By the time `refund.failed` arrives, the new handler's condition (the order is still `paid`)
   no longer holds, and it silently does nothing:

   > The student has lost access, hasn't been refunded, and isn't told.

   The stand-in in the PR's e2e scenario never settles a refund before failing it, so CI showed
   the happy version of this.

The Tester may open a fix PR when the fix is small and clear. It explained why it didn't:

> Fixing it means deciding how a refund failure after `charge.refunded` should restore the order
> and enrolment, or not treating a `pending` refund as refunded. That goes beyond a small fix, so
> I'm reporting it rather than opening a PR.

It also didn't touch the stage's Stripe connection, though re-saving it would fix the first cause:
"I didn't do that, because it changes stage configuration." So the issue stays open, with both
problems written up, how to reproduce them, and the choices for a person to make. It listed the
test data it left on the stage, and one error it saw that was already tracked elsewhere, so that
nobody would mistake it for a regression.

## What each gate caught

| Gate | What it caught | Why the gate before it didn't |
| --- | --- | --- |
| CI | A UI change with no screenshot, untested lines, and a broken locator in the agent's own e2e test | The Developer agent hadn't run the e2e suite |
| Reviewer agent | Another PR's commit riding along on the branch, and a new screen state with no screenshot | The extra commit passed every check, and CI only checks that some screenshot was added |
| Tester agent | A webhook endpoint that never receives the new events, and real Stripe reporting a failing refund as refunded first | The stand-in behaves the way the code expects, and no test sees the stage's configuration |

None of the three is clever on its own. Each one looks at something the others can't see: CI at
the rules, the Reviewer at the issue and the branch, the Tester at the running product and the
real services behind it.

## What the person did

1. Read PR #1195 and its screenshots, approved and merged.
2. Next: decide what a refund failure after `charge.refunded` should do, from the options the
   Tester wrote out.

Nobody wrote a prompt, pasted an error log, or clicked through the stage by hand.
