[How it works](../how-it-works/) describes the loop. This page shows it running once, on a real
pull request in [Discava](https://github.com/AlexTo/discava): the page where a student sees the
grade and feedback for an assignment they uploaded.

Every quote, number and link is from GitHub. Times are Sydney time (AEDT, UTC+11), all on 21 November 2026.

From the pull request opening to its merge: 54 minutes, two fixes, and two actions by a person.

## 1. A person merges the spec

The feature is grading for upload assignments: an instructor returns a student's work with points
and feedback, or asks for a resubmission, and the student sees the result.

The spec PR, [#662](https://github.com/AlexTo/discava/pull/662), holds only the spec folder: the
spec, the plan, a data model, three contracts and `tasks.md`, with **34 tasks in 8 phases**. No
product code. Its description lists five questions the agent asked while writing it and the
maintainer's answers. One of them: can a returned grade be changed? Yes, with the history kept
and the student told.

The maintainer read it, added `spec-ready` and merged it at 06:40. That is the first of the two
human gates. Two minutes later the automation opened the issue for phases 1 to 3.

## 2. The Developer agent takes phase 4

Phases 1 to 3 (the data, the rules and the instructor's API) went in as
[#667](https://github.com/AlexTo/discava/pull/667) and merged at 08:42. At 08:43 the **Agent
Issues** workflow read `tasks.md` again and opened
[#681](https://github.com/AlexTo/discava/issues/681) for the next phase with unticked tasks:

> Tasks `T016` to `T017` of `tasks.md`: every task under Phase 4: User Story 2 - Student sees the
> grade and feedback (student portal) (P1). Do not start tasks outside these phases.

Two tasks: a component that shows one round of feedback and a collapsed list of earlier rounds,
and the changes to the assignment page for each state a submission can be in.

The Developer agent picked the issue up on its next poll. Seven minutes after the issue opened it
raised [#683](https://github.com/AlexTo/discava/pull/683) on `openhands/issue-681`: tests first,
both tasks ticked in `tasks.md`, and a description that said what it had run and what it hadn't.

## 3. CI sends it back

The description also said this:

> No e2e screenshots here: the e2e scenario for this flow is a later phase's task.

The agent had made a judgement call, and it was a reasonable reading of the task list. But the
repository has a rule: a change to what a user sees ships with screenshots of it, so the person
reviewing can see the screen without running the app. The rule is a check, and the check doesn't
weigh arguments. Lint, unit tests, build and all six e2e shards passed. [**UI Screenshots** failed](https://github.com/AlexTo/discava/actions/runs/44823849814/job/136591295471).

**Agent CI Status** added `ci-fix-1` and sent the Developer agent back to the same PR. Its
[reply](https://github.com/AlexTo/discava/pull/683#issuecomment-7051758312), with the fix:

> The only finding was the failing `UI Screenshots` check (the PR added no `screenshot(` call). I
> added an e2e scenario in `assignment.e2e.ts` where a student sees the resubmission request
> beside the open form, then the returned grade and feedback. It takes a screenshot of each and
> drives the instructor side through the API. I did not run it locally, so PR CI is its first run.

The next run was green, and CI posted the two new screenshots in the
[**E2E screenshots** comment](https://github.com/AlexTo/discava/pull/683#issuecomment-7051642662).

## 4. The Reviewer agent finds a real bug

Once every check had finished, the Reviewer agent read the diff against the spec. Everything was
green, and the code was still wrong. From its
[review](https://github.com/AlexTo/discava/pull/683#pullrequestreview-6000171162):

> **Blocking: after a resubmission, the resubmission request's feedback disappears for the
> student.** The component always takes the newest round out of the "Earlier feedback" list. It
> only displays that round when the status is `resubmission_requested` or `returned`. Once the
> student uploads again, the status goes back to `submitted`, and the request round is hidden.
> This breaks FR-009, SC-007 and User Story 2's independent test [...] The new e2e step never
> checks the page in `submitted` after the resubmit, and no unit test covers `submitted` with a
> non-empty `feedback`, so nothing catches it.
>
> 🔄 CHANGES REQUESTED

In plain terms: an instructor writes "please cite your sources", the student uploads a new draft,
and the instructor's note vanishes from the student's page. The spec says earlier feedback must
stay visible (FR-009). No test failed, because no test looked at that state. The Reviewer found
it by comparing the code with the spec, and it named the missing tests too.

**Agent Review Status** added `review-fix-1`. Three minutes later the Developer agent pushed
[a fix](https://github.com/AlexTo/discava/pull/683/commits/0bdf55d485d5a5df692d1e8a41ec601499977c03) and [said what it did](https://github.com/AlexTo/discava/pull/683#issuecomment-7052122523):

> Fixed the blocking finding. The newest round is now shown in full only when the status is
> `returned` or `resubmission_requested`. In any other state every round goes under "Earlier
> feedback", so the request stays reachable after a resubmit. I added a unit test for `submitted`
> with a `resubmission_requested` round, and an e2e assertion right after the resubmit.

The Reviewer read the new head, ran the component tests itself (42 passing) and
[ended](https://github.com/AlexTo/discava/pull/683#pullrequestreview-6000351532) with
"No material findings remain. ✅ APPROVED".

## 5. A person approves

At 09:44 the maintainer [approved](https://github.com/AlexTo/discava/pull/683#pullrequestreview-6000379398) and merged. That is the second human gate. What they had in
front of them: a description listing what was and wasn't run, the two screenshots from CI, a
green check list, and a review trail showing one bug found and fixed. The PR was three commits and
508 lines across six files, three quarters of them tests.

## 6. The merge is deployed, and a test issue opens

On Discava, `main` deploys by itself to a development stage. That [deploy](https://github.com/AlexTo/discava/actions/runs/44833259729) finished at 10:09. A
minute later **Post-merge Verify** opened
[#712](https://github.com/AlexTo/discava/issues/712), `test(post-merge): verify #683 student sees
the grade and feedback (student portal)`. The issue says only what to test:

> Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
> through the flow with Playwright, then call the APIs behind it and check the stored data.

## 7. The Tester agent tests the deployed stage

The Tester agent doesn't rerun the test suite. It uses the deployed product the way a person
would, then checks what was stored. Its
[report](https://github.com/AlexTo/discava/issues/712#issuecomment-7054937096) lists every step:

1. As a test instructor, through the API, it created and published a course with one upload
   assignment, `pmt-683-essay`, worth 10 points.
2. As a test student, in a real browser, it enrolled, signed in on the hosted sign-in page and
   uploaded a first draft.
3. The instructor asked for a resubmission. The student reloaded, saw the request, and uploaded a
   second draft.
4. The instructor returned the work with 7 points, then amended the grade to 8.5. The student
   reloaded after each.
5. After every step it called the student's API, read the records in DynamoDB and the files in
   S3, tried the calls that should be refused, and at the end scanned the logs of all 46 Lambda
   functions on the stage for errors.

The report has three tables: 13 checks on the screens, 14 on the APIs and 5 on stored data. Some
of the rows a person would be least likely to try by hand:

| Check | Result |
| --- | --- |
| The student uploads again after the work is returned | Refused: 412, "This submission has been returned and can't be changed" |
| Another user, not enrolled, reads the submission | Refused: 403 |
| The student calls the instructor's grading API | Refused: 403 |
| The instructor returns 11 points on a 10-point assignment | Refused: 400, "Points must be between 0 and 10" |
| The instructor's return is sent twice | Refused: 409, and no second notification is sent |
| The stored feedback records name the instructor who gave them | They do, and the student's API doesn't return that field |

## 8. The Tester closes the issue

All 32 checks passed, so the report ended with a verdict and the Tester closed the issue:

> **PASS.** The student portal shows the grade and feedback as #681 asks

It also listed two things it saw that weren't from this PR, so that nobody would mistake them for
regressions.

### When the Tester doesn't close

A pass isn't the only outcome. The pull request before this one,
[#667](https://github.com/AlexTo/discava/pull/667), added the grading APIs, and its test issue
[#694](https://github.com/AlexTo/discava/issues/694) stayed open after the first run. Twenty-nine
checks passed and one failed:

> **Verdict: the new grading flow works end to end for submissions made after this deploy. It
> does not work for submissions stored before it.** Those have no `reviewRevision` attribute, so
> an instructor can't open or grade them.

No unit test, e2e test or review could have found this. They all start from an empty database,
and the bug only exists where there is old data. Three submissions on the stage had it.

The Tester may open a fix PR when the fix is small and clear. Here it [explained](https://github.com/AlexTo/discava/issues/694#issuecomment-7052102048) why it didn't:

> That is a choice between a migration and tolerant reads, and it changes concurrency conditions
> in two packages, so I haven't opened a fix PR.

So it stopped and left the decision to a person, with both options written out. The maintainer
backfilled the three records on the stage. The Tester [ran its checks again](https://github.com/AlexTo/discava/issues/694#issuecomment-7054905761), confirmed the old
submissions now had the field, and closed the issue with a warning that any other environment
holding old submissions needs the same backfill. A minor note from the same report (a refusal
message that said "returned" when nothing had been returned) became a 13-line fix,
[#708](https://github.com/AlexTo/discava/pull/708).

## What each gate caught

| Gate | What it caught | Why the gate before it didn't |
| --- | --- | --- |
| CI | A UI change with no screenshots | The Developer agent decided they belonged to a later phase |
| Reviewer agent | Feedback disappearing after a resubmit | No test covered that state, so CI was green |
| Tester agent (on #667) | Old records the new code can't read | Tests and review never see the stage's existing data |

None of the three is clever on its own. Each one looks at something the others can't see: CI at
the rules, the Reviewer at the spec, the Tester at the running product.

## What the person did

1. Answered five questions while the spec was written, then reviewed and merged the spec PR.
2. Read PR #683 and its screenshots, approved and merged.

Nobody wrote a prompt, pasted an error log, or clicked through the stage by hand.
