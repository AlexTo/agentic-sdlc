This repository *is* the workflow: the same Speckit setup, issue template, PR checks, agent
workflows and unit-tested glue that Discava runs, wrapped around a small notes app.

**Fork it, and you have Discava's setup.** Point your own OpenHands at the fork, write a spec for
the notes app, and it goes through the loop described in [How it works](../how-it-works/).

The notes app runs entirely locally (`pnpm dev`, with Docker for DynamoDB local), so CI can run
its e2e tests and the agent never needs cloud credentials.

## What you add

Only what can't live in a repository:

1. **GitHub settings**: a fork doesn't copy them, so `scripts/setup-repository.sh` sets them in
   one run.
2. **OpenHands**: Agent Canvas on your machine, a GitHub token, and the automations pointed at
   your fork.

## What's off until you add it

The cloud. The notes app has no cloud infrastructure, so merging ships nothing beyond the docs
site. `deploy.yml` and `post-merge-verify.yml` are in place but never run by themselves: add a CDK
app at `packages/infra` and set `AUTO_DEPLOY_STAGE`, and every green `main` deploys, then the
Tester agent tests what was deployed. [Adopt: deploy](../../adopt/deploy/) has the steps, and
[Deploy and security](../../discava/deploy-and-security/) describes Discava's pipeline.
