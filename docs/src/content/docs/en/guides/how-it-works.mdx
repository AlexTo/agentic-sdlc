This page follows one feature through the whole loop. Each step names who acts and what it leaves
behind.

Solid red is you, at the two steps you always do. Dashed red is you only when something goes wrong: agent tasks left unticked after a merge, or a failed test on the stage. Grey is an agent or automation working on its own, and indigo is an automated gate: CI, then the Reviewer agent, and after the merge the Tester agent.

The three agents are OpenHands automations: the **Developer** writes the code, the **Reviewer**
reviews it, and the **Tester** tests it once it is deployed.

## The steps

| # | Who | What happens | Artifact |
| --- | --- | --- | --- |
| 1 | 🧑🤖&nbsp;You + agent | `/speckit-specify` turns a one-paragraph idea into a spec. `/speckit-clarify` asks up to five questions and writes your answers back | `specs/<timestamp>-<name>/spec.md` |
| 2 | 🧑🤖&nbsp;You + agent | `/speckit-plan` decides *how*, and checks the plan against the constitution | `plan.md`, `data-model.md`, `contracts/` |
| 3 | 🧑🤖&nbsp;You + agent | `/speckit-tasks` writes an ordered task list, grouped into phases. `/speckit-analyze` cross-checks all three files | `tasks.md` |
| 4 | 🧑&nbsp;**You** | Open the spec PR, review it like code, add the `spec-ready` label, merge | A merged spec PR. **Human gate 1** |
| 5 | ⚙️&nbsp;Automation | The **Agent Issues** workflow reads `tasks.md` and opens an issue for the first group of phases, with the `openhands` label | An implementation issue |
| 6 | 🤖&nbsp;Developer agent | On its next poll, the agent picks the issue up, writes tests first, implements, ticks its tasks and opens a PR on `openhands/issue-<n>` | A pull request |
| 7 | ⚙️&nbsp;CI | PR checks run lint, unit tests, build, the `tasks.md` format check, e2e tests and the screenshots check | Check results |
| 8 | ⚙️🤖&nbsp;Automation + Developer agent | On a red run, **Agent CI Status** marks the PR as failing. The Developer agent sees it on the next poll and revises the same PR | `ci-fix-1` to `ci-fix-5` labels |
| 9 | 🤖&nbsp;Reviewer agent | Once every check has finished, the Reviewer agent reviews the head commit and ends with `✅ APPROVED` or `🔄 CHANGES REQUESTED`. **Agent Review Status** sends the Developer agent back on the second | A review, and maybe `review-fix-N` labels |
| 10 | 🧑&nbsp;**You** | You read the PR description and the **E2E screenshots** comment, do any **(human)** tasks, and merge | A merged PR. **Human gate 2** |
| 11 | ⚙️&nbsp;Automation | The merge runs **Agent Issues** again. It opens the issue for the next phase that has unticked agent tasks, and steps 6 to 10 repeat until none are left | The next issue, or done |
| 12 | ⚙️🤖&nbsp;Automation + Tester agent | Where `main` deploys by itself: once the merge is on the development stage, **Post-merge Verify** opens a test issue for it. The Tester agent clicks through the change, calls the APIs, verifies the data it wrote to the database, file storage and search index, and reports | A test report. The issue closes on a pass |

Step 12 needs a deployed stage. Discava has one. The example app in this repository doesn't, so a
fork stops at step 11.

## What you actually do

Per feature, you write and approve the spec once. Per pull request, you do one review and click
merge. You are pulled in early only when a loop runs out of attempts (`ci-fix-exhausted` or
`review-fix-exhausted`), when the agent comments that it is blocked, or when the Tester leaves a
test issue open because the change failed on the stage. While the agents work, you can write the
next spec.

## Where each piece lives

| Piece | File |
| --- | --- |
| Spec tooling | `.specify/`, the `speckit-*` skills, `specs/` |
| Project rules for every agent run | `.specify/memory/constitution.md`, `AGENTS.md` |
| The issue the agent receives | `.github/ISSUE_TEMPLATE/implement-phase.md` |
| Spec to issue | `.github/workflows/agent-issues.yml` |
| Finished spec to `specs/_archive/` | `.github/workflows/archive-specs.yml` |
| CI to agent | `.github/workflows/agent-ci.yml` |
| Reviewer to agent | `.github/workflows/agent-review.yml` |
| Checks | `.github/workflows/pr-checks.yml`, `ui-screenshots.yml`, `ci.yml` |
| Deploy to test issue (Discava only) | `.github/workflows/deploy.yml`, `post-merge-verify.yml` |
| The rules behind the glue, unit-tested | `packages/common/scripts/src/agent-*`, `ui-screenshots/` |
| The agent runtime and each role's prompt | OpenHands Agent Canvas, outside the repository |
