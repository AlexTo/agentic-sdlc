This guide shows you how to run a software lifecycle in which **agents write the code and people
make two decisions**: approve the spec, and approve the result. Everything in between (opening
issues, writing code and tests, reacting to CI, answering a review) runs on its own, through the
normal GitHub process.

The workflow runs every day on [Discava](https://github.com/AlexTo/discava), a serverless learning
management system on AWS. In the six days after it went live on 14 November 2026, sixteen feature
specs were written this way and 105 agent pull requests were merged to implement them, each one
written, fixed and reviewed by agents. Over the same period, 173 commits landed on main. All of
this with a single maintainer, a dad with a full-time job who works on Discava casually in his
spare time.

## The short version

Three off-the-shelf tools do most of the work:

| Tool | What it does here |
| --- | --- |
| [Speckit](https://github.com/github/spec-kit) | Turns an idea into `spec.md`, `plan.md` and `tasks.md`, checked against a project constitution |
| [OpenHands](https://github.com/OpenHands/OpenHands) | Turns a labelled issue into a pull request, and revises the pull request when told something is wrong. A second OpenHands automation reviews it |
| GitHub Actions | Runs the checks, and holds the glue between the other two |

None of them knows about the others. **This guide is mostly about the glue**: ten small, tested
pieces of automation that connect a finished spec to the agent, CI to the agent, and the reviewer to
the agent, with limits so that nothing loops forever.

## Who this is for

- **Tech leads and staff engineers** deciding whether to adopt the workflow. Start with
  [Concepts](../../concepts/principles/).
- **Anyone who wants to try it.** [Fork this repository](../fork-this-repo/), then follow
  [Set it up](../../setup/before-you-start/) to run a feature through the whole loop.
- **The engineer bringing it to a product repository.** Read
  [How Discava does it](../../discava/overview/), then
  [Adopt it in your own repository](../../adopt/overview/).
- **Developers who will use it day to day.** The [tutorial](../../tutorial/the-case/) follows one
  feature from idea to merge.

You should be comfortable with Git, GitHub pull requests and GitHub Actions. You don't need prior
experience with Speckit or OpenHands.

## Conventions

- `AGENTS.md` means the agent guidance file at the root of the repository. Name it whatever your
  coding agent reads.
- `<you>/agentic-sdlc` is your fork, and `owner/repo` is any repository.
- `@your-scope` is your workspace's npm scope. This repository uses `@agentic-sdlc`, and Discava
  uses `@discava`.
- Commands run from the repository root unless a step says otherwise.
- **(human)** marks a task an agent must not do. It is also the literal marker used in `tasks.md`.
