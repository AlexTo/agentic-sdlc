**You'll end with:** Issues and Actions on, every label the workflow uses, a `main` branch that
only takes pull requests with green checks and an approval, comments limited to collaborators, and
the agents' own account as a collaborator.

A fork copies the code, not the settings. `scripts/setup-repository.sh` sets all of them with the
`gh` CLI. Each step sets the same state every time, so it is safe to run again.

<Steps>

1. **Create the agents' account.** The agents work under their own GitHub account, a machine
   account that nothing else uses. Discava's is `discava-bot`. Create one. Its token is the one
   you create in [step 3](../openhands/), and its pull requests and comments show under it, so you
   approve them like anyone else's.

2. **Run the script** from your clone, signed in to `gh` as the fork's owner, with the agents'
   account:

   ```bash
   ./scripts/setup-repository.sh <you>/agentic-sdlc <agents-account>
   ```

   Add `--dry-run` first if you want to see each `gh` command before it runs. The script:

   | Sets | Why |
   | --- | --- |
   | Issues and Actions on | GitHub turns both off in a fork, and the workflow runs on issues |
   | 20 labels | Every label in [Reference: labels](../../reference/labels/) |
   | Branch protection on `main` | A pull request, one approval, stale approvals dismissed, and seven required checks: `Checks (lint)`, `Checks (test)`, `Checks (build)`, `Tasks format`, `Invariant coverage`, `E2E tests`, `UI Screenshots` |
   | Workflow tokens read-only, and Actions may not open or approve pull requests | A workflow that could open a pull request could also approve one. Archive Specs pushes the branch that moves a finished spec to `specs/_archive/` and warns with a link that opens its pull request, filled in, for you to submit |
   | Interactions limited to collaborators, for six months | A fork of a public repository is public, and the agents read every comment on what they work on while holding a token that can push |
   | GitHub Pages from Actions | CI's **Deploy Docs** job publishes this site |
   | The agents' account invited with write access | So the agents can push branches and open pull requests |

   The protection leaves bypass allowed, so you, as the owner, can merge a pull request you
   opened yourself, such as a spec PR, which GitHub won't let you approve.

3. **Accept the invitation** while signed in as the agents' account.

4. **Check Actions is on.** If your fork's **Actions** tab still shows **I understand my
   workflows, go ahead and enable them**, click it. GitHub sometimes asks for that click even
   after the API has turned Actions on.

</Steps>

<Aside type="caution">
The interaction limit expires six months after you set it, and nothing warns you. Note the date,
and run the script again before then. If you add the Tester agent later, which holds cloud
credentials, this limit is what keeps a stranger's comment from reaching it. See
[Who can comment](../../discava/post-merge-verify/#who-can-comment).
</Aside>

<Aside type="caution">
Don't add `software-factory/review` to the required checks. It is a signal to the agent, only ever
posted as `failure`, and requiring it would block every PR.
</Aside>

## Check it worked

The fork's **Issues → Labels** page lists the 20 labels, **Settings → Branches** shows the rule on
`main` with seven required checks, and **Settings → Moderation options → Interaction limits** shows
the collaborators-only limit with its end date. **Settings → Collaborators** lists the agents'
account with the **Write** role.
