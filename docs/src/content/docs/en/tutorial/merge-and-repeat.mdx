**You are here:** 🧑 human gate #2. **Output:** phase 1 merged, phase 2's issue open.

The PR reaches you green and approved by the agent reviewer. Your job is to judge the outcome,
not to hunt for problems.

<Steps>

1. Read the PR description and the **E2E screenshots** comment. For the website phase, this is
   how you see the feature without pulling the branch: the empty tag input, a note with three
   tags, the filter applied, the error shown on a sixth tag.

2. Check the **(human)** tasks the agent listed and do them.

3. Approve and merge. If the agents push with your own token, GitHub sees you as the PR's author
   and won't accept your approval, so bypass it as you did for the spec PR.

   To request changes instead, review the PR and add the `openhands-review` label. The reviewer
   agent's verdict then sends the implementing agent back, under the same five-attempt cap.

</Steps>

## What merging does

The **Agent Issues** workflow sees a merged PR on an `openhands/` branch and reads `tasks.md` as
the merge left it:

1. **Are this phase's agent tasks ticked?** The agent ticks each task in the PR, in the commit that
   finishes it. **(human)** tasks don't count: you did them in step 2, and they never hold up the
   chain.
2. **Yes:** it opens the issue for the next phase. Phase 2 (the website) now runs exactly as phase 1
   did: tests first, PR, gates, fix-ups, review.
3. **No:** nothing opens, and the merged PR gets a comment listing the unticked task IDs. Tick or
   finish them, then run **Agent Issues** by hand with the spec folder name.

Only the agent's own branches advance the chain. A PR of your own is ignored.

```text
spec PR merged ─► issue 1 ─► PR 1 merged ─► issue 2 ─► PR 2 merged ─► issue 3 ─► PR 3 merged ─► done
   (you)                       (you)                      (you)                      (you)
```
