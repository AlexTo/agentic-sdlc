**Al terminar tendrás:** una constitución ratificada propia, y plantillas de Speckit que generan archivos
que el workflow Agent Issues puede leer.

El `.specify/` que copiaste en el [paso 2](../speckit/) ya contiene una constitución y unas plantillas
que funcionan, escritas para la app de notas. Este paso las hace tuyas.

<Steps>

1. **Reescribe la constitución para tu proyecto.** En tu agente de programación:

   ```text
   /speckit-constitution
   ```

   Dale los principios propios de tu proyecto: arquitectura, modelo de datos, valores de seguridad por defecto, convenciones
   de código. [La de Discava](../../discava/constitution-and-guidance/) es un ejemplo completo. Conserva
   estas partes de la copiada, adaptando los comandos y los nombres de paquete a tu stack, porque
   el resto del workflow depende de ellas:

   | Conserva | De la constitución copiada | Por qué |
   | --- | --- | --- |
   | Los tests unitarios, los invariantes y los tests e2e son obligatorios, y los tests son una especificación | III. Layered Tests | El agente no puede debilitar un test para poner CI en verde |
   | Todo se ejecuta con `pnpm dev`, sin cuenta en la nube | II. Everything Runs Locally | Así el CI del PR puede ejecutar la suite e2e y darle al agente feedback real |
   | Los agentes implementan en su propia rama y PR, nunca ejecutan el stack local, y marcan como **(human)** las tareas que lo necesitan | Development Workflow | El agente no tiene Docker. CI ejecuta lo que él no puede |
   | El CI del PR es la puerta. Un agente nunca hace merge, push a `main`, ni edita workflows de CI ni debilita un test | Development Workflow | Lo que mantiene a un agente en su carril |

2. **Cambia las rutas de paquete en `tasks-template.md`.** Sus tareas de test nombran los paquetes de
   este repositorio: `packages/notes-table/src/helpers/invariants/` y `@agentic-sdlc/e2e`. Apúntalas a
   los tuyos. Deja el resto de la plantilla como está: las reglas de formato bajo **Read by automation**,
   el marcador **(human)**, los tests obligatorios y la nota contra editar tests existentes son
   aquello de lo que dependen el workflow Agent Issues y el check `Tasks format`.

3. **Conserva la línea de la issue padre** en `spec-template.md`:

   ```markdown
   **Parent issue**: [#<number>, or "none" if there is no tracking issue]
   ```

   Agent Issues escribe a partir de ella `Refs #<parent>` en cada issue.

</Steps>

## Comprueba que funciona

Genera una spec y unas tareas desechables para una feature mínima. Después, cuando el pegamento esté en su sitio
([paso 5](../glue-scripts/)):

```bash
pnpm nx run @your-scope/tooling-agent:validate-tasks
```

```text
1 tasks.md file(s) are in the expected format.
```

Borra después la carpeta de la spec desechable.

<Aside type="caution">
`/speckit-tasks` a veces escribe `### Phase 2` o indenta una tarea. Eso es exactamente lo que detecta el
validador, así que no relajes el validador. Corrige la redacción de la plantilla hasta que los archivos generados
pasen.
</Aside>
