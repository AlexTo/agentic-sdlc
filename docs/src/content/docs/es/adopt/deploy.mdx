import { Steps, Aside } from '@astrojs/starlight/components';

**Al terminar tendrás:** un escaneo de Trivy en cada push a `main`, un workflow Deploy que lleva cada
`main` en verde a un stage de desarrollo, despliegues a producción que esperan a una persona y, si lo
quieres, un agente Tester que prueba cada cambio fusionado en el stage de desarrollo.

Este repositorio incluye los workflows, desactivados: `deploy.yml` solo se ejecuta a mano o una vez
definida `AUTO_DEPLOY_STAGE`, y `post-merge-verify.yml` solo se ejecuta tras un despliegue. La app de
notas no tiene infraestructura en la nube, así que la parte que hay que escribir es tuya. Los pasos
hablan de AWS y CDK, como usa Discava, pero la estructura sirve para cualquier nube.

<Steps>

1. **Añade un target `trivy`** a los proyectos que quieras escanear (el `pnpm trivy` de la raíz ejecuta
   `nx run-many --target trivy --all`). El job `trivy` del `ci.yml` copiado lo ejecuta en cada
   push a `main`, como un job separado de `build`, para que un CVE recién publicado marque `main` sin
   bloquear nada más. Registra los hallazgos aceptados, un ID por línea, en `.trivyignore`.

2. **Añade tu infraestructura** como una app de CDK en `packages/infra`, con un stage por entorno en
   su `src/main.ts`:

   ```bash
   pnpm nx g @aws/nx-plugin:ts#infra --name=infra
   ```

   Su target `deploy-ci` es lo que ejecuta el workflow Deploy. Los constructs del sitio web de notas
   ya están en `packages/common/constructs`.

3. **Configura acceso a la nube sin claves** para cada stage: el proveedor OIDC de GitHub, un rol de
   despliegue en el que solo se confía para `repo:owner/repo:environment:<stage>`, un rol de ejecución
   de CloudFormation con un permissions boundary, el bootstrap de CDK, y un environment de GitHub con el
   nombre del stage y las variables `AWS_REGION`, `AWS_DEPLOY_ROLE_ARN` y `AWS_EXECUTION_ROLE_ARN`. El
   [`scripts/setup-stage.sh`](https://github.com/AlexTo/discava/blob/main/scripts/setup-stage.sh) de
   Discava hace todo eso para sus stages; léelo antes de adaptarlo. No guardes claves de acceso.

4. **Copia `.github/workflows/deploy.yml`**, si no trabajas en un fork, y cambia su scope
   `@agentic-sdlc/` y el nombre del stage por defecto. Hace checkout del commit que verificó CI, se
   detiene pronto con un error claro si faltan `packages/infra` o las variables del environment, ejecuta
   Trivy, sintetiza y solo despliega si el commit sigue siendo el último de `main`. Esa comprobación de
   actualidad está *dentro* del hueco de concurrencia del job, así que refleja `main` justo antes del
   despliegue, aunque la ejecución haya esperado detrás de otra.

5. **Activa los despliegues automáticos** para el stage de desarrollo. En **Settings → Secrets and
   variables → Actions → Variables**, añade una variable de repositorio `AUTO_DEPLOY_STAGE` con el nombre de tu
   stage de desarrollo.

6. **Protege producción.** En **Settings → Environments**, abre el environment de tu stage de producción
   y añade **Required reviewers**. Para desplegarlo, abre **Actions → Deploy → Run
   workflow** e introduce el stage de producción. El job espera entonces la aprobación.

7. **Añade el agente Tester**, si quieres que se pruebe cada cambio desplegado (hueco 11). De este
   repositorio ya tienes su pegamento (`post-merge-test/` en el paso 5), su plantilla de issue (paso
   4) y `.github/workflows/post-merge-verify.yml`, que abre una issue de test por cada pull request que
   una ejecución de Deploy llevó al stage de test. Prueba en `TEST_STAGE`, una variable de repositorio
   que por defecto vale `AUTO_DEPLOY_STAGE`.

   En el lado de OpenHands, añade un perfil de agente `tester` y una automatización que sondee las
   issues con la label `openhands-test`. No hay plantilla de catálogo para ella. El worker de Discava
   y su prompt se describen en
   [Configuración de OpenHands](../../discava/openhands-setup/#tester-github-issue-tester)
   y en [Los prompts de los agentes](../../discava/agent-prompts/#tester). Dale al Tester:

   - una CLI de la nube con sesión iniciada en la cuenta de desarrollo, con el mínimo acceso que
     necesiten las pruebas
   - un usuario de prueba por cada rol de tu app, guardados como secretos de OpenHands
   - un navegador que pueda manejar, como Playwright con Chromium

   <Aside type="caution" title="¿Repositorio público? Limita primero los comentarios a los colaboradores">
   El Tester lee issues, pull requests y sus comentarios mientras tiene esas credenciales. Si tu
   repositorio es público, el comentario de un desconocido puede llevarle instrucciones.
   `scripts/setup-repository.sh` limita las interacciones a los colaboradores, durante seis meses como
   mucho, así que vuelve a ejecutarlo antes de que termine el límite. Conserva también el bloqueo de
   `helpers/conversation-lock.ts`, deja el "cómo probar" en el prompt de la propia automatización y no en
   la issue, y nunca lo apuntes a un stage cuyos datos importen.
   </Aside>

</Steps>

## Comprueba que funciona

Fusiona cualquier PR. CI se ejecuta y después **Deploy** arranca solo con el stage de desarrollo. Ejecuta CI otra vez
a mano sobre un commit más antiguo: Deploy registra `Skipping deploy: no longer main's latest commit` y
no despliega nada.

Con el Tester configurado: después de ese despliegue, **Post-merge Verify** abre una issue bloqueada
(locked) titulada `test(post-merge): verify #<pr> …`, con la label `openhands-test`. En un sondeo como
mucho, el Tester arranca, y su informe aparece como comentario en la issue.

<Aside type="note">
Ningún agente despliega, y ninguno ve estos roles. El Desarrollador y el Revisor solo necesitan el
token de GitHub. El acceso del Tester a la cuenta de desarrollo es independiente del rol de despliegue,
que solo lo asume un workflow que se ejecuta desde `main`, en el environment del stage.
</Aside>
