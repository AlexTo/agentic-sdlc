import { Steps, Aside, FileTree } from '@astrojs/starlight/components';

**Al terminar tendrás:** `pnpm dev` arrancando toda la app con sustitutos locales, una suite de Playwright que CI
ejecuta en cada PR, capturas de pantalla publicadas en el PR e invariantes comprobados después de cada test.

Este es el paso que más depende de tu stack. También es lo que permite que CI le dé al agente feedback
real sin credenciales de la nube.

<Steps>

1. **Dale a cada servicio de la nube un sustituto local**, arrancado por un target `dev`, para que `pnpm dev` lo ejecute
   todo. El `packages/tooling/local-dev/` de este repositorio arranca DynamoDB local en Docker para
   la tabla de notas. [Los sustitutos de Discava](../../discava/local-stack/#qué-se-ejecuta-en-local) cubren además
   S3, SQS, OpenSearch y Cognito, junto con un proceso "event runner" que llama a los mismos handlers
   que los triggers de Lambda, los streams y EventBridge llaman en la nube.

   Cambia el código de backend con un solo flag (`LOCAL_DEV=true`), con los endpoints en un módulo compartido.
   Lista en tu guía de contribución lo que todavía solo se ejecuta en la nube, y marca como **(human)** las tareas que
   lo necesitan.

2. **Copia el proyecto e2e** de este repositorio, `packages/e2e/`, y sustituye su escenario por los
   tuyos, un archivo por cada flujo de usuario. Lo que hay que conservar:

   <FileTree>
   - packages/e2e/
     - playwright.config.ts lee `E2E_SHARD` para que la matriz de CI pueda dividir la suite, arranca `pnpm dev`, un worker, reintentos solo en CI
     - src/helpers/
       - screenshots.ts `screenshot(page, 'name')`, que guarda las imágenes que sube el job `e2e` de PR Checks
       - table-invariants.ts un `test` de Playwright que comprueba los invariantes después de cada escenario
   </FileTree>

   Cada escenario crea sus propios usuarios y datos con nombres únicos, y ninguno reinicia los datos locales, así que
   se pueden ejecutar en cualquier orden. Llama a `screenshot` donde miraría una persona, después de un `expect` sobre lo que se muestra:

   ```ts
   await expect(page.getByRole('heading', { name: 'Reviews' })).toBeVisible();
   await screenshot(page, 'reviews section with three reviews');
   ```

3. **Copia los invariantes** de `packages/notes-table/src/helpers/invariants/` al paquete
   dueño de tu tabla. Para cada regla que abarque registros escritos por código distinto (contadores,
   agregados, orden), escribe una comprobación que recorra una instantánea de los datos y devuelva las violaciones,
   con un test unitario que la rompa. `packages/notes-table/README.md`, "Rules that span records",
   explica paso a paso cómo añadir una.

   Los escenarios toman `test` de `table-invariants.ts` en lugar de `@playwright/test`. Después de cada
   uno, hace fallar el escenario si la tabla tiene una violación que antes no tenía. Solo cuentan las
   violaciones *nuevas*, así que los datos locales antiguos nunca hacen fallar una ejecución, y `expect.poll` da
   tiempo al trabajo en segundo plano (handlers de streams, recálculos) para ponerse al día.

4. **Genera el mapa de writers y copia el hook pre-push.** Ejecuta
   `pnpm nx run @your-scope/tooling-agent:entity-writers` y haz commit del `entity-writers.json` que
   escribe. Copia `.husky/pre-push` de este repositorio, con sus `MAP` y `PATHS` apuntando a
   los tuyos: cuando una rama cambia código que podría escribir en la tabla, regenera el mapa y detiene
   el push si cambió. El PR check `Invariant coverage` compara entonces el mapa con el de la rama
   base, y retiene un PR que añade un writer hasta que los invariantes nombran la entidad.

5. **Añade tests de concurrencia** para las escrituras en las que dos usuarios podrían competir: lanza las mismas peticiones a la API en
   el mismo momento con `Promise.all`, y después comprueba el resultado y los invariantes.

</Steps>

## Comprueba que funciona

```bash
pnpm nx e2e @your-scope/e2e
ls dist/packages/e2e/screenshots/*/
```

Después abre un PR que cambie una página y añada una llamada a `screenshot(`. Cuando termine PR Checks, el PR
tiene un comentario titulado **E2E screenshots** que lista la nueva imagen bajo "Added by this pull
request".

<Aside type="tip">
Si tu app todavía no puede ejecutarse entera en local, empieza por lo que sí puede. Incluso una suite que solo cubra la
API y la base de datos detecta la mayoría de los errores de los agentes. Añade sustitutos servicio a servicio, y mantén
el resto como tareas **(human)** hasta entonces.
</Aside>
