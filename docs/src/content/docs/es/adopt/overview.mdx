La forma más rápida de tener el workflow es [hacer fork de este repositorio](../../setup/fork/). Esta sección
es para cuando no puedes: tienes un repositorio de producto existente y quieres la misma configuración en él.

Cada paso añade una pieza y explica cómo comprobarla. Casi cada pieza es un archivo o una carpeta que
copias de este repositorio tal cual y luego apuntas a tus propios paquetes: solo escribes config a mano
donde describe tu proyecto. Cuando hayas terminado, tu repositorio tiene lo mismo que un fork, y continúas desde
[2. Configura el repositorio](../../setup/github-repository/).

<Aside type="tip">
Haz fork de este repositorio de todos modos y ejecuta primero [tu primera feature](../../setup/first-feature/) en la app de
notas. Ver el bucle completo funcionar una vez hace que cada paso de aquí sea mucho más fácil de seguir.
</Aside>

## Decide esto primero

| Decisión | Predeterminado | Cámbialo si |
| --- | --- | --- |
| Label que dispara la implementación | `openhands` | Ya usas esa label |
| Prefijo de rama | `openhands/issue` | Rara vez. El worker revisa exactamente `openhands/issue-<n>`, y el pegamento responde a cualquier rama de un segmento bajo `openhands/`. Si lo cambias, cambia también `AGENT_BRANCH` y las condiciones de los workflows |
| Label de review | `openhands-review` | Igual que arriba |
| Intervalo de consulta | cada 5 minutos | Quieres menos coste y puedes esperar más (el predeterminado del catálogo es 15), o una respuesta más rápida (Discava sondea cada 2) |
| Máximo de intentos de corrección | 5 por bucle | Rara vez. Es `MAX_*_FIX_ATTEMPTS` en dos archivos `plan.ts` |
| Numeración de carpetas de spec | timestamp | Nunca, si hay más de un autor de specs |

En cada comando y archivo copiado, sustituye `@your-scope` o `@agentic-sdlc` por el scope npm de tu
workspace.
