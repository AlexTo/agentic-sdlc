**La versión corta:** OpenHands ejecuta tres automatizaciones programadas contra tu repositorio, una
por cada rol de agente. El **Desarrollador** implementa issues etiquetadas y revisa los pull requests
marcados como fallidos. El **Revisor** revisa los pull requests cuando terminan sus checks. El
**Tester** prueba cada cambio fusionado en el stage de desarrollo desplegado. Cada una arranca un
agente de programación normal con un prompt fijo. Ninguna necesita que abras un chat.

## Los tres roles

| Rol | Automatización | Arranca a partir de | Deja tras de sí |
| --- | --- | --- | --- |
| **Desarrollador** | GitHub issue to PR | Una issue con la label `openhands`, o un status fallido `software-factory/review` en su propio PR | Un pull request en `openhands/issue-<n>`, y sus revisiones |
| **Revisor** | GitHub code review | Un PR con la label `openhands-review`, cuando han terminado todos los checks | Una revisión que termina en `✅ APPROVED` o `🔄 CHANGES REQUESTED` |
| **Tester** | GitHub issue tester | Una issue con la label `openhands-test`, abierta después de un despliegue | Un informe de test en la issue, con evidencia de la UI, las API y los datos guardados y, a veces, un pequeño PR de corrección |

El Desarrollador y el Revisor son todo lo que necesita un repositorio para ejecutar el bucle hasta el
merge. El Tester necesita algo desplegado que probar, así que llega con los
[despliegues automáticos](../../adopt/deploy/). La app de ejemplo de este repositorio no tiene
despliegue, así que un fork ejecuta los dos primeros.

```d2
direction: right

machine: Tu máquina {
  style.stroke-dash: 3
  canvas: Agent Canvas {
    i2p: issue a PR
    review: revisión de código
    test: tester de issues
  }
  dev: agente Desarrollador
  rev: agente Revisor
  tester: agente Tester
  canvas.i2p -> dev: implementar o revisar
  canvas.review -> rev: revisión
  canvas.test -> tester: probar
}

github: GitHub {
  style.stroke-dash: 3
  issues: issues {shape: page}
  prs: pull requests {shape: page}
  statuses: commit statuses {shape: document}
}

stage: stage de desarrollo {shape: cylinder}

machine.canvas -> github: sondea cada 2 minutos
machine.dev -> github.prs: "push, abrir"
machine.rev -> github.prs: revisar
machine.tester -> stage: "clic, llamar, leer"
machine.tester -> github.issues: informe
```

## Las partes

| Parte | Qué es |
| --- | --- |
| **Agent Canvas** | La app de OpenHands que ejecutas tú mismo (`npx @openhands/agent-canvas`). Incluye el servidor del agente, el backend de automatizaciones y una interfaz web |
| **Agent profile** | Qué agente se ejecuta y con qué modelo. Un perfil puede ser el propio agente de OpenHands con cualquier LLM, o un agente de programación externo mediante ACP (el Agent Client Protocol) |
| **Automation** | Un pequeño worker de Python que se ejecuta según una programación cron. Lee GitHub, decide qué hacer y arranca o reanuda conversaciones con el agente. Se instala desde el catálogo de Agent Canvas |
| **Secret** | Una credencial con nombre, como el token de GitHub. A una conversación solo se le entregan los secretos de su lista de permitidos |

## Las tres automatizaciones

### Desarrollador: GitHub issue to PR

En cada sondeo, para cada repositorio que vigila, el worker:

1. Busca PR abiertos en ramas `openhands/issue-<n>` cuyo commit de cabeza tenga un commit status
   llamado `software-factory/review` en estado `failure` o `error`. Para cada uno envía un turno de
   **revisión** a la conversación de esa issue: leer las revisiones, los comentarios y los checks
   fallidos, corregirlos y hacer push a la misma rama.
2. Busca issues abiertas con la label de disparo (`openhands`) que todavía no tienen PR, y arranca
   un turno de **implementación**: clonar, crear `openhands/issue-<n>`, implementar, probar, hacer
   push, abrir el PR y añadir la label `openhands-review`.

Cada issue es un *sujeto* con una conversación estable. Una revisión va a la misma conversación que
la implementación original, así que el agente conserva su contexto.

### Revisor: GitHub code review

En cada sondeo, busca PR que lleven la label `openhands-review`, que tengan una solicitud de
revisión pendiente para su cuenta, o que estén abiertos, no sean borradores, no tengan solicitud ni
revisión. Para cada uno, espera hasta que **todos los checks del commit de cabeza hayan terminado** y
después inicia una revisión de ese commit exacto. La revisión termina con un veredicto en su propia
línea: `✅ APPROVED` o `🔄 CHANGES REQUESTED`.

<Aside type="caution">
El worker de issue a PR solo revisa un PR cuando ve el status fallido `software-factory/review`. Ni
una ejecución de CI en rojo ni el "changes requested" del Revisor ponen ese status por sí solos.
Cerrar ese hueco son dos piezas del [pegamento que falta](../the-missing-glue/).
</Aside>

### Tester: GitHub issue tester

Las dos primeras automatizaciones vienen del catálogo de Agent Canvas. Esta está escrita a mano, y es
pequeña: un worker de unas cien líneas, construido sobre los helpers de GitHub del catálogo, y un
archivo de prompt.

En cada sondeo, busca issues abiertas con la label de disparo (`openhands-test`) que haya abierto la
propia cuenta del workflow, `github-actions[bot]`. Para cada una arranca un turno de **test**: clonar
el repositorio en el commit que ejecuta el stage, averiguar qué cambió el pull request fusionado,
probarlo en el stack desplegado y comentar el resultado en la issue.

El test tiene tres partes, y la tercera es lo que lo distingue de recorrer una página haciendo clic:

1. **La UI**, en un navegador real, con la sesión iniciada como un usuario de prueba.
2. **Las API** que hay detrás de esas pantallas, llamadas con el token del usuario de prueba,
   incluidos los casos que deberían rechazarse.
3. **Los datos guardados.** Después de cada acción, el Tester lee lo que el cambio debería haber
   escrito y lo comprueba: los registros de la base de datos, los archivos del almacenamiento, el
   índice de búsqueda y los logs. En Discava eso es DynamoDB, S3, OpenSearch y CloudWatch.

Tres detalles lo mantienen seguro y silencioso:

- **La issue solo dice qué probar.** Cómo probarlo (las herramientas, los usuarios de prueba, las
  comprobaciones, el informe) es el prompt de la propia automatización, en la máquina. Nadie que
  pueda editar una issue puede cambiarlo.
- **Una issue abierta por cualquier otro se omite**, porque su cuerpo se convertiría en las
  instrucciones del agente.
- **Un test por cada etiquetado.** Cada vez que se pone la label cuenta una vez, así que los
  comentarios del propio Tester nunca arrancan un segundo test. Quita y vuelve a poner la label para
  probar de nuevo.

Nada abre estas issues por defecto. Un workflow que abre una por cada pull request desplegado es la
última pieza del [pegamento que falta](../the-missing-glue/). El de Discava está en
[Verificación post-merge](../../discava/post-merge-verify/).

## Por qué sondeo y no webhooks

Las automatizaciones sondean (cada 2 minutos en Discava, cada 15 por defecto), así que Agent Canvas
puede ejecutarse en un portátil o en un servidor doméstico sin URL pública ni secreto de webhook. El
coste es, como mucho, un intervalo de sondeo de latencia, que es poco comparado con el tiempo que
tarda el agente en trabajar.

## Memoria que sobrevive a la ejecución

Una conversación conserva su contexto para una issue. Los agentes también guardan una memoria que
la sobrevive. OpenHands la almacena en la máquina que ejecuta Agent Canvas, y los tres roles la leen
y escriben en ella. Lo que aprende una ejecución, como una rareza del stack local, un check que
sigue fallando por la misma razón o una convención que el Revisor pide una y otra vez, queda ahí
para cada ejecución posterior, sea cual sea el rol, la issue o la persona que la pidió.

Esa es la diferencia con un agente en un editor, donde lo que aprende se queda en la estación de
trabajo de un desarrollador. Aquí la memoria pertenece al runtime, así que crece con cada tarea que
el equipo ha dado a los agentes, no solo con las que ejecutó una persona.

<Aside type="caution">
Los agentes escriben en la memoria directamente y nadie la revisa. Una lección equivocada se repite
hasta que alguien la quita, y el texto que un agente leyó en una issue o un comentario puede acabar
en ella, otra razón más para que solo los colaboradores puedan comentar. Lee la memoria de vez en
cuando. Una lección que en realidad es una regla va en `AGENTS.md` o, mejor, en un check que la
haga cumplir. La memoria vive en una sola máquina, así que haz copia de seguridad de ella junto con
el resto del estado de Agent Canvas.
</Aside>

## A qué puede acceder el agente y a qué no

Los prompts del Desarrollador y del Revisor nombran un secreto, el token de GitHub, para que el
Desarrollador pueda leer la issue y hacer push de su rama y el Revisor pueda publicar su revisión.
Ninguno necesita acceso a la nube: todo lo que ejecutan se ejecuta en el stack local.

El Tester es la excepción. Tiene que llegar al stage desplegado, así que trabaja con una CLI de la
nube con sesión iniciada en la cuenta de desarrollo, que su prompt le dice que use en solo lectura, y
un usuario de prueba por cada rol de la app. Nunca recibe los roles de despliegue, y su prompt le
prohíbe cambiar la infraestructura, desplegar o tocar otro stage. Como lee issues y pull requests
mientras tiene esas credenciales, nadie sin acceso de escritura puede comentar en ellos. En un
repositorio público, eso supone poner el límite de interacción de GitHub en solo colaboradores.

Qué más no pueden hacer nunca los agentes, y qué impone cada límite, está en
[Controles humanos](../human-gates/#lo-que-los-agentes-nunca-pueden-hacer).

## Elegir agentes

Discava ejecuta las tres con **Claude Code mediante ACP**, cada una con su propio perfil de agente:
Sonnet para el Desarrollador, Opus para el Revisor y el Tester. Usar un modelo más potente para la
revisión es deliberado: el Revisor es la última comprobación antes de una persona, y lee mucho menos
código del que escribe el Desarrollador. El Tester recibe el mismo modelo porque su trabajo también
es de criterio: decidir qué debería hacer un cambio, y si lo que ve en el stage, y lo que encuentra en su almacenamiento, es correcto.
Cualquier agente ACP, o el propio agente de OpenHands con cualquier LLM, encaja en los mismos
perfiles.

El prompt con el que se ejecuta cada rol está en
[Los prompts de los agentes](../../discava/agent-prompts/).
