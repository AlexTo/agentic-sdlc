Los agentes de Discava se ejecutan en una estación de trabajo Linux, bajo OpenHands Agent Canvas. No
hay despliegue de OpenHands en la nube ni webhooks. Todo es sondeo saliente hacia GitHub.

## Agent Canvas

Agent Canvas 1.45.0, instalado desde npm (`@openhands/agent-canvas`) y ejecutado como servicio de
usuario. Su estado vive en `~/.openhands/`: ajustes, perfiles de agente, secretos y la base de datos
SQLite de las automatizaciones.

## Ajustes de las conversaciones

Los ajustes que determinan cómo trabajan los agentes:

| Ajuste | Valor | Por qué |
| --- | --- | --- |
| Agent | ACP, servidor `claude-code` | Un agente de programación externo, mediante el Agent Client Protocol |
| ACP prompt timeout | 30 minutos | Un turno de implementación es largo |
| Max iterations | 500 | Margen para una fase entera en una conversación |
| Confirmation mode | desactivado | Sin supervisión. No hay nadie para confirmar |
| Security analyzer | LLM | Los comandos se siguen filtrando por riesgo |
| Runtime | local | Se ejecuta en el host, donde ya están Node, pnpm y git |
| Worktree branch prefix | `openhands/` | Cada rama que crea un agente empieza así. El pegamento se basa en ello |

## Perfiles de agente

Un perfil por cada rol de agente:

| Perfil | Rol | Agente | Modelo | Lo usa |
| --- | --- | --- | --- | --- |
| `developer` | Desarrollador | Claude Code (ACP) | Sonnet | GitHub issue to PR |
| `reviewer` | Revisor | Claude Code (ACP) | Opus | GitHub code review |
| `tester` | Tester | Claude Code (ACP) | Opus | GitHub issue tester |

Cada uno tiene un prompt timeout de 30 minutos.

## Secretos

Guardados en Agent Canvas (**Settings → Secrets**), por nombre:

| Nombre | Se usa para |
| --- | --- |
| `GITHUB_PERSONAL_ACCESS_TOKEN` | El installation token actual de la GitHub App, pese al nombre. Las automatizaciones leen GitHub con él. Las conversaciones lo reciben para clonar, hacer push, abrir PR, revisar y comentar |
| `OPENHANDS_AUTOMATION_API_KEY` | La clave propia del backend de automatizaciones |
| `DISCAVA_STUDENT_USERNAME`, `DISCAVA_STUDENT_PASSWORD` | El estudiante del Tester en `discava-development` |
| `DISCAVA_INSTRUCTOR_USERNAME`, `DISCAVA_INSTRUCTOR_PASSWORD` | El instructor del Tester |
| `DISCAVA_ADMIN_USERNAME`, `DISCAVA_ADMIN_PASSWORD` | El administrador del Tester |

Los seis secretos `DISCAVA_*` son usuarios de prueba de Cognito en el stage de desarrollo, uno por
cada rol de la app. El Tester inicia sesión en los portales con ellos y obtiene tokens de API con
ellos.

## La GitHub App

Los agentes actúan como `alex-coding-agent`, una GitHub App instalada solo en `AlexTo/discava`, así que
todo lo que abren, publican con push y dicen aparece como `alex-coding-agent[bot]`. No tiene webhook, y
tiene acceso de lectura y escritura a contents, issues y pull requests.

Hasta el 25 de noviembre de 2026 trabajaban como `discava-bot`, una cuenta de máquina con un personal
access token clásico. GitHub marcó la cuenta, lo que ocultó sus 210 issues y pull requests a todo el
mundo, incluidos sus propios listados. Las 44 issues abiertas y los 11 pull requests abiertos se
volvieron a abrir como la app (#1129–#1183), y los originales se cerraron con un enlace a cada copia.
Su trabajo fusionado sigue en `main`, con `discava-bot` como autor.

Un installation token dura una hora, así que la clave privada de la app se queda en la máquina, fuera
de Agent Canvas, y un timer la convierte en tokens:

| Pieza | Qué hace |
| --- | --- |
| `~/.ssh/alex-coding-agent.pem` | La clave privada de la app: el único secreto de larga duración |
| `alex-coding-agent-token.timer` | Un timer de usuario de systemd que ejecuta el script de emisión cada 45 minutos, y una vez al minuto de arrancar |
| El script de emisión | [`scripts/agent-app-token.sh`](https://github.com/AlexTo/agentic-sdlc/blob/main/scripts/agent-app-token.sh) de la plantilla es una copia de él. Firma un JSON Web Token con la clave, lo cambia por un installation token, lo escribe en un archivo que solo su propietario puede leer, y lo pone en el secret `GITHUB_PERSONAL_ACCESS_TOKEN` a través de la API del propio Agent Canvas |
| Un drop-in para `canvas.service` | Ejecuta el script de emisión antes de que arranque Agent Canvas, pone `GIT_AUTHOR_*` y `GIT_COMMITTER_*` a `alex-coding-agent[bot]` y su dirección noreply, y da a Agent Canvas su propio `GIT_CONFIG_GLOBAL` y un `gh` que leen el archivo del token |

Así, las conversaciones interactivas usan la app a través de git y `gh`, y las automatizaciones a
través del secret. Tu propia terminal conserva tu propio login. Las variables de entorno del drop-in
son lo que atribuye los commits a la app: las plantillas de automatización escriben `OpenHands` como
autor en cada checkout, y el formulario **Git Settings** de Agent Canvas rechaza un email con corchetes,
así que Discava también escribió a mano el nombre y la dirección del bot en `~/.openhands/settings.json`.

Dos restos actuaban como el mantenedor, no como el bot, y se quitaron: un servidor MCP de GitHub
(`api.githubcopilot.com`) con el token del mantenedor, y los antiguos personal access tokens.

El pegamento cuenta las revisiones de la app mediante la variable de repositorio `AGENT_APP_LOGIN`
(`alex-coding-agent[bot]`): GitHub no da a una app ninguna asociación con el repositorio, así que sin
ella los veredictos del Revisor ya no devolverían el trabajo al Desarrollador
([#1184](https://github.com/AlexTo/discava/pull/1184)).

## Lo que tiene el Tester en la máquina

El Desarrollador y el Revisor solo necesitan Node, pnpm, git y `gh`. El Tester usa además:

| Herramienta | Para |
| --- | --- |
| AWS CLI, con sesión iniciada en la cuenta que contiene los stacks `discava-development-*` | Encontrar el stage (outputs de los stacks), obtener tokens de Cognito, leer DynamoDB, S3 y los logs de CloudWatch. Su prompt le dice que la use en solo lectura |
| Playwright con Chromium | Manejar los portales desplegados |
| `tmp/screenshots/` del checkout de Discava | Donde se guardan sus capturas, una carpeta por pull request |

<Aside type="caution">
Este es el único lugar donde un agente de Discava trabaja con acceso a la nube. Por eso el stage es
`discava-development`, con datos desechables, y por eso
[solo los colaboradores pueden comentar](../post-merge-verify/#quién-puede-comentar) en lo que leen los agentes. Para un equipo, dale al Tester su propio rol de solo
lectura y su propia máquina o VM.
</Aside>

## Las tres automatizaciones

Las dos primeras se instalaron desde el catálogo de automatizaciones de Agent Canvas, no se
escribieron a mano. La tercera es propia de Discava. Lo que hace cada una en un sondeo está en
[El runtime del agente](../../concepts/the-agent-runtime/#las-tres-automatizaciones), y el prompt que
cada una le da a su agente está en [Los prompts de los agentes](../agent-prompts/).

### Desarrollador: GitHub issue to PR

| Campo | Valor |
| --- | --- |
| Plantilla | `github-issue-to-pr` 1.2.4 |
| Repositorio | `AlexTo/discava` |
| Label de disparo | `openhands` |
| Prefijo de rama | `openhands/issue` → ramas `openhands/issue-<n>` |
| Modo de pull request | Ready for review |
| Secreto del token de GitHub | `GITHUB_PERSONAL_ACCESS_TOKEN` |
| Programación | `*/2 * * * *`, Australia/Sydney |
| Perfil de agente | `developer` |

Un turno de revisión le dice al agente que vuelva a poner después la label `openhands-review`,
para que se revise la nueva cabeza.

### Revisor: GitHub code review

| Campo | Valor |
| --- | --- |
| Plantilla | `github-pr-reviewer` 1.11.2, parcheada para el token de la app (abajo) |
| Repositorio | `alexto/discava` |
| Label de disparo | `openhands-review` |
| Revisor solicitado | `all-hands-bot` (no se usa en la práctica: la label hace el trabajo) |
| Revisiones nuevas por barrido | 2 |
| Tono de la revisión | Concise |
| Mantenedores | ninguno |
| Programación | `*/2 * * * *`, Australia/Sydney |
| Perfil de agente | `reviewer` |

La plantilla pregunta a `GET /user` con qué cuenta actúa, algo que GitHub rechaza a un installation
token con `403 Resource not accessible by integration`, así que tras el cambio a la app todos los
barridos fallaban antes de revisar. La copia de Discava pregunta a GraphQL `viewer { login }` cuando
`/user` se niega, en la búsqueda del login del worker y en su comprobación del token, y se volvió a
subir en lugar del bundle del catálogo. La 1.11.3 del catálogo sigue teniendo el problema.

Mientras los checks siguen ejecutándose, el Revisor publica un comentario "⏳ Review waiting on
checks" y vuelve a intentarlo en un barrido posterior. Sus revisiones empiezan con "_This review was
posted by an AI agent (OpenHands)._" y llevan un marcador oculto `<!-- openhands-review-run: <id> -->`.

### Tester: GitHub issue tester

No hay plantilla de catálogo para esta. Es un worker de unas cien líneas, construido sobre los mismos
helpers de GitHub y de conversaciones que usan las plantillas del catálogo, con su prompt en un
archivo junto a él.

| Campo | Valor |
| --- | --- |
| Plantilla | ninguna: `worker.py`, `prompt.md` y `config.json`, escritos a mano |
| Repositorio | `AlexTo/discava` |
| Label de disparo | `openhands-test` |
| Autores de las issues | `github-actions[bot]` |
| Prefijo de rama | `openhands/test-fix` → ramas de corrección `openhands/test-fix-<n>` |
| Tests nuevos por barrido | 2 |
| Archivo de prompt | `prompt.md` |
| Secreto del token de GitHub | `GITHUB_PERSONAL_ACCESS_TOKEN` |
| Programación | `*/2 * * * *`, Australia/Sydney |
| Perfil de agente | `tester` |

En cada sondeo, el worker:

1. Lista las issues abiertas que llevan `openhands-test`, de menor a mayor número.
2. Omite cualquier issue que no haya abierto uno de los **autores de las issues**. El cuerpo de una
   issue pasa a formar parte de lo que lee el agente, así que solo se prueban las issues del propio
   workflow.
3. Encuentra el último evento que puso la label. El número de la issue y el ID de ese evento forman
   una entrega, así que un sondeo posterior del mismo etiquetado se ignora, y los comentarios del
   propio Tester nunca arrancan un segundo test. Quitar y volver a poner la label es un evento nuevo
   y, por tanto, un test nuevo.
4. Arranca o reanuda la conversación de la issue con el prompt, hasta dos tests nuevos por sondeo.

Las issues que sondea las abre [Post-merge Verify](../post-merge-verify/). Los comentarios del Tester
terminan con "_This comment was posted by an AI agent (OpenHands)._".

<Aside title="Una identidad para los agentes">
En Discava, el Desarrollador, el Revisor y el Tester actúan todos como `alex-coding-agent[bot]`, y el
mantenedor usa su propia cuenta. Así el mantenedor puede aprobar el PR de un agente con normalidad, y se
ve qué comentarios vienen de un agente. El Revisor y el Desarrollador siguen compartiendo esa identidad,
y GitHub no deja que nadie apruebe su propio PR, así que el veredicto del Revisor se publica como una
revisión `COMMENTED`. El pegamento lee la línea del veredicto, no el estado de la revisión, así que no
importa.
</Aside>
