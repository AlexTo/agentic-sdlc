Hueco 11: todos los checks anteriores al merge se ejecutaron contra sustitutos locales, y nadie mira
el cambio allí donde realmente se ejecuta. Discava lo cierra con un tercer rol de agente. Después de
cada despliegue a `discava-development`, un workflow abre una issue de test por cada pull request que
llevaba el despliegue, y el **agente Tester** prueba ese cambio en el stage: los portales en un
navegador real, las API como los usuarios de prueba y los datos que escribió el cambio.

```d2
direction: down

deploy: "Deploy\n(discava-development)"
verify: "Post-merge Verify\npost-merge-test"
issue: "issue de test\nbloqueada, después openhands-test" {shape: page}
tester: "agente Tester\n(OpenHands, siguiente sondeo)"
stage: discava-development {shape: cylinder}
report: "informe en la issue" {shape: document}
fix: "PR de corrección\nopenhands/test-fix-<n>" {shape: page}

deploy -> verify: terminado
verify -> issue: una por PR desplegado
issue -> tester
tester -> stage: "Playwright, API, AWS CLI"
tester -> report
tester -> fix: "solo una corrección pequeña y clara" {style.stroke-dash: 3}
```

## Post-merge Verify

`.github/workflows/post-merge-verify.yml` se ejecuta con `workflow_run`, cuando termina **Deploy**, y
a mano con un número de pull request. Hace checkout de la rama por defecto y ejecuta
`post-merge-test`. Las ejecuciones comparten un único grupo de concurrencia, así que dos despliegues
muy seguidos no pueden abrir dos issues para el mismo pull request.

El script (`src/post-merge-test/`):

1. **Comprueba que la ejecución desplegó el stage de test.** Lee los jobs de la ejecución de Deploy.
   Una ejecución cuyo paso `Deploy` se omitió (su commit ya no era el último de `main`) no desplegó
   nada, y una ejecución para otro stage no se prueba.
2. **Busca lo que llevaba el despliegue.** Un despliegue puede contener varios merges, porque un
   despliegue omitido deja su commit al siguiente. Así que toma los commits entre el anterior
   despliegue correcto del stage y este, y el pull request con el que se fusionó cada uno.
3. **Decide, por cada pull request** (`decide()` en `plan.ts`). No hay issue cuando:
   - ya existe una para él (se encuentra por su marcador oculto)
   - lleva la label `skip-deploy-test`
   - no cambia nada que se despliegue: solo docs, specs, tests, tooling, CI u otros archivos que
     nunca llegan a un stack
4. **Genera la issue** (`renderIssue()`). Solo dice qué probar.
5. **La abre sin label, bloquea y después etiqueta.** Se bloquean (lock) la issue, el pull request
   que prueba y las issues que cierra ese pull request. Solo entonces se pone `openhands-test`. Si
   algo no se puede bloquear, la label no se añade nunca y la ejecución falla, indicando qué hay que
   bloquear a mano.

Ejecutado a mano con un número de pull request, abre una issue aunque ya exista una. Así es como se
vuelve a probar un cambio desde cero.

## La issue que abre

Una real, [#654](https://github.com/AlexTo/discava/issues/654):

```markdown
<!-- post-merge-test pr:647 -->

## What to test

- Pull request: #647 (feat(stripe-checkout): a refund takes access away)
- Issue it closes: #646
- Merged as `b4dc4f7…`, deployed to `discava-development` at `b4dc4f7…` ([Deploy run](…))
- Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
  through the flow with Playwright, then call the APIs behind it and check the stored data.

<details><summary>Deployed files it changes (4)</summary>

- `packages/events/src/local/stripe-stand-in.ts`
- `packages/events/src/payments/events/charge-refunded.ts`
- `packages/events/src/payments/stripe-webhook.ts`
- `packages/websites/student-portal/src/routes/learn/$courseId/-components/enrolment-actions.tsx`

</details>
```

El título es `test(post-merge): verify #647 a refund takes access away`: una cabecera de Conventional
Commit de 100 caracteres como máximo, para que el Tester pueda reutilizarla. El tipo es `UI change`
cuando el pull request toca un portal o los componentes compartidos, y `backend change or fix` en
caso contrario.

<Aside type="note" title="Qué probar, nunca cómo">
La issue no tiene instrucciones. Cómo probar (las herramientas, los usuarios de prueba, las
comprobaciones, el informe) es el [prompt](../agent-prompts/#tester) propio del Tester en OpenHands,
así que nadie que pueda editar una issue puede cambiarlo.
`.github/ISSUE_TEMPLATE/test-deployed-pr.md` es el mismo formulario para abrir una a mano.
</Aside>

## Qué hace el Tester

En su siguiente sondeo, la automatización `github-issue-tester` toma la issue y arranca el Tester. Su
prompt tiene ocho pasos:

1. Averiguar qué cambió, a partir del pull request, su diff, la issue que cierra y su spec, y anotar
   qué debería ser cierto ahora.
2. Probar la UI, si la hay: iniciar sesión en la página alojada de Cognito con Playwright, recorrer
   el flujo, tomar una captura en cada paso y mirarlas todas.
3. Llamar a las API con el token de acceso de un usuario de prueba, incluidos los casos de error.
4. Comprobar los datos guardados: ítems de DynamoDB, documentos de OpenSearch, objetos de S3 y los
   logs de las Lambdas.
5. Usar sus propios datos, con nombres `pmt-<pr>-<what>`.
6. Informar en la issue: qué probó, una tabla con cada comprobación, si pasa o falla y su evidencia,
   y un veredicto.
7. Cerrar la issue si pasa. Si falla, dejarla abierta con los pasos para reproducirlo. Abrir un pull
   request de corrección solo cuando la causa está clara y la corrección es pequeña.
8. No cambiar nunca la infraestructura, IAM, los usuarios ni la configuración del stage, ni
   desplegar, tocar otro stage, editar workflows o hacer merge.

### Ejecución 1: bloqueado, y lo dice

El cambio pone fin a la inscripción de un estudiante cuando Stripe comunica un reembolso. Para
probarlo tiene que haber un pedido pagado que reembolsar, y el stage no tenía cuenta de pagos. El
Tester no dio el test por bueno ni hizo conjeturas. Su [veredicto](https://github.com/AlexTo/discava/issues/654#issuecomment-7033260676) fue "blocked, not verified", con la evidencia: el
`payment.status` de la API de administración respondió `not-connected`, y la tabla principal no
contenía ningún pedido.

Después comprobó lo que podía sin un pago: la función del webhook desplegada contiene el nuevo
handler de `charge.refunded`, el bundle del portal que se sirve tiene la nueva pantalla "You're no
longer enrolled", un aviso de reembolso falsificado se rechaza con un 400 y no escribe nada, y las
páginas del curso siguen funcionando para un curso gratuito. Pasaron nueve comprobaciones. Listó las
seis cosas que *no* había verificado, y qué las desbloquearía.

También dijo lo que no iba a hacer. Conectar una cuenta de pagos supone guardar una clave de Stripe,
lo que cambia la configuración del stage, y su [prompt](../agent-prompts/#tester) lo prohíbe. Así que
dejó la issue abierta para una persona.

### Ejecución 3: una compra real

Una vez conectada al stage una cuenta de Stripe en modo de prueba, el Tester empezó desde el principio
del flujo, porque un reembolso necesita una compra. Cada paso de los siguientes es una fila de su
[tercer informe](https://github.com/AlexTo/discava/issues/654#issuecomment-7037624120):

1. Como el instructor, a través de la API, creó un curso llamado `pmt-647-course`, le puso un precio
   de 19,99 USD y lo publicó.
2. Como el estudiante, en un navegador real, inició sesión en la página alojada de Cognito, abrió el
   curso, eligió **Buy now** y pagó en el checkout alojado de Stripe con una tarjeta de prueba.
3. Volvió a la página del curso, que decía "Confirming your payment", y observó tres cosas: la
   página, el registro del pedido en DynamoDB y los logs de la función del webhook.

La última imagen es igual que la primera, y ese es el fallo. El pago se completó, pero el pedido
nunca salió de `pending`, no apareció ninguna inscripción y la página volvió a mostrar
**Buy now**. Nada en la pantalla dice que algo vaya mal: ningún error, ninguna petición fallida en la
consola. El Tester lo detectó porque también leyó el registro del pedido y los logs de la función,
que mostraban el porqué:

```text
REPORT … Duration: 10000.00 ms … Memory Size: 128 MB  Max Memory Used: 117 MB  Status: timeout
REPORT … Duration: 10000.00 ms … Memory Size: 128 MB  Max Memory Used: 117 MB  Status: timeout
```

El aviso de Stripe de que el checkout estaba pagado nunca llegó a entrar. La función que lo recibe se
ejecutaba con los 128 MB por defecto de Lambda, y su arranque en frío (las entidades de la tabla
principal, AppConfig, el SDK de Stripe) no terminaba dentro del timeout de 10 segundos. Un runtime
que agota el tiempo se descarta, así que cada reintento de Stripe arrancaba en frío y fallaba igual.
El Tester la comparó con la función de checkout, que tiene 256 MB y tardó 8,1 segundos en arrancar.

Al reembolso que se quería probar nunca se llegó. Lo que encontró el Tester está un paso antes, y es
peor: en el stage desplegado, un estudiante podía pagar un curso y no recibirlo nunca.

### Por qué nada lo detectó antes

El defecto es anterior al pull request que se estaba probando, y había pasado todas las capas:

- **Los tests unitarios** ejercitan la lógica del handler, que es correcta.
- **Los tests e2e** se ejecutan contra el stack local, donde un sustituto hace de Stripe y nada tiene
  límite de memoria ni un timeout de 10 segundos.
- **El agente Revisor** y **la persona** leen un diff en el que no aparece ningún ajuste de memoria,
  porque la línea que falta es el defecto.

Solo existe allí donde la función está desplegada. Ese es el hueco para el que está el Tester.

### El PR de corrección

La causa estaba clara y la corrección era pequeña, así que el prompt del Tester permitía un pull
request. [#657](https://github.com/AlexTo/discava/pull/657) es un solo [commit](https://github.com/AlexTo/discava/commit/854760c3c30a5ceb1ee7c7e52ebd596bef3374f1) que cambia
dos archivos: cuatro líneas en el construct `StripeWebhookApi` que ponen la memoria de la función en
512 MB, y un test de doce líneas que falla sin ellas (`Missing key 'MemorySize'`). Salió de `main`
como la rama `openhands/test-fix-654`, y su descripción hace referencia tanto a [#647](https://github.com/AlexTo/discava/pull/647) como a
[#654](https://github.com/AlexTo/discava/issues/654).

La descripción también es clara sobre su límite: "Not verified on a deployed stage. The fix only
takes effect once deployed." (no verificado en un stage desplegado; la corrección solo surte efecto
una vez desplegada).

Después el Tester se detuvo. No hizo merge ni desplegó. Los [PR Checks](https://github.com/AlexTo/discava/actions/runs/44722377986)
salieron en verde, y la label `openhands-review` lo entregó al agente Revisor. La review se atascó
durante cuarenta minutos por algo que ningún agente había hecho mal: el pull request estaba bloqueado
(locked), y GitHub no acepta una review en un pull request bloqueado. Una vez desbloqueado, el Revisor
lo aprobó. Por eso Discava dejó de bloquear los pull requests (consulta
[Quién puede comentar](#quién-puede-comentar)). Lo fusiona una persona, como cualquier otro. La issue de test [#654](https://github.com/AlexTo/discava/issues/654) sigue abierta hasta que el propio reembolso se pruebe en un
stage donde los pagos se liquiden. El último informe del Tester lista los datos de prueba que dejó:
el curso y el pedido en `pending`.

Las capturas se quedan en la estación de trabajo, en `tmp/screenshots/pr-<pr>/` del checkout de
Discava. Los informes nombran cada archivo y dicen qué muestra. Las cuatro de arriba se copiaron de
allí para esta página.

## Quién puede comentar

Discava es un repositorio público, así que cualquiera puede comentar en sus issues y pull requests.
Los agentes leen esos comentarios mientras tienen un token que puede hacer push, y el Tester tiene
además acceso a AWS y las contraseñas de los usuarios de prueba. Un comentario es, por tanto, una
forma de darle instrucciones a un agente: una inyección de prompt. Los prompts le dicen a cada agente
que trate lo que lee como datos, pero un prompt es una petición, no una garantía.

Así que Discava mantiene a los desconocidos fuera de la conversación, de dos maneras:

| Capa | Qué hace |
| --- | --- |
| **Límite de interacción** | En GitHub, **Settings → Moderation options → Interaction limits** está en **Limit to repository collaborators**. Nadie más puede comentar, abrir una issue ni abrir un pull request en ninguna parte del repositorio |
| **Issues de agente bloqueadas** | Agent Issues y Post-merge Verify abren cada issue sin su label, la bloquean (lock) (en una issue de test, también el pull request que prueba y las issues que cierra ese pull request) y solo entonces añaden la label. Si algo no se puede bloquear, la label no se añade nunca y la ejecución falla. El código compartido es `src/helpers/conversation-lock.ts` |

Vienen con él dos reglas más:

- **Los marcadores son de confianza según el autor.** Los workflows encuentran sus issues anteriores
  por un marcador oculto. Un marcador solo cuenta en una issue abierta por `github-actions[bot]` o
  por alguien con acceso de escritura (`src/helpers/issue-author.ts`), así que un desconocido no
  puede estancar una cadena ni detener un test abriendo una issue con un marcador dentro.
- **El Tester solo prueba las issues del workflow.** Su automatización omite cualquier issue de test
  que no haya abierto `github-actions[bot]`, y sus instrucciones son su propio prompt, nunca la issue.

<Aside type="caution" title="Un repositorio público necesita el límite de interacción">
Si tu repositorio es público, pon el límite de interacción en **solo colaboradores** antes de activar
el agente Tester, y mejor aún antes que cualquier agente. Sin él, cualquiera puede comentar en una
issue de test o en el pull request que prueba, y el Tester lee ese comentario mientras tiene
credenciales de la nube y las contraseñas de los usuarios de prueba.

El límite dura como mucho seis meses. El de Discava llega hasta el 20 de mayo de 2027. Apunta la
renovación en un calendario, porque nada te avisa cuando caduca. Un repositorio privado no lo
necesita: allí solo pueden comentar las personas con acceso.

Los comentarios escritos antes de poner el límite, o antes de etiquetar una issue, se quedan. Léelos
antes de etiquetar a mano una issue existente.
</Aside>

### Por qué Discava dejó de bloquear los pull requests

Hasta [#658](https://github.com/AlexTo/discava/pull/658), un workflow llamado **Agent Lock** también bloqueaba cada pull request que abría
un agente, y cualquier issue que alguien etiquetara a mano para un agente. Mantenía fuera a los
desconocidos, pero tenía dos costes:

- **El agente Revisor no podía hacer la review.** GitHub rechaza una review nativa en un pull request
  bloqueado, incluso desde una cuenta con acceso de escritura. El PR de corrección [#657](https://github.com/AlexTo/discava/pull/657) se
  bloqueó a las 10:49 y se etiquetó para review a las 10:54, y no recibió ninguna review hasta que se
  desbloqueó a mano a las 11:34. El Revisor lo aprobó cinco minutos después.
- **Las capturas E2E no se podían publicar.** GitHub también le niega al token de Actions un
  comentario en una conversación bloqueada, así que la
  [lista de capturas](../pr-checks/#ui-screenshots-y-el-comentario-e2e-screenshots) tuvo que pasar
  al resumen del job.

El límite de interacción hace el mismo trabajo para todo el repositorio, sin bloquear nada en lo que
los agentes tengan que escribir. Agent Lock y su script se eliminaron, y los cuatro pull requests de
agente que había bloqueado se desbloquearon a mano.

## Ejecución en seco

```bash
DRY_RUN=true GITHUB_REPOSITORY=AlexTo/discava GITHUB_EVENT_NAME=workflow_dispatch PR_NUMBER=647 \
  pnpm nx run @discava/tooling-agent:post-merge-test
```

Esto imprime el título y el cuerpo de la issue que abriría, y no crea nada. Aun así lee el pull
request mediante `gh`, así que necesitas haber iniciado sesión.
