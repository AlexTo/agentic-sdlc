Desde que se abrió el pull request hasta su merge: cuatro rondas de corrección, tres de CI y una de la
revisión, y una acción de una persona. Después, el Tester encontró dos problemas que ninguno de ellos
podía haber visto.

## 1. La issue

Un estudiante que pide un reembolso ve "Refund requested" mientras Stripe lo procesa, y la página del
curso comprueba cada 2 segundos si se ha completado. [#1166](https://github.com/AlexTo/discava/issues/1166)
dice qué fallaba en eso:

> While a student's refund is pending, the course page refetches `course.myEnrolment` and
> `payment.myOrder` every 2 s, and never stops. If the refund fails at Stripe or its event never
> arrives, the order stays `paid` with a refund requested, the page keeps polling for as long as
> it is open, and the student isn't told anything has gone wrong.

Sus criterios de aceptación son dos líneas: el sondeo se detiene tras un límite, y un reembolso
fallido, simulado en el sustituto de Stripe, termina el estado pendiente con un mensaje claro.

Esta issue no salió de una spec. El agente Revisor la planteó mientras revisaba el PR que permitía a
un estudiante pedir un reembolso, como un problema fuera del alcance de ese PR, y se convirtió en una
issue propia. (#1166 es una copia: GitHub marcó la antigua cuenta de máquina de los agentes, lo que
ocultó todo lo que había abierto, y la GitHub App que usan ahora los agentes
[volvió a abrir](../../discava/openhands-setup/#la-github-app) las issues abiertas.)

## 2. El agente Desarrollador abre el PR

El agente Desarrollador tomó la issue y abrió [#1195](https://github.com/AlexTo/discava/pull/1195)
en `openhands/issue-1166`. El cambio recorre cuatro paquetes: un límite de 2 minutos y un botón "Check
again" en la página del curso, un handler de webhook para los eventos de reembolso fallido de Stripe,
un campo `refundFailedAt` en el pedido con un invariante que exige que un fallo siga a una petición, y
"Your refund failed" en la página del curso. La descripción terminaba con lo que había ejecutado y lo
que no:

> Unit tests cover the helper, the webhook, the invariant and the UI (poll limit, check again,
> failure message). [...] I did not run the e2e tests or try the stand-in control in a browser.

## 3. CI lo devuelve, tres veces

**`ci-fix-1`: sin capturas, y líneas sin tests.** El PR cambiaba lo que ve un estudiante pero no
tomaba ninguna captura, así que [**UI Screenshots** falló](https://github.com/AlexTo/discava/actions/runs/45619342535/job/139224403383).
**codecov/patch** también falló: había líneas nuevas sin test. **Agent CI Status** añadió `ci-fix-1` y
devolvió al agente Desarrollador. Su [respuesta](https://github.com/AlexTo/discava/pull/1195#issuecomment-7164484931)
muestra que, por el camino, encontró un problema en su propio primer intento:

> **UI Screenshots:** added a `learner-refund` e2e scenario for a failed refund, with
> `screenshot(student, 'refund-failed')`. For this the Stripe stand-in has a new
> `fail-next-refund` control. [...] This replaces the `refund-fail` control from the first push,
> which the scenario could not use, because the stand-in completed the refund before it could
> fail.

**`ci-fix-2`: un fallo que no era suyo.** La siguiente ejecución falló en **Checks (build)**, en un
test de CDK synth del paquete de infraestructura. El agente leyó el log y
[no cambió código por ello](https://github.com/AlexTo/discava/pull/1195#issuecomment-7165688653):

> the one failure was `@discava/infra` `instructor-api-stack.test.ts` [...], which hit its 30s
> timeout while the sibling CDK synth tests in that file took 22–31s. This PR doesn't touch infra
> or anything the stack synthesises [...], so I made no code change for it. The push below
> re-runs the build.

Cubrió la única línea parcial que codecov seguía señalando, y el push volvió a ejecutar el build, que
pasó. Un agente que "corrige" un fallo cambiando código que no entiende es peor que uno que dice que
el fallo no es suyo y por qué.

**`ci-fix-3`: su propio test nuevo estaba mal.** Después de la revisión (siguiente sección), el agente
añadió un escenario e2e para el límite de 2 minutos, y falló en [**E2E tests (11/12)**](https://github.com/AlexTo/discava/actions/runs/45685812586/job/139458011986).
Cinco minutos después, [la causa](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172674824):

> the new `a pending refund stops polling and offers to check again` scenario failed with a
> Playwright strict-mode violation, not a product bug. `getByText('Still being processed')` also
> matched the alert's description ("Your refund is still being processed…"), so it resolved to two
> elements. The page did reach the timed-out state. I now match the title with `{ exact: true }`.

El agente no había ejecutado ningún escenario e2e en local, y lo dijo cada vez. PR CI es donde se
ejecutan por primera vez, y el [comentario E2E screenshots](https://github.com/AlexTo/discava/pull/1195#issuecomment-7163204279)
lista las dos pantallas que capturó la ejecución: `learner-refund/01-refund-failed.png` y
`learner-refund/01-refund-still-being-processed.png`.

## 4. El agente Revisor encuentra lo que CI no podía

Cuando terminaron todos los checks del commit de cabeza, el agente Revisor leyó el diff contra la
issue. Vio que el código de pagos estaba bien, ejecutó él mismo 361 tests específicos, y aun así
[bloqueó el merge](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6063632214):

> 1. **The branch carries another open PR's change.** Commit `e7cb9bc9`, "fix(student-portal):
>    surface completions and progress load errors on start route", is the change from open PR
>    #1188, not part of #1166. [...] Merging this PR would ship #1188's start-route error behaviour
>    under a payments title, before #1188 is reviewed.
> 2. **Live evidence is missing for the "Still being processed" / "Check again" state.** [...] The
>    new timed-out state [...] has only unit tests, and no capture from the running app.
>
> 🔄 CHANGES REQUESTED

El primer punto es el tipo de cosa que pasa todos los checks. El commit de más compilaba y sus tests
pasaban; simplemente no pertenecía al PR. El checkout del agente había partido de una rama que ya lo
tenía. El segundo punto es otra vez la regla de las capturas, aplicada por un lector: CI comprueba que
un PR añade una captura, y el Revisor comprueba que cada estado nuevo tiene la suya.

**Agent Review Status** añadió `review-fix-1`. Ocho minutos después, el agente Desarrollador
[había](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172386579) hecho rebase de sus
propios cuatro commits sobre `main` sin los otros dos, y había añadido un control en el sustituto que
mantiene un reembolso pendiente y un escenario e2e que instala el reloj falso de Playwright y avanza
125 segundos. Es el escenario que `ci-fix-3` corrigió después.

En el commit de cabeza final, el Revisor [confirmó](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066801083)
que los dos puntos estaban resueltos, que los 12 shards de e2e habían pasado, y nombró las dos
capturas: "No material findings [...] ✅ APPROVED".

## 5. Una persona aprueba

A las 11:33 el mantenedor [aprobó](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066944326)
e hizo merge. Fue lo único que hizo una persona en este PR. Lo que tenía delante: una descripción que
decía qué se había ejecutado y qué no, las dos capturas de CI, una lista de checks en verde y un rastro
de cuatro revisiones, cada una con su motivo.

## 6. El merge se despliega, y se abre una issue de test

En Discava, `main` se despliega solo en un stage de desarrollo. El [despliegue](https://github.com/AlexTo/discava/actions/runs/45734764281)
que llevaba este merge terminó a las 12:28, y un minuto después **Post-merge Verify** abrió
[#1240](https://github.com/AlexTo/discava/issues/1240). Lista los 12 archivos desplegados que cambió
el PR y dice qué tipo de test hay que hacer:

> Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
> through the flow with Playwright, then call the APIs behind it and check the stored data.

## 7. El agente Tester prueba el stage desplegado

El agente Tester no vuelve a ejecutar la suite de tests, y no usa el sustituto de Stripe. Usa el
producto desplegado como lo haría una persona, con Stripe real en modo sandbox. Su
[informe](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815) lista cada paso:

1. Como un instructor de prueba, a través de la API, creó dos cursos a $19.99.
2. Como un estudiante de prueba, en un navegador real, inició sesión y compró cada uno en Stripe
   Checkout, con las tarjetas de prueba de Stripe para "el reembolso falla" y "el reembolso queda
   pendiente".
3. Pidió un reembolso de cada uno desde la página del curso.
4. Después de cada paso llamó a las API, leyó los pedidos y las inscripciones en DynamoDB, y leyó los
   logs de las Lambda del webhook y de la API.

## 8. El Tester deja la issue abierta

Fallaron tres comprobaciones, y dos terminaron en un estado que el PR no esperaba. El
[veredicto](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815):

> **Verdict: the student-facing UI and `payment.myOrder` work as the PR describes. The
> failed-refund path does not work end to end on the deployed stage.**

Encontró dos causas, ambas fuera de lo que podían alcanzar los tests del PR:

1. **El webhook de Stripe del stage nunca recibe los eventos nuevos.** El PR añadió `refund.failed` y
   `charge.refund.updated` a la lista de eventos, pero esa lista solo se envía a Stripe cuando un
   administrador lo conecta por primera vez. El stage se conectó seis días antes. El Tester contó
   exactamente cuatro invocaciones del webhook en esa media hora, ninguna por un fallo.
2. **Con Stripe real, un reembolso fallido llega cuando el pedido ya está `refunded`.** Stripe envía
   `charge.refunded` en cuanto se crea un reembolso, incluso uno que está pendiente o que va a fallar.
   Cuando llega `refund.failed`, la condición del nuevo handler (el pedido sigue `paid`) ya no se
   cumple, y no hace nada sin avisar:

   > The student has lost access, hasn't been refunded, and isn't told.

   El sustituto del escenario e2e del PR nunca liquida un reembolso antes de hacerlo fallar, así que
   CI mostró la versión feliz de esto.

El Tester puede abrir un PR de corrección cuando la corrección es pequeña y clara. Explicó por qué no
lo hizo:

> Fixing it means deciding how a refund failure after `charge.refunded` should restore the order
> and enrolment, or not treating a `pending` refund as refunded. That goes beyond a small fix, so
> I'm reporting it rather than opening a PR.

Tampoco tocó la conexión de Stripe del stage, aunque volver a guardarla corregiría la primera causa:
"I didn't do that, because it changes stage configuration." Así que la issue sigue abierta, con los
dos problemas descritos, cómo reproducirlos y las decisiones que debe tomar una persona. Listó los
datos de prueba que dejó en el stage, y un error que vio y que ya se seguía en otro sitio, para que
nadie lo confundiera con una regresión.

<Aside type="tip">
[Verificación post-merge](../../discava/post-merge-verify/) sigue otra issue de test en la que el
Tester encontró un fallo, lo rastreó hasta su causa y sí abrió el PR de corrección.
</Aside>

## Qué detectó cada puerta

| Puerta | Qué detectó | Por qué no lo detectó la anterior |
| --- | --- | --- |
| CI | Un cambio de UI sin captura, líneas sin tests y un localizador roto en el propio test e2e del agente | El agente Desarrollador no había ejecutado la suite e2e |
| Agente Revisor | El commit de otro PR colado en la rama, y un estado de pantalla nuevo sin captura | El commit de más pasaba todos los checks, y CI solo comprueba que se añadió alguna captura |
| Agente Tester | Un endpoint de webhook que nunca recibe los eventos nuevos, y Stripe real dando primero por reembolsado un reembolso que falla | El sustituto se comporta como espera el código, y ningún test ve la configuración del stage |

Ninguna de las tres es ingeniosa por sí sola. Cada una mira algo que las otras no pueden ver: CI, las
reglas; el Revisor, la issue y la rama; el Tester, el producto en ejecución y los servicios reales que
tiene detrás.

## Lo que hizo la persona

1. Leyó el PR #1195 y sus capturas, lo aprobó e hizo merge.
2. Lo siguiente: decidir qué debe hacer un fallo de reembolso después de `charge.refunded`, entre las

Nadie escribió un prompt, pegó un log de errores ni recorrió el stage a mano.
