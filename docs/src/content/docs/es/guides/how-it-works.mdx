Esta página sigue una feature a lo largo de todo el bucle. Cada paso indica quién actúa y qué
deja tras de sí.

```d2
grid-rows: 2
grid-columns: 4
horizontal-gap: 140
vertical-gap: 90

# Top row runs left to right, bottom row right to left, so the loop wraps.
spec: "PR de spec\n(tú)" {shape: document}
issues: "Agent Issues\n(GitHub Actions)"
issue: issue {shape: page}
implement: "implementar\n(OpenHands)"
merge: "merge\n(tú)"
review: "revisión\n(OpenHands)"
checks: "PR Checks\n(GitHub Actions)"
pr: pull request {shape: page}

spec -> issues: spec-ready
issues -> issue
issue -> implement
implement -> pr
pr -> checks
checks -> review: verde
review -> merge: aprobado
merge -> issues: siguiente fase
```

## Los pasos

| # | Quién | Qué ocurre | Artefacto |
| --- | --- | --- | --- |
| 1 | 🧑🤖&nbsp;Tú + agente | `/speckit-specify` convierte una idea de un párrafo en una spec. `/speckit-clarify` hace hasta cinco preguntas y escribe tus respuestas en ella | `specs/<timestamp>-<name>/spec.md` |
| 2 | 🧑🤖&nbsp;Tú + agente | `/speckit-plan` decide el *cómo* y comprueba el plan contra la constitución | `plan.md`, `data-model.md`, `contracts/` |
| 3 | 🧑🤖&nbsp;Tú + agente | `/speckit-tasks` escribe una lista ordenada de tareas, agrupadas en fases. `/speckit-analyze` revisa los tres archivos entre sí | `tasks.md` |
| 4 | 🧑&nbsp;**Tú** | Abres el PR de la spec, lo revisas como si fuera código, añades la label `spec-ready` y haces merge | Un PR de spec fusionado. **Control humano 1** |
| 5 | ⚙️&nbsp;Automatización | El workflow **Agent Issues** lee `tasks.md` y abre una issue para el primer grupo de fases, con la label `openhands` | Una issue de implementación |
| 6 | 🤖&nbsp;OpenHands | En su siguiente sondeo, el agente toma la issue, escribe primero los tests, implementa, marca sus tareas y abre un PR en `openhands/issue-<n>` | Un pull request |
| 7 | ⚙️&nbsp;CI | Los PR checks ejecutan lint, tests unitarios, build, el check de formato de `tasks.md`, los tests e2e y el check de capturas | Resultados de los checks |
| 8 | ⚙️🤖&nbsp;Automatización + OpenHands | Si una ejecución sale en rojo, **Agent CI Status** marca el PR como fallido. El agente lo ve en el siguiente sondeo y revisa el mismo PR | Labels de `ci-fix-1` a `ci-fix-5` |
| 9 | 🤖&nbsp;OpenHands | Cuando han terminado todos los checks, el agente revisor revisa el commit de cabeza y termina con `✅ APPROVED` o `🔄 CHANGES REQUESTED`. En el segundo caso, **Agent Review Status** devuelve el trabajo al agente | Una revisión y, quizá, labels `review-fix-N` |
| 10 | 🧑&nbsp;**Tú** | Lees la descripción del PR y el comentario **E2E screenshots**, haces las tareas **(human)** que haya y haces merge | Un PR fusionado. **Control humano 2** |
| 11 | ⚙️&nbsp;Automatización | El merge vuelve a ejecutar **Agent Issues**. Abre la issue de la siguiente fase que tenga tareas de agente sin marcar, y los pasos 6 a 10 se repiten hasta que no quede ninguna | La siguiente issue, o terminado |

## Lo que haces tú realmente

Por cada feature, escribes y apruebas la spec una vez. Por cada pull request, haces una
revisión y pulsas merge. Solo se te requiere antes si un bucle agota sus intentos (`ci-fix-exhausted`
o `review-fix-exhausted`), o si el agente comenta que está bloqueado. Mientras los agentes trabajan,
puedes escribir la siguiente spec.

## Dónde vive cada pieza

| Pieza | Archivo |
| --- | --- |
| Herramientas de specs | `.specify/`, las skills `speckit-*`, `specs/` |
| Reglas del proyecto para cada ejecución de un agente | `.specify/memory/constitution.md`, `AGENTS.md` |
| La issue que recibe el agente | `.github/ISSUE_TEMPLATE/implement-phase.md` |
| De la spec a la issue | `.github/workflows/agent-issues.yml` |
| De la spec terminada a `specs/_archive/` | `.github/workflows/archive-specs.yml` |
| Del CI al agente | `.github/workflows/agent-ci.yml` |
| Del revisor al agente | `.github/workflows/agent-review.yml` |
| Checks | `.github/workflows/pr-checks.yml`, `ui-screenshots.yml`, `ci.yml` |
| Las reglas detrás del pegamento, con tests unitarios | `packages/common/scripts/src/agent-*`, `ui-screenshots/` |
| El runtime del agente | OpenHands Agent Canvas, fuera del repositorio |

Los detalles están en Conceptos: [cómo las fases se convierten en issues](../../concepts/one-phase-at-a-time/) y
[cómo un fallo devuelve el trabajo al agente](../../concepts/feedback-loops/).
