import { Steps, Aside } from '@astrojs/starlight/components';

**Al terminar tendrás:** una GitHub App con la que actúan los agentes, instalada en tu fork; Issues y
Actions activados, todas las labels que usa el workflow, una rama `main` que solo acepta pull requests con
checks en verde y una aprobación, y los comentarios limitados a los colaboradores.

<Steps>

1. **Crea la GitHub App de los agentes.** Los agentes actúan como una app que no usa nada más, así que
   sus pull requests y comentarios aparecen con ella, y los apruebas como los de cualquier otra persona.
   La de Discava es `alex-coding-agent`.

   Abre
   [**New GitHub App**, ya relleno](https://github.com/settings/apps/new?url=https%3A%2F%2Fgithub.com%2FAlexTo%2Fagentic-sdlc&public=false&contents=write&issues=write&pull_requests=write&workflows=write&checks=read&statuses=read&actions=read).
   El enlace rellena el formulario, así que tú solo tienes que:

   - Escribir un **nombre**. Los nombres de app son únicos en todo GitHub, así que prueba con
     `<you>-coding-agent`.
   - Comprobar que **Webhook → Active** está desmarcado. Agent Canvas hace polling, así que nada
     necesita llegar a tu máquina.
   - Hacer clic en **Create GitHub App**.

   Los permisos que selecciona el enlace, en **Repository permissions**, por si quieres comprobarlos:

   | Permiso | Acceso | Por qué |
   | --- | --- | --- |
   | Contents | Read and write | Clonar y hacer push de las ramas de los agentes |
   | Issues | Read and write | Leer issues, comentar, poner labels |
   | Pull requests | Read and write | Abrir pull requests, hacer review y comentar en ellos |
   | Workflows | Read and write | Sin él, GitHub rechaza un push entero que toque `.github/workflows/`, algo que puede hacer un merge de `main`. Los agentes nunca editan workflows |
   | Checks, Commit statuses, Actions | Read-only | El Revisor espera a que terminen los checks antes de hacer la review |
   | Metadata | Read-only | Lo exige GitHub |

2. **Consigue la clave de la app e instálala.** En la página que GitHub te muestra a continuación, los
   ajustes de la app:

   - Apunta el **App ID**, un número cerca de la parte superior.
   - En **Private keys**, haz clic en **Generate a private key**. Tu navegador descarga un archivo
     `.pem`. Es el único secreto de larga duración: los agentes solo ven tokens de una hora creados a
     partir de él.
   - En la barra lateral, haz clic en **Install App**, luego en **Install**, elige **Only select
     repositories** y selecciona tu fork.

   Necesitas el App ID y el archivo `.pem` en el [paso 3](../openhands/).

3. **Ejecuta el script de configuración** desde tu clon, con la sesión de `gh` iniciada como propietario
   del fork, pasando el nombre de la app tal como aparece en su dirección, `github.com/apps/<app-name>`:

   ```bash
   ./scripts/setup-repository.sh <you>/agentic-sdlc <app-name>
   ```

   Un fork copia el código, no los ajustes. El script los configura con la CLI `gh`, y deja siempre el
   mismo estado, así que puedes volver a ejecutarlo sin problema.

   Añade primero `--dry-run` si quieres ver cada comando de `gh` antes de que se ejecute. El script configura:

   | Configura | Por qué |
   | --- | --- |
   | Issues y Actions activados | GitHub desactiva ambos en un fork, y el workflow funciona sobre issues |
   | 20 labels | Todas las labels de [Referencia: labels](../../reference/labels/) |
   | Protección de rama en `main` | Un pull request, una aprobación, las aprobaciones obsoletas descartadas y siete checks obligatorios: `Checks (lint)`, `Checks (test)`, `Checks (build)`, `Tasks format`, `Invariant coverage`, `E2E tests`, `UI Screenshots` |
   | Tokens de los workflows de solo lectura, y Actions no puede abrir ni aprobar pull requests | Un workflow que pudiera abrir un pull request también podría aprobar uno. Archive Specs hace push de la rama que mueve una spec terminada a `specs/_archive/` y avisa con un enlace que abre su pull request, ya relleno, para que lo envíes |
   | Interacciones limitadas a los colaboradores, durante seis meses | Un fork de un repositorio público es público, y los agentes leen cada comentario de aquello en lo que trabajan mientras tienen un token que puede hacer push |
   | GitHub Pages desde Actions | El job **Deploy Docs** de CI publica este sitio |
   | La variable de repositorio `AGENT_APP_LOGIN`, con el login del bot de la app, `<app-name>[bot]` | GitHub no da a las reviews de una app ninguna asociación con el repositorio, así que el pegamento solo devuelve el trabajo al agente por un veredicto del Revisor de personas con acceso de escritura y de la app que esta variable nombra |

   La protección deja permitido el bypass, así que tú, como propietario, puedes fusionar un pull request
   que abriste tú mismo, como un PR de spec, que GitHub no te deja aprobar.

4. **Comprueba que Actions está activado.** Si la pestaña **Actions** de tu fork todavía muestra **I understand my
   workflows, go ahead and enable them**, haz clic. GitHub a veces pide ese clic incluso
   después de que la API haya activado Actions.

</Steps>

<Aside type="tip" title="Por qué una app, y no una segunda cuenta">
Los agentes de Discava trabajaron primero como `discava-bot`, una cuenta de máquina con un personal
access token. En noviembre de 2026 GitHub la marcó, lo que ocultó a todo el mundo sus 210 issues y
pull requests. Los tokens de una app caducan al cabo de una hora y solo llegan a los repositorios en
los que está instalada. Una segunda cuenta con un token clásico (los scopes `repo` y `workflow`) sigue
funcionando: pásale esa cuenta al script en su lugar, y se invita como colaboradora.
</Aside>

<Aside type="caution">
El límite de interacción caduca seis meses después de ponerlo, y nada te avisa. Apunta la fecha
y vuelve a ejecutar el script antes. Si más adelante añades el agente Tester, que tiene credenciales de
la nube, este límite es lo que impide que el comentario de un desconocido le llegue. Consulta
[Quién puede comentar](../../discava/post-merge-verify/#quién-puede-comentar).
</Aside>

<Aside type="caution">
No añadas `software-factory/review` a los checks obligatorios. Es una señal para el agente, que solo se
publica como `failure`, y hacerlo obligatorio bloquearía todos los PR.
</Aside>

## Comprueba que funciona

La página **Issues → Labels** del fork lista las 20 labels, **Settings → Branches** muestra la regla en
`main` con siete checks obligatorios, y **Settings → Moderation options → Interaction limits** muestra
el límite de solo colaboradores con su fecha de fin. **Settings → Secrets and variables → Actions →
Variables** muestra `AGENT_APP_LOGIN`, y **Settings → GitHub Apps** lista tu app.
