import { Steps, Aside } from '@astrojs/starlight/components';

**Résultat :** un `AGENTS.md` que chaque agent lit en premier, et
`.github/ISSUE_TEMPLATE/implement-phase.md`, la source des instructions permanentes de chaque
issue d'implémentation.

<Steps>

1. **Écrivez `AGENTS.md`** à la racine du dépôt. Limitez-le à ce dont un agent a besoin à chaque exécution, et
   renvoyez vers `CONTRIBUTING.md` pour le reste. Utilisez ces sections :

   ```markdown
   # AGENTS.md

   Read CONTRIBUTING.md before opening a PR.

   ## What this is
   One paragraph: the product, the stack, the monorepo tool.

   ## Commands
   Install; build, lint, test everything; one project's tests, once (not watch mode);
   one test file; `nx affected`; e2e; local dev; resetting local data.

   ## Architecture
   One bullet per package: what it is, what it may import, where new code of each kind goes.

   ## Conventions
   - Conventional Commits for commit and PR titles (enforced by commitlint).
   - The formatter and linter, by name, so the agent doesn't add another.
   - Where helpers go. Where shared code goes.
   - Every rule a reviewer has had to repeat twice.
   ```

   <Aside type="tip">
   La section des commandes est la plus importante. Un agent qui ne trouve pas « lancer un fichier de test, une fois » lancera
   toute la suite en mode watch et restera bloqué.
   </Aside>

   Quand la section d'architecture dépasse une ligne par package, déplacez le détail de chaque package dans un
   `AGENTS.md` imbriqué dans son dossier, et laissez à la racine une ligne qui y renvoie. Un agent ne charge un
   fichier imbriqué que lorsqu'il travaille dans ce dossier, donc une exécution ne lit que le détail dont elle a besoin.

2. **Copiez le template d'issue** de ce dépôt vers
   `.github/ISSUE_TEMPLATE/implement-phase.md`. Le script Agent Issues écrit lui-même les sections de spec et
   de périmètre de l'issue, et lit tout ce qui se trouve sous `## Instructions for the agent` dans le
   template au moment de l'exécution :

   ```markdown
   ## Instructions for the agent

   - Read `AGENTS.md`, `.specify/memory/constitution.md` and the spec folder first.
   - Work through the scope in order, writing each story's tests first. Tick each task in `tasks.md` in the same commit that completes it.
   - Do not use `pnpm dev`, Docker or the e2e runner locally. Run unit and component tests (once, not in watch mode), `pnpm lint`, typecheck and `pnpm build` on what you changed. E2E and concurrency tests run on PR CI: write them, then read CI's result.
   - A change to what a user sees ships with `screenshot(page, 'name')` calls (`packages/e2e/src/helpers/screenshots.ts`) in the e2e scenario for that flow, at each state a reviewer would want to see: PR CI posts them as the `E2E screenshots` comment, and the `UI Screenshots` check fails without them. Don't leave screenshots to a **(human)** task.
   - Skip tasks marked **(human)** and list them in the PR description for the reviewer.
   - Use Conventional Commits for every commit. The PR title is a Conventional Commit too, for example `feat(assignments): submit work to an upload assignment`, not `[#n] ...`.
   - In the PR description write `Refs #<parent>`. Never use `Closes` or `Fixes` against the parent issue; closing this issue is fine.
   - Never weaken a test to make it pass, never edit `.github/workflows/`, never merge, and don't touch cloud credentials.
   - If you are blocked, comment on this issue with what you tried and stop.
   ```

   Gardez `#<parent>` tel quel. Le script le remplace par l'issue parente de la spec, et supprime la
   puce quand la spec n'en a pas. Gardez exactement le titre `## Instructions for the agent`, car
   le script le cherche et échoue sans lui.

3. **Adaptez les instructions à votre stack** : les commandes, le chemin du helper de captures d'écran, et
   ce que « cloud credentials » signifie pour vous.

</Steps>

## Vérifier que ça marche

```bash
grep -c '^## Instructions for the agent$' .github/ISSUE_TEMPLATE/implement-phase.md
```

```text
1
```
