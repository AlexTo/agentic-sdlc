**Résultat :** des workflows qui ouvrent des issues à partir des specs, renvoient l'agent au travail sur une CI
en rouge ou une review « changes requested », et archivent une spec dès que toutes ses tâches sont cochées.

<Steps>

1. **Copiez les quatre workflows** depuis le dossier `.github/workflows/` de ce dépôt : `agent-issues.yml`,
   `agent-ci.yml`, `agent-review.yml`, et `agent-status.yml`, qui contient les étapes que partagent les deux
   workflows de statut. Changez-y le scope `@agentic-sdlc/`. Leurs déclencheurs et permissions sont listés dans
   [Référence : workflows](../../reference/workflows/).

   Si vos agents agissent sous une GitHub App, réglez la variable de dépôt `AGENT_APP_LOGIN` sur le
   login de son bot, par exemple `my-agent[bot]`. `agent-status.yml` la transmet à `agent-review-status`.
   GitHub donne aux reviews d'une app l'association `NONE`, donc sans elle les verdicts du Relecteur ne
   renvoient jamais l'agent au travail. Les agents qui agissent sous un compte avec un accès en écriture
   n'ont besoin de rien.

2. **Vérifiez que les conditions `if:` correspondent à vos décisions.** Si vous avez changé le préfixe de branche ou les
   labels, changez-les ici aussi :

   ```yaml
   # agent-issues.yml
   if: >-
     github.event_name == 'workflow_dispatch' ||
     (github.event.pull_request.merged == true &&
     ((github.event.action == 'closed' &&
     (contains(github.event.pull_request.labels.*.name, 'spec-ready') ||
     startsWith(github.event.pull_request.head.ref, 'openhands/'))) ||
     (github.event.action == 'labeled' &&
     github.event.label.name == 'spec-ready')))

   # agent-ci.yml
   if: >-
     github.event.workflow_run.event == 'pull_request' &&
     startsWith(github.event.workflow_run.head_branch, 'openhands/') &&
     (github.event.workflow_run.conclusion == 'failure' ||
     github.event.workflow_run.conclusion == 'timed_out')

   # agent-review.yml
   if: >-
     startsWith(github.event.pull_request.head.ref, 'openhands/') &&
     github.event.pull_request.head.repo.full_name == github.repository &&
     contains(github.event.review.body, 'CHANGES REQUESTED')
   ```

3. **Gardez les permissions et le checkout exactement tels que copiés.** Chaque workflow ne demande que ce
   qu'il écrit. `pull-requests: write` semble superflu mais ne l'est pas : les labels et les commentaires sur une PR passent par
   l'API des issues, qui refuse le token du workflow sans cette permission.

   Les deux workflows de statut font le checkout de la **branche par défaut**, dans `agent-status.yml`. Agent Issues fait le checkout du
   **commit de merge**, pour voir les cases cochées par la PR mergée. Ne changez jamais l'un ou l'autre pour faire le checkout du
   head de la PR : ces jobs détiennent un token qui peut écrire.

4. **Gardez le verrou avant le label.** Agent Issues ouvre chaque issue sans son label `openhands`,
   verrouille sa conversation pour que seuls les collaborateurs puissent commenter ce que lit l'agent, et
   n'ajoute le label qu'ensuite. Si le verrouillage échoue, le label n'est jamais ajouté et l'exécution échoue, en
   nommant l'issue à verrouiller à la main. Le code se trouve dans `helpers/conversation-lock.ts`.

5. **Gardez les groupes de concurrence.** Chacun est par PR ou par branche, avec `cancel-in-progress: false`.
   Ainsi, deux événements pour une même PR ne peuvent pas compter chacun une tentative, et les merges de PR différentes ne
   s'annulent jamais entre eux.

6. **Copiez `archive-specs.yml`**, si vous voulez que les specs terminées soient rangées. Quand un push sur
   `main` modifie un `specs/*/tasks.md` actif, il prépare une PR sur la branche `archive-spec/<folder>`
   pour chaque spec dont toutes les tâches sont cochées, tâches **(human)** comprises. La PR déplace le dossier vers
   `specs/_archive/` et réécrit les liens qui y mènent et qui en partent. Agent Issues ignore `specs/_archive/`,
   et `Tasks format` échoue si un `tasks.md` archivé contient une tâche non cochée.

   Il ignore une spec qui a une issue d'agent ouverte, et une spec qui a déjà eu une PR d'archivage. Fermez cette
   PR sans la merger pour garder la spec active.

   <Aside type="caution">
   Laissez désactivé le paramètre de dépôt « Allow GitHub Actions to create and approve pull requests »,
   comme le fait `scripts/setup-repository.sh` : il permettrait aussi à un workflow d'approuver une PR. Le
   workflow pousse alors la branche et son exécution affiche un avertissement avec un lien qui ouvre la PR,
   titre et description pré-remplis, pour que vous la soumettiez. Une PR que vous ouvrez déclenche PR Checks
   d'elle-même. Tant que personne ne l'a fait, chaque exécution pousse à nouveau la branche et répète
   l'avertissement.
   </Aside>

</Steps>

## Vérifier que ça marche

Les workflows apparaissent dans l'onglet **Actions** du dépôt une fois arrivés sur `main`. Ouvrez
**Actions → Agent Issues → Run workflow**, et saisissez un dossier de spec qui n'existe pas, comme
`does-not-exist`.

L'exécution réussit avec une notice : `No issue created: no spec folder with a tasks.md was found`.

<Aside type="note">
Les workflows `workflow_run` et `pull_request_review` ne s'exécutent que depuis la version de la branche par défaut.
Leurs modifications prennent effet une fois mergées. C'est aussi pour cela qu'un agent ne peut pas les modifier dans sa
propre PR.
</Aside>
