import { Steps, Aside } from '@astrojs/starlight/components';

**Résultat :** votre propre constitution ratifiée, et des templates Speckit qui produisent des fichiers
que le workflow Agent Issues peut lire.

Le `.specify/` que vous avez copié à [l'étape 2](../speckit/) contient déjà une constitution et des
templates qui fonctionnent, écrits pour l'application de notes. Cette étape les fait vôtres.

<Steps>

1. **Réécrivez la constitution pour votre projet.** Dans votre agent de code :

   ```text
   /speckit-constitution
   ```

   Donnez-lui les principes propres à votre projet : architecture, modèle de données, sécurité par défaut, conventions
   de code. [Celle de Discava](../../discava/constitution-and-guidance/) est un exemple complet. Gardez
   ces parties de celle que vous avez copiée, en adaptant les commandes et les noms de packages à votre stack, car
   le reste du workflow en dépend :

   | À garder | Dans la constitution copiée | Pourquoi |
   | --- | --- | --- |
   | Tests unitaires, invariants et tests e2e sont obligatoires, et les tests sont une spécification | III. Layered Tests | L'agent ne peut pas affaiblir un test pour faire passer la CI au vert |
   | Tout tourne sous `pnpm dev`, sans compte cloud | II. Everything Runs Locally | La CI de PR peut alors lancer la suite e2e et donner à l'agent un vrai retour |
   | Les agents implémentent sur leur propre branche et PR, ne lancent jamais la stack locale, et marquent **(human)** les tâches qui en ont besoin | Development Workflow | L'agent n'a pas Docker. La CI lance ce qu'il ne peut pas lancer |
   | La CI de PR est le garde-fou. Un agent ne merge jamais, ne pousse jamais sur `main`, ne modifie jamais les workflows de CI et n'affaiblit jamais un test | Development Workflow | Ce qui garde un agent dans son couloir |

2. **Changez les chemins de packages dans `tasks-template.md`.** Ses tâches de test nomment les
   packages de ce dépôt : `packages/notes-table/src/helpers/invariants/` et `@agentic-sdlc/e2e`. Faites-les pointer vers
   les vôtres. Gardez le reste du template tel quel : les règles de format sous **Read by automation**,
   le marqueur **(human)**, les tests obligatoires, et la note interdisant de modifier les tests existants sont
   ce sur quoi reposent le workflow Agent Issues et le check `Tasks format`.

3. **Gardez la ligne d'issue parente** dans `spec-template.md` :

   ```markdown
   **Parent issue**: [#<number>, or "none" if there is no tracking issue]
   ```

   Agent Issues en tire le `Refs #<parent>` qu'il écrit dans chaque issue.

</Steps>

## Vérifier que ça marche

Générez une spec et des tâches jetables pour une toute petite fonctionnalité. Puis, une fois les scripts de glue en place
([étape 5](../glue-scripts/)) :

```bash
pnpm nx run @your-scope/tooling-agent:validate-tasks
```

```text
1 tasks.md file(s) are in the expected format.
```

Supprimez ensuite le dossier de spec jetable.

<Aside type="caution">
`/speckit-tasks` écrit parfois `### Phase 2` ou indente une tâche. C'est précisément ce que le
validateur détecte, donc n'assouplissez pas le validateur. Corrigez la formulation du template jusqu'à ce que les fichiers générés
passent.
</Aside>
