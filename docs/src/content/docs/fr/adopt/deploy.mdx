import { Steps, Aside } from '@astrojs/starlight/components';

**Résultat :** un scan Trivy à chaque push sur `main`, un workflow Deploy qui livre chaque `main`
au vert sur un stage de développement, des déploiements en production qui attendent une personne, et,
si vous le souhaitez, un agent Testeur qui teste chaque changement mergé sur le stage de développement.

Ce dépôt fournit les workflows, désactivés : `deploy.yml` ne s'exécute qu'à la main ou une fois
`AUTO_DEPLOY_STAGE` défini, et `post-merge-verify.yml` ne s'exécute qu'après un déploiement. L'application de notes n'a
pas d'infrastructure cloud, donc la partie à écrire vous revient. Les étapes parlent d'AWS et de CDK, comme Discava,
mais la structure convient à n'importe quel cloud.

<Steps>

1. **Ajoutez une cible `trivy`** aux projets que vous voulez scanner (le `pnpm trivy` racine lance
   `nx run-many --target trivy --all`). Le job `trivy` du `ci.yml` copié le lance à chaque push sur `main`,
   dans un job séparé de `build`, pour qu'une CVE nouvellement publiée signale `main` sans bloquer quoi que ce soit
   d'autre. Consignez les résultats acceptés, un ID par ligne, dans `.trivyignore`.

2. **Ajoutez votre infrastructure** sous forme d'application CDK dans `packages/infra`, avec un stage par environnement
   dans son `src/main.ts` :

   ```bash
   pnpm nx g @aws/nx-plugin:ts#infra --name=infra
   ```

   Sa cible `deploy-ci` est ce que lance le workflow Deploy. Les constructs du site web des notes
   se trouvent déjà dans `packages/common/constructs`.

3. **Mettez en place un accès cloud sans clé** pour chaque stage : le fournisseur OIDC de GitHub, un rôle de déploiement
   approuvé uniquement pour `repo:owner/repo:environment:<stage>`, un rôle d'exécution CloudFormation avec une
   limite de permissions, le bootstrap CDK, et un environnement GitHub nommé d'après le stage avec
   les variables `AWS_REGION`, `AWS_DEPLOY_ROLE_ARN` et `AWS_EXECUTION_ROLE_ARN`. Le
   [`scripts/setup-stage.sh`](https://github.com/AlexTo/discava/blob/main/scripts/setup-stage.sh) de Discava
   fait tout cela pour ses stages ; lisez-le avant de l'adapter. Ne stockez pas de clés d'accès.

4. **Copiez `.github/workflows/deploy.yml`**, si vous ne travaillez pas dans un fork, et changez son
   scope `@agentic-sdlc/` et le nom du stage par défaut. Il fait le checkout du commit vérifié par la CI, s'arrête
   tôt avec une erreur claire si `packages/infra` ou les variables de l'environnement manquent, lance
   Trivy, synthétise, et ne déploie que si le commit est toujours le dernier de `main`. Cette vérification de
   fraîcheur se trouve *à l'intérieur* du créneau de concurrence du job, donc elle reflète `main` juste avant le déploiement,
   même si l'exécution a attendu derrière une autre.

5. **Activez les déploiements automatiques** pour le stage de développement. Sous **Settings → Secrets and
   variables → Actions → Variables**, ajoutez une variable de dépôt `AUTO_DEPLOY_STAGE` contenant le nom de votre
   stage de développement.

6. **Protégez la production.** Sous **Settings → Environments**, ouvrez l'environnement de votre stage de
   production et ajoutez des **Required reviewers**. Pour le déployer, ouvrez **Actions → Deploy → Run
   workflow** et saisissez le stage de production. Le job attend alors une approbation.

7. **Ajoutez l'agent Testeur**, si vous voulez que chaque changement déployé soit testé (manque 11). Depuis ce
   dépôt, vous avez déjà sa glue (`post-merge-test/` à l'étape 5), son template d'issue (étape
   4), et `.github/workflows/post-merge-verify.yml`, qui ouvre une issue de test pour chaque pull
   request qu'une exécution de Deploy a mise sur le stage de test. Il teste sur `TEST_STAGE`, une variable de dépôt
   qui vaut par défaut `AUTO_DEPLOY_STAGE`.

   Côté OpenHands, ajoutez un profil d'agent `tester` et une automatisation qui recherche les issues
   portant le label `openhands-test`. Il n'existe pas de template de catalogue pour cela. Le worker de Discava
   et son prompt sont décrits dans [Configuration d'OpenHands](../../discava/openhands-setup/#testeur--github-issue-tester)
   et [Les prompts des agents](../../discava/agent-prompts/#testeur). Donnez au Testeur :

   - un CLI cloud connecté au compte de développement, avec aussi peu d'accès que les tests l'exigent
   - un utilisateur de test par rôle de votre application, stocké comme secrets OpenHands
   - un navigateur qu'il peut piloter, comme Playwright avec Chromium

   <Aside type="caution" title="Dépôt public ? Limitez d'abord les commentaires aux collaborateurs">
   Le Testeur lit des issues, des pull requests et leurs commentaires tout en détenant ces identifiants.
   Si votre dépôt est public, le commentaire d'un inconnu peut lui transmettre des instructions.
   `scripts/setup-repository.sh` limite les interactions aux collaborateurs, pour au plus six mois, donc
   relancez-le avant la fin de la limite. Gardez aussi le verrouillage dans `helpers/conversation-lock.ts`, gardez le « comment tester » dans le prompt propre de
   l'automatisation plutôt que dans l'issue, et ne le pointez jamais vers un stage dont les données comptent.
   </Aside>

</Steps>

## Vérifier que ça marche

Mergez une PR quelconque. La CI tourne, puis **Deploy** démarre de lui-même avec le stage de développement. Relancez la CI
à la main sur un commit plus ancien : Deploy journalise `Skipping deploy: no longer main's latest commit` et
ne livre rien.

Avec le Testeur en place : après ce déploiement, **Post-merge Verify** ouvre une issue verrouillée intitulée
`test(post-merge): verify #<pr> …`, avec le label `openhands-test`. En un passage, le Testeur démarre,
et son rapport apparaît en commentaire sur l'issue.

<Aside type="note">
Aucun agent ne déploie, et aucun ne voit ces rôles. Le Développeur et le Relecteur n'ont besoin que du token
GitHub. L'accès du Testeur au compte de développement est distinct du rôle de déploiement, qui
n'est endossé que par un workflow qui s'exécute depuis `main`, dans l'environnement du stage.
</Aside>

Suite : votre dépôt contient maintenant tout ce que contient un fork de celui-ci. Continuez à partir de
[2. Configurer le dépôt](../../setup/github-repository/), avec votre propre dépôt à la place
du fork.
