import { Steps, Aside } from '@astrojs/starlight/components';

**Résultat :** un scan Trivy à chaque push sur `main`, un workflow Deploy qui livre chaque `main`
au vert sur un stage de développement, des déploiements en production qui attendent une personne, et,
si vous le souhaitez, un agent Testeur qui teste chaque changement mergé sur le stage de développement.

Les détails de cette étape sont propres à Discava (AWS, CDK), mais la structure convient à n'importe quel cloud. L'application
de notes d'exemple de ce dépôt n'a pas de déploiement, donc copiez depuis
[le `deploy.yml` de Discava](https://github.com/AlexTo/discava/blob/main/.github/workflows/deploy.yml).

<Steps>

1. **Ajoutez une cible `trivy`** aux projets que vous voulez scanner (le `pnpm trivy` racine lance
   `nx run-many --target trivy --all`). Ajoutez le job `trivy` à `ci.yml`, comme dans ce dépôt. Gardez-le
   séparé du job `build`, pour qu'une CVE nouvellement publiée signale `main` sans bloquer quoi que ce soit
   d'autre. Consignez les résultats acceptés, un ID par ligne, dans `.trivyignore`.

2. **Mettez en place un accès cloud sans clé.** Sur AWS, le `scripts/setup-stage.sh` de Discava crée, par stage :
   le fournisseur OIDC de GitHub, un rôle de déploiement approuvé uniquement pour
   `repo:owner/repo:environment:<stage>`, un rôle d'exécution CloudFormation avec une limite de
   permissions, et les variables de l'environnement GitHub (`AWS_REGION`, `AWS_DEPLOY_ROLE_ARN`,
   `AWS_EXECUTION_ROLE_ARN`). Utilisez de la même façon la fédération OIDC de votre cloud pour GitHub Actions.
   Ne stockez pas de clés d'accès.

3. **Ajoutez le workflow Deploy**, déclenché par la fin de la CI sur `main` et à la main :

   ```yaml
   on:
     workflow_run: { workflows: [CI], types: [completed], branches: [main] }
     workflow_dispatch:
       inputs: { stage: { type: string, required: true } }

   jobs:
     deploy:
       if: ${{ github.event_name == 'workflow_dispatch' ||
               (github.event.workflow_run.conclusion == 'success' && vars.AUTO_DEPLOY_STAGE != '') }}
       environment: ${{ inputs.stage || vars.AUTO_DEPLOY_STAGE }}
       concurrency: { group: 'deploy-${{ inputs.stage || vars.AUTO_DEPLOY_STAGE }}', cancel-in-progress: false }
       steps:
         - uses: actions/checkout@<sha>
           with: { ref: '${{ github.event.workflow_run.head_sha || github.sha }}' }
         # init, then: pnpm trivy, configure credentials (OIDC), synth
         - name: Check commit is still main's latest
           id: freshness
           if: ${{ github.event_name == 'workflow_run' }}
           run: |
             main_sha="$(git ls-remote --exit-code origin refs/heads/main | cut -f1)"
             if [[ "$main_sha" == "$(git rev-parse HEAD)" ]]; then
               echo "current=true" >> "$GITHUB_OUTPUT"
             else
               echo "::notice::Skipping deploy: no longer main's latest commit"
               echo "current=false" >> "$GITHUB_OUTPUT"
             fi
         - name: Deploy
           if: ${{ github.event_name != 'workflow_run' || steps.freshness.outputs.current == 'true' }}
           run: pnpm nx run @your-scope/infra:deploy-ci "$STAGE/*" --role-arn "$AWS_EXECUTION_ROLE_ARN"
   ```

   La vérification de fraîcheur se trouve *à l'intérieur* du créneau de concurrence, donc elle reflète `main` juste avant le
   déploiement, même si l'exécution a attendu derrière une autre.

4. **Activez les déploiements automatiques** pour le stage de développement. Sous **Settings → Secrets and
   variables → Actions → Variables**, ajoutez une variable de dépôt `AUTO_DEPLOY_STAGE` contenant le nom de votre
   stage de développement.

5. **Protégez la production.** Sous **Settings → Environments**, ouvrez l'environnement de votre stage de
   production et ajoutez des **Required reviewers**. Pour le déployer, ouvrez **Actions → Deploy → Run
   workflow** et saisissez le stage de production. Le job attend alors une approbation.

6. **Ajoutez l'agent Testeur**, si vous voulez que chaque changement déployé soit testé (manque 11). C'est la
   pièce la plus récente, et elle vit dans Discava, pas dans ce dépôt. Copiez depuis là-bas :

   - `packages/tooling/agent/src/post-merge-test/`, `src/agent-lock/` et `src/helpers/`, avec leurs
     cibles Nx `post-merge-test` et `agent-lock`
   - `.github/workflows/post-merge-verify.yml` et `agent-lock.yml`
   - `.github/ISSUE_TEMPLATE/test-deployed-pr.md`, pour ouvrir une issue de test à la main

   Adaptez ensuite à votre dépôt le nom du stage (`TEST_STAGE`), et les chemins qui n'atteignent jamais une
   stack déployée (`NOT_DEPLOYED` dans `plan.ts`).

   Côté OpenHands, ajoutez un profil d'agent `tester` et une automatisation qui recherche les issues
   portant le label `openhands-test`. Il n'existe pas de template de catalogue pour cela. Le worker de Discava
   et son prompt sont décrits dans [Configuration d'OpenHands](../../discava/openhands-setup/#testeur--github-issue-tester)
   et [Les prompts des agents](../../discava/agent-prompts/#testeur). Donnez au Testeur :

   - un CLI cloud connecté au compte de développement, avec aussi peu d'accès que les tests l'exigent
   - un utilisateur de test par rôle de votre application, stocké comme secrets OpenHands
   - un navigateur qu'il peut piloter, comme Playwright avec Chromium

   <Aside type="caution">
   Le Testeur lit des issues et des pull requests tout en détenant ces identifiants. Gardez le verrouillage
   (`agent-lock.yml` et `helpers/conversation-lock.ts`), gardez le « comment tester » dans le prompt propre de
   l'automatisation plutôt que dans l'issue, et ne le pointez jamais vers un stage dont les données comptent.
   </Aside>

</Steps>

## Vérifier que ça marche

Mergez une PR quelconque. La CI tourne, puis **Deploy** démarre de lui-même avec le stage de développement. Relancez la CI
à la main sur un commit plus ancien : Deploy journalise `Skipping deploy: no longer main's latest commit` et
ne livre rien.

Avec le Testeur en place : après ce déploiement, **Post-merge Verify** ouvre une issue verrouillée intitulée
`test(post-merge): verify #<pr> …`, avec le label `openhands-test`. En un passage, le Testeur démarre,
et son rapport apparaît en commentaire sur l'issue.

<Aside type="note">
Aucun agent ne déploie, et aucun ne voit ces rôles. Le Développeur et le Relecteur n'ont besoin que du token
GitHub. L'accès du Testeur au compte de développement est distinct du rôle de déploiement, qui
n'est endossé que par un workflow qui s'exécute depuis `main`, dans l'environnement du stage.
</Aside>

Suite : votre dépôt contient maintenant tout ce que contient un fork de celui-ci. Continuez à partir de
[2. Configurer le dépôt](../../setup/github-repository/), avec votre propre dépôt à la place
du fork.
