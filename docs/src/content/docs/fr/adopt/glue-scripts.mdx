import { Steps, Aside, FileTree } from '@astrojs/starlight/components';

**Résultat :** un projet `tooling-agent` avec dix cibles Nx et 223 tests unitaires qui passent.
Les workflows des étapes 6, 7 et 9 ne font qu'appeler ces cibles.

<Steps>

1. **Copiez `packages/tooling/agent/`** depuis ce dépôt, en entier. Son `project.json` déclare déjà
   chaque cible qu'appellent les workflows, et son `AGENTS.md` indique à un agent ce que contient chaque
   dossier :

   <FileTree>
   - packages/tooling/agent/src/
     - agent-issues/ spec → issue, le validateur de `tasks.md`, et l'archivage des specs terminées
     - agent-ci/ CI rouge → agent
     - agent-review/ « changes requested » → agent
     - helpers/ verrouiller les issues que lit un agent, et distinguer les auteurs de confiance des inconnus
     - ui-screenshots/ la règle des captures d'écran, et le commentaire `E2E screenshots`
     - invariant-coverage/ quel code écrit quelle entité, et la règle selon laquelle les nouveaux writers ont besoin d'invariants
     - post-merge-test/ PR déployée → issue de test pour le Testeur
   </FileTree>

   Ils ne dépendent que des modules intégrés de Node, de TypeScript (pour l'analyse des invariants) et du CLI `gh`.
   `tsx` les exécute. Ajoutez le dossier au `pnpm-workspace.yaml` de votre workspace et aux références du
   `tsconfig.json` racine si vos globs ne couvrent pas déjà `packages/tooling/*`.

2. **Renommez le scope.** Remplacez `@agentic-sdlc/` par le scope de votre workspace dans le
   `package.json`, le `project.json` et le `vitest.config.mts` du projet, ainsi que dans les commentaires de ses fichiers
   `main.ts`. Chaque workflow que vous copierez ensuite nomme aussi `@agentic-sdlc/tooling-agent`.

3. **Modifiez les constantes selon votre configuration.** Celles en gras pointent vers l'application de notes de ce
   dépôt, donc vous les changerez presque à coup sûr. Les autres ne changent que si vous avez changé une décision
   de [la vue d'ensemble](../overview/) :

   | Constante | Fichier | Par défaut |
   | --- | --- | --- |
   | **`UI_SOURCE`** | `ui-screenshots/check.ts` | `.tsx`/`.css` sous `packages/notes-website/src/` et `packages/common/shadcn/src/` |
   | **`WRITER_PACKAGES`**, **`ENTITIES_PACKAGE`** | `invariant-coverage/scan.ts` | Les packages dont le code écrit dans la table, et celui qui contient ses entités (`notes-table`) |
   | **`WRITER_MAP_PATH`**, **`INVARIANTS_PATH`**, **`HELPERS`** | `invariant-coverage/check.ts` | `packages/notes-table/entity-writers.json`, `packages/notes-table/src/helpers/invariants`, `notes-table` |
   | **`UI_PATHS`**, **`NOT_DEPLOYED`** | `post-merge-test/plan.ts` | Ce qui compte comme une modification d'UI qui vaut la peine d'être parcourue, et les chemins qui n'atteignent jamais une stack déployée |
   | `SPEC_READY_LABEL`, `AGENT_BRANCH_PREFIX` | `agent-issues/gate.ts` | `spec-ready`, `openhands/` |
   | `AGENT_LABEL` | `agent-issues/issue.ts` | `openhands` |
   | `AGENT_BRANCH`, `REVIEW_STATUS_CONTEXT`, `MAX_CI_FIX_ATTEMPTS` | `agent-ci/plan.ts` | `^openhands\/issue-\d+$`, `software-factory/review`, `5` |
   | `MAX_REVIEW_FIX_ATTEMPTS`, `CHANGES_REQUESTED` | `agent-review/plan.ts` | `5`, `🔄 CHANGES REQUESTED` |
   | `WAIVER_LABEL` | `ui-screenshots/check.ts`, `invariant-coverage/check.ts` | `no-ui-screenshots`, `no-new-invariant` |

   Si vous ne vérifiez pas encore les invariants, laissez le dossier `invariant-coverage` en place et ne
   copiez pas son job PR Checks à l'étape 6. Certains tests unitaires lisent les vrais fichiers d'invariants, donc mettez à jour
   ces tests (dans `invariant-coverage/check.test.ts`) ou les chemins ci-dessus.

   <Aside type="caution">
   Ne changez pas `REVIEW_STATUS_CONTEXT`. `software-factory/review` est le statut que cherche le worker
   issue-to-PR d'OpenHands. Avec tout autre nom, l'agent n'est jamais renvoyé au travail.
   </Aside>

4. **Lancez les tests.**

   ```bash
   pnpm nx run @your-scope/tooling-agent:test
   ```

</Steps>

## Essayer une exécution à blanc

Chacun des scripts d'agent lit l'événement GitHub depuis `GITHUB_EVENT_PATH` et, avec
`DRY_RUN=true`, affiche sa décision au lieu de l'appliquer. Pour rejouer un cas réel, enregistrez le payload
d'une exécution de workflow passée et faites pointer le script dessus :

```bash
DRY_RUN=true GITHUB_REPOSITORY=owner/repo GITHUB_EVENT_PATH=./event.json \
  pnpm nx run @your-scope/tooling-agent:agent-ci-status
```

```json
{
  "pullRequest": 470,
  "plan": {
    "action": "send-back",
    "attempt": 1,
    "label": "ci-fix-1",
    "description": "CI failed (fix attempt 1 of 5): E2E tests (4/4)"
  }
}
```
