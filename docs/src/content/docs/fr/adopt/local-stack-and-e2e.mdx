import { Steps, Aside, FileTree } from '@astrojs/starlight/components';

**Résultat :** `pnpm dev` qui démarre toute l'application avec des substituts locaux, une suite Playwright que la CI
lance sur chaque PR, des captures d'écran publiées sur la PR, et des invariants vérifiés après chaque test.

C'est l'étape qui dépend le plus de votre stack. C'est aussi ce qui permet à la CI de donner à l'agent un vrai
retour sans identifiants cloud.

<Steps>

1. **Donnez à chaque service cloud un substitut local**, démarré par une cible `dev`, pour que `pnpm dev` lance
   tout. Le `packages/tooling/local-dev/` de ce dépôt démarre DynamoDB local dans Docker pour
   la table des notes. [Les substituts de Discava](../../discava/local-stack/#ce-qui-tourne-en-local) couvrent aussi
   S3, SQS, OpenSearch et Cognito, plus un processus « event runner » qui appelle les mêmes handlers
   que ceux qu'appellent les déclencheurs Lambda, les streams et EventBridge dans le cloud.

   Basculez le code backend sur un seul flag (`LOCAL_DEV=true`), avec les endpoints dans un module partagé.
   Listez dans votre guide de contribution ce qui ne tourne encore que dans le cloud, et marquez les tâches qui en ont besoin
   **(human)**.

2. **Copiez le projet e2e** depuis ce dépôt, `packages/e2e/`, et remplacez son scénario par
   les vôtres, un fichier par parcours utilisateur. Ce qu'il faut garder :

   <FileTree>
   - packages/e2e/
     - playwright.config.ts lit `E2E_SHARD` pour que la matrice de la CI puisse découper la suite, démarre `pnpm dev`, un seul worker, des relances uniquement en CI
     - src/helpers/
       - screenshots.ts `screenshot(page, 'name')`, qui enregistre les images que téléverse le job `e2e` de PR Checks
       - table-invariants.ts un `test` Playwright qui vérifie les invariants après chaque scénario
   </FileTree>

   Chaque scénario crée ses propres utilisateurs et des données aux noms uniques, et aucun ne réinitialise les données locales, donc ils
   s'exécutent dans n'importe quel ordre. Appelez `screenshot` là où une personne regarderait, après un `expect` sur ce qui s'affiche :

   ```ts
   await expect(page.getByRole('heading', { name: 'Reviews' })).toBeVisible();
   await screenshot(page, 'reviews section with three reviews');
   ```

3. **Copiez les invariants** depuis `packages/notes-table/src/helpers/invariants/` dans le package
   qui possède votre table. Pour chaque règle qui porte sur des enregistrements écrits par du code différent (compteurs,
   agrégats, ordre), écrivez une vérification qui parcourt un instantané des données et renvoie les violations,
   avec un test unitaire qui la casse. La section « Rules that span records » de `packages/notes-table/README.md`
   explique comment en ajouter une.

   Les scénarios prennent `test` depuis `table-invariants.ts` au lieu de `@playwright/test`. Après chacun,
   il fait échouer le scénario si la table présente une violation qu'elle n'avait pas avant. Seules les *nouvelles*
   violations comptent, donc d'anciennes données locales ne font jamais échouer une exécution, et `expect.poll` laisse au travail
   en arrière-plan (handlers de streams, recalculs) le temps de rattraper son retard.

4. **Générez la carte des writers, et copiez le hook pre-push.** Lancez
   `pnpm nx run @your-scope/tooling-agent:entity-writers` et committez le `entity-writers.json` qu'il
   écrit. Copiez `.husky/pre-push` depuis ce dépôt, avec ses `MAP` et `PATHS` pointés vers
   les vôtres : quand une branche modifie du code qui pourrait écrire dans la table, il régénère la carte et arrête
   le push si elle a changé. Le check de PR `Invariant coverage` compare ensuite la carte avec celle de la branche
   de base, et retient une PR qui ajoute un writer jusqu'à ce que les invariants nomment l'entité.

5. **Ajoutez des tests de concurrence** pour les écritures sur lesquelles deux utilisateurs pourraient entrer en concurrence : envoyez les mêmes requêtes d'API au
   même instant avec `Promise.all`, puis vérifiez le résultat et les invariants.

</Steps>

## Vérifier que ça marche

```bash
pnpm nx e2e @your-scope/e2e
ls dist/packages/e2e/screenshots/*/
```

Ouvrez ensuite une PR qui modifie une page et ajoute un appel `screenshot(`. Quand PR Checks se termine, la PR
porte un commentaire intitulé **E2E screenshots** qui liste la nouvelle image sous « Added by this pull
request ».

<Aside type="tip">
Si votre application ne peut pas encore tourner entièrement en local, commencez par ce qui le peut. Même une suite qui ne couvre que
l'API et la base de données attrape la plupart des erreurs des agents. Ajoutez les substituts un service à la fois, et gardez
le reste en tâches **(human)** d'ici là.
</Aside>
