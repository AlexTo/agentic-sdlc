Le moyen le plus rapide d'obtenir le workflow est de [forker ce dépôt](../../setup/fork/). Cette section
est pour le cas où vous ne pouvez pas : vous avez un dépôt produit existant et voulez y mettre la même configuration.

Chaque étape ajoute un élément et indique comment le vérifier. Presque chaque élément est un fichier ou un dossier
que vous copiez tel quel depuis ce dépôt, puis que vous faites pointer vers vos propres packages : vous n'écrivez de la
configuration à la main que là où elle décrit votre projet. Une fois terminé, votre dépôt contient ce que contient
un fork, et vous continuez à partir de
[2. Configurer le dépôt](../../setup/github-repository/).

<Aside type="tip">
Forkez quand même ce dépôt et lancez d'abord [votre première fonctionnalité](../../setup/first-feature/) sur l'application
de notes. Voir toute la boucle fonctionner une fois rend chaque étape ici bien plus facile à suivre.
</Aside>

## À décider d'abord

| Décision | Par défaut | À changer si |
| --- | --- | --- |
| Label déclencheur de l'implémentation | `openhands` | Vous utilisez déjà ce label |
| Préfixe de branche | `openhands/issue` | Rarement. Le worker révise exactement `openhands/issue-<n>`, et la glue répond à toute branche d'un seul segment sous `openhands/`. Si vous le changez, changez aussi `AGENT_BRANCH` et les conditions des workflows |
| Label de review | `openhands-review` | Comme ci-dessus |
| Intervalle d'interrogation | toutes les 5 minutes | Vous voulez réduire le coût et pouvez attendre plus longtemps (la valeur par défaut du catalogue est 15), ou un délai de réponse plus court (Discava interroge toutes les 2) |
| Nombre max de tentatives de correction | 5 par boucle | Rarement. C'est `MAX_*_FIX_ATTEMPTS` dans deux fichiers `plan.ts` |
| Numérotation des dossiers de spec | horodatage | Jamais, avec plus d'un auteur de specs |

Dans chaque commande et chaque fichier copié, remplacez `@your-scope` ou `@agentic-sdlc` par le scope npm
de votre workspace.
