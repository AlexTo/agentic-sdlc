**La version courte :** OpenHands exécute trois automatisations planifiées sur votre dépôt, une par
rôle d'agent. Le **Développeur** implémente les issues labellisées et révise les pull requests
marquées comme en échec. Le **Relecteur** relit les pull requests une fois leurs checks terminés. Le
**Testeur** teste chaque changement mergé sur le stage de développement déployé. Chacune démarre un
agent de code ordinaire avec un prompt fixe. Aucune n'a besoin que vous ouvriez un chat.

## Les trois rôles

| Rôle | Automatisation | Part de | Laisse derrière lui |
| --- | --- | --- | --- |
| **Développeur** | GitHub issue to PR | Une issue portant le label `openhands`, ou un statut `software-factory/review` en échec sur sa propre PR | Une pull request sur `openhands/issue-<n>`, et ses révisions |
| **Relecteur** | GitHub code review | Une PR portant le label `openhands-review`, une fois tous les checks terminés | Une revue qui se termine par `✅ APPROVED` ou `🔄 CHANGES REQUESTED` |
| **Testeur** | GitHub issue tester | Une issue portant le label `openhands-test`, ouverte après un déploiement | Un rapport de test sur l'issue, avec des preuves tirées de l'UI, des API et des données stockées, et parfois une petite PR de correction |

Le Développeur et le Relecteur suffisent à un dépôt pour faire tourner la boucle jusqu'au merge. Le
Testeur a besoin d'un endroit déployé à tester, donc il vient avec les
[déploiements automatiques](../../adopt/deploy/). L'application d'exemple de ce dépôt n'a pas de
déploiement, donc un fork fait tourner les deux premiers.

```d2
direction: right

machine: Votre machine {
  style.stroke-dash: 3
  canvas: Agent Canvas {
    i2p: issue vers PR
    review: revue de code
    test: testeur d'issues
  }
  dev: agent Développeur
  rev: agent Relecteur
  tester: agent Testeur
  canvas.i2p -> dev: implémente ou révise
  canvas.review -> rev: relit
  canvas.test -> tester: teste
}

github: GitHub {
  style.stroke-dash: 3
  issues: issues {shape: page}
  prs: pull requests {shape: page}
  statuses: statuts de commit {shape: document}
}

stage: stage de développement {shape: cylinder}

machine.canvas -> github: interroge toutes les 5 minutes
machine.dev -> github.prs: "push, ouverture"
machine.rev -> github.prs: revue
machine.tester -> stage: "clique, appelle, lit"
machine.tester -> github.issues: rapport
```

## Les éléments

| Élément | Ce que c'est |
| --- | --- |
| **Agent Canvas** | L'application OpenHands que vous faites tourner vous-même (`npx @openhands/agent-canvas`). Elle regroupe le serveur d'agent, le backend d'automatisation et une interface web |
| **Profil d'agent** | Quel agent s'exécute, et avec quel modèle. Un profil peut être l'agent propre d'OpenHands avec n'importe quel LLM, ou un agent de code externe via ACP (l'Agent Client Protocol) |
| **Automatisation** | Un petit worker Python qui s'exécute selon un planning cron. Il lit GitHub, décide quoi faire, et démarre ou reprend des conversations d'agent. Installée depuis le catalogue d'Agent Canvas |
| **Secret** | Un identifiant nommé, comme le token GitHub. Une conversation ne reçoit que les secrets de sa liste d'autorisation |

## Les trois automatisations

### Développeur : GitHub issue to PR

À chaque passage, pour chaque dépôt qu'il surveille, le worker :

1. Trouve les PR ouvertes sur des branches `openhands/issue-<n>` dont le commit de tête porte un
   statut de commit nommé `software-factory/review` à l'état `failure` ou `error`. Pour chacune, il
   envoie un tour de **révision** à la conversation de cette issue : lire les revues, les
   commentaires et les checks en échec, les corriger, et pousser sur la même branche.
2. Trouve les issues ouvertes avec le label déclencheur (`openhands`) qui n'ont pas encore de PR, et
   démarre un tour d'**implémentation** : cloner, créer `openhands/issue-<n>`, implémenter, tester,
   pousser, ouvrir la PR, et ajouter le label `openhands-review`.

Chaque issue est un *sujet* avec une conversation stable. Une révision va dans la même conversation
que l'implémentation d'origine, donc l'agent garde son contexte.

### Relecteur : GitHub code review

À chaque passage, il cherche les PR qui portent le label `openhands-review`, ont une demande de revue
en attente pour son compte, ou sont ouvertes, hors brouillon, sans demande de revue et non relues.
Pour chacune, il attend que **tous les checks du commit de tête soient terminés**, puis démarre une
revue de ce commit précis. La revue se termine par un verdict sur sa propre ligne : `✅ APPROVED` ou
`🔄 CHANGES REQUESTED`.

<Aside type="caution">
Le worker issue-to-PR ne révise une PR que lorsqu'il voit le statut `software-factory/review` en
échec. Ni une exécution de CI rouge ni le « changes requested » du Relecteur ne pose ce statut par
lui-même. Combler ce manque, ce sont deux pièces de la [glue manquante](../the-missing-glue/).
</Aside>

### Testeur : GitHub issue tester

Les deux premières automatisations viennent du catalogue d'Agent Canvas. Celle-ci est écrite à la
main, et elle est petite : un worker d'une centaine de lignes, construit sur les utilitaires GitHub
du catalogue, et un fichier de prompt.

À chaque passage, il cherche les issues ouvertes avec le label déclencheur (`openhands-test`) qui
ont été ouvertes par le compte propre du workflow, `github-actions[bot]`. Pour chacune, il démarre
un tour de **test** : cloner le dépôt au commit que le stage exécute, déterminer ce que la pull
request mergée a changé, le tester sur la stack déployée, et commenter le résultat sur l'issue.

Le test comporte trois parties, et la troisième est ce qui le distingue du simple parcours d'une
page :

1. **L'UI**, dans un vrai navigateur, connecté comme utilisateur de test.
2. **Les API** derrière ces écrans, appelées avec le token de l'utilisateur de test, y compris les
   cas qui devraient être refusés.
3. **Les données stockées.** Après chaque action, le Testeur lit ce que le changement aurait dû
   écrire et le vérifie : les enregistrements en base, les fichiers dans le stockage, l'index de
   recherche, et les logs. Dans Discava, il s'agit de DynamoDB, S3, OpenSearch et CloudWatch.

Trois détails le gardent sûr et discret :

- **L'issue dit seulement quoi tester.** La façon de le tester (les outils, les utilisateurs de
  test, les vérifications, le rapport) est le prompt propre de l'automatisation, sur la machine.
  Personne parmi ceux qui peuvent modifier une issue ne peut le changer.
- **Une issue ouverte par quelqu'un d'autre est sautée**, parce que son corps deviendrait les
  instructions de l'agent.
- **Un test par pose du label.** Chaque pose du label compte une fois, donc les propres
  commentaires du Testeur ne démarrent jamais un second test. Retirez et remettez le label pour
  tester à nouveau.

Rien n'ouvre ces issues par défaut. Un workflow qui en ouvre une pour chaque pull request déployée
est la dernière pièce de la [glue manquante](../the-missing-glue/). Celui de Discava se trouve sur
[Vérification après merge](../../discava/post-merge-verify/).

## Pourquoi l'interrogation périodique plutôt que des webhooks

Les automatisations interrogent GitHub périodiquement (toutes les 5 minutes dans Discava, toutes les
15 par défaut), donc Agent Canvas peut tourner sur un portable ou un serveur domestique sans URL
publique ni secret de webhook. Le coût est une latence d'au plus un intervalle d'interrogation, ce
qui est peu à côté du temps que l'agent met à travailler.

## Une mémoire qui survit à l'exécution

Une conversation garde son contexte pour une issue. Les agents gardent aussi une mémoire qui lui
survit. OpenHands la stocke sur la machine qui exécute Agent Canvas, et les trois rôles la lisent et
y écrivent. Ce qu'une exécution apprend, comme une bizarrerie du stack local, un check qui échoue
toujours pour la même raison ou une convention que le Relecteur réclame sans cesse, reste là pour
chaque exécution suivante, quels que soient le rôle, l'issue ou la personne qui l'a demandée.

C'est la différence avec un agent dans un éditeur, où ce qu'il apprend reste sur le poste d'un seul
développeur. Ici, la mémoire appartient au runtime, elle s'enrichit donc de chaque tâche que
l'équipe a confiée aux agents, pas seulement de celles qu'une personne a lancées.

<Aside type="caution">
Les agents écrivent directement dans la mémoire, et personne ne la relit. Une leçon fausse est
répétée jusqu'à ce que quelqu'un la retire, et un texte qu'un agent a lu dans une issue ou un
commentaire peut s'y retrouver, une raison de plus pour que seuls les collaborateurs puissent
commenter. Relisez la mémoire de temps en temps. Une leçon qui est en fait une règle a sa place dans
`AGENTS.md` ou, mieux, dans un check qui l'applique. La mémoire vit sur une seule machine :
sauvegardez-la avec le reste de l'état d'Agent Canvas.
</Aside>

## Ce à quoi l'agent a accès, et ce à quoi il n'a pas accès

Les prompts du Développeur et du Relecteur nomment un seul secret, le token GitHub, pour que le
Développeur puisse lire l'issue et pousser sa branche et que le Relecteur puisse publier sa revue.
Aucun des deux n'a besoin d'un accès au cloud : tout ce qu'ils exécutent s'exécute sur la stack
locale.

Le Testeur est l'exception. Il doit atteindre le stage déployé, donc il travaille avec un CLI cloud
connecté au compte de développement, que son prompt lui dit d'utiliser en lecture seule, et un
utilisateur de test pour chaque rôle de l'application. Il ne reçoit jamais les rôles de déploiement,
et son prompt lui interdit de modifier l'infrastructure, de déployer, ou de toucher à un autre
stage. Comme il lit des issues et des pull requests tout en détenant ces identifiants, personne sans
accès en écriture ne peut les commenter. Sur un dépôt public, cela veut dire régler la limite
d'interaction de GitHub sur les collaborateurs uniquement.

Ce que les agents ne doivent par ailleurs jamais faire, et ce qui fait respecter chaque limite, se
trouve sur [Contrôles humains](../human-gates/#ce-que-les-agents-ne-doivent-jamais-faire).

## Choisir les agents

Discava exécute les trois sur **Claude Code via ACP**, chacun avec son propre profil d'agent :
Sonnet pour le Développeur, Opus pour le Relecteur et le Testeur. Un modèle plus puissant pour la
revue est un choix délibéré : le Relecteur est la dernière vérification avant une personne, et il lit
beaucoup moins de code que le Développeur n'en écrit. Le Testeur reçoit le même modèle parce que son
travail est aussi affaire de jugement : décider ce qu'un changement devrait faire, et si ce qu'il
voit sur le stage, et trouve dans son stockage, est correct. N'importe quel agent ACP, ou l'agent propre d'OpenHands avec
n'importe quel LLM, se branche sur les mêmes profils.

Le prompt avec lequel chaque rôle s'exécute se trouve sur
[Les prompts des agents](../../discava/agent-prompts/).
