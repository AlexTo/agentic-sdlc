Cette page suit une fonctionnalité dans le vrai dépôt Discava : **les notes et les avis écrits sur les
cours**. Chaque chiffre et chaque lien viennent de GitHub. Les heures sont en UTC, le 18 novembre 2026
sauf mention contraire.

## L'idée

[Issue #279](https://github.com/AlexTo/discava/issues/279), écrite par une personne :

> Enrolled students leave one 1-5 rating plus an optional text review per course (editable,
> deletable). The course carries an aggregate rating and count, kept consistent through a
> core-table helper. Shown on catalogue cards, the course page and as a search sort/boost. The
> instructor can respond; an admin can remove abusive reviews. One review per student per course
> under concurrency; an average/count invariant in `helpers/invariants.ts`.

## La spec

[PR #358](https://github.com/AlexTo/discava/pull/358), `docs(specs): course ratings and written
reviews`, sur la branche `spec/reviews` : 14 commits, 923 lignes, toutes sous
`specs/20261116-013307-course-reviews/`.

- `/speckit-clarify` s'est exécuté sans personne à qui poser les questions, donc l'agent a consigné
  ses réponses sous « Clarifications ». Par exemple : *"Must a student have made progress before they may review? → No.
  Any student whose enrolment is not dropped may review."* Le relecteur de la PR de spec pouvait
  contester n'importe laquelle d'entre elles avant que le code n'existe.
- `tasks.md` en est ressorti avec **huit phases et 36 tâches**. La phase 1 est la première user story
  (les enregistrements, le résumé et l'écrivain partagé), et les phases 2 à 8 indiquent chacune quelle
  PR elles sont (« core-api review procedures (PR 2) »). Deux tâches sont **(human)** : un parcours
  manuel sur une stack locale, et des vérifications sur le stage déployé.

Ouverte le 15 novembre, labellisée `spec-ready`, mergée le 18 novembre à 06:47.

## Ce qu'a fait la personne

1. Elle a écrit l'issue de suivi d'un paragraphe.
2. Elle a relu et mergé la PR de spec.
3. Pour chacune des huit PR : elle a lu la description et le commentaire des captures d'écran, et
   mergé.

Personne n'a ouvert d'issue, écrit de prompt ni collé d'erreur.

## Ce que les boucles ont rattrapé

- **PR #464** : l'agent relecteur a demandé des changements. Agent Review Status a renvoyé l'agent au
  travail une fois, et la PR a été mergée après la revue suivante.
- **PR #470** : un nouveau scénario e2e utilisait un localisateur qui correspondait à deux éléments,
  donc un shard a échoué. Agent CI Status a renvoyé l'agent au travail une fois. L'agent a corrigé le
  localisateur et a expliqué pourquoi dans un commentaire. Voir [Boucles de retour](../feedback-loops/)
  pour la chronologie complète.
- **PR #476** : un échec de CI, corrigé à la première tentative.
- **PR #497** : un tour de changements demandés en revue.
- **PR #504** : un échec de CI, corrigé à la première tentative.

<Aside type="note">
Le titre de chaque PR commence par `[#<issue>]`, le format propre à l'automatisation issue-to-PR, même
si l'issue demande un titre Conventional Commit simple. Cela montre les deux couches à l'œuvre :
l'instruction dans l'issue est du texte, et le format de l'automatisation est du code. Le code
l'emporte, donc si le titre vous importe, faites-le respecter avec un check.
</Aside>

## Ce qui reste pour une personne

Les deux tâches **(human)** de la phase 8 : un parcours manuel sur une stack locale, et des
vérifications sur le stage déployé. La dernière PR a été mergée alors que les deux n'étaient toujours
pas cochées dans `tasks.md`, donc l'automatisation ne les a pas attendues, et rien d'autre non plus.
Ce qui en garde la trace, c'est le workflow
[Archive Specs](../spec-to-issue/#archiver-une-spec-terminée) : le dossier de spec reste actif
jusqu'à ce qu'une personne coche les deux.
