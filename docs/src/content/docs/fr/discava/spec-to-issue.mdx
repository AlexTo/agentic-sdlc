Manques 1 et 7 : rien ne transforme une spec terminée en travail pour l'agent, et merger la PR de
l'agent ne lance pas la phase suivante. Discava comble les deux avec un seul workflow, **Agent
Issues**, et le script qui se trouve derrière.

## Quand il s'exécute

`.github/workflows/agent-issues.yml` écoute les pull requests vers `main` qui sont `closed` ou
`labeled`, plus un `workflow_dispatch` manuel avec une entrée `spec_folder`. Le job ne s'exécute que
dans ces cas :

| Événement | Condition | Signification |
| --- | --- | --- |
| PR fermée | mergée, et avec le label `spec-ready` | Une spec a été approuvée : ouvrir la première issue |
| PR fermée | mergée, et la branche commence par `openhands/` | Une PR d'agent est arrivée : ouvrir l'issue suivante |
| PR labellisée | déjà mergée, et le label est `spec-ready` | Quelqu'un a oublié le label avant le merge |
| Exécution manuelle | un nom de dossier de spec | Relancer une chaîne à la main |

Toute autre PR mergée est ignorée, [même une qui touche à `specs/`](../../concepts/one-phase-at-a-time/#ce-qui-ouvre-lissue-suivante).

Le job récupère le **commit de merge**, donc il voit les cases que la PR vient de cocher. Son groupe
de concurrence est propre à chaque PR, jamais global : un groupe global ne garde que la plus récente
des exécutions en attente, donc deux merges rapprochés s'annuleraient mutuellement.

## Ce que fait le script

```d2
direction: right

merged: PR mergée {shape: page}
gate: "branche d'agent,\nou spec-ready ?" {shape: diamond}
ignore: ignorer
folder: trouver le dossier de spec
valid: "tasks.md valide ?" {shape: diamond}
fail: faire échouer l'exécution
next: "groupe suivant avec\ndes tâches d'agent restantes ?" {shape: diamond}
done: terminé
exists: "une issue existe\ndéjà pour lui ?" {shape: diamond}
stalled: commenter sur la PR
open: ouvrir l'issue {shape: page}

merged -> gate
gate -> ignore: non
gate -> folder: oui
folder -> valid
valid -> fail: non
valid -> next: oui
next -> done: non
next -> exists: oui
exists -> stalled: oui
exists -> open: non
```

`pnpm nx run @discava/tooling-agent:agent-issue`, dans `src/agent-issues/` :

1. **Filtrer** (`gate.ts`). `decide()` classe la PR comme `spec`, `implementation` ou `ignore`.
2. **Trouver le dossier de spec** (`discover.ts`). Pour une PR d'agent, il lit l'issue que la PR
   ferme et prend le dossier dans le marqueur caché de cette issue. Sinon, il utilise les chemins
   `specs/<folder>/` que la PR a modifiés.
3. **Valider** (`validate.ts`). Un `tasks.md` qui échoue à la vérification du format fait échouer
   l'exécution, plutôt que de donner à l'agent les mauvaises tâches.
4. **Grouper les phases** (`tasks.ts`) : tout jusqu'à la première phase `User Story` incluse, puis
   chaque phase suivante seule.
5. **Choisir le groupe suivant** : le premier qui a une tâche non cochée qui n'est pas **(human)**.
6. **Chercher une issue existante.** Chaque corps d'issue commence par un marqueur comme
   `<!-- agent-issue spec:20261116-013307-course-reviews group:3 -->`. Si une issue existe déjà pour
   ce groupe (ouverte ou fermée), le script n'en ouvre pas d'autre. Un marqueur ne compte que dans
   une issue ouverte par le workflow ou par quelqu'un avec un accès en écriture, donc l'issue d'un
   inconnu ne peut pas bloquer la chaîne d'une spec. Il commente plutôt sur la PR, par exemple :

   > The next implementation issue for `specs/…/` was not opened: an issue for "Ratings in search"
   > already exists, and these tasks in its `tasks.md` are not ticked: T017, T018.

7. **Générer et créer l'issue** (`issue.ts`), sans label.
8. **La verrouiller, puis la labelliser** (`helpers/conversation-lock.ts`). L'issue est verrouillée,
   pour que seules les personnes avec un accès en écriture puissent commenter ce que lira l'agent
   Développeur, et ne reçoit le label `openhands` qu'ensuite. Si le verrouillage échoue, le label
   n'est jamais ajouté et l'exécution échoue, en nommant l'issue à verrouiller et à labelliser à la
   main.

## L'issue qu'il ouvre

Une vraie, [#466](https://github.com/AlexTo/discava/issues/466) :

```markdown
<!-- agent-issue spec:20261116-013307-course-reviews group:3 -->

## Spec

- Spec folder: `specs/20261116-013307-course-reviews/` (read `spec.md`, `plan.md`, `tasks.md`,
  `data-model.md` and `contracts/`)
- Parent issue: #279

## Scope

Tasks `T015` to `T019` of `tasks.md`: every task under Phase 4: Ratings in search (PR 4). Do not
start tasks outside these phases.

## Instructions for the agent

- Read `AGENTS.md`, `.specify/memory/constitution.md` and the spec folder first.
- …the rest of the template's bullets, with `#<parent>` filled in as `#279`
```

Le titre est un en-tête Conventional Commit construit à partir du dossier et de la phase :
`feat(course-reviews): ratings in search (PR 4)`. Il a un sujet en minuscules et au plus 100
caractères, pour que l'agent puisse le réutiliser pour sa PR sans faire échouer commitlint. Le premier
groupe ajoute ` (with setup and foundations)`.

<Aside type="note">
Les instructions permanentes sont lues depuis le template d'issue au moment de l'exécution, donc il
n'y a qu'un seul endroit où les modifier. Modifier `.github/ISSUE_TEMPLATE/implement-phase.md` change
toutes les issues futures.
</Aside>

## Exécution à blanc

```bash
DRY_RUN=true GITHUB_REPOSITORY=owner/repo GITHUB_EVENT_NAME=workflow_dispatch \
  SPEC_FOLDER=20261116-013307-course-reviews \
  pnpm nx run @discava/tooling-agent:agent-issue
```

Cela affiche le titre et le corps de l'issue qu'il ouvrirait. Il lit quand même les issues existantes
via `gh`, donc vous devez être connecté.

## Archiver une spec terminée

Un second workflow, **Archive Specs** (`.github/workflows/archive-specs.yml`), clôt la chaîne. Il
s'exécute lors d'un push sur `main` qui modifie un `specs/*/tasks.md` actif, et à la main. Il a besoin
de son propre déclencheur parce que la dernière case cochée est en général une tâche **(human)**, dans
une PR qu'Agent Issues ignore.

`pnpm nx run @discava/tooling-agent:archive-specs`, dans `src/agent-issues/archive-specs.ts` :

1. Trouve chaque spec active dont toutes les tâches sont cochées, y compris les tâches **(human)**.
2. Saute une spec qui a une issue d'agent ouverte, et une qui a déjà eu une PR d'archivage. Fermer
   cette PR sans la merger garde la spec active.
3. Pousse la branche `archive-spec/<folder>`, qui déplace le dossier vers `specs/_archive/` et
   réécrit les liens vers lui et depuis lui, et ouvre sa PR.

Agent Issues ignore `specs/_archive/`, donc une PR d'archivage n'ouvre jamais d'issue. Le check
`Tasks format` lit aussi les fichiers `tasks.md` archivés, et échoue si l'un d'eux a une tâche non
cochée.

<Aside type="caution">
Discava garde désactivé le paramètre de dépôt « Allow GitHub Actions to create and approve pull
requests », car il permettrait aussi à un workflow d'approuver une PR. Le token du workflow peut donc
pousser la branche mais pas ouvrir la PR. L'exécution affiche un avertissement avec un lien qui
l'ouvre, titre et description pré-remplis, et un mainteneur la soumet. Une PR ouverte par une
personne déclenche PR Checks, ce que ne ferait pas une PR ouverte avec le token du workflow. Tant que
personne ne l'a soumise, chaque exécution pousse à nouveau la branche et répète l'avertissement.
</Aside>
