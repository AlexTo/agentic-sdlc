[Comment ça marche](../how-it-works/) décrit la boucle. Cette page la montre en train de tourner une
fois, sur une vraie pull request de [Discava](https://github.com/AlexTo/discava) : ce que voit un
étudiant après avoir demandé le remboursement d'un cours qu'il a acheté.

Chaque citation, chaque chiffre et chaque lien viennent de GitHub. Les heures sont à l'heure de
Sydney (AEDT, UTC+11), les 25 et 26 novembre 2026.

De l'ouverture de la pull request à son merge : quatre tours de correction, trois venant de la CI et
un de la revue, et une action d'une personne. Ensuite, le Testeur a trouvé deux problèmes qu'aucun
d'eux n'aurait pu voir.

## 1. L'issue

Un étudiant qui demande un remboursement voit « Refund requested » pendant que Stripe le traite, et
la page du cours vérifie toutes les 2 secondes s'il est passé. [#1166](https://github.com/AlexTo/discava/issues/1166)
dit ce qui n'allait pas :

> While a student's refund is pending, the course page refetches `course.myEnrolment` and
> `payment.myOrder` every 2 s, and never stops. If the refund fails at Stripe or its event never
> arrives, the order stays `paid` with a refund requested, the page keeps polling for as long as
> it is open, and the student isn't told anything has gone wrong.

Ses critères d'acceptation tiennent en deux lignes : l'interrogation s'arrête après une limite, et un
remboursement échoué, simulé dans le substitut de Stripe, met fin à l'état en attente avec un message
clair.

Cette issue ne venait pas d'une spec. L'agent Relecteur l'a soulevée en relisant la PR qui permettait
à un étudiant de demander un remboursement, comme un problème hors du périmètre de cette PR, et elle
est devenue une issue à part entière. (#1166 est une copie : GitHub a signalé l'ancien compte machine
des agents, ce qui a masqué tout ce qu'il avait ouvert, et les issues ouvertes ont été
[rouvertes](../../discava/openhands-setup/#la-github-app) par la GitHub App qu'utilisent maintenant
les agents.)

## 2. L'agent Développeur ouvre la PR

L'agent Développeur a pris l'issue et ouvert [#1195](https://github.com/AlexTo/discava/pull/1195)
sur `openhands/issue-1166`. Le changement traverse quatre packages : une limite de 2 minutes et un
bouton « Check again » sur la page du cours, un handler de webhook pour les événements de
remboursement échoué de Stripe, un champ `refundFailedAt` sur la commande avec un invariant qui veut
qu'un échec suive une demande, et « Your refund failed » sur la page du cours. La description se
terminait par ce qu'il avait exécuté et ce qu'il n'avait pas exécuté :

> Unit tests cover the helper, the webhook, the invariant and the UI (poll limit, check again,
> failure message). [...] I did not run the e2e tests or try the stand-in control in a browser.

## 3. La CI la renvoie, trois fois

**`ci-fix-1` : pas de captures d'écran, et des lignes sans tests.** La PR changeait ce que voit un
étudiant mais ne prenait aucune capture, donc [**UI Screenshots** a échoué](https://github.com/AlexTo/discava/actions/runs/45619342535/job/139224403383).
**codecov/patch** a échoué aussi : de nouvelles lignes n'avaient pas de test. **Agent CI Status** a
ajouté `ci-fix-1` et renvoyé l'agent Développeur. Sa [réponse](https://github.com/AlexTo/discava/pull/1195#issuecomment-7164484931)
montre qu'en chemin il a trouvé un problème dans sa propre première tentative :

> **UI Screenshots:** added a `learner-refund` e2e scenario for a failed refund, with
> `screenshot(student, 'refund-failed')`. For this the Stripe stand-in has a new
> `fail-next-refund` control. [...] This replaces the `refund-fail` control from the first push,
> which the scenario could not use, because the stand-in completed the refund before it could
> fail.

**`ci-fix-2` : un échec qui n'était pas le sien.** L'exécution suivante a échoué dans **Checks
(build)**, sur un test CDK synth du package d'infrastructure. L'agent a lu le log et
[n'a changé aucun code pour ça](https://github.com/AlexTo/discava/pull/1195#issuecomment-7165688653) :

> the one failure was `@discava/infra` `instructor-api-stack.test.ts` [...], which hit its 30s
> timeout while the sibling CDK synth tests in that file took 22–31s. This PR doesn't touch infra
> or anything the stack synthesises [...], so I made no code change for it. The push below
> re-runs the build.

Il a couvert la seule ligne partielle que codecov signalait encore, et le push a relancé le build,
qui est passé. Un agent qui « corrige » un échec en changeant du code qu'il ne comprend pas est pire
qu'un agent qui dit que l'échec n'est pas le sien, et pourquoi.

**`ci-fix-3` : son propre nouveau test était faux.** Après la revue (section suivante), l'agent a
ajouté un scénario e2e pour la limite de 2 minutes, et il a échoué dans [**E2E tests (11/12)**](https://github.com/AlexTo/discava/actions/runs/45685812586/job/139458011986).
Cinq minutes plus tard, [la cause](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172674824) :

> the new `a pending refund stops polling and offers to check again` scenario failed with a
> Playwright strict-mode violation, not a product bug. `getByText('Still being processed')` also
> matched the alert's description ("Your refund is still being processed…"), so it resolved to two
> elements. The page did reach the timed-out state. I now match the title with `{ exact: true }`.

L'agent n'avait exécuté aucun scénario e2e en local, et il l'a dit à chaque fois. C'est dans la CI de
PR qu'ils tournent pour la première fois, et le [commentaire E2E screenshots](https://github.com/AlexTo/discava/pull/1195#issuecomment-7163204279)
liste les deux écrans que l'exécution a capturés : `learner-refund/01-refund-failed.png` et
`learner-refund/01-refund-still-being-processed.png`.

## 4. L'agent Relecteur trouve ce que la CI ne pouvait pas voir

Une fois tous les checks du commit de tête terminés, l'agent Relecteur a lu le diff en le comparant à
l'issue. Il a jugé le code de paiement correct, a relancé lui-même 361 tests ciblés, et a quand même
[bloqué le merge](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6063632214) :

> 1. **The branch carries another open PR's change.** Commit `e7cb9bc9`, "fix(student-portal):
>    surface completions and progress load errors on start route", is the change from open PR
>    #1188, not part of #1166. [...] Merging this PR would ship #1188's start-route error behaviour
>    under a payments title, before #1188 is reviewed.
> 2. **Live evidence is missing for the "Still being processed" / "Check again" state.** [...] The
>    new timed-out state [...] has only unit tests, and no capture from the running app.
>
> 🔄 CHANGES REQUESTED

Le premier point est le genre de chose qui passe tous les checks. Le commit en trop compilait et ses
tests passaient ; il n'avait simplement rien à faire là. Le checkout de l'agent était parti d'une
branche qui le contenait déjà. Le second point, c'est encore la règle des captures d'écran,
appliquée par un lecteur : la CI vérifie qu'une PR ajoute une capture, et le Relecteur vérifie que
chaque nouvel état a la sienne.

**Agent Review Status** a ajouté `review-fix-1`. Huit minutes plus tard, l'agent Développeur
[avait](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172386579) rebasé ses quatre
propres commits sur `main` sans les deux autres, et ajouté un contrôle dans le substitut qui maintient
un remboursement en attente, ainsi qu'un scénario e2e qui installe la fausse horloge de Playwright et
avance de 125 secondes. C'est ce scénario que `ci-fix-3` a ensuite corrigé.

Sur le commit de tête final, le Relecteur a [confirmé](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066801083)
que les deux points étaient résolus, que les 12 shards e2e étaient passés, et a nommé les deux
captures : « No material findings [...] ✅ APPROVED ».

## 5. Une personne approuve

À 11:33, le mainteneur a [approuvé](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066944326)
et mergé. C'est la seule chose qu'une personne a faite sur cette PR. Ce qu'il avait sous les yeux :
une description qui disait ce qui avait été exécuté et ce qui ne l'avait pas été, les deux captures
d'écran de la CI, une liste de checks verte, et une trace de quatre révisions, chacune avec sa raison.

## 6. Le merge est déployé, et une issue de test s'ouvre

Sur Discava, `main` se déploie de lui-même sur un stage de développement. Le [déploiement](https://github.com/AlexTo/discava/actions/runs/45734764281)
qui portait ce merge s'est terminé à 12:28, et une minute plus tard **Post-merge Verify** a ouvert
[#1240](https://github.com/AlexTo/discava/issues/1240). Elle liste les 12 fichiers déployés que la PR
a changés et dit quel type de test faire :

> Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
> through the flow with Playwright, then call the APIs behind it and check the stored data.

## 7. L'agent Testeur teste le stage déployé

L'agent Testeur ne relance pas la suite de tests, et n'utilise pas le substitut de Stripe. Il utilise
le produit déployé comme le ferait une personne, avec le vrai Stripe en mode sandbox. Son
[rapport](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815) liste chaque étape :

1. En tant que formateur de test, via l'API, il a créé deux cours à $19.99.
2. En tant qu'étudiant de test, dans un vrai navigateur, il s'est connecté et a acheté chacun d'eux
   sur Stripe Checkout, avec les cartes de test de Stripe pour « le remboursement échoue » et « le
   remboursement reste en attente ».
3. Il a demandé un remboursement pour chacun depuis la page du cours.
4. Après chaque étape, il a appelé les API, lu les commandes et les inscriptions dans DynamoDB, et lu
   les logs des Lambda du webhook et de l'API.

Ce n'est pas la bonne fin. Le remboursement de cette carte échoue, mais Stripe le signale d'abord
comme réussi, donc la commande a été marquée `refunded` et l'inscription a pris fin en trois secondes environ. L'échec est
arrivé plus tard, et rien n'est arrivé pour lui. Le Testeur a cherché pourquoi, et a trouvé deux
causes distinctes (section suivante).

Sur ce stage, le vrai Stripe ne pouvait ni maintenir un remboursement en attente ni en enregistrer un
échoué. Donc, pour vérifier les nouveaux écrans dans le bundle déployé, le Testeur a réécrit la
réponse de `payment.myOrder` dans le navigateur, puis a vérifié séparément les vraies réponses de
l'API et les données stockées. Il a chronométré la limite : « Still being processed » est apparu
**120.2 s** après l'affichage du remboursement en attente, et aucune requête n'a suivi dans les 20
secondes suivantes (`13-still-being-processed-after-2-minutes.png`) :

| Vérification | Résultat |
| --- | --- |
| L'interrogation s'arrête après 2 minutes | 120.2 s, puis 0 requête dans les 20 s suivantes |
| « Check again » relance l'interrogation | 4 requêtes dans les 8 s suivantes, et l'encart disparaît |
| `payment.myOrder` sans jeton | Refusé : 401 |
| `payment.myOrder` en tant qu'utilisateur qui n'a pas acheté | 200 avec `null` : aucune commande d'autrui |
| `payment.requestRefund` sur une commande déjà remboursée | Refusé : 412, « No purchase to refund » |

## 8. Le Testeur laisse l'issue ouverte

Trois vérifications ont échoué, et deux se sont terminées dans un état que la PR n'attendait pas. Le
[verdict](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815) :

> **Verdict: the student-facing UI and `payment.myOrder` work as the PR describes. The
> failed-refund path does not work end to end on the deployed stage.**

Il a trouvé deux causes, toutes deux hors de portée des tests de la PR :

1. **Le webhook Stripe du stage ne reçoit jamais les nouveaux événements.** La PR a ajouté
   `refund.failed` et `charge.refund.updated` à la liste des événements, mais cette liste n'est
   envoyée à Stripe que lorsqu'un administrateur le connecte pour la première fois. Le stage avait été
   connecté six jours plus tôt. Le Testeur a compté exactement quatre invocations du webhook dans la
   demi-heure, aucune pour un échec.
2. **Avec le vrai Stripe, un remboursement échoué arrive alors que la commande est déjà `refunded`.**
   Stripe envoie `charge.refunded` dès qu'un remboursement est créé, même s'il est en attente ou va
   échouer. Quand `refund.failed` arrive, la condition du nouveau handler (la commande est toujours
   `paid`) n'est plus remplie, et il ne fait rien, sans rien signaler :

   > The student has lost access, hasn't been refunded, and isn't told.

   Le substitut du scénario e2e de la PR ne règle jamais un remboursement avant de le faire échouer,
   donc la CI a montré la version heureuse de tout ça.

Le Testeur peut ouvrir une PR de correction quand la correction est petite et claire. Il a expliqué
pourquoi il ne l'a pas fait :

> Fixing it means deciding how a refund failure after `charge.refunded` should restore the order
> and enrolment, or not treating a `pending` refund as refunded. That goes beyond a small fix, so
> I'm reporting it rather than opening a PR.

Il n'a pas non plus touché à la connexion Stripe du stage, même si l'enregistrer de nouveau
corrigerait la première cause : « I didn't do that, because it changes stage configuration. » L'issue
reste donc ouverte, avec les deux problèmes décrits, comment les reproduire, et les choix qu'une
personne doit faire. Il a listé les données de test qu'il a laissées sur le stage, et une erreur qu'il
a vue et qui était déjà suivie ailleurs, pour que personne ne la prenne pour une régression.

<Aside type="tip">
[Vérification après merge](../../discava/post-merge-verify/) suit une autre issue de test, où le
Testeur a trouvé un échec, est remonté jusqu'à sa cause et a bel et bien ouvert la PR de correction.
</Aside>

## Ce que chaque contrôle a rattrapé

| Contrôle | Ce qu'il a rattrapé | Pourquoi le contrôle précédent ne l'a pas vu |
| --- | --- | --- |
| CI | Un changement d'UI sans capture d'écran, des lignes sans tests et un locator cassé dans le propre test e2e de l'agent | L'agent Développeur n'avait pas exécuté la suite e2e |
| Agent Relecteur | Le commit d'une autre PR embarqué sur la branche, et un nouvel état d'écran sans capture | Le commit en trop passait tous les checks, et la CI vérifie seulement qu'une capture a été ajoutée |
| Agent Testeur | Un endpoint de webhook qui ne reçoit jamais les nouveaux événements, et le vrai Stripe qui signale d'abord comme remboursé un remboursement qui échoue | Le substitut se comporte comme le code s'y attend, et aucun test ne voit la configuration du stage |

Aucun des trois n'est malin à lui seul. Chacun regarde quelque chose que les autres ne peuvent pas
voir : la CI les règles, le Relecteur l'issue et la branche, le Testeur le produit qui tourne et les
vrais services derrière lui.

## Ce qu'a fait la personne

1. Elle a lu la PR #1195 et ses captures d'écran, l'a approuvée et mergée.
2. Ensuite : décider ce que doit faire un échec de remboursement après `charge.refunded`, parmi les
   options que le Testeur a écrites.

Personne n'a écrit de prompt, collé de log d'erreur ni parcouru le stage à la main.
