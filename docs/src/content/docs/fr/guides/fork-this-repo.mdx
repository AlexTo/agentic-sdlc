Ce dépôt *est* le workflow : la même configuration Speckit, le même template d'issue, les mêmes
checks de PR, les mêmes workflows d'agent et la même glue testée unitairement que Discava utilise,
autour d'une petite application de notes.

**Forkez-le, et vous avez la configuration de Discava.** Pointez votre propre OpenHands sur le fork,
écrivez une spec pour l'application de notes, et elle passe par la boucle décrite dans
[Comment ça marche](../how-it-works/).

## Ce que vous obtenez

<FileTree>
- AGENTS.md ce que chaque agent lit en premier, écrit pour l'application de notes
- .specify/ templates et scripts Speckit, et la constitution
- .husky/ Conventional Commits, scan de secrets et Biome au commit, carte des invariants au push
- scripts/
  - setup-repository.sh labels, protection de branche et les autres paramètres qu'un fork ne copie pas
  - start-agent-canvas.mjs démarre Agent Canvas sous la GitHub App des agents et garde son token à jour
- .github/
  - ISSUE_TEMPLATE/
    - implement-phase.md les instructions que porte chaque issue d'implémentation
    - test-deployed-pr.md une issue de test pour l'agent Testeur, à la main
  - actions/ configuration CI partagée, le Chromium de Playwright, vérifications des chemins modifiés
  - dependabot.yml garde à jour les actions épinglées et les dépendances
  - workflows/
    - pr-checks.yml lint, tests, build, format des tâches, couverture des invariants, e2e, commentaire des captures d'écran
    - ui-screenshots.yml la règle des captures d'écran
    - ci.yml checks, Trivy et le déploiement de la doc sur main
    - agent-issues.yml spec → issue, merge → issue suivante
    - archive-specs.yml spec terminée → PR d'archivage
    - agent-ci.yml CI rouge → agent
    - agent-review.yml « changes requested » → agent
    - agent-status.yml les étapes que ces deux-là partagent
    - deploy.yml main au vert → un stage, désactivé tant que vous n'ajoutez pas d'infrastructure
    - post-merge-verify.yml PR déployée → issue de test pour le Testeur
    - cache-cleanup.yml les caches d'une PR fermée
- packages/
  - tooling/agent/ les règles de la glue, avec 223 tests unitaires
  - tooling/local-dev/ démarre DynamoDB local pour `pnpm dev`
  - notes-table/ entité ElectroDB, DynamoDB local, invariants
  - notes-api/ procédures tRPC
  - notes-website/ React, Vite, TanStack Router, shadcn/ui
  - e2e/ scénarios Playwright, l'utilitaire `screenshot()`, invariants après chaque test
- docs/ ce site
</FileTree>

L'application de notes tourne entièrement en local (`pnpm dev`, avec Docker pour DynamoDB local),
donc la CI peut exécuter ses tests e2e et l'agent n'a jamais besoin d'identifiants cloud.

## Ce que vous ajoutez

Seulement ce qui ne peut pas vivre dans un dépôt :

1. **Les paramètres GitHub** : la GitHub App sous laquelle agissent les agents, et les paramètres qu'un
   fork ne copie pas, que `scripts/setup-repository.sh` règle en une seule exécution.
2. **OpenHands** : Agent Canvas sur votre machine, démarré sous l'app avec `pnpm agent-canvas`, et
   les automatisations pointées sur votre fork.

## Ce qui reste désactivé tant que vous ne l'ajoutez pas

Le cloud. L'application de notes n'a pas d'infrastructure cloud, donc un merge ne livre rien d'autre que le
site de documentation. `deploy.yml` et `post-merge-verify.yml` sont en place mais ne s'exécutent jamais d'eux-mêmes : ajoutez
une application CDK dans `packages/infra` et définissez `AUTO_DEPLOY_STAGE`, et chaque `main` au vert est déployé, puis
l'agent Testeur teste ce qui a été déployé. [Adopter : déploiement](../../adopt/deploy/) donne les étapes, et
[Déploiement et sécurité](../../discava/deploy-and-security/) décrit le pipeline de Discava.
