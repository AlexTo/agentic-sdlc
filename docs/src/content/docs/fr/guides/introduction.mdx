Ce guide vous montre comment faire tourner un cycle de vie logiciel dans lequel **les agents écrivent
le code et les personnes prennent deux décisions** : approuver la spec, et approuver le résultat.
Tout ce qui se passe entre les deux (ouvrir des issues, écrire le code et les tests, réagir à la CI,
répondre à une revue) tourne tout seul, à travers le processus GitHub habituel. Trois rôles d'agent
font ce travail : un **Développeur**, un **Relecteur** et un **Testeur**.

Le workflow tourne tous les jours sur [Discava](https://github.com/AlexTo/discava), un système de
gestion de l'apprentissage serverless sur AWS. Dans les sept jours qui ont suivi sa mise en service le
14 novembre 2026, vingt-quatre specs de fonctionnalités ont été écrites de cette façon et 139 pull requests
d'agents ont été mergées pour les implémenter, chacune écrite, corrigée et relue par des agents. Sur
la même période, 222 commits sont arrivés sur main. Tout cela avec un seul mainteneur, un papa avec
un emploi à temps plein qui travaille sur Discava de temps en temps, sur son temps libre. 😅

## La version courte

Trois outils du marché font l'essentiel du travail :

| Outil | Ce qu'il fait ici |
| --- | --- |
| [Speckit](https://github.com/github/spec-kit) | Transforme une idée en `spec.md`, `plan.md` et `tasks.md`, vérifiés par rapport à une constitution du projet |
| [OpenHands](https://github.com/OpenHands/OpenHands) | Exécute les trois rôles d'agent, une automatisation chacun. Le Développeur transforme une issue labellisée en pull request, et la révise quand on lui signale un problème. Le Relecteur la relit. Le Testeur teste le changement mergé sur un stage déployé |
| GitHub Actions | Exécute les checks, et contient la glue entre les deux autres |

Aucun d'eux ne connaît les autres. **Ce guide parle surtout de la glue** : onze petites pièces
d'automatisation testées qui relient une spec terminée au Développeur, la CI et le Relecteur au
Développeur, et un déploiement au Testeur, avec des limites pour que rien ne boucle indéfiniment.

## À qui il s'adresse

- **Les tech leads et staff engineers** qui décident d'adopter ou non le workflow. Commencez par
  [Concepts](../../concepts/principles/).
- **Toute personne qui veut l'essayer.** [Forkez ce dépôt](../fork-this-repo/), puis suivez
  [Le mettre en place](../../setup/before-you-start/) pour faire passer une fonctionnalité par toute la boucle.
- **L'ingénieur qui l'apporte dans un dépôt produit.** Lisez
  [Comment Discava procède](../../discava/overview/), puis
  [L'adopter dans votre propre dépôt](../../adopt/overview/).
- **Les développeurs qui l'utiliseront au quotidien.** Le [tutoriel](../../tutorial/the-case/) suit
  une fonctionnalité de l'idée au merge.

Vous devez être à l'aise avec Git, les pull requests GitHub et GitHub Actions. Aucune expérience
préalable de Speckit ou d'OpenHands n'est nécessaire.

## Conventions

- `AGENTS.md` désigne le fichier de guidage des agents à la racine du dépôt. Nommez-le comme
  le lit votre agent de code.
- `<you>/agentic-sdlc` est votre fork, et `owner/repo` n'importe quel dépôt.
- `@your-scope` est le scope npm de votre workspace. Ce dépôt utilise `@agentic-sdlc`, et Discava
  utilise `@discava`.
- Les commandes s'exécutent depuis la racine du dépôt, sauf indication contraire dans une étape.
- **(human)** marque une tâche qu'un agent ne doit pas faire. C'est aussi le marqueur littéral
  utilisé dans `tasks.md`.
