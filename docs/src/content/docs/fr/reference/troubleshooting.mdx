## La chaîne ne démarre pas ou ne continue pas

| Symptôme | Ce qui se passe | Quoi faire |
| --- | --- | --- |
| PR de spec mergée, pas d'issue | La PR n'avait pas le label `spec-ready` au moment du merge | Ajoutez `spec-ready` à la PR mergée. Agent Issues s'exécute aussi sur `labeled` |
| Agent Issues a tourné : `No issue created: it is not an agent branch and has no "spec-ready" label` | Idem, ou la PR était une PR humaine, ignorée par conception | Comme ci-dessus, ou lancez Agent Issues à la main avec le dossier de spec |
| Agent Issues a échoué : `tasks.md is not in the format the workflow reads` | La vérification de format a été sautée ou ignorée sur la PR de spec | Corrigez `tasks.md` dans une PR, puis lancez Agent Issues à la main |
| Un commentaire : « the next implementation issue … was not opened: an issue for … already exists » | L'issue de la phase existe, mais certaines de ses tâches d'agent ne sont pas cochées | Cochez-les si elles sont faites, ou terminez-les. Puis lancez Agent Issues à la main |
| Agent Issues a journalisé `no spec folder with a tasks.md was found` | L'issue de la PR d'agent mergée n'a pas de marqueur, et la PR n'a modifié aucun fichier de `specs/` | Lancez Agent Issues à la main avec le dossier de spec |
| La dernière phase a été mergée et rien ne s'est ouvert | Normal. Il ne reste que des tâches **(human)**, ou aucune | Terminé |

## L'agent ne prend pas en charge ou ne révise pas

| Symptôme | Ce qui se passe | Quoi faire |
| --- | --- | --- |
| Une issue avec le label n'est jamais prise en charge | Agent Canvas est arrêté, l'automatisation est désactivée, ou le token ne peut pas lire le dépôt | Vérifiez que `agent-canvas` tourne et que l'automatisation est activée. Consultez le journal de la dernière exécution de l'automatisation |
| La PR est en rouge, `ci-fix-1` ajouté, l'agent ne révise jamais | Le worker ne révise que `openhands/issue-<n>` exactement (les workflows de correction ajoutent aussi un label aux autres branches `openhands/`), ou l'issue a été fermée | Vérifiez le nom de la branche. Rouvrez l'issue, ou reprenez la PR vous-même |
| Pas de label `ci-fix-*` après une exécution en rouge | Agent CI Status n'a pas tourné, ou l'a ignorée (voir sa notice) | Ouvrez l'exécution d'Agent CI Status et lisez la notice, par ex. `the pull request has a newer commit than this run` |
| L'agent révise, puis rien ne relit le nouveau head | L'agent n'a pas remis `openhands-review` | Remettez-le à la main |
| Push rejeté : `refusing to allow a GitHub App to create or update workflow` | L'app n'a pas la permission d'écriture **Workflows**, et la branche touche `.github/workflows/` (souvent via un merge de `main`) | Accordez-la dans les paramètres de l'app, et acceptez la nouvelle permission sur l'installation. Le passage suivant réessaie. Avec un personal access token, le message en nomme un, et le token a besoin du scope `workflow` |
| Toutes les automatisations échouent : `The GitHub credential GITHUB_PERSONAL_ACCESS_TOKEN is unavailable`, ou `401 Bad credentials` | Le secret manque, ou contient un token d'app vieux de plus d'une heure | Démarrez Agent Canvas avec `pnpm agent-canvas` et laissez-le tourner : il remplace le token toutes les 45 minutes, et journalise chaque token qu'il stocke. Agent Canvas tourne comme un service ? Vérifiez le timer qui lance `pnpm agent-canvas --once` |
| `ci-fix-exhausted` | Cinq corrections n'ont pas abouti | Lisez le dernier échec. Le plus souvent, la spec ou le plan est ambigu. Corrigez-le, retirez les labels, relancez |

## Reviews

| Symptôme | Ce qui se passe | Quoi faire |
| --- | --- | --- |
| « ⏳ Review waiting on checks » et pas de review | Un check sur le head n'est pas terminé, ou est bloqué en file d'attente | Trouvez le check en attente. Un check requis qui ne tourne jamais bloque la review pour toujours |
| La review indique `🔄 CHANGES REQUESTED`, pas de label `review-fix-*` | La review n'a pas le marqueur d'exécution, ne vient ni d'un compte avec accès en écriture ni de l'app nommée dans `AGENT_APP_LOGIN`, ou la PR a avancé | Lisez la notice d'Agent Review Status. Si elle indique que la review ne vient ni d'un mainteneur ni de l'app de l'agent, réglez la variable de dépôt `AGENT_APP_LOGIN` sur le login du bot de l'app |
| Chaque passage de code review échoue avec `HTTP Error 403: Forbidden` | Le template `github-pr-reviewer` demande à `GET /user` qui il est, et GitHub y refuse l'installation token d'une app (`Resource not accessible by integration`) | Faites patcher le bundle de l'automatisation par un agent, avec le prompt de [Créer les deux automatisations, étape 3](../../setup/automations/). La correction : là où le worker lit son login depuis `GET /user` (`github_login` dans `worker.py`, la vérification du token dans `main.py`), rabattez-vous sur un 403 vers GraphQL `{ viewer { login } }`, qui renvoie `<app-name>[bot]` |
| Les reviews s'affichent en « Commented », pas en « Approved » | Le Relecteur publie avec la même identité que celle qui a ouvert la PR, et GitHub n'autorise pas l'auto-approbation | Attendu : le Développeur et le Relecteur partagent la GitHub App des agents. La glue lit la ligne du verdict, pas l'état de la revue |

## Checks

| Symptôme | Ce qui se passe | Quoi faire |
| --- | --- | --- |
| `UI Screenshots` échoue sur un refactoring | La règle ne sait pas distinguer un changement visible d'un changement invisible | Un mainteneur ajoute `no-ui-screenshots` et relance le check |
| Le job e2e de chaque PR télécharge Chromium | Le cache n'est enregistré que sur `main` | Gardez le job `playwright-cache` de la CI, avec la même clé que PR Checks |
| `Check for mutations` échoue sur `main` | Quelque chose a généré des fichiers que la PR n'a pas committés | Lancez `pnpm build` en local et committez le diff |
| `Resource not accessible by integration` lors de la pose d'un label | Le token du workflow peut écrire dans les issues mais pas dans les pull requests | Ajoutez `pull-requests: write` au workflow |

## Tests après merge

| Symptôme | Ce qui se passe | Quoi faire |
| --- | --- | --- |
| Une PR a été déployée, pas d'issue de test | Elle n'a rien changé qui soit déployé (docs, specs, tests, outillage ou CI uniquement), elle porte `skip-deploy-test`, ou l'exécution de Deploy n'a rien livré parce que son commit n'était plus le dernier de `main` | Lisez les notices de l'exécution de Post-merge Verify. Pour la tester quand même, lancez le workflow à la main avec le numéro de la PR |
| Issue de test ouverte, le Testeur ne la prend jamais en charge | L'issue n'a pas le label `openhands-test` parce qu'un élément vers lequel elle pointe n'a pas pu être verrouillé, ou elle a été ouverte par un compte auquel l'automatisation ne fait pas confiance | L'exécution de Post-merge Verify échoue et nomme ce qu'il faut verrouiller. Verrouillez-le, puis ajoutez le label à la main |
| Le Testeur a rendu son rapport, et vous voulez une autre exécution | Chaque pose du label est testée une fois | Retirez et remettez `openhands-test` |
| Le rapport indique « blocked » | Il manque au stage quelque chose dont le changement a besoin, comme un compte de paiement connecté | Corrigez le stage, puis remettez le label |
| Le commentaire **E2E screenshots** manque sur une PR | La PR est verrouillée, et GitHub refuse au token d'Actions un commentaire sur une conversation verrouillée | Lisez la liste dans le résumé du job `E2E screenshots`, ou déverrouillez la PR |
| L'agent Relecteur ne publie jamais de review, et la PR est verrouillée | GitHub refuse une review native sur une pull request verrouillée, même venant d'un compte avec un accès en écriture | Déverrouillez-la. Pour tenir les inconnus à l'écart, utilisez la limite d'interaction du dépôt plutôt que de verrouiller les pull requests |

## Déploiement

| Symptôme | Ce qui se passe | Quoi faire |
| --- | --- | --- |
| Le déploiement est annulé avec `is not authorized to perform` sur une ressource qu'aucune stack n'avait créée auparavant | Une stack a commencé à utiliser un type de ressource que les politiques du rôle d'exécution CloudFormation ne couvrent pas | Ajoutez les actions à `setup-stage.sh` et relancez-le. Il est idempotent et publie une nouvelle version de la politique |
