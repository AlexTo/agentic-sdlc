**Résultat :** une fonctionnalité pour l'application de notes, menée de votre idée en une ligne jusqu'au code mergé par
les agents, et la preuve que chaque passage de relais de la boucle fonctionne dans votre fork.

La fonctionnalité : **des tags sur les notes**. *Un utilisateur peut ajouter jusqu'à cinq tags à une note, et filtrer la liste
des notes par tag.* Elle est petite, mais elle touche la table, l'API et le site web, donc chaque étape a
quelque chose de réel à faire. Le [tutoriel](../../tutorial/the-case/) couvre chaque étape plus en détail.

<Steps>

1. **Écrivez la spec** avec votre agent de code, dans votre clone, sur une branche `main` à jour :

   ```text
   /speckit-specify Users can add up to five tags to a note and filter the note list by tag. Tags are case-insensitive and unique per note.
   /speckit-clarify
   /speckit-plan
   /speckit-tasks
   /speckit-analyze
   ```

   `/speckit-specify` crée une branche pour la spec et bascule dessus, avec un nom du type
   `<timestamp>-note-tags`. Répondez aux questions que pose `/speckit-clarify`. Vous obtenez
   `spec.md`, `plan.md` et `tasks.md` sous `specs/<timestamp>-note-tags/`.

2. **Ouvrez la PR de spec, avec le label `spec-ready`, et mergez-la.**

   ```bash
   git add specs/ && git commit -m "docs(specs): add note tags spec"
   git push -u origin HEAD
   gh pr create --fill --label spec-ready
   ```

   `gh` ouvre la pull request dans votre fork et affiche son adresse. (Le site web de GitHub propose
   le dépôt d'origine comme base de la pull request d'un fork, ce qui n'est pas ce que vous voulez.)
   Lisez-y la spec comme vous reliriez du code, puis mergez une fois les checks au vert. C'est vous
   qui avez ouvert la PR, donc GitHub ne vous laissera pas l'approuver : cochez **Merge without
   waiting for requirements to be met**.

   ✅ **Tasks format** passe sur la PR. Après le merge, **Agent Issues** ouvre une issue intitulée
   `feat(<feature>): … (with setup and foundations)`, avec le label `openhands`, limitée au premier groupe de phases.

3. **Attendez l'agent.** Vous ne faites rien.

   ✅ Au passage suivant, une conversation pour l'issue démarre dans Agent Canvas. Quand elle se termine, une
   PR ouverte par votre app apparaît sur `openhands/issue-<n>` avec `openhands-review`, et `tasks.md` coché pour
   exactement ces phases.

4. **Observez les contrôles.**

   ✅ Les PR Checks tournent. Si l'un échoue, **Agent CI Status** ajoute `ci-fix-1` et l'agent Développeur révise la
   même PR au passage suivant. Une fois tous les checks terminés, l'agent Relecteur relit le head
   et conclut par `✅ APPROVED` ou `🔄 CHANGES REQUESTED`. Une demande de modifications renvoie aussi l'agent
   au travail, avec `review-fix-1`.

5. **Relisez et mergez.** Lisez la description de la PR, les éventuelles tâches **(human)** qu'elle liste et, pour la
   phase du site web, le commentaire **E2E screenshots**. Puis approuvez et mergez.

   ✅ **Agent Issues** tourne à nouveau et ouvre l'issue de la phase suivante. Les étapes 3 à 5 se répètent.

6. **Mergez la dernière PR.**

   ✅ Agent Issues journalise `No issue created: … no tasks left for the agent`. La fonctionnalité est terminée.
   **Archive Specs** pousse ensuite une branche qui déplace la spec terminée vers `specs/_archive/`, et
   son exécution affiche un lien qui ouvre cette pull request, pré-remplie, pour que vous la soumettiez.

</Steps>

<Aside type="tip" title="Vous n'avez pas vu de boucle de correction ?">
Si l'agent a tout réussi du premier coup, vous n'avez pas encore vu la boucle CI. Pour la tester, poussez
sur une PR d'agent ouverte un commit qui casse l'un de ses tests unitaires. PR Checks échoue, `ci-fix-1`
apparaît, et l'agent pousse un correctif au passage suivant. Il se peut qu'il annule simplement votre commit, ce qui est la
bonne correction ici.
</Aside>

## Auto-vérification

Vous avez le même workflow que Discava quand vous pouvez répondre oui à tout ceci :

- [ ] Merger une PR de spec `spec-ready` a ouvert une issue, sans que personne ne l'ouvre à la main.
- [ ] L'agent a ouvert une PR sur `openhands/issue-<n>` et a coché exactement ses tâches.
- [ ] Une exécution CI en rouge a renvoyé l'agent au travail, et la PR porte `ci-fix-1`.
- [ ] L'agent Relecteur a relu le head de la PR une fois ses checks terminés.
- [ ] Merger la PR de l'agent a ouvert l'issue de la phase suivante.
- [ ] La modification du site web est arrivée avec des captures d'écran listées sur la PR.
- [ ] Le dernier merge n'a rien ouvert.
- [ ] À aucun moment vous n'avez collé une erreur ou écrit un prompt pour l'agent.

Quelque chose ne s'est pas produit ? Voir [Dépannage](../../reference/troubleshooting/).
