import { Steps, Aside } from '@astrojs/starlight/components';

**Résultat :** une GitHub App sous laquelle agissent les agents, installée sur votre fork ; Issues et
Actions activés, tous les labels qu'utilise le workflow, une branche `main` qui n'accepte que des pull
requests avec des checks au vert et une approbation, et des commentaires limités aux collaborateurs.

<Steps>

1. **Créez la GitHub App des agents.** Les agents agissent sous une app que rien d'autre n'utilise,
   donc leurs pull requests et leurs commentaires apparaissent sous elle, et vous les approuvez comme
   ceux de n'importe qui. Celle de Discava est `alex-coding-agent`.

   Ouvrez
   [**New GitHub App**, pré-rempli](https://github.com/settings/apps/new?url=https%3A%2F%2Fgithub.com%2FAlexTo%2Fagentic-sdlc&public=false&contents=write&issues=write&pull_requests=write&workflows=write&checks=read&statuses=read&actions=read).
   Le lien remplit le formulaire, il vous reste seulement à :

   - Saisir un **nom**. Les noms d'app sont uniques sur tout GitHub, essayez donc
     `<you>-coding-agent`.
   - Vérifier que **Webhook → Active** est décoché. Agent Canvas interroge GitHub, donc rien n'a
     besoin d'atteindre votre machine.
   - Cliquer sur **Create GitHub App**.

   Les permissions que le lien sélectionne, sous **Repository permissions**, si vous voulez les
   vérifier :

   | Permission | Accès | Pourquoi |
   | --- | --- | --- |
   | Contents | Read and write | Cloner et pousser les branches des agents |
   | Issues | Read and write | Lire les issues, commenter, poser des labels |
   | Pull requests | Read and write | Ouvrir des pull requests, les relire et les commenter |
   | Workflows | Read and write | Sans elle, GitHub refuse un push entier qui touche `.github/workflows/`, ce qu'un merge de `main` peut faire. Les agents ne modifient jamais les workflows |
   | Checks, Commit statuses, Actions | Read-only | Le Relecteur attend la fin des checks avant de relire |
   | Metadata | Read-only | Exigé par GitHub |

2. **Récupérez la clé de l'app et installez-la.** Sur la page que GitHub vous affiche ensuite, les
   paramètres de l'app :

   - Notez l'**App ID**, un nombre vers le haut de la page.
   - Sous **Private keys**, cliquez sur **Generate a private key**. Votre navigateur télécharge un
     fichier `.pem`. C'est le seul secret de longue durée : les agents ne voient jamais que des
     tokens d'une heure créés à partir de lui.
   - Dans la barre latérale, cliquez sur **Install App**, puis sur **Install**, choisissez **Only
     select repositories**, et sélectionnez votre fork.

   Il vous faut l'App ID et le fichier `.pem` à l'[étape 3](../openhands/).

3. **Lancez le script de configuration** depuis votre clone, connecté à `gh` en tant que propriétaire
   du fork, avec le nom de l'app tel qu'il apparaît dans son adresse, `github.com/apps/<app-name>` :

   ```bash
   ./scripts/setup-repository.sh <you>/agentic-sdlc <app-name>
   ```

   Un fork copie le code, pas les paramètres. Le script les règle avec le CLI `gh`, et pose le même
   état à chaque fois, vous pouvez donc le relancer sans risque.

   Ajoutez d'abord `--dry-run` si vous voulez voir chaque commande `gh` avant qu'elle s'exécute. Le script règle :

   | Réglage | Pourquoi |
   | --- | --- |
   | Issues et Actions activés | GitHub désactive les deux dans un fork, et le workflow repose sur les issues |
   | 20 labels | Chaque label de [Référence : labels](../../reference/labels/) |
   | Protection de branche sur `main` | Une pull request, une approbation, les approbations périmées révoquées, et sept checks requis : `Checks (lint)`, `Checks (test)`, `Checks (build)`, `Tasks format`, `Invariant coverage`, `E2E tests`, `UI Screenshots` |
   | Tokens des workflows en lecture seule, et Actions ne peut ni ouvrir ni approuver de pull requests | Un workflow qui pourrait ouvrir une pull request pourrait aussi en approuver une. Archive Specs pousse la branche qui déplace une spec terminée vers `specs/_archive/` et affiche un avertissement avec un lien qui ouvre sa pull request, pré-remplie, pour que vous la soumettiez |
   | Interactions limitées aux collaborateurs, pour six mois | Le fork d'un dépôt public est public, et les agents lisent chaque commentaire sur ce qu'ils traitent tout en détenant un token qui peut pousser |
   | GitHub Pages depuis Actions | Le job **Deploy Docs** de la CI publie ce site |
   | La variable de dépôt `AGENT_APP_LOGIN`, réglée sur le login du bot de l'app, `<app-name>[bot]` | GitHub ne donne aux reviews d'une app aucune association avec le dépôt, donc la glue ne renvoie l'agent au travail sur un verdict du Relecteur que s'il vient de personnes avec un accès en écriture ou de l'app que cette variable nomme |

   La protection laisse le contournement autorisé, pour que vous, en tant que propriétaire, puissiez merger une pull request que vous
   avez ouverte vous-même, comme une PR de spec, que GitHub ne vous laisse pas approuver.

4. **Vérifiez qu'Actions est activé.** Si l'onglet **Actions** de votre fork affiche encore **I understand my
   workflows, go ahead and enable them**, cliquez dessus. GitHub demande parfois ce clic même
   après que l'API a activé Actions.

</Steps>

<Aside type="tip" title="Pourquoi une app, et pas un second compte">
Les agents de Discava ont d'abord travaillé sous `discava-bot`, un compte machine avec un personal
access token. En novembre 2026, GitHub l'a signalé, ce qui a masqué à tout le monde ses 210 issues
et pull requests. Les tokens d'une app expirent au bout d'une heure et n'atteignent que les dépôts
sur lesquels elle est installée. Un second compte avec un token classique (les scopes `repo` et
`workflow`) fonctionne toujours : passez ce compte au script à la place, et il est invité comme
collaborateur.
</Aside>

<Aside type="caution">
La limite d'interactions expire six mois après que vous l'avez posée, et rien ne vous prévient. Notez la date,
et relancez le script avant. Si vous ajoutez plus tard l'agent Testeur, qui détient des identifiants
cloud, c'est cette limite qui empêche le commentaire d'un inconnu de l'atteindre. Voir
[Qui peut commenter](../../discava/post-merge-verify/#qui-peut-commenter).
</Aside>

<Aside type="caution">
N'ajoutez pas `software-factory/review` aux checks requis. C'est un signal destiné à l'agent, publié uniquement
en `failure`, et l'exiger bloquerait toutes les PR.
</Aside>

## Vérifier que ça marche

La page **Issues → Labels** du fork liste les 20 labels, **Settings → Branches** affiche la règle sur
`main` avec sept checks requis, et **Settings → Moderation options → Interaction limits** affiche
la limite réservée aux collaborateurs avec sa date de fin. **Settings → Secrets and variables → Actions →
Variables** affiche `AGENT_APP_LOGIN`, et **Settings → GitHub Apps** liste votre app.
