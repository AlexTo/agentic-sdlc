**Résultat :** Issues et Actions activés, tous les labels qu'utilise le workflow, une branche `main` qui
n'accepte que des pull requests avec des checks au vert et une approbation, des commentaires limités aux collaborateurs, et
le compte propre aux agents comme collaborateur.

Un fork copie le code, pas les paramètres. `scripts/setup-repository.sh` les règle tous avec le CLI
`gh`. Chaque étape pose le même état à chaque fois, vous pouvez donc le relancer sans risque.

<Steps>

1. **Créez le compte des agents.** Les agents travaillent sous leur propre compte GitHub, un compte
   machine que rien d'autre n'utilise. Celui de Discava est `discava-bot`. Créez-en un. Son token est celui
   que vous créez à l'[étape 3](../openhands/), et ses pull requests et ses commentaires apparaissent sous ce compte, donc vous
   les approuvez comme ceux de n'importe qui.

2. **Lancez le script** depuis votre clone, connecté à `gh` en tant que propriétaire du fork, avec le compte
   des agents :

   ```bash
   ./scripts/setup-repository.sh <you>/agentic-sdlc <agents-account>
   ```

   Ajoutez d'abord `--dry-run` si vous voulez voir chaque commande `gh` avant qu'elle s'exécute. Le script règle :

   | Réglage | Pourquoi |
   | --- | --- |
   | Issues et Actions activés | GitHub désactive les deux dans un fork, et le workflow repose sur les issues |
   | 20 labels | Chaque label de [Référence : labels](../../reference/labels/) |
   | Protection de branche sur `main` | Une pull request, une approbation, les approbations périmées révoquées, et sept checks requis : `Checks (lint)`, `Checks (test)`, `Checks (build)`, `Tasks format`, `Invariant coverage`, `E2E tests`, `UI Screenshots` |
   | Tokens des workflows en lecture seule, et Actions ne peut ni ouvrir ni approuver de pull requests | Un workflow qui pourrait ouvrir une pull request pourrait aussi en approuver une. Archive Specs pousse la branche qui déplace une spec terminée vers `specs/_archive/` et affiche un avertissement avec un lien qui ouvre sa pull request, pré-remplie, pour que vous la soumettiez |
   | Interactions limitées aux collaborateurs, pour six mois | Le fork d'un dépôt public est public, et les agents lisent chaque commentaire sur ce qu'ils traitent tout en détenant un token qui peut pousser |
   | GitHub Pages depuis Actions | Le job **Deploy Docs** de la CI publie ce site |
   | Le compte des agents invité avec un accès en écriture | Pour que les agents puissent pousser des branches et ouvrir des pull requests |

   La protection laisse le contournement autorisé, pour que vous, en tant que propriétaire, puissiez merger une pull request que vous
   avez ouverte vous-même, comme une PR de spec, que GitHub ne vous laisse pas approuver.

3. **Acceptez l'invitation** en étant connecté avec le compte des agents.

4. **Vérifiez qu'Actions est activé.** Si l'onglet **Actions** de votre fork affiche encore **I understand my
   workflows, go ahead and enable them**, cliquez dessus. GitHub demande parfois ce clic même
   après que l'API a activé Actions.

</Steps>

<Aside type="caution">
La limite d'interactions expire six mois après que vous l'avez posée, et rien ne vous prévient. Notez la date,
et relancez le script avant. Si vous ajoutez plus tard l'agent Testeur, qui détient des identifiants
cloud, c'est cette limite qui empêche le commentaire d'un inconnu de l'atteindre. Voir
[Qui peut commenter](../../discava/post-merge-verify/#qui-peut-commenter).
</Aside>

<Aside type="caution">
N'ajoutez pas `software-factory/review` aux checks requis. C'est un signal destiné à l'agent, publié uniquement
en `failure`, et l'exiger bloquerait toutes les PR.
</Aside>

## Vérifier que ça marche

La page **Issues → Labels** du fork liste les 20 labels, **Settings → Branches** affiche la règle sur
`main` avec sept checks requis, et **Settings → Moderation options → Interaction limits** affiche
la limite réservée aux collaborateurs avec sa date de fin. **Settings → Collaborators** liste le compte
des agents avec le rôle **Write**.
