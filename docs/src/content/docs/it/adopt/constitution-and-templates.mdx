**Alla fine avrai:** una costituzione ratificata tutta tua, e template di Speckit che producono file
che il workflow Agent Issues può leggere.

Il `.specify/` che hai copiato al [passaggio 2](../speckit/) contiene già una costituzione e dei
template funzionanti, scritti per l'app di note. Questo passaggio li rende tuoi.

<Steps>

1. **Riscrivi la costituzione per il tuo progetto.** Nel tuo coding agent:

   ```text
   /speckit-constitution
   ```

   Dagli i principi del tuo progetto: architettura, modello dei dati, impostazioni di sicurezza
   predefinite, convenzioni del codice. [Quella di Discava](../../discava/constitution-and-guidance/)
   è un esempio completo. Mantieni queste parti di quella copiata, adattando i comandi e i nomi dei
   package al tuo stack, perché il resto del workflow dipende da esse:

   | Mantieni | Dalla costituzione copiata | Perché |
   | --- | --- | --- |
   | Unit test, invarianti e test e2e sono obbligatori, e i test sono una specifica | III. Layered Tests | L'agente non può indebolire un test per far diventare verde la CI |
   | Tutto gira con `pnpm dev`, senza account cloud | II. Everything Runs Locally | La CI delle PR può così eseguire la suite e2e e dare all'agente un feedback reale |
   | Gli agenti implementano sul proprio branch e sulla propria PR, non avviano mai lo stack locale, e marcano **(human)** i task che ne hanno bisogno | Development Workflow | L'agente non ha Docker. La CI esegue ciò che lui non può |
   | La CI delle PR è il cancello. Un agente non fa mai merge, non fa push su `main`, non modifica i workflow della CI e non indebolisce un test | Development Workflow | È ciò che tiene un agente nella sua corsia |

2. **Cambia i percorsi dei package in `tasks-template.md`.** I suoi task di test nominano i package di
   questo repository: `packages/notes-table/src/helpers/invariants/` e `@agentic-sdlc/e2e`. Puntali sui
   tuoi. Lascia il resto del template com'è: le regole di formato sotto **Read by automation**, il
   marcatore **(human)**, i test obbligatori e la nota contro la modifica dei test esistenti sono ciò
   su cui si basano il workflow Agent Issues e il check `Tasks format`.

3. **Mantieni la riga della issue padre** in `spec-template.md`:

   ```markdown
   **Parent issue**: [#<number>, or "none" if there is no tracking issue]
   ```

   Agent Issues ne ricava il `Refs #<parent>` che scrive in ogni issue.

</Steps>

## Verifica che funzioni

Genera una spec e dei task usa e getta per una feature minuscola. Poi, quando il collante è a posto
([passaggio 5](../glue-scripts/)):

```bash
pnpm nx run @your-scope/tooling-agent:validate-tasks
```

```text
1 tasks.md file(s) are in the expected format.
```

Poi elimina la cartella della spec usa e getta.

<Aside type="caution">
`/speckit-tasks` a volte scrive `### Phase 2` o indenta un task. È esattamente ciò che il
validatore intercetta, quindi non allentare il validatore. Correggi il testo del template finché i file generati
non passano.
</Aside>
