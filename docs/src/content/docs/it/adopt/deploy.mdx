**Alla fine avrai:** una scansione Trivy a ogni push su `main`, un workflow Deploy che porta ogni `main`
verde su uno stage di sviluppo, deploy in produzione che aspettano una persona e, se lo vuoi, un
agente Tester che testa ogni modifica mergiata sullo stage di sviluppo.

Questo repository include i workflow, disattivati: `deploy.yml` gira solo a mano o una volta che
`AUTO_DEPLOY_STAGE` è impostata, e `post-merge-verify.yml` gira solo dopo un deploy. L'app di note non
ha infrastruttura cloud, quindi la parte da scrivere è tua. I passaggi parlano di AWS e CDK, come usa
Discava, ma lo schema funziona per qualsiasi cloud.

<Steps>

1. **Aggiungi un target `trivy`** ai progetti che vuoi scansionare (il `pnpm trivy` della radice esegue
   `nx run-many --target trivy --all`). Il job `trivy` nel `ci.yml` copiato lo esegue a ogni push su
   `main`, come job separato da `build`, così una CVE appena pubblicata segnala `main` senza bloccare
   nient'altro. Registra i risultati accettati, un ID per riga, in `.trivyignore`.

2. **Aggiungi la tua infrastruttura** come app CDK in `packages/infra`, con uno stage per ambiente nel
   suo `src/main.ts`:

   ```bash
   pnpm nx g @aws/nx-plugin:ts#infra --name=infra
   ```

   Il suo target `deploy-ci` è ciò che esegue il workflow Deploy. I construct per il sito delle note
   sono già in `packages/common/constructs`.

3. **Configura un accesso al cloud senza chiavi** per ogni stage: il provider OIDC di GitHub, un ruolo
   di deploy considerato affidabile solo per `repo:owner/repo:environment:<stage>`, un ruolo di
   esecuzione CloudFormation con un permissions boundary, il bootstrap di CDK, e un environment GitHub
   con il nome dello stage e le variabili `AWS_REGION`, `AWS_DEPLOY_ROLE_ARN` e
   `AWS_EXECUTION_ROLE_ARN`. Lo script
   [`scripts/setup-stage.sh`](https://github.com/AlexTo/discava/blob/main/scripts/setup-stage.sh) di
   Discava fa tutto questo per i suoi stage; leggilo prima di adattarlo. Non salvare chiavi di accesso.

4. **Copia `.github/workflows/deploy.yml`**, se non lavori in un fork, e cambia il suo scope
   `@agentic-sdlc/` e il nome dello stage predefinito. Fa il checkout del commit verificato dalla CI,
   si ferma subito con un errore chiaro se mancano `packages/infra` o le variabili dell'environment,
   esegue Trivy, fa il synth, e fa il deploy solo se il commit è ancora l'ultimo di `main`. Quel
   controllo di attualità sta *dentro* lo slot di concurrency del job, quindi riflette `main` subito
   prima del deploy, anche se l'esecuzione ha aspettato dietro un'altra.

5. **Attiva i deploy automatici** per lo stage di sviluppo. In **Settings → Secrets and
   variables → Actions → Variables**, aggiungi una variabile di repository `AUTO_DEPLOY_STAGE` con il nome del tuo
   stage di sviluppo.

6. **Proteggi la produzione.** In **Settings → Environments**, apri l'environment del tuo stage di produzione
   e aggiungi **Required reviewers**. Per farne il deploy, apri **Actions → Deploy → Run
   workflow** e inserisci lo stage di produzione. Il job poi aspetta l'approvazione.

7. **Aggiungi l'agente Tester**, se vuoi che ogni modifica deployata venga testata (lacuna 11). Da
   questo repository hai già il suo collante (`post-merge-test/` nel passaggio 5), il suo template di
   issue (passaggio 4), e `.github/workflows/post-merge-verify.yml`, che apre una issue di test per
   ogni pull request che un'esecuzione di Deploy ha portato sullo stage di test. Testa su `TEST_STAGE`,
   una variabile di repository che per default vale `AUTO_DEPLOY_STAGE`.

   Sul lato OpenHands, aggiungi un agent profile `tester` e un'automazione che fa polling delle issue
   con la label `openhands-test`. Non c'è un template del catalogo per questo. Il worker di Discava e il suo prompt
   sono descritti in [Configurazione di OpenHands](../../discava/openhands-setup/#tester-github-issue-tester)
   e in [I prompt degli agenti](../../discava/agent-prompts/#tester). Dai al Tester:

   - una CLI del cloud autenticata sull'account di sviluppo, con il minimo accesso che serve per testare
   - un utente di test per ogni ruolo della tua app, salvati come secret di OpenHands
   - un browser che possa pilotare, come Playwright con Chromium

   <Aside type="caution" title="Repository pubblico? Prima limita i commenti ai collaboratori">
   Il Tester legge issue, pull request e i loro commenti mentre ha in mano quelle credenziali. Se
   il tuo repository è pubblico, il commento di un estraneo può portargli delle istruzioni.
   `scripts/setup-repository.sh` limita le interazioni ai collaboratori, per al massimo sei mesi,
   quindi rieseguilo prima che il limite scada. Mantieni anche il lock in
   `helpers/conversation-lock.ts`, tieni il "come testare" nel prompt dell'automazione invece che
   nella issue, e non puntarlo mai su uno stage i cui dati contano.
   </Aside>

</Steps>

## Verifica che funzioni

Fai il merge di una PR qualsiasi. La CI gira, poi **Deploy** parte da solo con lo stage di sviluppo. Riesegui la CI
a mano su un commit più vecchio: Deploy registra `Skipping deploy: no longer main's latest commit` e
non porta nulla in produzione.

Con il Tester configurato: dopo quel deploy, **Post-merge Verify** apre una issue con il lock, intitolata
`test(post-merge): verify #<pr> …`, con la label `openhands-test`. Entro un polling il Tester parte,
e il suo report compare come commento sulla issue.

<Aside type="note">
Nessun agente fa deploy, e nessuno vede questi ruoli. Al Developer e al Reviewer serve solo il token
GitHub. L'accesso del Tester all'account di sviluppo è separato dal ruolo di deploy, che viene
assunto solo da un workflow che gira da `main`, nell'environment dello stage.
</Aside>

Avanti: il tuo repository ora ha tutto ciò che ha un fork di questo. Continua da
[2. Configura il repository](../../setup/github-repository/), con il tuo repository al posto
del fork.
