import { Steps, Aside, FileTree } from '@astrojs/starlight/components';

**Alla fine avrai:** un progetto `tooling-agent` con dieci target Nx e 223 unit test che passano.
I workflow dei passaggi 6, 7 e 9 si limitano a chiamare questi target.

<Steps>

1. **Copia `packages/tooling/agent/`** da questo repository, per intero. Il suo `project.json`
   dichiara già ogni target che chiamano i workflow, e il suo `AGENTS.md` dice a un agente cosa
   contiene ogni cartella:

   <FileTree>
   - packages/tooling/agent/src/
     - agent-issues/ spec → issue, il validatore di `tasks.md`, e l'archiviazione delle spec finite
     - agent-ci/ CI rossa → agente
     - agent-review/ "changes requested" → agente
     - helpers/ il lock delle issue che legge un agente, e la distinzione tra autori fidati ed estranei
     - ui-screenshots/ la regola degli screenshot, e il commento `E2E screenshots`
     - invariant-coverage/ quale codice scrive quale entità, e la regola per cui i nuovi writer hanno bisogno di invarianti
     - post-merge-test/ PR deployata → issue di test per il Tester
   </FileTree>

   Dipendono solo dai moduli integrati di Node, da TypeScript (per la scansione degli invarianti) e
   dalla CLI `gh`. Li esegue `tsx`. Aggiungi la cartella al `pnpm-workspace.yaml` del tuo workspace e
   ai riferimenti del `tsconfig.json` della radice, se i tuoi glob non coprono già `packages/tooling/*`.

2. **Rinomina lo scope.** Sostituisci `@agentic-sdlc/` con lo scope del tuo workspace nel
   `package.json`, nel `project.json` e nel `vitest.config.mts` del progetto, e nei commenti dei suoi
   file `main.ts`. Anche ogni workflow che copierai più avanti nomina `@agentic-sdlc/tooling-agent`.

3. **Cambia le costanti per la tua configurazione.** Quelle in grassetto puntano all'app di note di
   questo repository, quindi quasi certamente le cambierai. Le altre cambiano solo se hai cambiato
   una decisione nella [panoramica](../overview/):

   | Costante | File | Predefinito |
   | --- | --- | --- |
   | **`UI_SOURCE`** | `ui-screenshots/check.ts` | `.tsx`/`.css` sotto `packages/notes-website/src/` e `packages/common/shadcn/src/` |
   | **`WRITER_PACKAGES`**, **`ENTITIES_PACKAGE`** | `invariant-coverage/scan.ts` | I package il cui codice scrive nella tabella, e quello che ne contiene le entità (`notes-table`) |
   | **`WRITER_MAP_PATH`**, **`INVARIANTS_PATH`**, **`HELPERS`** | `invariant-coverage/check.ts` | `packages/notes-table/entity-writers.json`, `packages/notes-table/src/helpers/invariants`, `notes-table` |
   | **`UI_PATHS`**, **`NOT_DEPLOYED`** | `post-merge-test/plan.ts` | Cosa conta come modifica alla UI da provare cliccando, e i percorsi che non arrivano mai a uno stack deployato |
   | `SPEC_READY_LABEL`, `AGENT_BRANCH_PREFIX` | `agent-issues/gate.ts` | `spec-ready`, `openhands/` |
   | `AGENT_LABEL` | `agent-issues/issue.ts` | `openhands` |
   | `AGENT_BRANCH`, `REVIEW_STATUS_CONTEXT`, `MAX_CI_FIX_ATTEMPTS` | `agent-ci/plan.ts` | `^openhands\/issue-\d+$`, `software-factory/review`, `5` |
   | `MAX_REVIEW_FIX_ATTEMPTS`, `CHANGES_REQUESTED` | `agent-review/plan.ts` | `5`, `🔄 CHANGES REQUESTED` |
   | `WAIVER_LABEL` | `ui-screenshots/check.ts`, `invariant-coverage/check.ts` | `no-ui-screenshots`, `no-new-invariant` |

   Se per ora non controllerai gli invarianti, lascia al suo posto la cartella `invariant-coverage` e
   non copiare il suo job di PR Checks al passaggio 6. Alcuni unit test leggono i veri file degli
   invarianti, quindi aggiorna quei test (in `invariant-coverage/check.test.ts`) o i percorsi qui sopra.

   <Aside type="caution">
   Non cambiare `REVIEW_STATUS_CONTEXT`. `software-factory/review` è lo status che cerca il worker
   issue-to-PR di OpenHands. Con qualsiasi altro nome l'agente non viene mai rimandato indietro.
   </Aside>

4. **Esegui i test.**

   ```bash
   pnpm nx run @your-scope/tooling-agent:test
   ```

</Steps>

## Prova un dry run

Ognuno degli script degli agenti legge l'evento GitHub da `GITHUB_EVENT_PATH`, e con
`DRY_RUN=true` stampa la sua decisione invece di eseguirla. Per riprodurre un caso reale, salva un payload
da un'esecuzione passata del workflow e punta lo script su di esso:

```bash
DRY_RUN=true GITHUB_REPOSITORY=owner/repo GITHUB_EVENT_PATH=./event.json \
  pnpm nx run @your-scope/tooling-agent:agent-ci-status
```

```json
{
  "pullRequest": 470,
  "plan": {
    "action": "send-back",
    "attempt": 1,
    "label": "ci-fix-1",
    "description": "CI failed (fix attempt 1 of 5): E2E tests (4/4)"
  }
}
```
