Il modo più rapido per avere il workflow è [fare il fork di questo repository](../../setup/fork/). Questa sezione
è per quando non puoi: hai un repository di prodotto esistente e vuoi la stessa configurazione al suo interno.

Ogni passaggio aggiunge un pezzo e dice come verificarlo. Quasi ogni pezzo è un file o una cartella
che copi da questo repository così com'è, per poi puntarlo ai tuoi package: scrivi la configurazione
a mano solo dove descrive il tuo progetto. Quando hai finito, il tuo repository ha ciò che ha un fork,
e continui da [2. Configura il repository](../../setup/github-repository/).

<Aside type="tip">
Fai comunque il fork di questo repository ed esegui prima [la tua prima feature](../../setup/first-feature/) sull'app
di note. Vedere l'intero loop funzionare una volta rende molto più facile seguire ogni passaggio qui.
</Aside>

## Decidi prima queste cose

| Decisione | Predefinito | Cambialo se |
| --- | --- | --- |
| Label che avvia l'implementazione | `openhands` | Usi già quell'label |
| Prefisso dei branch | `openhands/issue` | Raramente. Il worker rivede esattamente `openhands/issue-<n>`, e il collante risponde a qualsiasi branch di un solo segmento sotto `openhands/`. Se lo cambi, cambia anche `AGENT_BRANCH` e le condizioni dei workflow |
| Label di review | `openhands-review` | Come sopra |
| Intervallo di poll | ogni 5 minuti | Vuoi costi più bassi e puoi aspettare di più (il predefinito del catalogo è 15), o tempi di risposta più rapidi (Discava fa polling ogni 2) |
| Massimo di tentativi di correzione | 5 per loop | Raramente. È `MAX_*_FIX_ATTEMPTS` in due file `plan.ts` |
| Numerazione delle cartelle delle spec | timestamp | Mai, con più di un autore di spec |

In ogni comando e file copiato, sostituisci `@your-scope` o `@agentic-sdlc` con lo scope npm del tuo
workspace.

Avanti: [1. Workspace e igiene dei commit](../workspace/).
