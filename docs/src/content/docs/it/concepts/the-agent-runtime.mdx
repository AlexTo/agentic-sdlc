**In breve:** OpenHands esegue tre automazioni pianificate sul tuo repository, una per ogni ruolo
degli agenti. Il **Developer** implementa le issue con label e rivede le pull request segnate come
fallite. Il **Reviewer** revisiona le pull request quando i loro check finiscono. Il **Tester**
testa ogni modifica mergiata sullo stage di sviluppo deployato. Ciascuna avvia un normale coding
agent con un prompt fisso. Nessuna ha bisogno che tu apra una chat.

## I tre ruoli

| Ruolo | Automazione | Parte da | Cosa lascia |
| --- | --- | --- | --- |
| **Developer** | GitHub issue to PR | Una issue con la label `openhands`, o uno status `software-factory/review` fallito sulla sua PR | Una pull request su `openhands/issue-<n>`, e le sue revisioni |
| **Reviewer** | GitHub code review | Una PR con la label `openhands-review`, una volta finiti tutti i check | Una review che termina con `✅ APPROVED` o `🔄 CHANGES REQUESTED` |
| **Tester** | GitHub issue tester | Una issue con la label `openhands-test`, aperta dopo un deploy | Un report di test sulla issue, con prove dalla UI, dalle API e dai dati salvati, e a volte una piccola PR di correzione |

Il Developer e il Reviewer sono tutto ciò che serve a un repository per far girare il loop fino al
merge. Al Tester serve qualcosa di deployato da testare, quindi arriva con i
[deploy automatici](../../adopt/deploy/). L'app di esempio in questo repository non ha un deploy,
quindi un fork esegue i primi due.

```d2
direction: right

machine: La tua macchina {
  style.stroke-dash: 3
  canvas: Agent Canvas {
    i2p: da issue a PR
    review: code review
    test: issue tester
  }
  dev: agente Developer
  rev: agente Reviewer
  tester: agente Tester
  canvas.i2p -> dev: implementa o rivedi
  canvas.review -> rev: revisiona
  canvas.test -> tester: testa
}

github: GitHub {
  style.stroke-dash: 3
  issues: issue {shape: page}
  prs: pull request {shape: page}
  statuses: commit status {shape: document}
}

stage: stage di sviluppo {shape: cylinder}

machine.canvas -> github: polling ogni 2 minuti
machine.dev -> github.prs: "push, apertura"
machine.rev -> github.prs: review
machine.tester -> stage: "clicca, chiama, legge"
machine.tester -> github.issues: report
```

## Le parti

| Parte | Cos'è |
| --- | --- |
| **Agent Canvas** | L'app OpenHands che esegui tu stesso (`npx @openhands/agent-canvas`). Include l'agent server, il backend delle automazioni e una UI web |
| **Agent profile** | Quale agente gira, e con quale modello. Un profilo può essere l'agente di OpenHands con qualsiasi LLM, o un coding agent esterno tramite ACP (l'Agent Client Protocol) |
| **Automazione** | Un piccolo worker Python che gira su una pianificazione cron. Legge GitHub, decide cosa fare, e avvia o riprende conversazioni con l'agente. Si installa dal catalogo di Agent Canvas |
| **Secret** | Una credenziale con un nome, come il token GitHub. A una conversazione vengono dati solo i secret nella sua allow-list |

## Le tre automazioni

### Developer: GitHub issue to PR

A ogni polling, per ogni repository che osserva, il worker:

1. Trova le PR aperte sui branch `openhands/issue-<n>` il cui commit di testa ha un commit status
   chiamato `software-factory/review` in stato `failure` o `error`. Per ognuna invia un turno di
   **revisione** alla conversazione di quella issue: leggi le review, i commenti e i check falliti,
   correggili, e fai push sullo stesso branch.
2. Trova le issue aperte con la label di attivazione (`openhands`) che non hanno ancora una PR, e
   avvia un turno di **implementazione**: clona, crea `openhands/issue-<n>`, implementa, testa, fai
   push, apri la PR e aggiungi la label `openhands-review`.

Ogni issue è un *soggetto* con una conversazione stabile. Una revisione va alla stessa conversazione
dell'implementazione originale, così l'agente mantiene il suo contesto.

### Reviewer: GitHub code review

A ogni polling, cerca le PR che hanno la label `openhands-review`, hanno una richiesta di review in
sospeso per il suo account, oppure sono aperte, non in bozza, senza richieste e senza review. Per
ognuna, aspetta che **ogni check sul commit di testa sia finito**, poi avvia una review di quel
preciso commit. La review termina con un verdetto su una riga a sé: `✅ APPROVED` o
`🔄 CHANGES REQUESTED`.

<Aside type="caution">
Il worker issue-to-PR rivede una PR solo quando vede lo status `software-factory/review` fallito. Né
un'esecuzione rossa della CI né il "changes requested" del Reviewer impostano quello status da soli.
Colmare questa lacuna richiede due pezzi del [collante mancante](../the-missing-glue/).
</Aside>

### Tester: GitHub issue tester

Le prime due automazioni vengono dal catalogo di Agent Canvas. Questa è scritta a mano, ed è
piccola: un worker di circa cento righe, costruito sugli helper GitHub del catalogo, e un file di
prompt.

A ogni polling, cerca le issue aperte con la label di attivazione (`openhands-test`) che sono state
aperte dall'account del workflow stesso, `github-actions[bot]`. Per ognuna avvia un turno di
**test**: clona il repository al commit che gira sullo stage, ricostruisci cosa ha cambiato la pull
request mergiata, testalo sullo stack deployato, e commenta il risultato sulla issue.

Il test ha tre parti, e la terza è ciò che lo distingue dal percorrere una pagina cliccando:

1. **La UI**, in un browser vero, con il login di un utente di test.
2. **Le API** dietro quelle schermate, chiamate con il token dell'utente di test, compresi i casi
   che dovrebbero essere rifiutati.
3. **I dati salvati.** Dopo ogni azione, il Tester legge ciò che la modifica avrebbe dovuto
   scrivere e lo controlla: i record del database, i file nello storage, l'indice di ricerca e i
   log. In Discava sono DynamoDB, S3, OpenSearch e CloudWatch.

Tre dettagli lo tengono sicuro e silenzioso:

- **La issue dice solo cosa testare.** Come testarlo (gli strumenti, gli utenti di test, i
  controlli, il report) è il prompt dell'automazione, sulla macchina. Nessuno che possa modificare
  una issue può cambiarlo.
- **Una issue aperta da chiunque altro viene saltata**, perché il suo corpo diventerebbe le
  istruzioni dell'agente.
- **Un test per ogni applicazione della label.** Ogni volta che la label viene applicata conta una
  volta, così i commenti del Tester non avviano mai un secondo test. Rimuovi e riapplica la label
  per testare di nuovo.

Niente apre queste issue di default. Un workflow che ne apre una per ogni pull request deployata è
l'ultimo pezzo del [collante mancante](../the-missing-glue/). Quello di Discava è in
[Verifica post-merge](../../discava/post-merge-verify/).

## Perché polling e non webhook

Le automazioni fanno polling (ogni 2 minuti in Discava, ogni 15 di default), così Agent Canvas può
girare su un laptop o su un server di casa senza URL pubblico e senza secret per i webhook. Il costo
è una latenza fino a un intervallo di polling, che è poca cosa rispetto al tempo che l'agente impiega
a lavorare.

## Una memoria che sopravvive all'esecuzione

Una conversazione mantiene il suo contesto per una issue. Gli agenti tengono anche una memoria che
le sopravvive. OpenHands la salva sulla macchina che esegue Agent Canvas, e tutti e tre i ruoli la
leggono e ci scrivono. Quello che un'esecuzione impara, come una stranezza dello stack locale, un
check che continua a fallire per lo stesso motivo o una convenzione che il Reviewer chiede ogni
volta, resta lì per ogni esecuzione successiva, qualunque sia il ruolo, la issue o la persona che
l'ha chiesta.

È questa la differenza rispetto a un agente in un editor, dove quello che impara resta sulla
workstation di un solo sviluppatore. Qui la memoria appartiene al runtime, quindi cresce con ogni
task che il team ha dato agli agenti, non solo con quelli avviati da una persona.

<Aside type="caution">
Gli agenti scrivono nella memoria direttamente, e nessuno la revisiona. Una lezione sbagliata viene
ripetuta finché qualcuno non la toglie, e un testo che un agente ha letto in una issue o in un
commento può finirci dentro: un motivo in più perché solo i collaboratori possano commentare. Leggi
la memoria ogni tanto. Una lezione che in realtà è una regola va in `AGENTS.md` o, meglio, in un
check che la faccia rispettare. La memoria vive su una sola macchina, quindi fanne il backup insieme
al resto dello stato di Agent Canvas.
</Aside>

## Cosa l'agente può e non può raggiungere

I prompt del Developer e del Reviewer nominano un solo secret, il token GitHub, così il Developer
può leggere la issue e fare push del suo branch e il Reviewer può pubblicare la sua review. A
nessuno dei due serve l'accesso al cloud: tutto ciò che eseguono gira sullo stack locale.

Il Tester è l'eccezione. Deve raggiungere lo stage deployato, quindi lavora con una CLI del cloud
autenticata sull'account di sviluppo, che il suo prompt gli dice di usare in sola lettura, e con un
utente di test per ogni ruolo dell'app. Non riceve mai i ruoli di deploy, e il suo prompt vieta di
modificare l'infrastruttura, fare deploy o toccare un altro stage. Poiché legge issue e pull
request mentre ha in mano quelle credenziali, nessuno senza accesso in scrittura può commentarle.
Su un repository pubblico, questo significa impostare il limite di interazione di GitHub su solo
collaboratori.

Cos'altro gli agenti non possono mai fare, e cosa garantisce ogni limite, è in
[Gate umani](../human-gates/#cosa-gli-agenti-non-possono-mai-fare).

## Scegliere gli agenti

Discava esegue tutte e tre su **Claude Code tramite ACP**, ciascuna con il proprio agent profile:
Sonnet per il Developer, Opus per il Reviewer e il Tester. Un modello più forte per la review è una
scelta voluta: il Reviewer è l'ultimo controllo prima di una persona, e legge molto meno codice di
quanto ne scriva il Developer. Il Tester riceve lo stesso modello perché anche il suo lavoro è di
giudizio: decidere cosa dovrebbe fare una modifica, e se ciò che vede sullo stage, e trova nel suo storage, è giusto.
Qualsiasi agente ACP, o l'agente di OpenHands con qualsiasi LLM, si collega agli stessi profili.

Il prompt con cui gira ogni ruolo è in [I prompt degli agenti](../../discava/agent-prompts/).
