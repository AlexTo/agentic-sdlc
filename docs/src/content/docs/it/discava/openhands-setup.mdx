Gli agenti di Discava girano su una workstation Linux, sotto OpenHands Agent Canvas. Non c'è un
deploy di OpenHands nel cloud e non c'è alcun webhook. Tutto è polling in uscita verso GitHub.

## Agent Canvas

Agent Canvas 1.45.0, installato da npm (`@openhands/agent-canvas`) ed eseguito come servizio utente.
Il suo stato sta in `~/.openhands/`: impostazioni, agent profile, secret e il database SQLite delle
automazioni.

## Impostazioni delle conversazioni

Le impostazioni che determinano come lavorano gli agenti:

| Impostazione | Valore | Perché |
| --- | --- | --- |
| Agent | ACP, server `claude-code` | Un coding agent esterno, tramite l'Agent Client Protocol |
| ACP prompt timeout | 30 minuti | Un turno di implementazione è lungo |
| Max iterations | 500 | Spazio per un'intera fase in una sola conversazione |
| Confirmation mode | off | Senza supervisione. Non c'è nessuno a confermare |
| Security analyzer | LLM | I comandi vengono comunque vagliati per il rischio |
| Runtime | local | Gira sull'host, dove ci sono già Node, pnpm e git |
| Worktree branch prefix | `openhands/` | Ogni branch creato da un agente inizia così. Il collante si basa su questo |

## Agent profile

Un profilo per ogni ruolo degli agenti:

| Profilo | Ruolo | Agente | Modello | Usato da |
| --- | --- | --- | --- | --- |
| `developer` | Developer | Claude Code (ACP) | Sonnet | GitHub issue to PR |
| `reviewer` | Reviewer | Claude Code (ACP) | Opus | GitHub code review |
| `tester` | Tester | Claude Code (ACP) | Opus | GitHub issue tester |

Ciascuno ha un prompt timeout di 30 minuti.

## Secret

Salvati in Agent Canvas (**Settings → Secrets**), per nome:

| Nome | Usato per |
| --- | --- |
| `GITHUB_PERSONAL_ACCESS_TOKEN` | L'installation token corrente della GitHub App, nonostante il nome. Le automazioni lo usano per leggere GitHub. Le conversazioni lo ricevono per clonare, fare push, aprire PR, fare review e commentare |
| `OPENHANDS_AUTOMATION_API_KEY` | La chiave propria del backend delle automazioni |
| `DISCAVA_STUDENT_USERNAME`, `DISCAVA_STUDENT_PASSWORD` | Lo studente del Tester su `discava-development` |
| `DISCAVA_INSTRUCTOR_USERNAME`, `DISCAVA_INSTRUCTOR_PASSWORD` | L'istruttore del Tester |
| `DISCAVA_ADMIN_USERNAME`, `DISCAVA_ADMIN_PASSWORD` | L'admin del Tester |

I sei secret `DISCAVA_*` sono utenti di test Cognito sullo stage di sviluppo, uno per ogni ruolo
dell'app. Il Tester li usa per accedere ai portali e per ottenere i token delle API.

## La GitHub App

Gli agenti agiscono come `alex-coding-agent`, una GitHub App installata solo su `AlexTo/discava`,
così tutto ciò che aprono, pushano e dicono compare come `alex-coding-agent[bot]`. Non ha webhook,
e ha accesso in lettura e scrittura a contents, issue e pull request.

Fino al 25 novembre 2026 lavoravano come `discava-bot`, un account macchina con un personal access
token classico. GitHub ha segnalato l'account, e questo ha nascosto a tutti tutte le sue 210 issue e
pull request, comprese le sue stesse liste. Le 44 issue aperte e le 11 pull request aperte sono state
riaperte come l'app (#1129–#1183), e gli originali chiusi con un link a ciascuna copia. Il suo lavoro
già unito è ancora in `main`, con autore `discava-bot`.

Un installation token dura un'ora, quindi la chiave privata dell'app resta sulla macchina, fuori da
Agent Canvas, e un timer la trasforma in token:

| Pezzo | Cosa fa |
| --- | --- |
| `~/.ssh/alex-coding-agent.pem` | La chiave privata dell'app: l'unico secret a lunga durata |
| `alex-coding-agent-token.timer` | Un timer utente di systemd che esegue lo script di mint ogni 45 minuti, e una volta un minuto dopo l'avvio |
| Lo script di mint | Firma un JSON Web Token con la chiave, lo scambia con un installation token, lo scrive in un file che solo il proprietario può leggere, e lo mette nel secret `GITHUB_PERSONAL_ACCESS_TOKEN` tramite l'API di Agent Canvas stessa. Nel template, `pnpm agent-canvas --once` fa lo stesso |
| Un drop-in per `canvas.service` | Esegue lo script di mint prima che Agent Canvas parta, imposta `GIT_AUTHOR_*` e `GIT_COMMITTER_*` su `alex-coding-agent[bot]` e il suo indirizzo noreply, e dà ad Agent Canvas un suo `GIT_CONFIG_GLOBAL` e un `gh` che leggono il file del token |

Così le conversazioni interattive usano l'app tramite git e `gh`, e le automazioni tramite il
secret. Il tuo terminale mantiene il tuo login. Sono le variabili d'ambiente del drop-in ad
attribuire i commit all'app: i template delle automazioni scrivono `OpenHands` come autore in ogni
checkout, e il form **Git Settings** di Agent Canvas rifiuta un'email con parentesi quadre, quindi
Discava ha scritto a mano anche il nome e l'indirizzo del bot in `~/.openhands/settings.json`.

Due residui agivano come il maintainer, non come il bot, e sono stati rimossi: un server MCP di
GitHub (`api.githubcopilot.com`) con il token del maintainer, e i vecchi personal access token.

Il collante conta le review dell'app tramite la variabile di repository `AGENT_APP_LOGIN`
(`alex-coding-agent[bot]`): GitHub non dà a un'app alcuna association con il repository, quindi
senza di essa i verdetti del Reviewer non rimanderebbero più indietro il Developer
([#1184](https://github.com/AlexTo/discava/pull/1184)).

## Cosa ha il Tester sulla macchina

Al Developer e al Reviewer servono solo Node, pnpm, git e `gh`. Il Tester usa anche:

| Strumento | Per |
| --- | --- |
| AWS CLI, autenticata sull'account che contiene gli stack `discava-development-*` | Trovare lo stage (output degli stack), ottenere token Cognito, leggere DynamoDB, S3 e i log di CloudWatch. Il suo prompt gli dice di usarla in sola lettura |
| Playwright con Chromium | Pilotare i portali deployati |
| `tmp/screenshots/` del checkout di Discava | Dove vengono salvati i suoi screenshot, una cartella per pull request |

<Aside type="caution">
Questo è l'unico punto in cui un agente in Discava lavora con accesso al cloud. È il motivo per cui
lo stage è `discava-development`, con dati usa e getta, e per cui
[solo i collaboratori possono commentare](../post-merge-verify/#chi-può-commentare) ciò che gli
agenti leggono. Per un team, dai al Tester un suo ruolo in sola
lettura e una sua macchina o VM.
</Aside>

## Le tre automazioni

Le prime due sono state installate dal catalogo delle automazioni di Agent Canvas, non scritte a
mano. La terza è di Discava. Cosa fa ciascuna a ogni polling è in
[Il runtime dell'agente](../../concepts/the-agent-runtime/#le-tre-automazioni), e il prompt che
ciascuna dà al suo agente è in [I prompt degli agenti](../agent-prompts/).

### Developer: GitHub issue to PR

| Campo | Valore |
| --- | --- |
| Template | `github-issue-to-pr` 1.2.4 |
| Repository | `AlexTo/discava` |
| Trigger label | `openhands` |
| Branch prefix | `openhands/issue` → branch `openhands/issue-<n>` |
| Pull request mode | Ready for review |
| GitHub token secret | `GITHUB_PERSONAL_ACCESS_TOKEN` |
| Schedule | `*/2 * * * *`, Australia/Sydney |
| Agent profile | `developer` |

Un turno di revisione dice all'agente di riapplicare dopo la label `openhands-review`, così il nuovo
commit di testa viene revisionato.

### Reviewer: GitHub code review

| Campo | Valore |
| --- | --- |
| Template | `github-pr-reviewer` 1.11.2, con una patch per il token dell'app (sotto) |
| Repository | `alexto/discava` |
| Trigger label | `openhands-review` |
| Requested reviewer | `all-hands-bot` (non usato in pratica: il lavoro lo fa la label) |
| New reviews per scan | 2 |
| Review tone | Concise |
| Maintainers | nessuno |
| Schedule | `*/2 * * * *`, Australia/Sydney |
| Agent profile | `reviewer` |

Il template chiede a `GET /user` come quale account agisce, cosa che GitHub rifiuta a un installation
token con `403 Resource not accessible by integration`, quindi dopo il passaggio all'app ogni
scansione falliva prima di fare la review. La copia di Discava chiede a GraphQL `viewer { login }`
quando `/user` rifiuta, nella ricerca del login del worker e nel suo controllo del token, ed è stata
ricaricata al posto del bundle del catalogo. La 1.11.3 del catalogo ha ancora il problema.

Mentre i check stanno ancora girando, il Reviewer pubblica un commento "⏳ Review waiting on checks"
e riprova a una scansione successiva. Le sue review iniziano con "_This review was posted by an AI
agent (OpenHands)._" e contengono un marcatore nascosto `<!-- openhands-review-run: <id> -->`.

### Tester: GitHub issue tester

Per questa non c'è un template del catalogo. È un worker di circa cento righe, costruito sugli
stessi helper per GitHub e per le conversazioni che usano i template del catalogo, con il suo
prompt in un file accanto.

| Campo | Valore |
| --- | --- |
| Template | nessuno: `worker.py`, `prompt.md` e `config.json`, scritti a mano |
| Repository | `AlexTo/discava` |
| Trigger label | `openhands-test` |
| Issue authors | `github-actions[bot]` |
| Branch prefix | `openhands/test-fix` → branch di correzione `openhands/test-fix-<n>` |
| New tests per scan | 2 |
| Prompt file | `prompt.md` |
| GitHub token secret | `GITHUB_PERSONAL_ACCESS_TOKEN` |
| Schedule | `*/2 * * * *`, Australia/Sydney |
| Agent profile | `tester` |

A ogni polling, il worker:

1. Elenca le issue aperte che hanno `openhands-test`, dal numero più basso.
2. Salta ogni issue non aperta da uno degli **issue authors**. Il corpo di una issue diventa parte
   di ciò che l'agente legge, quindi vengono testate solo le issue del workflow stesso.
3. Trova l'ultimo evento che ha applicato la label. Il numero della issue e l'ID di quell'evento
   formano una sola consegna, quindi un polling successivo della stessa applicazione della label
   viene ignorato, e i commenti del Tester non avviano mai un secondo test. Rimuovere e riapplicare
   la label è un nuovo evento, e quindi un nuovo test.
4. Avvia o riprende la conversazione della issue con il prompt, fino a due nuovi test per polling.

Le issue di cui fa polling vengono aperte da [Post-merge Verify](../post-merge-verify/). I commenti
del Tester terminano con "_This comment was posted by an AI agent (OpenHands)._".

<Aside title="Un'identità per gli agenti">
In Discava il Developer, il Reviewer e il Tester agiscono tutti come `alex-coding-agent[bot]`, e il
maintainer usa il proprio account. Così il maintainer può approvare normalmente la PR di un agente, e
si vede quali commenti vengono da un agente. Il Reviewer e il Developer condividono ancora
quell'identità, e GitHub non permette a nessuno di approvare la propria PR, quindi il verdetto del
Reviewer viene pubblicato come review `COMMENTED`. Il collante legge la riga del verdetto, non lo stato della
review, quindi non è un problema.
</Aside>
