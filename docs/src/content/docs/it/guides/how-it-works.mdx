Questa pagina segue una funzionalità attraverso tutto il loop. Ogni passo indica chi agisce e cosa
lascia dietro di sé.

```d2
grid-rows: 2
grid-columns: 4
horizontal-gap: 140
vertical-gap: 90

# Top row runs left to right, bottom row right to left, so the loop wraps.
spec: "PR della spec\n(tu)" {shape: document}
issues: "Agent Issues\n(GitHub Actions)"
issue: issue {shape: page}
implement: "implementazione\n(OpenHands)"
merge: "merge\n(tu)"
review: "review\n(OpenHands)"
checks: "PR Checks\n(GitHub Actions)"
pr: pull request {shape: page}

spec -> issues: spec-ready
issues -> issue
issue -> implement
implement -> pr
pr -> checks
checks -> review: verde
review -> merge: approvata
merge -> issues: fase successiva
```

## I passi

| # | Chi | Cosa succede | Artefatto |
| --- | --- | --- | --- |
| 1 | 🧑🤖&nbsp;Tu + agente | `/speckit-specify` trasforma un'idea di un paragrafo in una spec. `/speckit-clarify` fa fino a cinque domande e riscrive le tue risposte nella spec | `specs/<timestamp>-<name>/spec.md` |
| 2 | 🧑🤖&nbsp;Tu + agente | `/speckit-plan` decide *come*, e verifica il piano rispetto alla constitution | `plan.md`, `data-model.md`, `contracts/` |
| 3 | 🧑🤖&nbsp;Tu + agente | `/speckit-tasks` scrive una lista ordinata di task, raggruppati in fasi. `/speckit-analyze` confronta tra loro i tre file | `tasks.md` |
| 4 | 🧑&nbsp;**Tu** | Apri la PR della spec, la revisioni come codice, aggiungi la label `spec-ready`, fai il merge | Una PR della spec mergiata. **Gate umano 1** |
| 5 | ⚙️&nbsp;Automazione | Il workflow **Agent Issues** legge `tasks.md` e apre una issue per il primo gruppo di fasi, con la label `openhands` | Una issue di implementazione |
| 6 | 🤖&nbsp;OpenHands | Al polling successivo, l'agente prende la issue, scrive prima i test, implementa, spunta i suoi task e apre una PR su `openhands/issue-<n>` | Una pull request |
| 7 | ⚙️&nbsp;CI | I check della PR eseguono lint, unit test, build, il controllo del formato di `tasks.md`, i test e2e e il controllo degli screenshot | Risultati dei check |
| 8 | ⚙️🤖&nbsp;Automazione + OpenHands | Se un'esecuzione è rossa, **Agent CI Status** segna la PR come fallita. L'agente se ne accorge al polling successivo e rivede la stessa PR | Label da `ci-fix-1` a `ci-fix-5` |
| 9 | 🤖&nbsp;OpenHands | Quando tutti i check sono finiti, l'agente reviewer revisiona il commit di testa e chiude con `✅ APPROVED` o `🔄 CHANGES REQUESTED`. Nel secondo caso **Agent Review Status** rimanda indietro l'agente | Una review, ed eventualmente label `review-fix-N` |
| 10 | 🧑&nbsp;**Tu** | Leggi la descrizione della PR e il commento **E2E screenshots**, svolgi gli eventuali task **(human)** e fai il merge | Una PR mergiata. **Gate umano 2** |
| 11 | ⚙️&nbsp;Automazione | Il merge esegue di nuovo **Agent Issues**. Apre la issue per la fase successiva che ha task degli agenti non spuntati, e i passi da 6 a 10 si ripetono finché non ne restano più | La issue successiva, oppure fine |

## Cosa fai davvero tu

Per ogni funzionalità, scrivi e approvi la spec una volta. Per ogni pull request, fai una review e
clicchi merge. Vieni coinvolto prima solo quando un loop esaurisce i tentativi (`ci-fix-exhausted` o
`review-fix-exhausted`), o quando l'agente commenta che è bloccato. Mentre gli agenti lavorano, puoi
scrivere la spec successiva.

## Dove sta ogni pezzo

| Pezzo | File |
| --- | --- |
| Strumenti per le spec | `.specify/`, le skill `speckit-*`, `specs/` |
| Regole del progetto per ogni esecuzione dell'agente | `.specify/memory/constitution.md`, `AGENTS.md` |
| La issue che riceve l'agente | `.github/ISSUE_TEMPLATE/implement-phase.md` |
| Dalla spec alla issue | `.github/workflows/agent-issues.yml` |
| Dalla spec finita a `specs/_archive/` | `.github/workflows/archive-specs.yml` |
| Dalla CI all'agente | `.github/workflows/agent-ci.yml` |
| Dal reviewer all'agente | `.github/workflows/agent-review.yml` |
| Check | `.github/workflows/pr-checks.yml`, `ui-screenshots.yml`, `ci.yml` |
| Le regole dietro il collante, con unit test | `packages/common/scripts/src/agent-*`, `ui-screenshots/` |
| Il runtime dell'agente | OpenHands Agent Canvas, fuori dal repository |

I dettagli sono nei Concetti: [come le fasi diventano issue](../../concepts/one-phase-at-a-time/), e
[come un fallimento rimanda indietro l'agente](../../concepts/feedback-loops/).
