## La catena non parte o non prosegue

| Sintomo | Cosa sta succedendo | Cosa fare |
| --- | --- | --- |
| PR della spec unita, nessuna issue | La PR non aveva l'label `spec-ready` quando è stata unita | Aggiungi `spec-ready` alla PR unita. Agent Issues gira anche su `labeled` |
| Agent Issues ha girato: `No issue created: it is not an agent branch and has no "spec-ready" label` | Come sopra, oppure la PR era di una persona, che per scelta viene ignorata | Come sopra, oppure esegui Agent Issues a mano con la cartella della spec |
| Agent Issues è fallito: `tasks.md is not in the format the workflow reads` | Il check del formato è stato saltato o ignorato sulla PR della spec | Correggi `tasks.md` in una PR, poi esegui Agent Issues a mano |
| Un commento: "the next implementation issue … was not opened: an issue for … already exists" | La issue della fase esiste, ma alcuni task dell'agente in essa non sono spuntati | Spuntali se sono fatti, o completali. Poi esegui Agent Issues a mano |
| Agent Issues ha registrato `no spec folder with a tasks.md was found` | La issue della PR dell'agente unita non ha un marcatore, e la PR non ha modificato nessun file in `specs/` | Esegui Agent Issues a mano con la cartella della spec |
| L'ultima fase è stata unita e non si è aperto nulla | È corretto. Restano solo task **(human)** o nessuno | Fatto |

## L'agente non prende in carico o non rivede

| Sintomo | Cosa sta succedendo | Cosa fare |
| --- | --- | --- |
| Issue con label mai presa in carico | Agent Canvas è fermo, l'automazione è disattivata, o il token non può leggere il repository | Verifica che `agent-canvas` sia in esecuzione e che l'automazione sia attiva. Controlla il log dell'ultima esecuzione dell'automazione |
| La PR è rossa, `ci-fix-1` aggiunta, l'agente non rivede mai | Il worker rivede solo esattamente `openhands/issue-<n>` (i workflow di correzione mettono la label anche ad altri branch `openhands/`), oppure la issue è stata chiusa | Controlla il nome del branch. Riapri la issue, o prendi in carico tu la PR |
| Nessuna label `ci-fix-*` dopo un'esecuzione rossa | Agent CI Status non ha girato, o l'ha ignorata (vedi il suo avviso) | Apri l'esecuzione di Agent CI Status e leggi l'avviso, ad es. `the pull request has a newer commit than this run` |
| L'agente rivede, poi nessuno fa la review del nuovo head | L'agente non ha riapplicato `openhands-review` | Riapplicala a mano |
| Push rifiutato: `refusing to allow a GitHub App to create or update workflow` | All'app manca il permesso di scrittura **Workflows**, e il branch tocca `.github/workflows/` (spesso tramite un merge di `main`) | Concedilo nelle impostazioni dell'app, e accetta il nuovo permesso sull'installazione. Il poll successivo riprova. Con un personal access token il messaggio nomina quello, e al token serve lo scope `workflow` |
| Ogni automazione fallisce: `The GitHub credential GITHUB_PERSONAL_ACCESS_TOKEN is unavailable`, oppure `401 Bad credentials` | Il secret manca, oppure contiene un token dell'app vecchio di più di un'ora | Verifica che `scripts/agent-app-token.sh` giri ancora ogni 45 minuti e che la sua ultima esecuzione abbia aggiornato il secret |
| `ci-fix-exhausted` | Cinque correzioni non sono arrivate a una soluzione | Leggi l'ultimo fallimento. Di solito la spec o il plan sono ambigui. Correggili, rimuovi le label, riesegui |

## Review

| Sintomo | Cosa sta succedendo | Cosa fare |
| --- | --- | --- |
| "⏳ Review waiting on checks" e nessuna review | Un check sull'head non è terminato, o è bloccato in coda | Trova il check in sospeso. Un check obbligatorio che non gira mai blocca la review per sempre |
| La review dice `🔄 CHANGES REQUESTED`, nessuna label `review-fix-*` | Alla review manca il marcatore dell'esecuzione, non viene da un account con accesso in scrittura né dall'app indicata in `AGENT_APP_LOGIN`, o la PR è andata avanti | Leggi l'avviso di Agent Review Status. Se dice che la review non viene da un maintainer o dall'app dell'agente, imposta la variabile di repository `AGENT_APP_LOGIN` al login del bot dell'app |
| Ogni scansione di code review fallisce con `HTTP Error 403: Forbidden` | Il template `github-pr-reviewer` chiede a `GET /user` chi è, e GitHub lì rifiuta l'installation token di un'app (`Resource not accessible by integration`) | Applica una patch al bundle: dove il worker legge il suo login da `GET /user` (`github_login` in `worker.py`, il controllo del token in `main.py`), in caso di 403 ripiega su GraphQL `{ viewer { login } }`, che restituisce `<app-name>[bot]`. Carica il bundle modificato con l'API delle automazioni (`POST /api/automation/v1/uploads`, poi `PATCH /api/automation/v1/<id>` con il suo `tarball_path`) |
| Le review compaiono come "Commented", non "Approved" | Il Reviewer pubblica con la stessa identità che ha aperto la PR, e GitHub non permette l'auto-approvazione | Previsto: il Developer e il Reviewer condividono la GitHub App degli agenti. Il collante legge la riga del verdetto, non lo stato della review |

## Check

| Sintomo | Cosa sta succedendo | Cosa fare |
| --- | --- | --- |
| `UI Screenshots` fallisce su un refactoring | La regola non sa distinguere una modifica visibile da una invisibile | Un maintainer aggiunge `no-ui-screenshots` e riesegue il check |
| Il job e2e di ogni PR scarica Chromium | La cache viene salvata solo su `main` | Mantieni il job `playwright-cache` della CI, con la stessa chiave di PR Checks |
| `Check for mutations` fallisce su `main` | Qualcosa ha generato file che la PR non ha committato | Esegui `pnpm build` in locale e fai il commit delle differenze |
| `Resource not accessible by integration` quando si mettono label | Il token del workflow può scrivere le issue ma non le pull request | Aggiungi `pull-requests: write` al workflow |

## Test post-merge

| Sintomo | Cosa sta succedendo | Cosa fare |
| --- | --- | --- |
| È stato fatto il deploy di una PR, nessuna issue di test | Non ha cambiato nulla che venga deployato (solo docs, spec, test, tooling o CI), ha la label `skip-deploy-test`, oppure l'esecuzione di Deploy non ha rilasciato nulla perché il suo commit non era più l'ultimo di `main` | Leggi gli avvisi dell'esecuzione di Post-merge Verify. Per testarla comunque, esegui il workflow a mano con il numero della PR |
| Issue di test aperta, il Tester non la prende mai in carico | La issue non ha la label `openhands-test` perché non è stato possibile mettere il lock a qualcosa a cui rimanda, oppure è stata aperta da un account di cui l'automazione non si fida | L'esecuzione di Post-merge Verify fallisce e indica a cosa mettere il lock. Metti il lock, poi aggiungi la label a mano |
| Il Tester ha fatto il report, e vuoi un'altra esecuzione | Ogni applicazione della label viene testata una volta | Rimuovi e riapplica `openhands-test` |
| Il report dice "blocked" | Allo stage manca qualcosa che serve alla modifica, come un account di pagamento collegato | Sistema lo stage, poi riapplica la label |
| Il commento **E2E screenshots** manca su una PR | La PR ha il lock, e GitHub rifiuta al token di Actions un commento su una conversazione con il lock | Leggi la lista nel summary del job `E2E screenshots`, oppure togli il lock alla PR |
| L'agente Reviewer non pubblica mai una review, e la PR ha il lock | GitHub rifiuta una review nativa su una pull request con il lock, anche da un account con accesso in scrittura | Togli il lock. Per tenere fuori gli estranei, usa il limite di interazione del repository invece di mettere il lock alle pull request |
