**このステップで得られるもの:** `main` への push ごとの Trivy スキャン、グリーンになった `main` を毎回
開発ステージに出荷する Deploy workflow、人を待つ本番デプロイ、そして必要であれば、マージされた変更を毎回
開発ステージでテストするテスト担当エージェント。

このリポジトリは workflow をオフの状態で同梱しています。`deploy.yml` は手動で実行したときか、
`AUTO_DEPLOY_STAGE` を設定したときだけ実行され、`post-merge-verify.yml` はデプロイの後にだけ実行されます。
ノートアプリにはクラウドインフラがないので、書くべき部分はあなたのものです。手順は Discava と同じく AWS と CDK を
前提にしていますが、全体の形はどのクラウドでも使えます。

<Steps>

1. スキャンしたいプロジェクトに **`trivy` ターゲットを追加します**（ルートの `pnpm trivy` は
   `nx run-many --target trivy --all` を実行します）。コピーした `ci.yml` の `trivy` ジョブが、`main` への push のたびに
   `build` とは別のジョブとしてこれを実行するので、新たに公開された CVE が他を何もブロックせずに `main` にフラグを立てます。
   受け入れた検出結果は、1 行に 1 つの ID で `.trivyignore` に記録します。

2. `packages/infra` に CDK アプリとして **インフラを追加します**。その `src/main.ts` に、environment ごとに
   1 つのステージを置きます。

   ```bash
   pnpm nx g @aws/nx-plugin:ts#infra --name=infra
   ```

   その `deploy-ci` ターゲットが、Deploy workflow が実行するものです。ノートのウェブサイト用の construct は
   すでに `packages/common/constructs` にあります。

3. ステージごとに **キーレスのクラウドアクセスを設定します**。GitHub OIDC プロバイダー、
   `repo:owner/repo:environment:<stage>` に対してのみ信頼されるデプロイロール、permissions boundary 付きの
   CloudFormation 実行ロール、CDK の bootstrap、そしてステージ名を付けた GitHub environment と、その変数
   `AWS_REGION`、`AWS_DEPLOY_ROLE_ARN`、`AWS_EXECUTION_ROLE_ARN` です。Discava の
   [`scripts/setup-stage.sh`](https://github.com/AlexTo/discava/blob/main/scripts/setup-stage.sh)
   は自分のステージに対してこれをすべて行います。流用する前に読んでください。アクセスキーは保存しないでください。

4. fork で作業していない場合は、**`.github/workflows/deploy.yml` をコピーし**、その `@agentic-sdlc/` スコープと
   デフォルトのステージ名を変更します。この workflow は CI が検証したコミットをチェックアウトし、`packages/infra` や
   environment の変数が足りなければ明確なエラーで早めに止まり、Trivy を実行し、synth し、そのコミットがまだ `main` の
   最新である場合にだけデプロイします。この最新かどうかのチェックはジョブの concurrency のスロットの *内側* にあるので、
   実行が別の実行の後ろで待っていた場合でも、デプロイ直前の `main` を反映します。

5. 開発ステージの **自動デプロイをオンにします**。**Settings → Secrets and
   variables → Actions → Variables** で、リポジトリ変数 `AUTO_DEPLOY_STAGE` を開発ステージの名前で追加します。

6. **本番を保護します。** **Settings → Environments** で本番ステージの environment を開き、
   **Required reviewers** を追加します。本番にデプロイするには、**Actions → Deploy → Run
   workflow** を開いて本番ステージを入力します。するとジョブは承認を待ちます。

7. デプロイされた変更を毎回テストしたい場合は、**テスト担当エージェントを追加します**（ギャップ 11）。このリポジトリから、
   そのグルー（ステップ 5 の `post-merge-test/`）、issue テンプレート（ステップ 4）、そして
   `.github/workflows/post-merge-verify.yml` がすでに手元にあります。この workflow は、Deploy の実行がテストステージに
   載せた pull request ごとにテスト issue を開きます。テストは `TEST_STAGE` 上で行われます。これはリポジトリ変数で、
   デフォルトは `AUTO_DEPLOY_STAGE` です。

   OpenHands 側では、`tester` エージェントプロファイルと、`openhands-test` ラベルの付いた issue を
   ポーリングする automation を追加します。これにはカタログのテンプレートがありません。Discava のワーカーとそのプロンプトは
   [OpenHands のセットアップ](../../discava/openhands-setup/#テスト担当-github-issue-tester) と
   [エージェントのプロンプト](../../discava/agent-prompts/#テスト担当) で説明しています。テスト担当には次を与えます:

   - 開発アカウントにサインインしたクラウドの CLI。アクセス権はテストに必要な最小限にします
   - アプリのロールごとに 1 人のテストユーザー。OpenHands のシークレットとして保存します
   - 操作できるブラウザ。たとえば Chromium 付きの Playwright

   <Aside type="caution" title="公開リポジトリですか? 先にコメントをコラボレーターに限定する">
   テスト担当は、これらの認証情報を持ったまま issue、pull request、そのコメントを読みます。リポジトリが
   公開されている場合、見知らぬ人のコメントがテスト担当への指示を運ぶ可能性があります。
   `scripts/setup-repository.sh` はやり取りをコラボレーターに限定しますが、期間は最長 6 か月なので、
   制限が切れる前にもう一度実行してください。また、`helpers/conversation-lock.ts` のロックを維持し、「どうテストするか」は issue ではなく
   automation 自身のプロンプトに置き、データが重要なステージには決して向けないでください。
   </Aside>

</Steps>

## 動作を確認する

何か PR をマージします。CI が実行され、続いて **Deploy** が開発ステージで自動的に始まります。古いコミットで
CI を手動でもう一度実行すると、Deploy は `Skipping deploy: no longer main's latest commit` とログに出し、
何も出荷しません。

テスト担当を設定している場合: そのデプロイの後、**Post-merge Verify** が `test(post-merge): verify #<pr> …` という
タイトルで、`openhands-test` ラベルの付いた、ロックされた issue を開きます。1 回のポーリング以内にテスト担当が始まり、
そのレポートが issue へのコメントとして現れます。

<Aside type="note">
どのエージェントもデプロイすることはなく、これらのロールを目にすることもありません。開発担当とレビュー担当に必要なのは GitHub の
トークンだけです。テスト担当の開発アカウントへのアクセスは、デプロイロールとは別のものです。デプロイロールを引き受けるのは、
`main` から、そのステージの environment で実行される workflow だけです。
</Aside>
