この workflow をいちばん手早く使い始める方法は、[このリポジトリを fork する](../../setup/fork/)ことです。この
セクションは、それができない場合のためのものです。既存のプロダクトリポジトリがあり、そこに同じセットアップを入れたい場合です。

各ステップでは、このリポジトリからコピーした要素を 1 つずつ追加し、その確認方法を説明します。すべて
終えると、あなたのリポジトリには fork と同じものがそろい、そこから
[2. リポジトリを設定する](../../setup/github-repository/)に進めます。

<Aside type="tip">
それでも、まずこのリポジトリを fork して、notes アプリで[最初の機能](../../setup/first-feature/)を
実行してみてください。ループ全体が一度動くのを見ておくと、ここでの各ステップがずっと理解しやすくなります。
</Aside>

## 最初に決めておくこと

| 決めること | デフォルト | 変更するのは |
| --- | --- | --- |
| 実装のトリガーラベル | `openhands` | そのラベルをすでに使っている場合 |
| ブランチのプレフィックス | `openhands/issue` | まれです。グルーは `openhands/issue-<n>` に厳密に一致させます。変更する場合は、`AGENT_BRANCH` と workflow の条件も変更してください |
| レビューラベル | `openhands-review` | 上と同じ |
| ポーリング間隔 | 5 分ごと | コストを下げたく、長く待ってもよい場合（カタログのデフォルトは 15） |
| 修正の試行の上限 | ループごとに 5 回 | まれです。2 つの `plan.ts` ファイルにある `MAX_*_FIX_ATTEMPTS` です |
| spec フォルダの番号付け | タイムスタンプ | spec を書く人が 2 人以上いるなら、決して変更しない |

すべてのコマンドとコピーしたファイルで、`@your-scope` や `@agentic-sdlc` を自分のワークスペースの
npm スコープに置き換えてください。
