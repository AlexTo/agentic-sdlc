人はループから外されるわけではありません。判断が最も重要な 2 つの地点に移され、その間の待ち時間や入力作業からは離されます。

## ゲート 1: spec を承認する

spec PR はコードと同じようにレビューされます。**`spec-ready` ラベル付きで**マージすることだけが、実装を開始させます。

確認すること:

- `spec.md` は本当に望んでいることを述べていて、すべてのルールが要件として書かれているか?
- 各フェーズは、一度に座ってレビューできるほど小さいか?
- `plan.md` に、コードレビューなら却下するようなものはないか?

### これが今の主なボトルネック

ループが自動で回るようになると、コードレビューは小さくなります。フェーズごとに、green でエージェントが承認した PR が 1 つです。
最も遅い人間のステップはここです。どの機能も、誰かが spec は正しいと同意するまでここで待ちます。

待つ相手が開発者である必要はありません。`spec.md` は平易な言葉 (ユーザーストーリー、受け入れシナリオ、機能要件) で書かれているので、
**ビジネスアナリスト**や**プロダクトオーナー**が spec PR 上でレビューし、コメントし、承認できます。レビューはファイルごとに分けましょう。

| レビュアー | 読むもの | 問うこと |
| --- | --- | --- |
| プロダクトオーナー、ビジネスアナリスト | `spec.md` | これは私たちが望む機能か? ルールとエッジケースは正しいか? 足りないものはないか? |
| エンジニア | `plan.md`、`data-model.md`、`contracts/`、`tasks.md` | 設計は健全か? フェーズはレビューできるほど小さいか? |

リポジトリを読める人なら誰でもコメントできます。その人の承認をブランチ保護の条件に含めるには、書き込み権限が必要です。

## ゲート 2: 結果を承認する

各エージェントの PR は、CI が green になり、レビュー担当エージェントが承認した後にあなたのところに届きます。あなたの仕事は結果を判断することで、
問題を探し回ることではありません。

- PR の説明を読みます。何が変わったか、どのタスクか、どの **(human)** タスクがあなたに残されているか。
- ブランチを pull する代わりに、**E2E screenshots** コメントを見ます。機能が動いている様子が示されています。例は
  [検証が最も重要](../layers-of-trust/#検証が最も重要)を参照してください。
- **(human)** タスクを行います。ローカルスタックやデプロイ済みのステージでの手動チェックです。
- マージするか、変更を依頼します。変更をエージェントに行わせるには、レビューの後に `openhands-review` ラベルを付けます。
  レビュー担当エージェントが PR を再レビューし、その "changes requested" の判定によって、実装担当エージェントがレビュー修正ループに
  差し戻されます。回数は同じ `review-fix-*` ラベルで数えられます。

## エージェントが決してしてはいけないこと

| 禁止事項 | 強制するもの |
| --- | --- |
| マージする、または `main` に push する | 承認レビューを必須にするブランチ保護。エージェントのトークンは自分のブランチにしか使われない |
| `.github/workflows/` を編集する | constitution と issue の指示。レビュアーと人間のレビューが見つける。グルーのワークフローはデフォルトブランチのコードを実行するので、PR 内で編集されたワークフローはそれらを変えられない |
| テストを通すためにテストを弱める | constitution ("tests are a specification")、issue の指示、レビュー担当エージェント |
| クラウドの認証情報に触れる | 会話にはそれらが一切渡されない。デプロイは GitHub environment の短期間有効な OIDC ロールを使う |
| タスク範囲の外で作業する | issue が範囲を指定する。エージェントのタスクがすべてチェックされるまで次の issue は開かない |
| 永遠に再試行する | ループごとに 5 回まで、ラベルで数える |

## 早い段階で呼ばれるとき

| シグナル | 何が起きたか | 何をするか |
| --- | --- | --- |
| `ci-fix-exhausted` | 自動修正の後も CI が 5 回失敗した | 最後の失敗を読む。ガイダンスをコメントするか、自分で直すか、spec を直す。その後 [ループをリセットする](../../reference/labels/#ループをリセットする) |
| `review-fix-exhausted` | 5 ラウンド後もレビュアーが変更を求めている | レビュアーが正しいかどうかを判断する。spec が曖昧なことが多い |
| エージェントからの issue へのコメント | 指示どおり、ブロックされて止まった | それに答えてから、`openhands` ラベルを外して付け直す |
| マージされた PR へのコメント: "the next implementation issue … was not opened" | フェーズのタスクがすべてはチェックされていない | タスクにチェックを入れるか終わらせてから、その spec フォルダについて Agent Issues を手動で実行する |

## 本番環境は 3 つ目の、任意のゲート

開発ステージへのデプロイは、`main` が green になるたびに自動で行えます。本番環境へのデプロイは、GitHub environment の
必須レビュアーを使って、人を待つべきです。[デプロイとセキュリティ](../../discava/deploy-and-security/)を参照してください。
