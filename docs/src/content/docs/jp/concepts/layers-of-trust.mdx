自動化に価値があるのは、出てきたものを信頼できる場合だけです。すべての変更はチェックの層を通ります。安価で自動のチェックが先に実行されて
大半を見つけ、それらが判断できないものだけが人に届きます。

<p>
  <img alt="5 つの層からなる逆三角形。広いものから狭いものへ: コードベース、静的解析、検証、文章、人間のレビュー" src="/agentic-sdlc/diagrams/automation-trust.svg" width="640" />
</p>

| レベル | 層 | 何を見つけるか |
| --- | --- | --- |
| **コードベース** | ユニットテスト | 間違ったビジネスロジックと壊れたルール |
| | invariant | 複数のレコードにまたがるルールを破るデータ。e2e テストのたびにチェックされる |
| | 並行性テスト | 2 つのリクエストが同時に来たときの競合状態 |
| **静的解析** | lint、型チェック、ビルド | スタイル、型、ビルドのエラー |
| | Tasks format チェック | チェーンを黙って止めてしまう、形式の崩れた `tasks.md` |
| | 生成ファイルのチェック | エージェントがコミットし忘れた lint やビルドの出力 |
| **検証** | E2E テスト | 壊れたユーザーフロー。ローカルスタックに対して実際のブラウザで確認する |
| | スクリーンショット | 誰も見ていない UI の変更 |
| **文章** | constitution、`AGENTS.md`、スキル | エージェントが書く*前に*読むガイダンス。慣習は見つけて直すのではなく、守られるようになる |
| | エージェントのレビュアー | どのテストもカバーしていない問題。コードレビューのように読む |
| **人間のレビュー** | 最終レビュー | 上の層が判断できないもの。マージするのは常に人 |

## 検証が最も重要

ユニットテスト、lint、型が示すのは、コードがそれ自体と矛盾していないことです。機能が*動く*こと、つまりユーザーが見るとおりに、実際のスタックに対して
動くことを示せるのは、e2e テストとスクリーンショットだけです。これが
[原則 1](../principles/#1-検証が最優先-エージェントに手と目を与える)です。また、人が最も速く確認できる層でもあります。スクリーンショットがあれば、
ブランチを pull せずに数分で PR を判断できます。

CI はこれをデフォルトにしています。

1. UI のフローのすべての e2e シナリオは、レビュアーが見たいと思う各状態で `screenshot(page, 'name')` を呼びます。
2. CI は PR に **E2E screenshots** コメントを投稿し、その PR が追加したスクリーンショットを (すでにあったものとは分けて) 列挙し、
   実行のアーティファクトにリンクします。
3. `UI Screenshots` チェックは、UI の変更がスクリーンショットなしで出荷されると失敗します。

Discava の [#486](https://github.com/AlexTo/discava/pull/486#issuecomment-6980411897)、通知設定の例です。

レビュアーは 9 枚の新しいスクリーンショットを開き、各状態を確認します。すべての種類が並んだ設定、保存されたスイッチ、停止されてから再開されたメール、
有効な配信停止リンクと無効な配信停止リンク、エラーと「再試行」。どれも spec の要件であり、それが動いているのを目で確かめられます。

## 文章は導き、コードは強制する

文章 (constitution、`AGENTS.md`、issue の指示) は書くのが安く、ほとんどのミスを防ぎますが、エージェントは読み違えたり読み飛ばしたりすることがあります。
そのため、重要なルールにはすべて、失敗するチェックも用意します。[原則 5](../principles/#5-ルールとスキルを決定的にする) に Discava のものが並んでいます。

ルールを追加するときは、こう問いかけてください。エージェントがこれを無視したら、何が赤になるのか?

## テストは spec である

Discava の constitution で最も重要なルールです。

> A failing test MUST be resolved by fixing the code, unless the spec or plan changes the behavior
> it covers. Weakening an existing test (loosening an assertion, deleting a case, adding `skip` or
> `only`, widening a mock or snapshot) is allowed only when a task names the behavior change that
> justifies it, and the PR description says so.

CI を green にするよう迫られたエージェントは、遅かれ早かれテストを「直す」ようになります。issue テンプレートでも繰り返され、レビュー担当エージェントが
チェックするこのルールこそが、テストスイートに意味を持たせ続けています。

## invariant: データのためのテスト

ユニットテストは 1 つの関数をチェックします。E2E テストは 1 つのフローをチェックします。異なる PR で異なるエージェントの実行によって書かれた 2 つの機能が、
両方にまたがるルールを破る状態をデータベースに残しても、どちらも気づきません。invariant はそのギャップを埋めます。invariant はすべてのデータに対する
チェックのリストで、たとえば「コースの評価数は、表示されているレビューの数と等しい」といったものです。これを**すべての** e2e テストの後に実行します。
invariant が破られると、その原因となったテストが失敗します。

<Aside type="tip">
invariant は、エージェントが書くコードが増えるほど効果が大きくなる層です。2 つのエージェントがそれぞれ局所的には正しいことから生じるミスを見つけます。
</Aside>
