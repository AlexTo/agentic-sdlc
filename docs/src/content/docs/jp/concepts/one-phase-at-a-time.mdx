**要約:** spec はエージェントに一度にまとめて渡されるわけではありません。`tasks.md` はフェーズに分かれていて、エージェントは
**issue ごとに 1 つのフェーズのグループ**を受け取ります。各 issue は 1 つの pull request になります。その pull request がマージされると、
エージェントのタスクが残らなくなるまで、次の issue が自動で開きます。

```d2
direction: right

spec: spec PR {shape: document}
i1: "issue 1\nセットアップから最初のストーリーまで" {shape: page}
p1: PR 1
i2: "issue 2\n次のフェーズ" {shape: page}
p2: PR 2
i3: "issue 3\n最後のフェーズ" {shape: page}
p3: PR 3
done: 何も開かない

spec -> i1: マージ
i1 -> p1
p1 -> i2: マージ
i2 -> p2
p2 -> i3: マージ
i3 -> p3
p3 -> done: マージ
```

## なぜ spec 全体を一度にやらないのか?

- **レビューが可能なままになる。** 機能全体を 1 つの PR にすると、誰もきちんと読まない数千行になります。
  1 つのフェーズなら、一度に座ってレビューできる PR になります。
- **各ステップがマージ済みのコードの上に積み上がる。** フェーズ 3 は、レビューとテストを経たフェーズ 1 と 2 がすでに入った `main` から始まり、
  エージェント自身のレビューされていない作業から始まるのではありません。
- **ミスが小さく収まる。** フェーズがうまくいかなければ、捨てるのは機能ではなく 1 つの PR です。
- **エージェントのコンテキストが絞られたままになる。** 1 つのフェーズは、エージェントが最初のテストから最後のコミットまで頭に入れておける範囲です。

## フェーズのグループ分け

`tasks.md` は `/speckit-tasks` によってフェーズごとに書かれます。通常はセットアップ、基盤、ユーザーストーリーごとに 1 フェーズ、
そして仕上げです。Agent Issues ワークフローはそれらを次のようにグループ化します。

| グループ | フェーズ | 理由 |
| --- | --- | --- |
| 0 | **最初の** `User Story` フェーズまで (そのフェーズを含む) のすべて | セットアップと基盤だけでは、誰も試せるものを届けられない。MVP のストーリーと一緒に出荷すれば、最初の PR が動くスライスになる |
| 1, 2, … | 以降の各フェーズを単独で | 1 フェーズ、1 issue、1 PR |

issue にはタスクの範囲が書かれ ("Tasks `T015` to `T019` … Do not start tasks outside these
phases")、エージェントは各タスクを終えるたびに `tasks.md` でチェックを入れます。

## 次の issue を開くもの

Agent Issues は pull request が `main` にマージされたときに実行され、2 種類のマージにだけ反応します。

1. **`spec-ready` ラベル付きの spec PR。** グループ 0 を開きます。
2. **エージェントのブランチ (`openhands/…`) からの PR。** マージによって更新されたばかりの `tasks.md` を読み、**(human)** ではない
   未チェックのタスクを持つ最初のグループを見つけて、その issue を開きます。

それ以外のマージは、`specs/` を編集するものであっても無視されます。エージェント自身の PR は `tasks.md` を変更するので、
「`specs/**` が変わったら実行する」といったルールでは自分自身をトリガーしてしまいます。

## チェーンを止めるもの

| 状況 | 何が起きるか |
| --- | --- |
| エージェントのタスクがすべてチェック済み | 何も開かない。機能は完了。**(human)** タスクはレビュアーに残される |
| マージされた PR がタスクをすべてチェックしていない | そのグループの次の issue はすでに存在するので、重複は開かない。マージされた PR に、未チェックのタスク ID を列挙したコメントが付く |
| `tasks.md` が想定した形式ではない | エージェントに間違ったタスクを渡す代わりに、実行が失敗する。通常は Tasks format の PR チェックがもっと早い段階でこれを止める |
| spec PR が `spec-ready` なしでマージされた | 何も開かない。マージされた PR にラベルを付ければ始まる |

止まったチェーンを再開するには、`tasks.md` を直し (タスクにチェックを入れるか、タスクを終わらせる)、spec のフォルダ名を指定して
**Agent Issues** を手動で実行します。

## 多くの機能を同時に

チェーンは 1 つの spec の**中では**順番に進みます。異なる spec は互いに独立しています。それぞれが自分のチェーンを持ち、エージェントは
それらの開いている issue すべてに取り組みます。スループットはここから生まれます。

<Aside type="tip">
spec を途中で変えるのは普通のことです。`spec.md` と `plan.md` を更新し、次の未使用の ID で新しいタスクを `tasks.md` に追加して、
マージします。次にエージェントの PR がマージされたとき、それらは他のタスクと同じように拾われます。
</Aside>

1 つの機能に 6 つの issue がある実例は、[実際の機能: コースレビュー](../../discava/a-real-feature/)にあります。正確な形式のルールは
[リファレンス: tasks.md の形式](../../reference/tasks-format/)にあります。
