このワークフローのすべては、1 つの動きから導かれます。**開発者をループの中から外し、ループの両端に置くこと。**
人は*何を*作るか、そして*それが良いかどうか*を決めます。その間のすべてを、エージェントが通常の GitHub のプロセスを通じて行います。

原則は重要な順に並んでいます。いくつかしかできないなら、上から始めてください。

## 1. 検証が最優先: エージェントに手と目を与える<Icon name="magnifier" class="heading-icon" />

アプリを動かして自分が作ったものを見られないエージェントは推測しているだけで、他のすべての原則はその推測を整理するにすぎません。
コンパイルが通り、ユニットテストに合格したコードでも、ユーザーにとっては失敗していることがあります。そのため、エージェントは
人と同じように、**作ったものをバックエンドからフロントエンドまで動かす**必要があります。

- **手:** クラウドアカウントなしでローカルスタック上にアプリ全体を起動し、API を呼び、サインインし、実際のブラウザでフローを
  クリックして進み、その裏にあるバックグラウンド処理を起動します。
- **目:** 返ってきたものを読みます。レスポンス、ログ、データベースに残ったデータ、そしてレビュアーが見たいと思うすべての状態の
  スクリーンショットです。

エージェントはこれを自分のマシンで行うわけではありません。エージェントが e2e シナリオを書き、CI がすべての PR で、新しいローカルスタックに対して
それを実行します。結果、invariant の失敗、スクリーンショットが PR に戻ってくるので、エージェントは自分のミスに気づき、
すべての PR が証拠付きで届きます。

初日からこれに備えて作りましょう。すべてのクラウドサービスにはローカルの代替が、すべてのユーザーフローには e2e シナリオが、
すべての UI の状態にはスクリーンショットが必要です。エージェントが動かせないものは、人が検証しなければならないタスクになります。

## 2. spec が信頼できる唯一の情報源<Icon name="document" class="heading-icon" />

機能は `spec.md`、`plan.md`、`tasks.md` から始まり、コードと同じようにレビューされます。エージェントはそれらをもとに実装します。
振る舞いを変えるには、spec を変更し、plan とタスクを再生成します。コードを手で修正して spec を古いまま放置してはいけません。

## 3. フィードバックを返すのはあなたではなく自動のゲート<Icon name="approve-check-circle" class="heading-icon" />

lint、型チェック、ユニットテスト、invariant、e2e テスト、並行性テスト、スクリーンショット、エージェントのレビュアーが、
すべての PR で実行されます。赤い結果は、その変更を書いたエージェントにそのまま戻ります。誰もエラーメッセージを貼り付けません。

## 4. 重要な 2 つの判断は人が持つ<Icon name="star" class="heading-icon" />

1. **spec を承認する。** `spec-ready` ラベル付きで spec PR をマージすることが、開始の合図です。
2. **結果を承認する。** 人が最終レビューを行い、各 PR をマージします。

## 5. ルールとスキルを決定的にする<Icon name="setting" class="heading-icon" />

`AGENTS.md` や constitution に書いただけのルールは、お願いにすぎません。エージェントは見落とすかもしれないし、2 通りに解釈するかもしれないし、
長いセッションの中で忘れるかもしれません。スクリプトでルールをチェックできるところでは必ずスクリプトを書き、hook や PR チェックで実行し、
文章は説明として残しましょう。チェックが失敗すると、他の赤い結果と同じフィードバックループを通じて、何がどこで間違っているかが
エージェントに正確に伝わります。

Discava は随所でこれを行っています。

| 文章で書かれたルール | それを強制するもの |
| --- | --- |
| `tasks.md` は決まった形式に従う | `Tasks format` PR チェック。これがないと、形式の崩れたフェーズは黙ってスキップされる |
| UI の変更では e2e シナリオでスクリーンショットを撮る | `UI Screenshots` チェックは、マークアップやスタイルが変わったのに `screenshot(` 呼び出しが増えたシナリオがない場合に失敗する。メンテナーは `no-ui-screenshots` で免除できる |
| 複数のレコードにまたがるルールには invariant が必要 | `Invariant coverage` チェックは、コアテーブルへの書き込み元を変えながら `helpers/invariants/` の invariant チェックに触れていない PR を失敗させる。pre-push hook が書き込み元のマップを最新に保つ。メンテナーは `no-new-invariant` で免除できる |
| Conventional Commits、シークレットをコミットしない | `commit-msg` hook の commitlint、すべてのコミットでの `git-secrets` |
| Speckit の各ステップはそれぞれのブランチとコミットを持つ | エージェントが覚えているかどうかに関係なく、スキルが Speckit の extension hook からそのためのスクリプトを実行する |

レビューで同じ指摘を 2 回書いたなら、それはおそらくチェックが欠けています。

## 6. グルーはプロンプトではなくコード<Icon name="puzzle" class="heading-icon" />

同じことがステップの間にも当てはまります。*次に何が起きるか*を決めるもの (どの issue を開くか、エージェントを差し戻すかどうか、
いつ止めるか) はすべて、ユニットテスト付きのスクリプトで、ワークフローから実行されます。エージェントに頼むのは、判断が必要なことだけです。
つまりコードを書くことと、それをレビューすることです。プロンプトは無視されることがあります。ワークフローは無視されません。

## 7. 制限された自律性<Icon name="padlock" class="heading-icon" />

エージェントはマージできず、ワークフローを編集できず、クラウドの認証情報に触れられず、green にするためにテストを弱めることもできません。
各修正ループは 5 回までに制限されています。それを超えると止まり、人に判断を求めます。

## 8. 小さく範囲を絞った作業単位<Icon name="list-format" class="heading-icon" />

spec はフェーズに分かれます。フェーズのグループごとに 1 つの issue と 1 つの pull request があり、エージェントが外れてはいけない
タスク範囲が決まっています。小さな PR はレビューしやすく、捨てるのも簡単です。

## 9. すべてのステップが成果物を残す<Icon name="notes" class="heading-icon" />

意図は spec に、範囲は issue に、履歴は pull request に、そして実行が止まった理由はラベルやコメントに残ります。チャットウィンドウや
誰かの頭の中にしかないものは何もありません。そのため、新しいチームメイトや新しいエージェントが、前の人が止まったところから引き継げます。
