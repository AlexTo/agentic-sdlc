**要約:** OpenHands は、リポジトリに対して 3 つのスケジュール実行の automation を、エージェントの役割ごとに 1 つずつ動かします。
**開発担当 (Developer)** はラベル付きの issue を実装し、失敗とマークされた pull request を修正します。**レビュー担当 (Reviewer)** は、
チェックが終わった pull request をレビューします。**テスト担当 (Tester)** は、マージされた変更を毎回、デプロイされた開発ステージでテストします。
いずれも、決まったプロンプトで普通のコーディングエージェントを起動します。いずれも、あなたがチャットを開く必要はありません。

## 3 つの役割

| 役割 | automation | 起点 | 残すもの |
| --- | --- | --- | --- |
| **開発担当 (Developer)** | GitHub issue to PR | `openhands` ラベルの付いた issue、または自分の PR に付いた失敗の `software-factory/review` ステータス | `openhands/issue-<n>` 上の pull request と、その修正 |
| **レビュー担当 (Reviewer)** | GitHub code review | `openhands-review` ラベルの付いた PR (すべてのチェックが終わった後) | `✅ APPROVED` または `🔄 CHANGES REQUESTED` で終わるレビュー |
| **テスト担当 (Tester)** | GitHub issue tester | デプロイの後に開かれた、`openhands-test` ラベルの付いた issue | UI、API、保存されたデータからの証拠を添えた issue 上のテストレポートと、ときには小さな修正 PR |

マージまでのループを回すのにリポジトリが必要とするのは、開発担当とレビュー担当だけです。テスト担当にはテストするためのデプロイ先が
必要なので、[自動デプロイ](../../adopt/deploy/)と一緒に導入します。このリポジトリのサンプルアプリにはデプロイがないので、
フォークでは最初の 2 つを動かします。

```d2
direction: right

machine: あなたのマシン {
  style.stroke-dash: 3
  canvas: Agent Canvas {
    i2p: issue から PR へ
    review: コードレビュー
    test: issue テスター
  }
  dev: 開発担当エージェント
  rev: レビュー担当エージェント
  tester: テスト担当エージェント
  canvas.i2p -> dev: 実装または修正
  canvas.review -> rev: レビュー
  canvas.test -> tester: テスト
}

github: GitHub {
  style.stroke-dash: 3
  issues: issues {shape: page}
  prs: pull requests {shape: page}
  statuses: コミットステータス {shape: document}
}

stage: 開発ステージ {shape: cylinder}

machine.canvas -> github: 5 分ごとにポーリング
machine.dev -> github.prs: "push、open"
machine.rev -> github.prs: review
machine.tester -> stage: "クリック、呼び出し、読み取り"
machine.tester -> github.issues: レポート
```

## 構成要素

| 要素 | 何であるか |
| --- | --- |
| **Agent Canvas** | 自分で動かす OpenHands のアプリ (`npx @openhands/agent-canvas`)。エージェントサーバー、automation のバックエンド、Web UI がまとめられている |
| **エージェントプロファイル** | どのエージェントを、どのモデルで動かすか。プロファイルは、任意の LLM を使う OpenHands 自身のエージェントにも、ACP (Agent Client Protocol) 経由の外部のコーディングエージェントにもできる |
| **automation** | cron スケジュールで動く小さな Python のワーカー。GitHub を読み、何をするか決め、エージェントの会話を開始または再開する。Agent Canvas のカタログからインストールする |
| **シークレット** | GitHub トークンのような、名前付きの認証情報。会話には、その許可リストにあるシークレットだけが渡される |

## 3 つの automation

### 開発担当: GitHub issue to PR

ポーリングのたびに、ワーカーは監視している各リポジトリについて次のことを行います。

1. `openhands/issue-<n>` ブランチ上の開いている PR のうち、head コミットに `software-factory/review` という名前で状態が
   `failure` または `error` のコミットステータスが付いているものを探します。それぞれについて、その issue の会話に **revise** のターンを送ります。
   レビュー、コメント、失敗しているチェックを読み、それらを直し、同じブランチに push するというものです。
2. トリガーラベル (`openhands`) が付いていて、まだ PR がない開いている issue を探し、**implement** のターンを開始します。
   clone し、`openhands/issue-<n>` を作り、実装し、テストし、push し、PR を開き、`openhands-review` ラベルを付けます。

各 issue は、安定した会話を持つ 1 つの*サブジェクト*です。修正は元の実装と同じ会話に送られるので、エージェントはコンテキストを保ちます。

### レビュー担当: GitHub code review

ポーリングのたびに、`openhands-review` ラベルが付いている PR、自分のアカウントへのレビュー依頼が保留中の PR、または開いていてドラフトではなく、
依頼もレビューもされていない PR を探します。それぞれについて、**head コミットのすべてのチェックが終わる**まで待ち、そのコミットそのもののレビューを開始します。
レビューは、独立した行の判定で終わります。`✅ APPROVED` または `🔄 CHANGES REQUESTED` です。

<Aside type="caution">
issue-to-PR ワーカーが PR を修正するのは、失敗した `software-factory/review` ステータスを見たときだけです。赤い CI の実行も、レビュー担当の
"changes requested" も、それだけではそのステータスを設定しません。そのギャップを埋めるのが、[欠けているグルー](../the-missing-glue/)のうちの 2 つです。
</Aside>

### テスト担当: GitHub issue tester

最初の 2 つの automation は Agent Canvas のカタログから来ています。これは手で書いたもので、小さなものです。カタログの GitHub ヘルパーの上に
作られた 100 行ほどのワーカーと、プロンプトのファイルです。

ポーリングのたびに、トリガーラベル (`openhands-test`) が付いていて、ワークフロー自身のアカウント `github-actions[bot]` が開いた、
開いている issue を探します。それぞれについて **test** のターンを開始します。ステージで動いているコミットでリポジトリを clone し、
マージされた pull request が何を変えたかを把握し、デプロイされたスタックでそれをテストし、結果を issue にコメントするというものです。

テストは 3 つの部分からなり、3 つ目が、ページをクリックして回るだけのテストとの違いです。

1. **UI。** 実際のブラウザで、テストユーザーとしてサインインして確認します。
2. それらの画面の裏にある **API。** テストユーザーのトークンで呼び、拒否されるべきケースも含めます。
3. **保存されたデータ。** 操作のたびに、テスト担当は変更が書き込んだはずのものを読んで確認します。データベースのレコード、
   ストレージのファイル、検索インデックス、そしてログです。Discava では DynamoDB、S3、OpenSearch、CloudWatch です。

安全で静かに保つための 3 つの工夫があります。

- **issue に書かれるのは、何をテストするかだけです。** どうテストするか (ツール、テストユーザー、チェック、レポート) は、マシン上にある
  automation 自身のプロンプトです。issue を編集できる人の誰も、それを変えられません。
- **他の誰かが開いた issue はスキップされます。** その本文がエージェントへの指示になってしまうからです。
- **ラベル付け 1 回につきテスト 1 回。** ラベルが付けられるたびに 1 回と数えるので、テスト担当自身のコメントが 2 回目のテストを
  始めることはありません。もう一度テストするには、ラベルを外して付け直します。

デフォルトでは、これらの issue を開くものはありません。デプロイされた pull request ごとに issue を開くワークフローが、
[欠けているグルー](../the-missing-glue/)の最後の 1 つです。Discava のものは[マージ後の検証](../../discava/post-merge-verify/)にあります。

## なぜ webhook ではなくポーリングなのか

automation はポーリングします (Discava では 5 分ごと、デフォルトでは 15 分ごと)。そのため Agent Canvas は、公開 URL も webhook のシークレットもない
ノート PC や自宅サーバーで動かせます。代償は最大でポーリング間隔 1 回分の遅延ですが、エージェントが作業にかける時間に比べれば小さなものです。

## エージェントが届くもの、届かないもの

開発担当とレビュー担当のプロンプトは、GitHub トークンというシークレットを 1 つだけ指定します。これで開発担当は issue を読んでブランチを push でき、
レビュー担当はレビューを公開できます。どちらもクラウドへのアクセスは必要ありません。実行するものはすべてローカルスタックで動くからです。

テスト担当は例外です。デプロイされたステージに届く必要があるので、開発アカウントにサインインしたクラウドの CLI (プロンプトで読み取り専用で
使うよう指示されています) と、アプリの各ロールのテストユーザーを使って作業します。デプロイロールが渡されることはなく、プロンプトは
インフラの変更、デプロイ、他のステージに触れることを禁じています。これらの認証情報を持ったまま issue と pull request を読むので、
渡されるものはすべて先にロックされ、コメントできるのは書き込み権限のある人だけになります。

エージェントが他に決してしてはいけないこと、そしてそれぞれの制限を何が強制しているかは、
[人間のゲート](../human-gates/#エージェントが決してしてはいけないこと)にあります。

## エージェントの選び方

Discava は 3 つすべてを **ACP 経由の Claude Code** で、それぞれ専用のエージェントプロファイルで動かしています。開発担当には Sonnet、
レビュー担当とテスト担当には Opus です。レビューにより強いモデルを使うのは意図的です。レビュー担当は人の前の最後のチェックであり、
読むコードは開発担当が書くコードよりはるかに少ないからです。テスト担当に同じモデルを使うのは、その仕事も判断だからです。
変更が何をすべきか、そしてステージで見えているものと、そのストレージで見つかるものが正しいかどうかを決めます。どの ACP エージェントでも、任意の LLM を使う
OpenHands 自身のエージェントでも、同じプロファイルに組み込めます。

各役割が使うプロンプトは[エージェントのプロンプト](../../discava/agent-prompts/)にあります。
