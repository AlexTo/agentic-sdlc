Speckit は `tasks.md` で終わります。OpenHands はラベル付きの issue から始まり、pull request で止まります。
CI は結果を報告して次に進みます。どのツールも自分の仕事はうまくこなしますが、次のツールに作業を渡すものはありません。グルーがなければ、
受け渡しをするのは*あなた*です。タスクを issue にコピーし、CI が赤になったことに気づき、エージェントに修正を指示します。

ギャップと、それぞれを埋めるものは次のとおりです。

| # | ギャップ | それを埋めるもの |
| --- | --- | --- |
| 1 | 完了した spec をエージェントの作業に変えるものがない | ワークフローが `tasks.md` を読み、フェーズのグループごとに 1 つずつ、次の実装 issue を開く |
| 2 | エージェントは CI が失敗したことを知らない | ワークフローが失敗した実行を、エージェントがすでに監視しているコミットステータスとしてエージェントに報告する |
| 3 | レビュアーの "changes requested" が届かない | ワークフローがレビュー担当エージェントの判定についても同じことを行う |
| 4 | 行き詰まったエージェントが永遠にループするのを止めるものがない | 両方の修正ループは 5 回までに制限され、ラベルで数えられ、その後は人が引き継ぐ |
| 5 | `tasks.md` は慣習にすぎないので、形式が崩れるとチェーンが黙って止まる | PR チェックがその形式を検証する |
| 6 | UI の変更が、誰にも見られないままレビューに届く | チェックが e2e のスクリーンショットを必須にし、CI がそれを PR に投稿する |
| 7 | エージェントの PR をマージしても次のフェーズが始まらない | エージェントのブランチのマージが、spec が完了するまで次の issue を開く |
| 8 | エージェントはクラウドへのアクセスなしでは実際のスタックを動かせない | すべてのサービスのローカルの代替があり、アプリ全体と e2e テストが認証情報なしで動く |
| 9 | マージしても何も出荷されない | `main` での green のビルドが自動でデプロイし、最新でなくなったコミットはスキップし、本番環境は人を待つ |
| 10 | エージェントが漏洩したシークレットや脆弱な依存関係をコミットしうる | すべてのビルドで、さらに各デプロイの前に、シークレットと依存関係のスキャンを行う |
| 11 | マージされた変更を、実際に動く場所で誰も確認しない | 各デプロイが、それに含まれていたマージ済みの PR ごとにテスト issue を開き、テスト担当エージェントがデプロイされたステージで変更をテストする |

[Discava のやり方](../../discava/overview/)では、各行をそのファイルに対応付けています。

## グルーを書くためのルール

これらのルールは、Discava でグルーを作り、修正する中で生まれました。

### プロンプトではなくコードで決める

「次に何が起きるか」の判断はすべて、ユニットテスト付きの純粋関数です。どのマージが対象になるかは `gate.ts` の `decide()`、
エージェントを差し戻すかどうかは `planCi()` です。ワークフローファイルはイベントをスクリプトにつなぐだけです。判断は GitHub なしで
テストでき、エージェントが言いくるめて回避することもできません。

### 状態は GitHub に置く

データベースはありません。試行回数はラベル (`ci-fix-2`) です。フェーズのグループに対応する issue は、本文の隠しマーカー
(`<!-- agent-issue spec:<folder> group:2 -->`) で見つけます。「差し戻し済み」はコミットステータスです。誰でも状態を確認でき、
人が手で変更することもできます。たとえば、ラベルを外してもう 1 回試行させることができます。

### エージェントがすでに使っている言葉で話す

OpenHands は、head に失敗した `software-factory/review` ステータスが付いた PR をすでに修正するようになっています。そこでグルーは、
新しいトリガーを発明する代わりに、そのステータスを投稿します。OpenHands への変更は不要です。

### トークンでは信頼できるコードを実行する

グルーのワークフローは、ラベル、ステータス、コメントを書き込めるトークンを持っています。チェックアウトするのは
**デフォルトブランチ**であり、pull request は決してチェックアウトしません。そのため、エージェントやコントリビューターが書いたものが
そのトークンで実行されることはありません。PR から読み取ったもの (ブランチ名、本文) は、使う前に厳格なパターンと照合します。

### エージェントが読むものから見知らぬ人を締め出す

公開リポジトリの issue と pull request には誰でもコメントでき、エージェントは push できるトークンを持ったままそのコメントを読みます。
テスト担当は、デプロイされたステージへのアクセスも持っています。そのため、公開リポジトリでは GitHub の**インタラクション制限**をコラボレーターのみに設定します。
それ以外の人は、コメントも、issue や pull request の作成もできなくなります。ワークフローがエージェントのために開く issue も
**ロック**されます。ラベルなしで開かれ、ロックされ、その後にはじめてラベルが付きます。また、issue の隠しマーカーは、
その issue がワークフローか書き込み権限のある人によって開かれた場合にだけ有効です。

ただし、エージェントの pull request はロックしないでください。GitHub は、書き込み権限のあるアカウントからであっても、
ロックされた pull request へのレビューを拒否するので、レビュー担当エージェントがレビューを投稿できなくなります。

### 冪等にする

GitHub はイベントを複数回配信し、人はジョブを再実行します。すべてのスクリプトは動く前に確認します。同じグループに 2 つ目の issue は作らず、
同じコミットに 2 回目の試行はせず、もう head ではないコミットの実行には反応しません。

### 人が見る場所で、はっきりと失敗する

ワークフローの notice は誰にも読まれません。チェーンが止まったら、pull request の上でそう伝えましょう。「これらのタスクに
チェックが入っていないため、次の issue は開かれませんでした: T014, T015」。

<Aside type="note">
このリポジトリのグルーは約 1,600 行の TypeScript で、ユニットテストも同じくらいの量があり、`packages/common/scripts/src/` 内の
4 つのフォルダに分かれています。導入する前に読んでください。午後の半日ほどで読めます。
</Aside>
