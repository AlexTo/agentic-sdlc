このページでは、実際の Discava リポジトリで 1 つの機能をたどります: **コースの評価と文章によるレビュー**。
数字とリンクはすべて GitHub からのものです。時刻は UTC で、特に記載がなければ 2026 年 11 月 18 日です。

## アイデア

人が書いた [Issue #279](https://github.com/AlexTo/discava/issues/279):

> Enrolled students leave one 1-5 rating plus an optional text review per course (editable,
> deletable). The course carries an aggregate rating and count, kept consistent through a
> core-table helper. Shown on catalogue cards, the course page and as a search sort/boost. The
> instructor can respond; an admin can remove abusive reviews. One review per student per course
> under concurrency; an average/count invariant in `helpers/invariants.ts`.

## spec

ブランチ `spec/reviews` 上の [PR #358](https://github.com/AlexTo/discava/pull/358)、`docs(specs): course ratings and written
reviews`: 14 コミット、923 行で、すべて `specs/20261116-013307-course-reviews/` の下にあります。

- `/speckit-clarify` は尋ねる相手がいない状態で実行されたので、エージェントは回答を "Clarifications" に
  記録しました。たとえば: *"Must a student have made progress before they may review? → No.
  Any student whose enrolment is not dropped may review."* spec PR のレビュアーは、コードが存在する前に、
  そのどれにでも異議を唱えることができました。
- `tasks.md` は **8 フェーズ、36 タスク** になりました。フェーズ 1 は最初のユーザーストーリー (レコード、
  サマリー、共有の書き込み処理) で、フェーズ 2 〜 8 はそれぞれ自分がどの PR かを示しています
  ("core-api review procedures (PR 2)")。2 つのタスクは **(human)** です: ローカルスタックでの手動の通し確認と、
  デプロイされたステージでのチェックです。

11 月 15 日に開かれ、`spec-ready` ラベルが付けられ、11 月 18 日 06:47 にマージされました。

## 人がしたこと

1. 1 段落のトラッキング issue を書いた。
2. spec PR をレビューしてマージした。
3. 8 つの PR それぞれについて: 説明とスクリーンショットのコメントを読み、マージした。

issue を開いた人も、プロンプトを書いた人も、エラーを貼り付けた人もいません。

## ループが捕まえたもの

- **PR #464**: レビュー担当エージェントが変更を求めました。Agent Review Status が開発担当エージェントを 1 回差し戻し、
  次のレビューの後に PR はマージされました。
- **PR #470**: 新しい e2e シナリオが 2 つの要素にマッチする locator を使っていたため、1 つのシャードが失敗しました。
  Agent CI Status がエージェントを 1 回差し戻しました。エージェントは locator を直し、その理由をコメントで説明しました。
  全体の経過は [フィードバックループ](../feedback-loops/) を参照してください。
- **PR #476**: CI の失敗が 1 回、最初の試行で修正。
- **PR #497**: レビューによる変更が 1 ラウンド。
- **PR #504**: CI の失敗が 1 回、最初の試行で修正。

<Aside type="note">
issue はシンプルな Conventional Commit のタイトルを求めているのに、各 PR のタイトルは issue-to-PR automation
独自の形式である `[#<issue>]` で始まります。ここに 2 つの層の働きが表れています。issue の指示は文章で、
automation の形式はコードです。勝つのはコードなので、タイトルを気にするならチェックで強制してください。
</Aside>

## 人に残されたもの

フェーズ 8 の 2 つの **(human)** タスクです: ローカルスタックでの手動の通し確認と、デプロイされたステージでの
チェック。最後の PR は、`tasks.md` でその両方が未チェックのままマージされたので、automation はそれらを
待たず、ほかの何も待ちませんでした。それらを追跡しているのは
[Archive Specs](../spec-to-issue/#完了した-spec-のアーカイブ) ワークフローです。人が両方にチェックを付けるまで、
spec フォルダーは稼働中のままです。
