ギャップ 8: エージェントはクラウドへのアクセスなしでは本物のスタックを動かせず、あなたはエージェントに
クラウドへのアクセスを与えたくありません。Discava の答えは constitution の原則 III です。すべての AWS サービスに
ローカルの代替があり、`pnpm dev` が Docker でそれらすべてを起動します。

## ローカルで動くもの

| サービス | ポート | 代替するもの |
| --- | --- | --- |
| 受講者、講師、管理者のポータル | 4201, 4200, 4202 | CloudFront |
| core-api, instructor-api | 2022, 2023 | API Gateway と Lambda |
| DynamoDB local | 8001 | DynamoDB |
| S3Mock | 9090 | S3 |
| ElasticMQ | 9324 | SQS |
| OpenSearch (Docker) | | OpenSearch Serverless |
| Event runner | 2024 | DynamoDB streams とストリームルーター、MediaConvert (ffmpeg)、Transcribe (プレースホルダーのトラック)、SES (受信箱ページ)、EventBridge、Scheduler、Cognito トリガー |
| ローカル OIDC サーバー | 9400 | Cognito |

バックエンドのコードは `LOCAL_DEV=true` で切り替わります。共有の設定は 1 つのパッケージ
(`common-server-utils/local-dev`) にあるので、すべての Lambda が同じ方法でエンドポイントを解決します。各代替は
`packages/common/scripts` の Nx target で、そのコンテナを pull して起動します。

ローカルのサインインページには固定のユーザー (講師 1 人、受講者 2 人、管理者 1 人) と、任意の claim を指定できる
"Someone else" フォームがあります。パスワードも Cognito もありません。

## 誰が動かすか

**実装エージェントは動かしません**。その issue には `pnpm dev`、Docker、e2e ランナーを使わないよう書かれています。
エージェントはシナリオを書き、**PR の CI** がそれを実行します。各 e2e シャードは新しいランナー上で自分の
`pnpm dev` を起動します。エージェントのマシンはシンプルなままで、エージェントが読む結果は常にクリーンな
スタックからのものです。

人が動かすのは **(human)** タスクのためと、失敗を再現するためです。

## E2E シナリオ

`packages/e2e` には、ユーザーフローごとに 1 つの `src/scenarios/*.e2e.ts` があり、共有の helper から組み立てられています。
共有スタック上で、どんな順番で実行しても安全にするためのルールは次のとおりです。

- 各シナリオは自分のユーザーと、一意な名前のデータを作ります。
- どのシナリオもローカルデータをリセットしません。
- worker は 1 つ、CI ではリトライ 1 回、タイムアウトは 2 分。フローは進捗の再計算などのバックグラウンド処理を待ちます。

## 各テストの後の invariant

`packages/databases/core-table/src/helpers/invariants/` には、テーブル全体に対するチェックがトピックごとに 1 ファイル
(カリキュラム、受講者のアクティビティ、メディア、分析など) で置かれています: 「コースには講師がいる」、「受講者の
アクティビティ数は、その項目を使った受講者と一致する」、「兄弟要素の順序は一意である」、ほか 40 以上。

Playwright の fixture (`packages/e2e/src/helpers/table-invariants.ts`) が、それらを **すべての e2e テストの後に**
実行します。テストの前からあった違反を記録し、新しい違反だけで失敗するので、古いローカルデータで実行が失敗する
ことはありません。メッセージは invariant と問題のレコードを示します。カウンターを間違って書くエージェントは、
3 つ後の機能ではなく、それを書いたテストの中で気づきます。

書き込み元をまたぐルールはすべて、すべての書き込み元が呼ぶ 1 つの共有 helper (たとえば `studentActivityWrites`)
を通して書かれ、invariant とそれを破るテストを持ちます。

**Invariant coverage** の PR チェックが、これを守らせます。`core-table` の `entity-writers.json` は、各エンティティを
それを書き込む各パッケージ内のファイルに対応づけるもので、TypeScript コンパイラでコードから生成されます。
`main` と比較して、チェックは次の場合に PR を失敗させます。

- エンティティに、それまでのものとは別の書き込みパッケージが加わった
- `core-table` パッケージの外のファイルが、複数のパッケージが書き込むエンティティへの書き込みを始めた
- 新しいエンティティが現れた

PR が `helpers/invariants/` の下に追加した行 (テストと fixture は数えない) が、それらの各エンティティか、
`snapshot.enrolments` のような `TableSnapshot` のキーに言及すれば、再び通ります。`entity-writers.json` が
古いあいだもチェックは失敗します。pre-push フックがそれを再生成し、変わっていれば push を止めるので、
エージェントは CI より先に気づきます。

### チェックの免除

チェックにわかるのは、書き込み元の集合が変わったことだけです。ルールが今それらにまたがっているかどうかは
判断できないので、メンテナーはチェックを免除できます。PR に `no-new-invariant` ラベルを付けて、ジョブを再実行します。

書き込みが移動したり分割されたりしたが、新しいルールが関わらない場合にこのラベルを使います。よくあるのは
リファクタリングです。Discava が API プロシージャから helper をそれぞれのファイルに切り出したとき、既存の
書き込みが新しいファイルに現れてチェックに引っかかりましたが、それらが守るルールはすでにカバーされていました。

機能を通すために使ってはいけません。新しい書き込み元によって、別の API やハンドラーがあるレコードの正しさに
依存するようになるなら、そのルールはすべての書き込み元が呼ぶ `core-table` の helper に置き、
`helpers/invariants/` にチェックを置くべきです。このラベルは人が付けるもので、エージェントが付けるものでは
ありません。関わるルールがないと判断することこそ、このチェックが強制するために存在する判断だからです。

## 並行性テスト

`packages/e2e/src/concurrency/` は、2 人のユーザーが競合しうる書き込み (証明書の発行、字幕の添付、分析の
カウンター) について、API に直接、同時にリクエストを送ります。これらは同じ e2e ジョブで実行されます。

## デプロイされたステージでしか動かないもの

代替は完璧ではなく、`CONTRIBUTING.md` にはそれが及ばない箇所が正確に列挙されています: CloudFront の署名、
MediaConvert の正確な出力、本物の Transcribe、Cognito Managed Login、EventBridge のリトライ、失敗キュー。
それらに依存するタスクは **(human)** タスクで、デプロイ後に `discava-development` で確認します。
