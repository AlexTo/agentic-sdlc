Discava のエージェントは、1 台の Linux ワークステーション上の OpenHands Agent Canvas で動いています。
OpenHands のクラウドデプロイも webhook もありません。すべて GitHub へのアウトバウンドのポーリングです。

## Agent Canvas

Agent Canvas 1.41.0 を npm (`@openhands/agent-canvas`) からインストールし、ユーザーサービスとして動かしています。
状態は `~/.openhands/` にあります。設定、エージェントプロファイル、シークレット、そして automation の SQLite
データベースです。

## 会話の設定

エージェントの動き方を決める設定です。

| 設定 | 値 | 理由 |
| --- | --- | --- |
| Agent | ACP、サーバー `claude-code` | Agent Client Protocol 経由の外部コーディングエージェント |
| ACP prompt timeout | 30 分 | 実装のターンは長い |
| Max iterations | 500 | 1 つの会話でフェーズ全体をこなせる余裕 |
| Confirmation mode | off | 無人運用。確認する人はいない |
| Security analyzer | LLM | それでもコマンドはリスクについて審査される |
| Runtime | local | Node、pnpm、git がすでにあるホスト上で動く |
| Worktree branch prefix | `openhands/` | エージェントが作るすべてのブランチはこれで始まる。glue はこれを手がかりにする |

## エージェントプロファイル

エージェントの役割ごとに 1 つのプロファイルがあります。

| プロファイル | 役割 | エージェント | モデル | 使用元 |
| --- | --- | --- | --- | --- |
| `developer` | 開発担当 | Claude Code (ACP) | Sonnet | GitHub issue to PR |
| `reviewer` | レビュー担当 | Claude Code (ACP) | Opus | GitHub code review |
| `tester` | テスト担当 | Claude Code (ACP) | Opus | GitHub issue tester |

いずれもプロンプトのタイムアウトは 30 分です。

## シークレット

Agent Canvas (**Settings → Secrets**) に、名前ごとに保存されています。

| 名前 | 用途 |
| --- | --- |
| `GITHUB_PERSONAL_ACCESS_TOKEN` | automation はこれで GitHub を読む。会話はこれを受け取って clone、push、PR の作成、レビュー、コメントを行う |
| `OPENHANDS_AUTOMATION_API_KEY` | automation バックエンド自身のキー |
| `DISCAVA_STUDENT_USERNAME`, `DISCAVA_STUDENT_PASSWORD` | `discava-development` 上の、テスト担当の受講者 |
| `DISCAVA_INSTRUCTOR_USERNAME`, `DISCAVA_INSTRUCTOR_PASSWORD` | テスト担当の講師 |
| `DISCAVA_ADMIN_USERNAME`, `DISCAVA_ADMIN_PASSWORD` | テスト担当の管理者 |

GitHub トークンは、automation だけが使うマシンアカウント `discava-bot` の personal access token です。
このアカウントは書き込み権限を持つコラボレーターで、トークンはリポジトリの contents、issues、
pull requests、workflows への書き込み権限を持っています。

6 つの `DISCAVA_*` シークレットは、開発ステージ上の Cognito のテストユーザーで、アプリのロールごとに 1 人です。
テスト担当はこれらでポータルにサインインし、API トークンを取得します。

## テスト担当がマシン上で使うもの

開発担当とレビュー担当に必要なのは Node、pnpm、git、`gh` だけです。テスト担当は次のものも使います。

| ツール | 用途 |
| --- | --- |
| `discava-development-*` スタックを持つアカウントにサインインした AWS CLI | ステージを見つける (スタックの出力)、Cognito のトークンを取得する、DynamoDB、S3、CloudWatch のログを読む。プロンプトで読み取り専用で使うよう指示されている |
| Chromium 付きの Playwright | デプロイされたポータルを操作する |
| Discava のチェックアウトの `tmp/screenshots/` | スクリーンショットの保存先。pull request ごとに 1 フォルダー |

<Aside type="caution">
Discava でエージェントがクラウドへのアクセスを持って作業するのは、ここだけです。だからこそステージは使い捨てのデータを持つ
`discava-development` であり、エージェントが読むものに[コメントできるのはコラボレーターだけ](../post-merge-verify/#誰がコメントできるか)です。
チームで使う場合は、テスト担当に専用の読み取り専用ロールと、専用のマシンまたは VM を与えてください。
</Aside>

## 3 つの automation

最初の 2 つは手で書いたものではなく、Agent Canvas の automation カタログからインストールしました。3 つ目は
Discava 独自のものです。それぞれがポーリングで何をするかは
[エージェントのランタイム](../../concepts/the-agent-runtime/#3-つの-automation) に、それぞれがエージェントに渡す
プロンプトは [エージェントのプロンプト](../agent-prompts/) にあります。

### 開発担当: GitHub issue to PR

| フィールド | 値 |
| --- | --- |
| Template | `github-issue-to-pr` 1.2.4 |
| Repository | `AlexTo/discava` |
| Trigger label | `openhands` |
| Branch prefix | `openhands/issue` → ブランチ `openhands/issue-<n>` |
| Pull request mode | Ready for review |
| GitHub token secret | `GITHUB_PERSONAL_ACCESS_TOKEN` |
| Schedule | `*/5 * * * *`、Australia/Sydney |
| Agent profile | `developer` |

修正のターンでは、終わったあとに `openhands-review` ラベルを付け直すようエージェントに指示するので、
新しい head がレビューされます。

### レビュー担当: GitHub code review

| フィールド | 値 |
| --- | --- |
| Template | `github-pr-reviewer` 1.11.2 |
| Repository | `alexto/discava` |
| Trigger label | `openhands-review` |
| Requested reviewer | `all-hands-bot` (実際には使われない。ラベルが役目を果たす) |
| New reviews per scan | 2 |
| Review tone | Concise |
| Maintainers | なし |
| Schedule | `*/5 * * * *`、Australia/Sydney |
| Agent profile | `reviewer` |

チェックがまだ実行中のあいだ、レビュー担当は "⏳ Review waiting on checks" というコメントを投稿し、
後のスキャンで再試行します。レビューは "_This review was posted by an AI agent
(OpenHands)._" で始まり、隠しマーカー `<!-- openhands-review-run: <id> -->` を含みます。

### テスト担当: GitHub issue tester

これにはカタログのテンプレートがありません。カタログのテンプレートが使うのと同じ GitHub と会話のヘルパーの上に作った
100 行ほどのワーカーで、プロンプトはその隣のファイルにあります。

| フィールド | 値 |
| --- | --- |
| Template | なし: 手で書いた `worker.py`、`prompt.md`、`config.json` |
| Repository | `AlexTo/discava` |
| Trigger label | `openhands-test` |
| Issue authors | `github-actions[bot]` |
| Branch prefix | `openhands/test-fix` → 修正ブランチ `openhands/test-fix-<n>` |
| New tests per scan | 2 |
| Prompt file | `prompt.md` |
| GitHub token secret | `GITHUB_PERSONAL_ACCESS_TOKEN` |
| Schedule | `*/5 * * * *`、Australia/Sydney |
| Agent profile | `tester` |

ポーリングのたびに、ワーカーは次のことを行います。

1. `openhands-test` が付いた開いている issue を、番号の小さい順に列挙します。
2. **Issue authors** のいずれかが開いたものではない issue はスキップします。issue の本文はエージェントが読むものの
   一部になるので、ワークフロー自身の issue だけをテストします。
3. ラベルを付けた最新のイベントを探します。issue 番号とそのイベントの ID で 1 回の配信になるので、同じラベル付けに対する
   後のポーリングは無視され、テスト担当自身のコメントが 2 回目のテストを始めることはありません。ラベルを外して付け直すと
   新しいイベントになり、新しいテストになります。
4. その issue の会話をプロンプトで開始または再開します。新しいテストはポーリングごとに 2 件までです。

ポーリングの対象になる issue は [Post-merge Verify](../post-merge-verify/) が開きます。テスト担当の
コメントは "_This comment was posted by an AI agent (OpenHands)._" で終わります。

<Aside title="エージェント用に 1 つのアカウント">
Discava では、開発担当、レビュー担当、テスト担当がすべて `discava-bot` として投稿し、メンテナーは自分の
アカウントを使います。そのため、メンテナーはエージェントの PR を通常どおり承認でき、どのコメントがエージェントから
来たのかもわかります。レビュー担当と開発担当は今もアカウントを共有しており、GitHub ではアカウントが自分の PR を
承認できないため、レビュー担当の判定は `COMMENTED` レビューとして投稿されます。glue はレビューの状態ではなく
判定の行を読むので、問題にはなりません。
</Aside>
