ギャップ 11: マージ前のチェックはすべてローカルの代替に対して実行されたもので、変更が実際に動く場所では誰も見ていません。
Discava はこれを 3 つ目のエージェントの役割で埋めます。`discava-development` へのデプロイのたびに、ワークフローが
そのデプロイに含まれていた pull request ごとにテスト issue を開き、**テスト担当エージェント**がその変更をステージでテストします。
実際のブラウザでのポータル、テストユーザーとしての API、そして変更が書き込んだデータです。

```d2
direction: down

deploy: "Deploy\n(discava-development)"
verify: "Post-merge Verify\npost-merge-test"
issue: "テスト issue\nロックしてから openhands-test" {shape: page}
tester: "テスト担当エージェント\n(OpenHands、次のポーリング)"
stage: discava-development {shape: cylinder}
report: "issue 上のレポート" {shape: document}
fix: "修正 PR\nopenhands/test-fix-<n>" {shape: page}

deploy -> verify: 完了
verify -> issue: デプロイされた PR ごとに 1 つ
issue -> tester
tester -> stage: "Playwright、API、AWS CLI"
tester -> report
tester -> fix: "小さく明らかな修正のみ" {style.stroke-dash: 3}
```

## Post-merge Verify

`.github/workflows/post-merge-verify.yml` は `workflow_run` で、**Deploy** が完了したときに実行されます。pull request
番号を指定して手動でも実行できます。デフォルトブランチをチェックアウトし、`post-merge-test` を実行します。
実行は 1 つの concurrency グループを共有するので、近接した 2 つのデプロイが同じ pull request に 2 つの issue を
開くことはありません。

スクリプト (`src/post-merge-test/`):

1. **その実行がテスト対象のステージをデプロイしたことを確認します。** Deploy の実行のジョブを読みます。`Deploy` ステップが
   スキップされた実行 (コミットがもう `main` の最新ではなかった) は何もデプロイしておらず、別のステージに対する実行は
   テストしません。
2. **デプロイに何が含まれていたかを調べます。** 1 回のデプロイに複数のマージが入ることがあります。スキップされたデプロイは、
   そのコミットを次のデプロイに委ねるからです。そこで、そのステージで前回成功したデプロイから今回までのコミットと、
   それぞれがマージされた元の pull request を取ります。
3. **pull request ごとに判断します** (`plan.ts` の `decide()`)。次の場合、issue は開きません。
   - その pull request の issue がすでにある (隠しマーカーで見つける)
   - `skip-deploy-test` ラベルが付いている
   - デプロイされるものを何も変更していない。docs、spec、テスト、ツール、CI など、スタックに届かないファイルだけの場合
4. **issue を描画します** (`renderIssue()`)。書かれるのは、何をテストするかだけです。
5. **ラベルなしで開き、ロックしてから、ラベルを付けます。** その issue、それがテストする pull request、その pull request が
   閉じる issue がすべてロックされます。その後にはじめて `openhands-test` が付きます。ロックできないものがあれば、
   ラベルは付かず、実行は失敗して、手動でロックすべきものを示します。

pull request 番号を指定して手動で実行すると、issue がすでにあっても新しく開きます。変更を最初からもう一度テストするには
こうします。

## 開かれる issue

実際の例、[#654](https://github.com/AlexTo/discava/issues/654):

```markdown
<!-- post-merge-test pr:647 -->

## What to test

- Pull request: #647 (feat(stripe-checkout): a refund takes access away)
- Issue it closes: #646
- Merged as `b4dc4f7…`, deployed to `discava-development` at `b4dc4f7…` ([Deploy run](…))
- Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
  through the flow with Playwright, then call the APIs behind it and check the stored data.

<details><summary>Deployed files it changes (4)</summary>

- `packages/events/src/local/stripe-stand-in.ts`
- `packages/events/src/payments/events/charge-refunded.ts`
- `packages/events/src/payments/stripe-webhook.ts`
- `packages/websites/student-portal/src/routes/learn/$courseId/-components/enrolment-actions.tsx`

</details>
```

タイトルは `test(post-merge): verify #647 a refund takes access away` です。最大 100 文字の Conventional Commit の
ヘッダーなので、テスト担当はそれを再利用できます。Kind は、pull request がポータルか共有コンポーネントに触れていれば
`UI change`、そうでなければ `backend change or fix` です。

<Aside type="note" title="何をテストするかだけで、どうテストするかは決して書かない">
issue に指示はありません。どうテストするか (ツール、テストユーザー、チェック、レポート) は、OpenHands 内にある
テスト担当自身の[プロンプト](../agent-prompts/#テスト担当)です。そのため、issue を編集できる人の誰もそれを変えられません。
`.github/ISSUE_TEMPLATE/test-deployed-pr.md` は、issue を手動で開くための同じ書式です。
</Aside>

## テスト担当がすること

次のポーリングで、`github-issue-tester` automation が issue を拾い、テスト担当を起動します。
そのプロンプトには 8 つのステップがあります。

1. pull request、その diff、それが閉じる issue、その spec から何が変わったかを把握し、今なにが成り立つべきかを
   書き出します。
2. UI があればテストします。Playwright で Cognito のホストされたページからサインインし、フローをクリックして進み、
   各ステップでスクリーンショットを撮り、そのすべてを見ます。
3. テストユーザーのアクセストークンで API を呼びます。エラーケースも含めます。
4. 保存されたデータを確認します。DynamoDB のアイテム、OpenSearch のドキュメント、S3 のオブジェクト、Lambda のログです。
5. `pmt-<pr>-<what>` という名前を付けた、自分のデータを使います。
6. issue に報告します。何をテストしたか、合格か失敗かと証拠を添えたすべてのチェックの表、そして判定です。
7. 合格なら issue を閉じます。失敗なら、再現手順を付けて開いたままにします。修正の pull request を開くのは、
   原因が明らかで修正が小さいときだけです。
8. インフラ、IAM、ユーザー、ステージの設定の変更、デプロイ、他のステージに触れること、ワークフローの編集、マージは
   決して行いません。

### 実行 1: ブロックされ、そう報告する

この変更は、Stripe が返金を報告したときに受講者の受講登録を終了させます。それをテストするには、返金する対象の支払い済みの注文が
必要ですが、ステージには決済アカウントがありませんでした。テスト担当はテストを合格にせず、推測もしませんでした。
その[判定](https://github.com/AlexTo/discava/issues/654#issuecomment-7033260676)は "blocked, not verified" で、証拠が添えられていました。管理者 API の
`payment.status` は `not-connected` と答え、コアテーブルには注文が 1 件もありませんでした。

続いて、支払いなしで確認できることを確認しました。デプロイされた webhook の関数には新しい
`charge.refunded` ハンドラーが含まれている、配信されているポータルのバンドルには新しい "You're no longer enrolled" 画面がある、
偽造された返金通知は 400 で拒否されて何も書き込まない、無料コースではコースのページが引き続き動く。
9 つのチェックが合格しました。検証*していない* 6 つのことと、何があればそのブロックが解消するかも列挙しました。

何をしないかも述べました。決済アカウントを接続するには Stripe のキーを保存する必要があり、それはステージの設定を
変更することになります。[プロンプト](../agent-prompts/#テスト担当)はそれを禁じています。そこで、
人のために issue を開いたままにしました。

画面上には、何かがおかしいことを示すものが何もありません。エラーも、コンソールの失敗したリクエストもありません。
テスト担当がこれを見つけられたのは、注文のレコードと関数のログも読んだからです。
ログが理由を示していました。

```text
REPORT … Duration: 10000.00 ms … Memory Size: 128 MB  Max Memory Used: 117 MB  Status: timeout
REPORT … Duration: 10000.00 ms … Memory Size: 128 MB  Max Memory Used: 117 MB  Status: timeout
```

チェックアウトが支払われたという Stripe の通知は、一度も届きませんでした。それを受け取る関数は
Lambda のデフォルトの 128 MB で動いていて、コールドスタート (コアテーブルのエンティティ、AppConfig、Stripe
SDK) が 10 秒のタイムアウト内に終わりませんでした。タイムアウトしたランタイムは破棄されるので、
Stripe の再試行は毎回コールドスタートになり、同じように失敗しました。テスト担当はこれを、256 MB を持ち、
起動に 8.1 秒かかったチェックアウトの関数と比較しました。

テスト対象の返金には、たどり着きませんでした。テスト担当が見つけたものはその 1 つ手前にあり、
もっと深刻です。デプロイされたステージでは、受講者がコースの代金を払っても、コースを受け取れない可能性がありました。

### なぜもっと早く見つからなかったのか

この欠陥はテスト対象の pull request より古く、すべての層を通り抜けていました。

- **ユニットテスト**はハンドラーのロジックを実行しますが、ロジックは正しいものでした。
- **E2E テスト**はローカルスタックに対して動きます。そこでは代替が Stripe の役を務め、メモリ制限も
  10 秒のタイムアウトもありません。
- **レビュー担当エージェント**と**人**は、メモリの設定がどこにも現れない diff を読みました。
  欠けている行こそが欠陥だからです。

この欠陥は、関数がデプロイされた場所にしか存在しません。それが、テスト担当が埋めるためにいるギャップです。

### 修正 PR

原因が明らかで修正が小さかったので、テスト担当のプロンプトは pull request を許していました。
[#657](https://github.com/AlexTo/discava/pull/657) は 1 つの[コミット](https://github.com/AlexTo/discava/commit/854760c3c30a5ceb1ee7c7e52ebd596bef3374f1)で、
2 つのファイルを変更します。`StripeWebhookApi` construct で関数のメモリを 512 MB に設定する 4 行と、
それがなければ失敗する 12 行のテスト (`Missing key 'MemorySize'`) です。`main` から
`openhands/test-fix-654` として分岐し、その説明は [#647](https://github.com/AlexTo/discava/pull/647) と
[#654](https://github.com/AlexTo/discava/issues/654) の両方を参照しています。

説明は、その限界についても率直です。"Not verified on a deployed stage. The fix only
takes effect once deployed." (デプロイされたステージでは未検証。修正はデプロイされてはじめて効果を持つ。)

そして、テスト担当は止まりました。マージもデプロイもしませんでした。[PR Checks](https://github.com/AlexTo/discava/actions/runs/44722377986)
が green で通り、`openhands-review` ラベルがそれをレビュー担当エージェントに渡しました。レビューは、どのエージェントも
間違えていないことのせいで 40 分止まりました。pull request がロックされていて、GitHub はロックされた pull request への
レビューを受け付けないのです。ロックが解除されると、レビュー担当はそれを承認しました。Discava が pull request を
ロックするのをやめたのはこのためです ([誰がコメントできるか](#誰がコメントできるか)を参照)。他の PR と同じように、マージするのは人です。テスト issue [#654](https://github.com/AlexTo/discava/issues/654) は、支払いが確定するステージで返金そのものが
テストされるまで開いたままです。テスト担当の最後のレポートには、残したテストデータが列挙されています。
コースと `pending` の注文です。

スクリーンショットはワークステーション上の、Discava のチェックアウトの `tmp/screenshots/pr-<pr>/` に残ります。
レポートは各ファイルの名前を挙げ、何が写っているかを述べます。上の 4 枚は、このページのためにそこからコピーしたものです。

## 誰がコメントできるか

Discava は公開リポジトリなので、誰でもその issue と pull request にコメントできます。エージェントは、push できる
トークンを持ったままそれらのコメントを読み、テスト担当は AWS へのアクセスとテストユーザーのパスワードも持っています。
つまり、コメントはエージェントに指示を与える手段、すなわちプロンプトインジェクションになります。プロンプトは各エージェントに
読んだものをデータとして扱うよう指示しますが、プロンプトはお願いであって、保証ではありません。

そこで Discava は、2 つの方法で見知らぬ人を会話から締め出します。

| 層 | 何をするか |
| --- | --- |
| **インタラクション制限** | GitHub の **Settings → Moderation options → Interaction limits** が **Limit to repository collaborators** に設定されている。それ以外の人は、リポジトリのどこでもコメントも、issue や pull request の作成もできない |
| **ロックされたエージェントの issue** | Agent Issues と Post-merge Verify は、各 issue をラベルなしで開き、ロックし (テスト issue の場合は、それがテストする pull request と、その pull request が閉じる issue も)、それからはじめてラベルを付ける。ロックできないものがあれば、ラベルは付かず、実行は失敗する。共有のコードは `src/helpers/conversation-lock.ts` にある |

ポリシーにもそう書かれています。Discava の `CONTRIBUTING.md` は、外部からの issue や pull request を受け付けないこと
とその理由を述べています。エージェントはその両方を読んで動くので、issue の文章がエージェントへの指示になってしまうからです。
アイデア、質問、バグ報告は、どのエージェントも読まない GitHub Discussions へ送られ、やる価値のあるものはメンテナーが
spec にします。以前 `CONTRIBUTING.md` にあった開発者ガイドは `DEVELOPMENT.md` に移りました。

これに伴うルールがあと 2 つあります。

- **マーカーは作成者によって信頼されます。** ワークフローは、以前に開いた issue を隠しマーカーで見つけます。
  マーカーが有効なのは、`github-actions[bot]` か書き込み権限のある人が開いた issue の中にある場合だけです
  (`src/helpers/issue-author.ts`)。そのため、見知らぬ人がマーカー入りの issue を開いてチェーンを止めたり、
  テストを止めたりすることはできません。
- **テスト担当はワークフローの issue だけをテストします。** その automation は、`github-actions[bot]` が開いていない
  テスト issue をすべてスキップし、その指示は issue ではなく、常に自身のプロンプトです。

<Aside type="caution" title="公開リポジトリにはインタラクション制限が必要">
リポジトリが公開されているなら、テスト担当エージェントを有効にする前に、できればどのエージェントよりも前に、
インタラクション制限を**コラボレーターのみ**に設定してください。それがないと、誰でもテスト issue やそれがテストする
pull request にコメントでき、テスト担当はクラウドの認証情報とテストユーザーのパスワードを持ったままそのコメントを読みます。

制限の期間は最長 6 か月です。Discava の制限は 2027 年 5 月 20 日までです。失効しても何も警告されないので、
更新の予定をカレンダーに入れてください。非公開リポジトリには不要です。そこでは、アクセス権のある人しかコメントできません。

制限を設定する前、または issue にラベルが付く前に書かれたコメントは残ります。既存の issue に手動でラベルを付ける前に、
それらを読んでください。
</Aside>

### Discava が pull request のロックをやめた理由

[#658](https://github.com/AlexTo/discava/pull/658) までは、**Agent Lock** というワークフローが、エージェントが開くすべての
pull request と、誰かが手動でエージェント向けのラベルを付けた issue もロックしていました。見知らぬ人は締め出せましたが、
2 つの代償がありました。

- **レビュー担当エージェントがレビューできませんでした。** GitHub は、書き込み権限のあるアカウントからであっても、
  ロックされた pull request へのネイティブのレビューを拒否します。修正 PR [#657](https://github.com/AlexTo/discava/pull/657) は 10:49 にロックされ、
  10:54 にレビュー用のラベルが付きましたが、11:34 に手動でロックが解除されるまでレビューされませんでした。
  レビュー担当はその 5 分後に承認しました。
- **E2E のスクリーンショットを投稿できませんでした。** GitHub はロックされた会話への Actions トークンによるコメントも
  拒否するので、[スクリーンショットのリスト](../pr-checks/#ui-screenshots-と-e2e-screenshots-のコメント)は
  ジョブのサマリーに移す必要がありました。

インタラクション制限は、エージェントが書き込む必要のあるものを何もロックせずに、リポジトリ全体で同じ役目を果たします。
Agent Lock とそのスクリプトは削除され、それがロックしていた 4 つのエージェントの pull request は手動でロックが解除されました。

## ドライラン

```bash
DRY_RUN=true GITHUB_REPOSITORY=AlexTo/discava GITHUB_EVENT_NAME=workflow_dispatch PR_NUMBER=647 \
  pnpm nx run @discava/tooling-agent:post-merge-test
```

これは開くことになる issue のタイトルと本文を出力し、何も作成しません。pull request は引き続き `gh` で読むので、
サインインしておく必要があります。
