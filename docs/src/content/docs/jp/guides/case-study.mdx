[仕組み](../how-it-works/)ではループを説明しました。このページでは、そのループが 1 回まわる様子を、
[Discava](https://github.com/AlexTo/discava) の実際の pull request で示します。購入したコースの返金を求めた後に、
受講者が目にする画面です。

引用、数字、リンクはすべて GitHub からのものです。時刻はシドニー時間 (AEDT、UTC+11) で、2026 年 11 月 25 日と
26 日です。

pull request が開いてからマージされるまで: 修正ラウンドが 4 回 (CI から 3 回、レビューから 1 回)、人の操作は 1 回です。
その後、テスト担当が、どのゲートからも見えなかった問題を 2 つ見つけました。

## 1. issue

返金を求めた受講者には、Stripe が処理している間 "Refund requested" と表示され、コースページは 2 秒ごとに
返金が完了したかを確認します。[#1166](https://github.com/AlexTo/discava/issues/1166) には、そこで何が
問題だったかが書かれています。

> While a student's refund is pending, the course page refetches `course.myEnrolment` and
> `payment.myOrder` every 2 s, and never stops. If the refund fails at Stripe or its event never
> arrives, the order stays `paid` with a refund requested, the page keeps polling for as long as
> it is open, and the student isn't told anything has gone wrong.

受け入れ条件は 2 行です。ポーリングは上限に達したら止まること。そして、Stripe の代替でシミュレートした
失敗した返金は、わかりやすいメッセージとともに保留状態を終わらせること。

この issue は spec から来たものではありません。受講者が返金を求められるようにする PR をレビューしていたときに、
レビュー担当エージェントがその PR の範囲外の問題として挙げ、それが独立した issue になりました。(#1166 は
コピーです。エージェントの以前のマシンアカウントが GitHub にフラグを立てられ、そのアカウントが開いたものが
すべて非表示になりました。開いていた issue は、エージェントがいま使っている GitHub App によって
[開き直されました](../../discava/openhands-setup/#github-app)。)

## 2. 開発担当エージェントが PR を開く

開発担当エージェントは issue を拾い、`openhands/issue-1166` で [#1195](https://github.com/AlexTo/discava/pull/1195)
を開きました。変更は 4 つのパッケージにまたがります。コースページの 2 分の上限と "Check again" ボタン、
Stripe の返金失敗イベントを処理する webhook ハンドラー、失敗は必ず依頼の後に来るという invariant を持つ
注文の `refundFailedAt` フィールド、そしてコースページの "Your refund failed" です。説明の最後には、
何を実行して何を実行していないかが書かれていました。

> Unit tests cover the helper, the webhook, the invariant and the UI (poll limit, check again,
> failure message). [...] I did not run the e2e tests or try the stand-in control in a browser.

## 3. CI が 3 回差し戻す

**`ci-fix-1`: スクリーンショットがなく、テストのない行がある。** PR は受講者が見るものを変えていましたが、
スクリーンショットを撮っていなかったので、[**UI Screenshots** が失敗しました](https://github.com/AlexTo/discava/actions/runs/45619342535/job/139224403383)。
**codecov/patch** も失敗しました。新しい行にテストがなかったからです。**Agent CI Status** が `ci-fix-1` を付け、
開発担当エージェントを差し戻しました。その[返信](https://github.com/AlexTo/discava/pull/1195#issuecomment-7164484931)
からは、エージェントが途中で自分の最初の試みの問題にも気づいたことがわかります。

> **UI Screenshots:** added a `learner-refund` e2e scenario for a failed refund, with
> `screenshot(student, 'refund-failed')`. For this the Stripe stand-in has a new
> `fail-next-refund` control. [...] This replaces the `refund-fail` control from the first push,
> which the scenario could not use, because the stand-in completed the refund before it could
> fail.

**`ci-fix-2`: 自分のものではない失敗。** 次の実行は **Checks (build)** の、インフラパッケージにある CDK synth
テストで失敗しました。エージェントはログを読み、
[そのためのコードは変更しませんでした](https://github.com/AlexTo/discava/pull/1195#issuecomment-7165688653)。

> the one failure was `@discava/infra` `instructor-api-stack.test.ts` [...], which hit its 30s
> timeout while the sibling CDK synth tests in that file took 22–31s. This PR doesn't touch infra
> or anything the stack synthesises [...], so I made no code change for it. The push below
> re-runs the build.

codecov がまだ報告していた部分的にしかテストされていない 1 行をカバーし、その push でビルドが再実行されて
合格しました。理解していないコードを変えて失敗を「直す」エージェントは、その失敗が自分のものではないと
理由とともに言うエージェントより悪いものです。

**`ci-fix-3`: 自分で追加したテストが間違っていた。** レビューの後 (次の節)、エージェントは 2 分の上限のための
e2e シナリオを追加し、それが [**E2E tests (11/12)**](https://github.com/AlexTo/discava/actions/runs/45685812586/job/139458011986) で失敗しました。
5 分後、[原因](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172674824)です。

> the new `a pending refund stops polling and offers to check again` scenario failed with a
> Playwright strict-mode violation, not a product bug. `getByText('Still being processed')` also
> matched the alert's description ("Your refund is still being processed…"), so it resolved to two
> elements. The page did reach the timed-out state. I now match the title with `{ exact: true }`.

エージェントは e2e シナリオをローカルで 1 つも実行しておらず、毎回そう書いていました。シナリオが最初に
実行されるのは PR CI で、[E2E screenshots コメント](https://github.com/AlexTo/discava/pull/1195#issuecomment-7163204279)
には実行で撮られた 2 つの画面が並んでいます。`learner-refund/01-refund-failed.png` と
`learner-refund/01-refund-still-being-processed.png` です。

## 4. レビュー担当エージェントが CI に見つけられないものを見つける

head のすべてのチェックが終わると、レビュー担当エージェントが diff を issue と照らして読みました。決済のコードは
正しいと判断し、絞り込んだ 361 件のテストを自分で再実行し、それでも
[マージをブロックしました](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6063632214)。

> 1. **The branch carries another open PR's change.** Commit `e7cb9bc9`, "fix(student-portal):
>    surface completions and progress load errors on start route", is the change from open PR
>    #1188, not part of #1166. [...] Merging this PR would ship #1188's start-route error behaviour
>    under a payments title, before #1188 is reviewed.
> 2. **Live evidence is missing for the "Still being processed" / "Check again" state.** [...] The
>    new timed-out state [...] has only unit tests, and no capture from the running app.
>
> 🔄 CHANGES REQUESTED

1 つ目の指摘は、どのチェックもすり抜けてしまう種類のものです。余分なコミットはコンパイルでき、そのテストも
合格していました。ただ、ここに属していなかっただけです。エージェントのチェックアウトは、すでにそのコミットを
含むブランチから始まっていました。2 つ目の指摘は、スクリーンショットのルールを、読む側が改めて適用したものです。
CI は PR がスクリーンショットを追加したかを確認し、レビュー担当は新しい状態のそれぞれにスクリーンショットがあるかを
確認します。

**Agent Review Status** が `review-fix-1` を付けました。8 分後、開発担当エージェントは自分の 4 つのコミットを、
ほかの 2 つを除いて `main` に [rebase していました](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172386579)。
さらに、返金を保留のままにする代替のコントロールと、Playwright の偽の時計を入れて 125 秒早送りする e2e シナリオを
追加しました。これが、その後 `ci-fix-3` で直したシナリオです。

最終的な head で、レビュー担当は両方の指摘が解決したこと、12 個の e2e シャードがすべて合格したことを
[確認し](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066801083)、2 枚のスクリーンショットを名指ししました。
"No material findings [...] ✅ APPROVED"。

## 5. 人が承認する

11:33 にメンテナーが[承認](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066944326)してマージしました。
この PR で人がしたのはこれだけです。メンテナーの手元にあったのは、何を実行して何を実行していないかを書いた説明、
CI からの 2 枚のスクリーンショット、green のチェック一覧、そしてそれぞれに理由が付いた 4 回の修正の履歴です。

## 6. マージがデプロイされ、テスト issue が開く

Discava では、`main` が自動で開発ステージにデプロイされます。このマージを含む[デプロイ](https://github.com/AlexTo/discava/actions/runs/45734764281)
は 12:28 に完了し、1 分後に **Post-merge Verify** が [#1240](https://github.com/AlexTo/discava/issues/1240) を
開きました。issue には、PR が変更したデプロイ対象のファイル 12 個と、どの種類のテストをするかが書かれています。

> Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
> through the flow with Playwright, then call the APIs behind it and check the stored data.

## 7. テスト担当エージェントがデプロイされたステージをテストする

テスト担当エージェントはテストスイートを再実行せず、Stripe の代替も使いません。デプロイされたプロダクトを、
サンドボックスモードの本物の Stripe とともに、人と同じように使います。その
[レポート](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815)には、すべてのステップが並んでいます。

1. テスト用の講師として、API を通じて、$19.99 のコースを 2 つ作成しました。
2. テスト用の受講者として、実際のブラウザでサインインし、Stripe Checkout でそれぞれを購入しました。
   その際、"refund fails" と "refund pending" 用の Stripe のテストカードを使いました。
3. コースページから、それぞれについて返金を依頼しました。
4. 各ステップの後に API を呼び、DynamoDB の注文と受講登録を読み、webhook と API の Lambda のログを読みました。

以下のスクリーンショットはテスト担当自身のもので、ここでは重要な部分だけに切り抜いてあります。

返金が失敗するカードで 1 つ目のコースを購入する (`02-stripe-checkout-refund-fails-card.png`):

受講者が返金を求めてから 1 分後 (`07-refund-pending-after-60s.png`):

  <img alt="pmt-1195-refund-course のコースページ。Buy now ボタンの上に、You're no longer enrolled、Your enrolment has ended. Refunded on 26 November 2026 という通知がある" src="/agentic-sdlc/screenshots/post-merge-test-1195/07-refund-pending-after-60s.png" width="620" />

これは間違った結末です。このカードの返金は失敗しますが、Stripe は最初にそれを成功として報告するので、注文は
`refunded` とされ、約 3 秒で受講登録は終了しました。失敗はその後に起き、それについては何も届きませんでした。テスト担当は
理由を探しに行き、別々の原因を 2 つ見つけました (次の節)。

このステージでは、本物の Stripe で返金を保留のままにすることも、失敗した返金を記録することもできませんでした。
そこでテスト担当は、デプロイされたバンドルの新しい画面を確認するために、ブラウザで `payment.myOrder` の
レスポンスを書き換え、本物の API のレスポンスと保存されたデータは別に確認しました。上限の時間も測りました。
"Still being processed" は保留中の返金が表示されてから **120.2 s** 後に現れ、その後 20 秒間リクエストは
ありませんでした (`13-still-being-processed-after-2-minutes.png`):

そして、レスポンスに失敗した返金があると (`15-refund-failed-message.png`)、アラートが表示され、

レポートには 22 のチェックがあります。17 が合格し、その中にはこれらが含まれます。

| チェック | 結果 |
| --- | --- |
| 2 分後にポーリングが止まる | 120.2 s、その後 20 s の間リクエストは 0 |

| 購入していないユーザーとしての `payment.myOrder` | 200 で `null`: ほかの人の注文は返らない |
| すでに返金済みの注文への `payment.requestRefund` | 拒否: 412、"No purchase to refund" |

## 8. テスト担当が issue を開いたままにする

3 つのチェックが失敗し、そのうち 2 つは PR が想定していない状態で終わりました。
[判定](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815)です。

> **Verdict: the student-facing UI and `payment.myOrder` work as the PR describes. The
> failed-refund path does not work end to end on the deployed stage.**

原因は 2 つで、どちらも PR のテストが届く範囲の外にありました。

1. **ステージの Stripe webhook に新しいイベントが届かない。** PR は `refund.failed` と
   `charge.refund.updated` をイベントの一覧に追加しましたが、その一覧が Stripe に送られるのは、管理者が最初に
   接続するときだけです。ステージは 6 日前に接続されていました。テスト担当は、その 30 分間の webhook の呼び出しが
   ちょうど 4 回で、失敗に関するものは 1 つもないことを数えました。
2. **本物の Stripe では、失敗した返金は注文がすでに `refunded` になった後に届く。** Stripe は返金が作成されると
   すぐに、それが保留中でも失敗するものでも、`charge.refunded` を送ります。`refund.failed` が届く頃には、
   新しいハンドラーの条件 (注文がまだ `paid` であること) はもう成り立たず、ハンドラーは黙って何もしません。

   > The student has lost access, hasn't been refunded, and isn't told.

   PR の e2e シナリオにある代替は、返金を失敗させる前に確定させることがないので、CI はこのうまくいく
   場合だけを示していました。

テスト担当は、修正が小さく明らかなときには修正 PR を開くことができます。開かなかった理由を説明しています。

> Fixing it means deciding how a refund failure after `charge.refunded` should restore the order
> and enrolment, or not treating a `pending` refund as refunded. That goes beyond a small fix, so
> I'm reporting it rather than opening a PR.

ステージの Stripe 接続にも触れませんでした。保存し直せば 1 つ目の原因は直るのにです。
"I didn't do that, because it changes stage configuration." そのため issue は開いたままで、両方の問題、
その再現方法、人が下すべき選択肢が書かれています。ステージに残したテストデータと、すでに別の場所で追跡されている
目にとまったエラーも 1 つ挙げていました。誰もそれをリグレッションと取り違えないようにするためです。

<Aside type="tip">
[マージ後の検証](../../discava/post-merge-verify/)では、別のテスト issue をたどります。そこではテスト担当が
失敗を見つけ、原因を突き止め、実際に修正 PR を開きました。
</Aside>

## 各ゲートが捕まえたもの

| ゲート | 捕まえたもの | 手前のゲートが捕まえられなかった理由 |
| --- | --- | --- |
| CI | スクリーンショットのない UI の変更、テストのない行、エージェント自身の e2e テストの壊れたロケーター | 開発担当エージェントが e2e スイートを実行していなかった |
| レビュー担当エージェント | ブランチに紛れ込んだ別の PR のコミット、スクリーンショットのない新しい画面の状態 | 余分なコミットはすべてのチェックを通り、CI は何らかのスクリーンショットが追加されたかしか確認しない |
| テスト担当エージェント | 新しいイベントを受け取らない webhook エンドポイント、失敗する返金を最初は返金済みと報告する本物の Stripe | 代替はコードが期待するとおりに動き、ステージの設定を見るテストはない |

3 つのどれも、単独で賢いわけではありません。それぞれが、ほかからは見えないものを見ています。CI はルールを、
レビュー担当は issue とブランチを、テスト担当は動いているプロダクトとその背後にある本物のサービスを見ています。

## 人がしたこと

1. PR #1195 とそのスクリーンショットを読み、承認してマージした。
2. 次: テスト担当が書き出した選択肢から、`charge.refunded` の後の返金失敗をどう扱うかを決める。

プロンプトを書いた人も、エラーログを貼り付けた人も、ステージを手作業でクリックして回った人もいません。

次へ: [このリポジトリを fork する](../fork-this-repo/)と、同じループを小さなサンプルアプリで動かせます。
または、[1 つの機能全体にわたる pull request のチェーン](../../discava/a-real-feature/)を読んでください。
