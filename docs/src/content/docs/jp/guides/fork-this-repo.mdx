このリポジトリ*そのもの*がワークフローです。Discava が動かしているのと同じ Speckit のセットアップ、issue
テンプレート、PR チェック、エージェントのワークフロー、ユニットテスト済みのグルーを、小さなノートアプリの周りに組み込んでいます。

**fork すれば、Discava のセットアップが手に入ります。** 自分の OpenHands を fork に向け、ノートアプリの spec を書けば、
[仕組み](../how-it-works/)で説明しているループを通っていきます。

## 手に入るもの

<FileTree>
- AGENTS.md すべてのエージェントが最初に読むもの。ノートアプリ向けに書かれています
- .specify/ Speckit のテンプレート、スクリプト、constitution
- .husky/ コミット時に Conventional Commits、シークレットスキャン、Biome。push 時に invariant マップ
- scripts/
  - setup-repository.sh ラベル、ブランチ保護など、fork ではコピーされない設定
  - start-agent-canvas.mjs エージェントの GitHub App として Agent Canvas を起動し、トークンを新しく保つ
- .github/
  - ISSUE_TEMPLATE/
    - implement-phase.md すべての実装 issue に含まれる指示
    - test-deployed-pr.md テスト担当エージェント向けのテスト issue (手動用)
  - actions/ 共通の CI セットアップ、Playwright の Chromium、変更パスのチェック
  - dependabot.yml 固定したアクションと依存関係を最新に保つ
  - workflows/
    - pr-checks.yml lint、テスト、ビルド、tasks の形式、invariant のカバレッジ、e2e、スクリーンショットのコメント
    - ui-screenshots.yml スクリーンショットのルール
    - ci.yml main でのチェック、Trivy、ドキュメントのデプロイ
    - agent-issues.yml spec → issue、マージ → 次の issue
    - archive-specs.yml 完了した spec → アーカイブ PR
    - agent-ci.yml 赤い CI → エージェント
    - agent-review.yml "changes requested" → エージェント
    - agent-status.yml その 2 つが共有するステップ
    - deploy.yml 緑の main → ステージ。インフラを追加するまではオフ
    - post-merge-verify.yml デプロイされた PR → テスト担当向けのテスト issue
    - cache-cleanup.yml 閉じた PR のキャッシュ
- packages/
  - tooling/agent/ グルーのルールと 223 個のユニットテスト
  - tooling/local-dev/ `pnpm dev` 用に DynamoDB local を起動する
  - notes-table/ ElectroDB エンティティ、DynamoDB local、invariant
  - notes-api/ tRPC プロシージャ
  - notes-website/ React、Vite、TanStack Router、shadcn/ui
  - e2e/ Playwright のシナリオ、`screenshot()` ヘルパー、各テスト後の invariant
- docs/ このサイト
</FileTree>

ノートアプリは完全にローカルで動きます (`pnpm dev`、DynamoDB local 用に Docker を使用)。そのため CI で
e2e テストを実行でき、エージェントがクラウドの認証情報を必要とすることはありません。

## 追加するもの

リポジトリに置けないものだけです。

1. **GitHub の設定**: エージェントが動くための GitHub App と、fork ではコピーされない設定。後者は
   `scripts/setup-repository.sh` が 1 回の実行で設定します。
2. **OpenHands**: `pnpm agent-canvas` で App として起動する、自分のマシン上の Agent Canvas と、
   fork に向けた automation。

## 追加するまでオフのもの

クラウドです。ノートアプリにはクラウドインフラがないため、マージしてもドキュメントサイト以外は何も
出荷されません。`deploy.yml` と `post-merge-verify.yml` は用意されていますが、自動では実行されません。
`packages/infra` に CDK アプリを追加して `AUTO_DEPLOY_STAGE` を設定すると、緑の `main` のたびにデプロイされ、
その後テスト担当エージェントがデプロイされたものをテストします。手順は[導入: デプロイ](../../adopt/deploy/)にあり、
[デプロイとセキュリティ](../../discava/deploy-and-security/)では Discava のパイプラインを説明しています。
