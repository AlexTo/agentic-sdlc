**現在地:** 🧑 人間のゲート #2。**成果物:** マージされたフェーズ 1 と、開かれたフェーズ 2 の issue。

PR はグリーンで、エージェントのレビュアーに承認された状態であなたに届きます。あなたの仕事は結果を判断することであり、
問題を探し回ることではありません。

<Steps>

1. PR の説明と **E2E screenshots** コメントを読みます。ウェブサイトのフェーズでは、これがブランチを pull せずに
   機能を見る方法です: 空のタグ入力、3 つのタグが付いたノート、適用されたフィルター、6 つ目のタグで表示されるエラー。

2. エージェントが一覧にした **(human)** タスクを確認し、実施します。

3. 承認してマージします。エージェントがあなた自身のトークンで push している場合、GitHub はあなたを PR の作成者とみなし、
   承認を受け付けないので、spec PR のときと同じようにバイパスします。

   代わりに変更を要求するには、PR をレビューして `openhands-review` ラベルを付けます。するとレビュアーエージェントの
   判定が、同じ 5 回の上限のもとで実装エージェントを差し戻します。

</Steps>

## マージで何が起きるか

**Agent Issues** workflow は、`openhands/` ブランチのマージ済み PR を検知し、マージ後の状態の `tasks.md` を読みます:

1. **このフェーズのエージェントのタスクにチェックが付いているか?** エージェントは PR の中で、各タスクを完了したコミットで
   チェックを付けます。**(human)** タスクは数えません: 手順 2 であなたが実施したもので、チェーンを止めることはありません。
2. **はい:** 次のフェーズの issue を開きます。フェーズ 2(ウェブサイト)は、フェーズ 1 とまったく同じように進みます:
   テストを先に、PR、ゲート、修正、レビュー。
3. **いいえ:** 何も開かれず、マージ済みの PR に、チェックの付いていないタスク ID を一覧したコメントが付きます。
   チェックを付けるか完了させてから、spec フォルダー名を指定して **Agent Issues** を手動で実行します。

チェーンを進めるのはエージェント自身のブランチだけです。あなた自身の PR は無視されます。

```text
spec PR merged ─► issue 1 ─► PR 1 merged ─► issue 2 ─► PR 2 merged ─► issue 3 ─► PR 3 merged ─► done
   (you)                       (you)                      (you)                      (you)
```
