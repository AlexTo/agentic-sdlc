**現在地:** 🤖 エージェント、その後ふたたび 🧑 人間のゲート #2。**成果物:** タグを説明するドキュメント。

ドキュメントはコードです(このサイトは `docs/` にある MDX です)。そのため、同じチェーンで扱われます。

## エージェントがすること

タスク `T007` から `T008` の issue を受け取ると、エージェントは:

1. spec と、フェーズ 1 と 2 のマージ済みコードを読みます。spec は機能が何のためにあるかを述べ、
   コードは機能が何をするかを示します。
2. notes アプリのページを更新します: `tags` 属性、新しい API の入力とフィルター、そしてルール
   (タグは 5 つまで、重複なし、大文字小文字を区別しない)を、spec の記述どおりの言い回しで書きます。
3. 新しいスクリーンショットを作らず、e2e シナリオのスクリーンショットを再利用するので、ドキュメントは
   アプリが実際に何をするかを示します。
4. ドキュメントサイトをビルドするので、リンク切れや形式の崩れた MDX は、他のビルドエラーと同じように PR を失敗させます。

## 確認すること

- ページ上のすべてのルールが `spec.md` の要件と一致しているか?
- ドキュメントと spec が食い違う場合は **spec が優先です。** ドキュメントを手で直すのではなく、spec を変更します。
- コードがしていないことがドキュメントに書かれていないか?

## なぜチェーンに含まれるのか

後から別の人が記憶を頼りに書いたドキュメントは、ずれていきます。spec とマージ済みのコードから生成され、
同じゲートでレビューされたドキュメントは、ずれません。エージェントのレビュアーは安価な 2 人目の読み手でもあり、
どのテストやコードにも裏付けられていないドキュメントの記述を指摘します。

## 完了

ドキュメントの PR をマージします。エージェントのタスクが残っていないので、新しい issue は開かれません。
機能は 1 文からマージ済みのコードとドキュメントになり、あなたが行った決定は 2 種類だけでした:
spec の承認と、各結果の承認です。
