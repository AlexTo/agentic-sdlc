**결과:** spec에서 issue를 열고, 빨간 CI나 "changes requested" 리뷰가 나오면 에이전트를 되돌려 보내고,
모든 task가 체크되면 spec을 archive하는 workflow.

<Steps>

1. 이 저장소의 `.github/workflows/`에서 **네 개의 workflow를 복사**합니다: `agent-issues.yml`,
   `agent-ci.yml`, `agent-review.yml`, 그리고 두 상태 workflow가 공유하는 step을 담은
   `agent-status.yml`. 그 안의 `@agentic-sdlc/` scope를 바꾸세요. trigger와 권한은
   [레퍼런스: workflow](../../reference/workflows/)에 나와 있습니다.

   에이전트가 GitHub App으로 동작한다면 repository 변수 `AGENT_APP_LOGIN`을 그 bot 로그인(예:
   `my-agent[bot]`)으로 설정하세요. `agent-status.yml`이 이를 `agent-review-status`에 넘깁니다. GitHub는 앱의
   리뷰에 association `NONE`을 주므로, 이것이 없으면 리뷰어의 판정이 에이전트를 되돌려 보내지 못합니다. 쓰기 권한이
   있는 계정으로 동작하는 에이전트에는 아무것도 필요 없습니다.

2. **`if:` 조건이 여러분의 결정과 맞는지 확인**합니다. 브랜치 prefix나 label을 바꿨다면
   여기서도 바꾸세요.

   ```yaml
   # agent-issues.yml
   if: >-
     github.event_name == 'workflow_dispatch' ||
     (github.event.pull_request.merged == true &&
     ((github.event.action == 'closed' &&
     (contains(github.event.pull_request.labels.*.name, 'spec-ready') ||
     startsWith(github.event.pull_request.head.ref, 'openhands/'))) ||
     (github.event.action == 'labeled' &&
     github.event.label.name == 'spec-ready')))

   # agent-ci.yml
   if: >-
     github.event.workflow_run.event == 'pull_request' &&
     startsWith(github.event.workflow_run.head_branch, 'openhands/') &&
     (github.event.workflow_run.conclusion == 'failure' ||
     github.event.workflow_run.conclusion == 'timed_out')

   # agent-review.yml
   if: >-
     startsWith(github.event.pull_request.head.ref, 'openhands/') &&
     github.event.pull_request.head.repo.full_name == github.repository &&
     contains(github.event.review.body, 'CHANGES REQUESTED')
   ```

3. **권한과 checkout은 복사한 그대로 유지**합니다. 각 workflow는 자신이 쓰는 것만 요청합니다.
   `pull-requests: write`는 불필요해 보이지만 그렇지 않습니다. PR의 label과 댓글은 issues API를 거치는데,
   이 권한이 없으면 issues API가 workflow 토큰을 거부합니다.

   두 상태 workflow는 `agent-status.yml`에서 **기본 브랜치**를 checkout합니다. Agent Issues는 **merge 커밋**을
   checkout하므로 merge된 PR이 한 체크를 볼 수 있습니다. 어느 쪽도 PR의 head를 checkout하도록 바꾸지
   마세요. 이 job들은 쓰기가 가능한 토큰을 가지고 있습니다.

4. **label보다 lock을 먼저 유지**합니다. Agent Issues는 각 issue를 `openhands` label 없이 열고,
   에이전트가 읽는 내용에 collaborator만 댓글을 달 수 있도록 대화를 lock한 다음에야 label을
   추가합니다. lock이 실패하면 label은 추가되지 않고 실행이 실패하며, 직접 lock해야 할 issue를
   알려 줍니다. 코드는 `helpers/conversation-lock.ts`입니다.

5. **concurrency 그룹을 유지**합니다. 각 그룹은 PR별 또는 브랜치별이며, `cancel-in-progress: false`입니다.
   그래서 한 PR에 대한 두 event가 각각 시도 횟수를 세는 일이 없고, 서로 다른 PR의 merge가
   서로를 취소하지 않습니다.

6. 완료된 spec을 치워 두고 싶다면 **`archive-specs.yml`을 복사**합니다. `main`으로의 push가 살아 있는
   `specs/*/tasks.md`를 바꾸면, **(human)** task를 포함해 모든 task가 체크된 각 spec에 대해
   `archive-spec/<folder>` 브랜치로 PR을 준비합니다. 이 PR은 폴더를 `specs/_archive/`로 옮기고
   그 폴더로 가는 링크와 그 폴더에서 나가는 링크를 고쳐 씁니다. Agent Issues는 `specs/_archive/`를 건너뛰며,
   archive된 `tasks.md`에 체크되지 않은 task가 있으면 `Tasks format`이 실패합니다.

   열린 에이전트 issue가 있는 spec과, 이미 archive PR이 있었던 spec은 건너뜁니다. spec을 살아 있는
   상태로 두려면 그 PR을 merge하지 않고 닫으세요.

   <Aside type="caution">
   저장소 설정 "Allow GitHub Actions to create and approve pull requests"는
   `scripts/setup-repository.sh`처럼 꺼 두세요. 이 설정은 workflow가 PR을 승인하는 것도 허용합니다.
   그러면 workflow는 브랜치를 push하고, 실행이 경고와 함께 링크를 남깁니다. 이 링크는 제목과 본문이
   채워진 PR을 열어 주며, 여러분이 제출하면 됩니다. 여러분이 연 PR은 PR Checks를 스스로 시작합니다.
   누군가 제출할 때까지 매 실행이 브랜치를 다시 push하고 같은 경고를 반복합니다.
   </Aside>

</Steps>

## 동작 확인

workflow가 `main`에 들어가면 저장소의 **Actions** 탭에 나타납니다.
**Actions → Agent Issues → Run workflow**를 열고, `does-not-exist`처럼 존재하지 않는 spec 폴더를 입력합니다.

실행은 다음 notice와 함께 성공합니다: `No issue created: no spec folder with a tasks.md was found`.

<Aside type="note">
`workflow_run`과 `pull_request_review` workflow는 기본 브랜치에 있는 버전으로만 실행됩니다.
변경 사항은 merge된 뒤에야 적용됩니다. 에이전트가 자신의 PR에서 이 workflow를 바꿀 수 없는 이유이기도
합니다.
</Aside>
