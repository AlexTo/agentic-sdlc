**결과:** 비준된 constitution, Agent Issues workflow가 읽을 수 있는 파일을 만드는
`tasks-template.md`, 그리고 상위 issue 줄이 있는 `spec-template.md`.

<Steps>

1. **constitution을 작성합니다.** 코딩 에이전트에서:

   ```text
   /speckit-constitution
   ```

   프로젝트만의 원칙을 알려 주세요: 아키텍처, 데이터 모델, 보안 기본값, 코드
   컨벤션. [Discava의 constitution](../../discava/constitution-and-guidance/)이 완전한 예시입니다. 그런 다음
   다음 조항들이 들어 있는지 확인하세요. 나머지 workflow가 이 조항들에 의존합니다. 명령은
   여러분의 스택에 맞게 고치세요.

   ```markdown
   ### Layered tests
   - **Unit tests.** New business logic MUST ship with unit tests covering its main behavior and
     the rules it enforces.
   - **End to end.** A change to a main user flow MUST add or extend an e2e scenario. Scenarios
     MUST make their own users and uniquely named data.
   - **Tests are a specification.** A failing test MUST be resolved by fixing the code, unless the
     spec or plan changes the behavior it covers. Weakening an existing test (loosening an
     assertion, deleting a case, adding `skip` or `only`, widening a mock or snapshot) is allowed
     only when a task names the behavior change that justifies it, and the PR description says
     so. Never edit a test just to turn it green.

   ### Everything runs locally
   A feature MUST work under `pnpm dev` with Docker and no cloud account. Any cloud service a
   feature adds MUST get a local stand-in or a documented, justified exception.

   ## Development Workflow
   - Features are implemented by autonomous agents, each on its own branch and pull request, so a
     task list MUST NOT require a local stack, Docker or `pnpm dev`. The agent runs unit tests,
     lint, typecheck and build itself. It writes the e2e tests, but pull request CI runs them. A
     task that needs a running local stack or people MUST be marked `(human)` in `tasks.md` and
     is done by a reviewer before merge.
   - Pull request CI is the gate. An agent MUST NOT merge, push to `main`, edit CI workflows, or
     weaken a test to make CI pass.
   - Plans MUST pass the Constitution Check, and any violation MUST be recorded in the plan's
     Complexity Tracking with a justification.
   ```

2. **`tasks-template.md`에서 테스트를 필수로 만듭니다.** `**Tests**: The examples below include test tasks. Tests are OPTIONAL`로
   시작하는 기본 줄을 다음으로 바꿉니다.

   ```markdown
   **Tests**: The constitution requires tests, so include them. Unit tests cover new business
   logic. A change to a main user flow needs an e2e scenario. Drop only the layers the feature
   doesn't touch.

   **Who runs what**: an automated agent implements these tasks without `pnpm dev` or Docker. It
   runs unit and component tests, lint, typecheck and `build` locally. The e2e scenarios are
   written by the agent but run on PR CI; a CI failure is the feedback for those. Mark a task
   **(human)** when it needs a running local stack or people (manual checks, timing, screen
   readers); a reviewer does those before merge.
   ```

   각 `### Tests for User Story <n>` 제목에서 `(OPTIONAL - only if tests requested)`를 제거합니다.

3. 형식 범례 (`[P]`, `[Story]`) 뒤에 **`tasks-template.md`의 형식 규칙을 추가**합니다.
   범례에 다음 줄을 추가합니다.

   ```markdown
   - **(human)**: needs a running local stack or people; not done by the agent. Not for
     screenshots: a task that changes what a user sees adds `screenshot()` calls to its e2e
     scenario, and CI posts them on the pull request (`UI Screenshots` fails without them)
   ```

   그런 다음 이 블록을 추가합니다.

   ```markdown
   **Read by automation**: the Agent Issues workflow reads this file to decide which tasks to hand
   the implementing agent, so keep this structure (PR checks refuse a file that strays from it):

   - every phase is a heading `## Phase <number>: <title>`, numbered upwards, with at least one
     task;
   - a user story's phase is titled `User Story <n> - <what it delivers>`; the first one ends the
     first implementation issue (setup, foundations and that story);
   - every task is a line `- [ ] T<3 digits> <description>` starting in the first column, under a
     phase, with an id no other task has; a task added later takes the next unused id, wherever
     it is placed;
   - a finished task is ticked in place (`- [x]`), never deleted or renumbered.
   ```

4. `/speckit-tasks`가 항상 테스트 task를 생성하도록, `tasks-template.md`의 `### Tests for User Story 1`
   (그리고 2, 3) 아래에 **각 user story의 테스트 task를 추가**합니다.

   ```markdown
   - [ ] T01A [P] [US1] Unit tests for new procedures/access patterns in the API's `*.test.ts`
   - [ ] T01C [US1] (If it changes a main user flow) E2E scenario in `packages/e2e/src/scenarios/[flow].e2e.ts`
   ```

   Discava는 invariant를 위해 세 번째 task를 추가합니다: *"(If a rule spans records or writers) Invariant in
   `helpers/invariants/` and a test that breaks it, written before the shared write helper"*.

5. `tasks-template.md` **끝의 notes에 한 줄을 추가**합니다.

   ```markdown
   - Do not edit existing tests to make them pass. If one looks wrong, stop and raise it. A task
     that changes an existing test must cite the spec change behind it
   ```

6. header 필드 아래에 **`spec-template.md`의 상위 issue 줄을 추가**합니다.

   ```markdown
   **Parent issue**: [#<number>, or "none" if there is no tracking issue]
   ```

</Steps>

## 동작 확인

작은 기능으로 버릴 spec과 task를 생성합니다. 그런 다음 glue script가 준비되면
([5단계](../glue-scripts/)):

```bash
pnpm nx run @your-scope/common-scripts:validate-tasks
```

```text
1 tasks.md file(s) are in the expected format.
```

확인이 끝나면 버릴 spec 폴더를 삭제합니다.

<Aside type="caution">
`/speckit-tasks`는 가끔 `### Phase 2`라고 쓰거나 task를 들여씁니다. 그것이 바로 validator가 잡아내는
것이므로 validator를 느슨하게 만들지 마세요. 생성된 파일이 통과할 때까지 템플릿 문구를 고치세요.
</Aside>
