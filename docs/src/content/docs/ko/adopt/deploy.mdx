import { Steps, Aside } from '@astrojs/starlight/components';

**결과:** `main`으로의 모든 push에 대한 Trivy 스캔, 초록색이 된 각 `main`을 development stage로
배포하는 Deploy workflow, 사람을 기다리는 production 배포, 그리고 원한다면 merge된 각 변경을
development stage에서 테스트하는 테스터 에이전트.

이 저장소에는 workflow가 꺼진 상태로 들어 있습니다: `deploy.yml`은 직접 실행하거나
`AUTO_DEPLOY_STAGE`가 설정되어야만 실행되고, `post-merge-verify.yml`은 배포 뒤에만 실행됩니다. 노트 앱에는
클라우드 인프라가 없으므로, 작성할 부분은 여러분의 몫입니다. 각 단계는 Discava가 쓰는 AWS와 CDK를 기준으로
설명하지만, 구조는 어떤 cloud에서든 동작합니다.

<Steps>

1. 스캔하려는 프로젝트에 **`trivy` target을 추가**합니다 (루트의 `pnpm trivy`가
   `nx run-many --target trivy --all`을 실행합니다). 복사한 `ci.yml`의 `trivy` job이 `main`으로의 모든
   push에서 이를 실행합니다. `build`와는 별도의 job이므로, 새로 공개된 CVE가 다른 것을 막지 않고 `main`에만
   표시됩니다. 수용한 발견 사항은 `.trivyignore`에 한 줄에 ID 하나씩 기록합니다.

2. `packages/infra`에 CDK 앱으로 **인프라를 추가**하고, 그 `src/main.ts`에 environment마다 stage를 하나씩
   둡니다.

   ```bash
   pnpm nx g @aws/nx-plugin:ts#infra --name=infra
   ```

   Deploy workflow가 실행하는 것은 이 앱의 `deploy-ci` target입니다. 노트 웹사이트용 construct는 이미
   `packages/common/constructs`에 있습니다.

3. 각 stage에 대해 **key 없는 cloud 접근을 설정**합니다: GitHub OIDC provider,
   `repo:owner/repo:environment:<stage>`에 대해서만 신뢰하는 deploy role, permissions boundary가 있는
   CloudFormation execution role, CDK bootstrap, 그리고 `AWS_REGION`, `AWS_DEPLOY_ROLE_ARN`,
   `AWS_EXECUTION_ROLE_ARN` 변수를 가진, stage 이름을 딴 GitHub environment. Discava의
   [`scripts/setup-stage.sh`](https://github.com/AlexTo/discava/blob/main/scripts/setup-stage.sh)가
   자신의 stage에 대해 이 모두를 수행합니다. 고쳐 쓰기 전에 읽어 보세요. access key를 저장하지 마세요.

4. fork에서 작업하지 않는다면 **`.github/workflows/deploy.yml`을 복사**하고, 그 안의 `@agentic-sdlc/`
   scope와 기본 stage 이름을 바꿉니다. 이 workflow는 CI가 검증한 커밋을 checkout하고, `packages/infra`나
   environment의 변수가 없으면 명확한 에러와 함께 일찍 멈추며, Trivy를 실행하고, synth한 뒤, 그 커밋이 여전히
   `main`의 최신일 때만 배포합니다. 이 최신 여부 확인은 job의 concurrency slot *안에* 있으므로, 실행이 다른
   실행 뒤에서 기다렸더라도 배포 직전의 `main`을 반영합니다.

5. development stage에 대해 **자동 배포를 켭니다**. **Settings → Secrets and
   variables → Actions → Variables**에서 development stage의 이름으로 저장소 변수
   `AUTO_DEPLOY_STAGE`를 추가합니다.

6. **production을 보호합니다.** **Settings → Environments**에서 production stage의
   environment를 열고 **Required reviewers**를 추가합니다. 배포하려면 **Actions → Deploy → Run
   workflow**를 열고 production stage를 입력합니다. 그러면 job이 승인을 기다립니다.

7. 배포된 각 변경을 테스트하고 싶다면 **테스터 에이전트를 추가**합니다 (빈틈 11). 이 저장소에서 이미
   그 glue(5단계의 `post-merge-test/`), issue 템플릿(4단계), 그리고 Deploy 실행이 test stage에 올린 각
   pull request에 대해 테스트 issue를 여는 `.github/workflows/post-merge-verify.yml`을 갖고 있습니다.
   테스트는 `TEST_STAGE`에서 이루어지며, 이는 기본값이 `AUTO_DEPLOY_STAGE`인 저장소 변수입니다.

   OpenHands 쪽에서는 `tester` agent profile과, `openhands-test` label이 붙은 issue를 폴링하는
   automation을 추가합니다. 이를 위한 카탈로그 템플릿은 없습니다. Discava의 worker와 프롬프트는
   [OpenHands 설정](../../discava/openhands-setup/#테스터-github-issue-tester)과
   [에이전트 프롬프트](../../discava/agent-prompts/#테스터)에 설명되어 있습니다. 테스터에게 다음을 주세요.

   - development 계정에 로그인된 cloud CLI. 접근 권한은 테스트에 필요한 만큼만 줍니다
   - 앱의 역할마다 하나씩 둔 테스트 사용자. OpenHands secret으로 저장합니다
   - Playwright와 Chromium처럼 테스터가 조작할 수 있는 브라우저

   <Aside type="caution" title="공개 저장소인가요? 먼저 댓글을 collaborator로 제한하세요">
   테스터는 그 자격 증명을 가진 채로 issue, pull request, 그리고 그 댓글을 읽습니다. 저장소가 공개라면 낯선
   사람의 댓글이 테스터에게 지시를 전할 수 있습니다. `scripts/setup-repository.sh`가 상호작용을 최대 6개월 동안
   collaborator로 제한하므로, 제한이 끝나기 전에 다시 실행하세요. 또한 `helpers/conversation-lock.ts`의 잠금을
   유지하고, "테스트 방법"은 issue가 아니라 automation 자체의 프롬프트에 두며, 데이터가 중요한 stage를 절대
   대상으로 삼지 마세요.
   </Aside>

</Steps>

## 동작 확인

아무 PR이나 merge합니다. CI가 실행되고, 이어서 **Deploy**가 development stage로 저절로 시작됩니다.
오래된 커밋에서 CI를 수동으로 다시 실행합니다: Deploy가 `Skipping deploy: no longer main's latest commit`을
로그에 남기고 아무것도 배포하지 않습니다.

테스터를 설정했다면: 그 배포 뒤에 **Post-merge Verify**가 `test(post-merge): verify #<pr> …`라는 제목의
잠긴 issue를 `openhands-test` label을 붙여 엽니다. 폴링 한 번 안에 테스터가 시작하고, 그 보고서가 issue의
댓글로 나타납니다.

<Aside type="note">
어떤 에이전트도 배포하지 않으며, 이 role들을 보지도 못합니다. 개발자 에이전트와 리뷰어 에이전트에게는
GitHub 토큰만 있으면 됩니다. 테스터의 development 계정 접근은 deploy role과 별개이며, deploy role은 stage의
environment 안에서 `main`으로부터 실행되는 workflow만 assume합니다.
</Aside>

다음: 이제 여러분의 저장소에는 이 저장소의 fork에 있는 모든 것이 갖춰졌습니다. fork 대신
여러분의 저장소로 [2. 저장소 설정하기](../../setup/github-repository/)부터 이어서 진행하세요.
