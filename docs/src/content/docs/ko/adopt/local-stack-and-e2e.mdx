import { Steps, Aside, FileTree } from '@astrojs/starlight/components';

**결과:** 로컬 대체물로 앱 전체를 시작하는 `pnpm dev`, CI가 모든 PR에서 실행하는 Playwright suite,
PR에 게시되는 스크린샷, 그리고 매 테스트 후 확인되는 invariant.

이 단계는 여러분의 스택에 가장 크게 좌우됩니다. 또한 CI가 cloud 자격 증명 없이 에이전트에게 실제
피드백을 줄 수 있게 해 주는 단계이기도 합니다.

<Steps>

1. `pnpm dev`가 모든 것을 실행하도록, `dev` target으로 시작되는 **로컬 대체물을 모든 cloud 서비스에
   마련**합니다. 이 저장소의 `packages/tooling/local-dev/`는 노트 테이블을 위해 Docker로 DynamoDB local을
   시작합니다. [Discava의 대체물](../../discava/local-stack/#로컬에서-실행되는-것)은 S3, SQS, OpenSearch,
   Cognito도 다루며, cloud에서 Lambda trigger, stream, EventBridge가 호출하는 것과 같은 handler를 호출하는
   "event runner" 프로세스도 있습니다.

   backend 코드는 하나의 flag (`LOCAL_DEV=true`)로 전환하고, endpoint는 하나의 공유 모듈에 둡니다.
   여전히 cloud에서만 실행되는 것은 기여 가이드에 나열하고, 그것이 필요한 task는
   **(human)**으로 표시합니다.

2. 이 저장소에서 **e2e 프로젝트 `packages/e2e/`를 복사**하고, 그 시나리오를 여러분의 것으로 바꿉니다.
   사용자 흐름당 파일 하나입니다. 유지할 것:

   <FileTree>
   - packages/e2e/
     - playwright.config.ts CI matrix가 suite를 나눌 수 있도록 `E2E_SHARD`를 읽고, `pnpm dev`를 시작하며, worker 하나, CI에서만 재시도
     - src/helpers/
       - screenshots.ts `screenshot(page, 'name')`, PR Checks의 `e2e` job이 업로드하는 그림을 저장
       - table-invariants.ts 매 시나리오 후 invariant를 확인하는 Playwright `test`
   </FileTree>

   각 시나리오는 자신만의 사용자와 고유한 이름의 데이터를 만들고, 어떤 시나리오도 로컬 데이터를
   초기화하지 않으므로, 어떤 순서로든 실행됩니다. 사람이 볼 만한 곳에서, 화면에 보이는 것에 대한
   `expect` 다음에 `screenshot`을 호출하세요.

   ```ts
   await expect(page.getByRole('heading', { name: 'Reviews' })).toBeVisible();
   await screenshot(page, 'reviews section with three reviews');
   ```

3. `packages/notes-table/src/helpers/invariants/`의 **invariant를 복사**해 여러분의 테이블을 소유한
   패키지에 둡니다. 서로 다른 코드가 쓴 record에 걸친 규칙 (counter, aggregate, 순서)마다, 데이터의
   스냅샷을 훑어 위반 사항을 반환하는 검사를 작성하고, 그것을 깨뜨리는 단위 테스트도 작성합니다.
   `packages/notes-table/README.md`의 "Rules that span records"가 하나를 추가하는 과정을 안내합니다.

   시나리오는 `@playwright/test` 대신 `table-invariants.ts`에서 `test`를 가져옵니다. 각 시나리오가 끝난 뒤,
   테이블에 이전에 없던 위반이 있으면 그 시나리오를 실패시킵니다. *새로운* 위반만 세므로 오래된 로컬
   데이터 때문에 실행이 실패하는 일은 없고, `expect.poll`은 백그라운드 작업 (stream handler, 재계산)이
   따라잡을 시간을 줍니다.

4. **writer 맵을 생성하고, pre-push hook을 복사**합니다.
   `pnpm nx run @your-scope/tooling-agent:entity-writers`를 실행하고, 이것이 쓰는 `entity-writers.json`을
   커밋합니다. 이 저장소에서 `.husky/pre-push`를 복사하고, 그 `MAP`과 `PATHS`가 여러분의 것을 가리키게
   하세요: 브랜치가 테이블에 쓸 수 있는 코드를 바꾸면, 이 hook이 맵을 다시 생성하고 맵이 바뀌었다면 push를
   멈춥니다. 그러면 `Invariant coverage` PR 검사가 맵을 base 브랜치의 맵과 비교하고, writer를 추가하는
   PR을 invariant가 그 엔터티를 지정할 때까지 붙잡아 둡니다.

5. 두 사용자가 경쟁할 수 있는 쓰기에 대해 **동시성 테스트를 추가**합니다: `Promise.all`로 같은 API
   요청을 같은 순간에 보낸 뒤, 결과와 invariant를 검증합니다.

</Steps>

## 동작 확인

```bash
pnpm nx e2e @your-scope/e2e
ls dist/packages/e2e/screenshots/*/
```

그런 다음 페이지를 바꾸고 `screenshot(` 호출을 하나 추가하는 PR을 엽니다. PR Checks가 끝나면 PR에
**E2E screenshots** 제목의 댓글이 달리고, "Added by this pull
request" 아래에 새 그림이 나열됩니다.

<Aside type="tip">
앱이 아직 완전히 로컬에서 실행되지 않는다면, 실행되는 것부터 시작하세요. API와 데이터베이스만 다루는
suite라도 에이전트 실수의 대부분을 잡아냅니다. 대체물은 서비스 하나씩 추가하고, 그때까지 나머지는
**(human)** task로 두세요.
</Aside>
