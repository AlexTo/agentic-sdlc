사람이 루프에서 빠지는 것이 아닙니다. 판단이 가장 중요한 두 지점으로 옮겨 가고, 그 사이의 기다림과 타이핑에서는
멀어집니다.

## 게이트 1: spec 승인

spec PR은 코드처럼 리뷰됩니다. **`spec-ready` label과 함께** 이를 merge하는 것만이 구현을 시작시킵니다.

살펴볼 것:

- `spec.md`가 여러분이 실제로 원하는 것을 말하고 있으며, 모든 규칙이 요구 사항으로 명시되어 있는가?
- 각 phase가 한 번 앉은 자리에서 리뷰할 수 있을 만큼 작은가?
- `plan.md`에 코드 리뷰였다면 거절했을 내용이 있는가?

### 이제 이것이 주된 병목이다

루프가 스스로 돌아가기 시작하면 코드 리뷰는 작아집니다. phase마다 초록색이고 에이전트가 승인한 PR 하나입니다.
가장 느린 사람 단계는 바로 이 단계입니다. 모든 기능은 누군가 spec이 옳다고 동의할 때까지 여기서 기다립니다.

개발자를 기다려야 하는 것은 아닙니다. `spec.md`는 평이한 언어(사용자 스토리, 인수 시나리오, 기능 요구 사항)로
되어 있으므로, **비즈니스 분석가**나 **프로덕트 오너**가 spec PR에서 리뷰하고, 댓글을 달고, 승인할 수 있습니다.
리뷰를 파일별로 나누세요.

| 리뷰어 | 읽는 것 | 묻는 것 |
| --- | --- | --- |
| 프로덕트 오너, 비즈니스 분석가 | `spec.md` | 이것이 우리가 원하는 기능인가? 규칙과 엣지 케이스가 맞는가? 빠진 것이 있는가? |
| 엔지니어 | `plan.md`, `data-model.md`, `contracts/`, `tasks.md` | 설계가 견고한가? phase가 리뷰할 수 있을 만큼 작은가? |

저장소를 읽을 수 있는 사람은 누구나 댓글을 달 수 있습니다. 그들의 승인이 branch protection에 반영되려면 쓰기
권한이 필요합니다.

## 게이트 2: 결과 승인

각 에이전트 PR은 CI가 초록색이 되고 리뷰어 에이전트가 승인한 뒤에 여러분에게 도착합니다. 여러분의 일은 문제를
찾아다니는 것이 아니라 결과를 판단하는 것입니다.

- PR 설명을 읽습니다. 무엇이 바뀌었는지, 어떤 작업인지, 여러분에게 남겨진 **(human)** 작업이 무엇인지.
- 브랜치를 받아 오는 대신 **E2E screenshots** 댓글을 봅니다. 기능이 동작하는 모습을 보여 줍니다. 예시는
  [검증이 가장 중요하다](../layers-of-trust/#검증이-가장-중요하다)를 참고하세요.
- **(human)** 작업을 합니다. 로컬 스택이나 배포된 stage에서의 수동 확인입니다.
- merge하거나 변경을 요청합니다. 에이전트가 변경하게 하려면 리뷰 후에 `openhands-review` label을 붙이세요.
  리뷰어 에이전트가 PR을 다시 리뷰하고, "changes requested" 판정이 개발자 에이전트를 review-fix 루프로 돌려보내며,
  같은 `review-fix-*` label로 횟수가 세어집니다.

자동 배포를 쓰면, 그 뒤에 테스터 에이전트가 여러분이 merge한 것을 개발 stage에서 테스트하고 테스트 issue에
보고합니다. 그 보고서는 게이트 앞이 아니라 뒤에 옵니다. 변경이 실행되는 곳에서, 화면에서도 저장된 데이터에서도
동작하는지 알려 주며, 실패한 보고서는 여러분이 처리할 몫입니다.

## 에이전트가 절대 하면 안 되는 것

| 절대 안 됨 | 강제하는 것 |
| --- | --- |
| merge, 또는 `main`에 push | 승인 리뷰를 요구하는 branch protection. 에이전트의 토큰은 자기 브랜치에만 쓰입니다 |
| `.github/workflows/` 편집 | constitution과 issue 지시 사항. 리뷰어와 사람의 리뷰가 잡아냅니다. glue workflow는 기본 브랜치의 코드로 실행되므로, PR에서 workflow를 편집해도 이를 바꿀 수 없습니다 |
| 통과시키려고 테스트 약화 | constitution("tests are a specification"), issue 지시 사항, 리뷰어 에이전트 |
| 배포, 또는 인프라 변경 | 어떤 에이전트에게도 deploy role이 주어지지 않습니다. 배포는 GitHub environment의 수명이 짧은 OIDC role을 사용합니다. 개발자 에이전트와 리뷰어 에이전트는 클라우드 접근이 전혀 필요 없습니다. 테스터는 개발 stage에만 접근하며, 프롬프트가 테스터를 읽기와 앱을 통해 직접 만든 테스트 데이터로 제한합니다 |
| 낯선 사람의 지시 받기 | 에이전트에게 넘겨지는 모든 issue와 pull request는 잠기므로, 쓰기 권한이 있는 사람만 댓글을 달 수 있습니다. 테스터는 workflow가 연 issue만 테스트하며, 테스터의 지시 사항은 issue가 아니라 자신의 프롬프트입니다 |
| 작업 범위 밖에서 일하기 | issue가 범위를 지정합니다. 모든 에이전트 작업이 체크될 때까지 다음 issue는 열리지 않습니다 |
| 끝없이 재시도 | 루프당 다섯 번의 시도, label로 횟수를 셉니다 |

## 일찍 불려 가는 경우

| 신호 | 무슨 일이 있었나 | 해야 할 일 |
| --- | --- | --- |
| `ci-fix-exhausted` | 자동 수정 후에도 CI가 다섯 번 실패했습니다 | 마지막 실패를 읽으세요. 가이드를 댓글로 달거나, 직접 고치거나, spec을 고치세요. 그런 다음 [루프를 초기화](../../reference/labels/#루프-초기화)하세요 |
| `review-fix-exhausted` | 다섯 번의 라운드 후에도 리뷰어가 여전히 변경을 요청합니다 | 리뷰어가 옳은지 판단하세요. spec이 모호한 경우가 많습니다 |
| 에이전트가 issue에 남긴 댓글 | 지시받은 대로, 막혀서 멈췄습니다 | 답을 달고, `openhands` label을 제거했다가 다시 붙이세요 |
| merge된 PR의 댓글: "the next implementation issue … was not opened" | 해당 phase의 작업이 모두 체크되지 않았습니다 | 체크하거나 마무리한 뒤, 해당 spec 폴더에 대해 Agent Issues를 직접 실행하세요 |
| 실패했거나 막혔다는 보고서와 함께 열린 채 남은 테스트 issue | 테스터가 merge된 변경이 개발 stage에서 동작하지 않는다는 것을 발견했거나, 테스트할 수 없었습니다 | 보고서를 읽으세요. 수정 PR이 열렸다면 merge하거나, stage를 고치거나, 작업을 작성하세요. 다시 테스트하려면 `openhands-test`를 다시 붙이세요 |

## 프로덕션은 선택적인 세 번째 게이트

개발 stage로의 배포는 `main`이 초록색일 때마다 자동으로 할 수 있습니다. 프로덕션 배포는 GitHub environment의
required reviewers를 사용해 사람을 기다려야 합니다. [배포와 보안](../../discava/deploy-and-security/)을
참고하세요.
