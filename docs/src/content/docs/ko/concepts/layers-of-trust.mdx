자동화는 결과를 믿을 수 있을 때만 가치가 있습니다. 모든 변경은 여러 계층의 검사를 거칩니다. 비용이 적은 자동
검사가 먼저 실행되어 가장 많은 것을 잡아내고, 그것들이 판단할 수 없는 것만 사람에게 갑니다.

</p>

| 수준 | 계층 | 잡아내는 것 |
| --- | --- | --- |
| **코드베이스** | 단위 테스트 | 잘못된 비즈니스 로직과 깨진 규칙 |
| | invariant | 여러 레코드에 걸친 규칙을 깨는 데이터, 모든 e2e 테스트 후에 검사 |
| | 동시성 테스트 | 두 요청이 같은 순간에 들어올 때의 경쟁 상태 |
| **정적 분석** | lint, typecheck, build | 스타일, 타입, 빌드 오류 |
| | tasks 형식 검사 | 체인을 조용히 멈춰 버릴, 형식이 잘못된 `tasks.md` |
| | 생성된 파일 검사 | 에이전트가 커밋하는 것을 잊은 lint나 build 출력 |
| **검증** | end-to-end 테스트 | 실제 브라우저에서 로컬 스택을 대상으로 한, 깨진 사용자 흐름 |
| | 스크린샷 | 아무도 보지 않은 UI 변경 |
| | merge 후 테스트 | 모든 검사를 통과하고도 배포된 스택에서, 화면에서든 저장한 것에서든 실패하는 변경. merge 후에 테스터 에이전트가 찾아냅니다 |
| **글** | constitution, `AGENTS.md`, skill | 에이전트가 작성하기 *전에* 읽는 가이드. 그래서 관례가 잡히는 대신 지켜집니다 |
| | 리뷰어 에이전트 | 어떤 테스트도 다루지 않는 문제, 코드 리뷰처럼 읽어서 찾음 |
| **사람의 리뷰** | 최종 리뷰 | 위 계층들이 판단할 수 없는 모든 것. merge는 언제나 사람이 합니다 |

## 검증이 가장 중요하다

단위 테스트, lint, 타입은 코드가 그 자체로 일관된다는 것을 보여 줍니다. 기능이 실제 스택에서 사용자가 보는
방식대로 *동작한다*는 것은 e2e 테스트와 스크린샷만이 보여 줍니다. 이것이
[원칙 1](../principles/#1-검증-우선-에이전트에게-손과-눈을-주기)입니다. 사람이 가장 빨리 확인할 수 있는 계층이기도
합니다. 스크린샷이 있으면 브랜치를 받아 오지 않고도 몇 분 만에 PR을 판단할 수 있습니다.

CI가 이를 기본값으로 만듭니다.

1. UI 흐름에 대한 모든 e2e 시나리오는 리뷰어가 보고 싶어 할 각 상태에서 `screenshot(page, 'name')`을
   호출합니다.
2. CI가 PR에 **E2E screenshots** 댓글을 남깁니다. 이 PR이 추가한 스크린샷을 (이미 있던 것과 구분해) 나열하고
   실행의 artifact로 연결합니다.
3. UI 변경에 스크린샷이 없으면 `UI Screenshots` 검사가 실패합니다.

Discava [#486](https://github.com/AlexTo/discava/pull/486#issuecomment-6980411897)의 알림 설정 예시입니다.

리뷰하는 사람은 새 스크린샷 아홉 장을 열어 각 상태를 확인합니다. 모든 유형이 나열된 설정, 저장된 스위치, 중지되었다가
다시 켜진 이메일, 유효한 구독 취소 링크와 유효하지 않은 구독 취소 링크, 오류와 "다시 시도"입니다. 각각이 spec의
요구 사항이며, 동작하는 모습을 눈으로 확인한 것입니다.

### merge 후, 실제 스택에서

E2E 테스트는 로컬 대체물을 대상으로 실행됩니다. 메모리가 부족한 함수, 빠진 권한, 배포된 stage에서만 다른 설정은
볼 수 없습니다. 그래서 마지막 검증은 merge 후에 일어납니다. 변경이 개발 stage에 배포되면 **테스터 에이전트**가
테스트 사용자로 로그인하고, 흐름을 클릭해 보고, 그 뒤의 API를 호출합니다. 그런 다음 화면에 보인 것뿐 아니라
쓰인 것을 검증합니다. 데이터베이스의 레코드, 파일 저장소의 객체, 검색 인덱스의 문서(Discava에서는 DynamoDB, S3,
OpenSearch), 그리고 로그입니다. 보고서에는 모든 확인 항목이 증거와 함께 나열됩니다. [테스트 루프](../feedback-loops/#merge-후-테스트-루프)를 참고하세요.

## 글은 안내하고, 코드는 강제한다

글(constitution, `AGENTS.md`, issue의 지시 사항)은 작성 비용이 적고 대부분의 실수를 막아 주지만, 에이전트가
잘못 읽거나 건너뛸 수 있습니다. 그래서 중요한 규칙마다 실패하는 검사도 함께 둡니다.
[원칙 5](../principles/#5-규칙과-skill을-결정적으로-만들기)에 Discava의 검사가 나열되어 있습니다.

규칙을 추가할 때는 이렇게 물어보세요. 에이전트가 이것을 무시하면, 무엇이 빨간색이 되는가?

## 테스트는 명세다

Discava constitution에서 가장 중요한 규칙입니다.

> A failing test MUST be resolved by fixing the code, unless the spec or plan changes the behavior
> it covers. Weakening an existing test (loosening an assertion, deleting a case, adding `skip` or
> `only`, widening a mock or snapshot) is allowed only when a task names the behavior change that
> justifies it, and the PR description says so.

CI를 초록색으로 만들라는 압박을 받는 에이전트는 언젠가는 테스트를 "고칠" 것입니다. issue 템플릿에서 반복되고
리뷰어 에이전트가 검사하는 이 규칙이 테스트 스위트가 의미를 갖도록 지켜 줍니다.

## invariant: 데이터를 위한 테스트

단위 테스트는 함수 하나를 검사합니다. E2E 테스트는 흐름 하나를 검사합니다. 서로 다른 PR에서 서로 다른 에이전트
실행이 작성한 두 기능이, 둘 모두에 걸친 규칙을 깨는 상태로 데이터베이스를 남겨 두어도 둘 다 알아채지 못합니다.
invariant가 그 빈틈을 메웁니다. invariant는 모든 데이터에 대한 검사 목록으로, 예를 들어 "강좌의 평점 수는
공개된 리뷰 수와 같다" 같은 것이며, **모든** e2e 테스트 후에 실행됩니다. invariant가 위반되면 그것을 일으킨
테스트가 실패합니다.

<Aside type="tip">
invariant는 에이전트가 더 많은 코드를 작성할수록 가장 큰 효과를 내는 계층입니다. 두 에이전트가 각자 국소적으로는
옳을 때 생기는 실수를 잡아냅니다.
</Aside>
