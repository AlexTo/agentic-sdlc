이 워크플로의 모든 것은 하나의 결정에서 나옵니다. **개발자를 루프 안에서 꺼내 루프의 양 끝에 둡니다.**
사람은 *무엇을* 만들지, 그리고 *그것이 좋은지*를 결정합니다. 그 사이의 모든 일은 에이전트가 일반적인 GitHub
프로세스를 통해 합니다.

원칙은 중요한 순서대로 나열되어 있습니다. 몇 가지만 할 수 있다면 위에서부터 시작하세요.

## 1. 검증 우선: 에이전트에게 손과 눈을 주기<Icon name="magnifier" class="heading-icon" />

앱을 실행해서 자신이 만든 것을 볼 수 없는 에이전트는 추측하고 있을 뿐이고, 나머지 원칙들은 그 추측을
정리해 줄 뿐입니다. 컴파일되고 단위 테스트를 통과한 코드도 여전히 사용자에게는 실패할 수 있으므로, 에이전트는
사람이 하듯이 **자신이 만든 것을 백엔드부터 프런트엔드까지 실행해 봐야** 합니다.

- **손:** 클라우드 계정 없이 로컬 스택에서 앱 전체를 띄우고, API를 호출하고, 로그인하고, 실제 브라우저에서
  흐름을 클릭해 보고, 그 뒤의 백그라운드 작업을 실행시킵니다.
- **눈:** 돌아오는 것을 읽습니다. 응답, 로그, 데이터베이스에 남은 데이터, 그리고 리뷰어가 보고 싶어 할 모든
  상태의 스크린샷입니다.

에이전트가 이것을 자기 컴퓨터에서 하는 것은 아닙니다. 에이전트는 e2e 시나리오를 작성하고, CI가 모든 PR마다
새 로컬 스택에서 이를 실행합니다. 결과, invariant 실패, 스크린샷이 PR로 돌아오므로, 에이전트는 자기 실수를
스스로 잡아내고 모든 PR은 증거와 함께 도착합니다.

첫날부터 이를 염두에 두고 만드세요. 모든 클라우드 서비스에는 로컬 대체물이, 모든 사용자 흐름에는 e2e
시나리오가, 모든 UI 상태에는 스크린샷이 있어야 합니다. 에이전트가 실행할 수 없는 것은 사람이 검증해야 하는
작업이 됩니다.

## 2. spec이 진실의 원천<Icon name="document" class="heading-icon" />

기능은 코드처럼 리뷰되는 `spec.md`, `plan.md`, `tasks.md`로 시작합니다. 에이전트는 이 문서들을 바탕으로
구현합니다. 동작을 바꾸려면 spec을 바꾸고 plan과 tasks를 다시 생성하세요. 코드를 손으로 고치고 spec이 낡도록
내버려 두지 마세요.

## 3. 피드백은 여러분이 아니라 자동화된 게이트가 준다<Icon name="approve-check-circle" class="heading-icon" />

lint, typecheck, 단위 테스트, invariant, e2e 테스트, 동시성 테스트, 스크린샷, 에이전트 리뷰어가 모든 PR에서
실행됩니다. 빨간 결과는 변경을 작성한 에이전트에게 곧바로 돌아갑니다. 누구도 오류 메시지를 붙여 넣지
않습니다.

## 4. 사람은 중요한 두 가지 결정을 맡는다<Icon name="star" class="heading-icon" />

1. **spec 승인.** `spec-ready` label과 함께 spec PR을 merge하는 것이 시작 신호입니다.
2. **결과 승인.** 사람이 최종 리뷰를 하고 각 PR을 merge합니다.

## 5. 규칙과 skill을 결정적으로 만들기<Icon name="setting" class="heading-icon" />

`AGENTS.md`나 constitution에만 적힌 규칙은 부탁에 불과합니다. 에이전트는 이를 놓치거나, 두 가지로 해석하거나,
긴 세션에서 잊어버릴 수 있습니다. 스크립트로 규칙을 검사할 수 있는 곳이라면 어디든 스크립트를 작성하고, hook이나
PR 검사에서 실행하고, 글은 설명으로 남겨 두세요. 실패한 검사는 다른 빨간 결과와 같은 피드백 루프를 통해
무엇이 어디서 잘못되었는지 에이전트에게 정확히 알려 줍니다.

Discava는 곳곳에서 이렇게 합니다.

| 글로 쓴 규칙 | 이를 강제하는 것 |
| --- | --- |
| `tasks.md`는 정해진 형식을 따른다 | `Tasks format` PR 검사. 이것이 없으면 형식이 잘못된 phase는 조용히 건너뛰어집니다 |
| UI 변경은 e2e 시나리오에서 스크린샷을 찍는다 | 마크업이나 스타일이 바뀌었는데 어떤 시나리오에도 `screenshot(` 호출이 추가되지 않으면 `UI Screenshots` 검사가 실패합니다. 메인테이너는 `no-ui-screenshots`로 이를 면제할 수 있습니다 |
| 여러 레코드에 걸친 규칙에는 invariant가 필요하다 | 핵심 테이블에 쓰는 주체를 바꾸면서 `helpers/invariants/`의 invariant 검사를 건드리지 않는 PR은 `Invariant coverage` 검사가 실패시킵니다. pre-push hook이 writer 맵을 최신으로 유지합니다. 메인테이너는 `no-new-invariant`로 이를 면제할 수 있습니다 |
| Conventional Commits, 비밀 정보 커밋 금지 | `commit-msg` hook의 commitlint, 모든 커밋에 대한 `git-secrets` |
| Speckit의 각 단계는 자체 브랜치와 커밋을 가진다 | 에이전트가 기억하든 말든, skill이 Speckit의 extension hook에서 이를 위한 스크립트를 실행합니다 |

리뷰에서 같은 지적을 두 번 쓰고 있다면, 아마 검사가 하나 빠져 있는 것입니다.

## 6. glue는 프롬프트가 아니라 코드다<Icon name="puzzle" class="heading-icon" />

단계 사이에도 마찬가지입니다. *다음에 무슨 일이 일어날지*를 결정하는 모든 것(어떤 issue가 열릴지, 에이전트가
되돌아갈지, 언제 멈출지)은 단위 테스트를 갖춘 스크립트이며, workflow가 실행합니다. 에이전트에게는 판단이 필요한
일만 요청합니다. 코드를 작성하고, 리뷰하는 일입니다. 프롬프트는 무시될 수 있습니다. workflow는 그럴 수
없습니다.

## 7. 제한된 자율성<Icon name="padlock" class="heading-icon" />

에이전트는 merge할 수 없고, workflow를 편집할 수 없고, 클라우드 자격 증명에 손댈 수 없고, 통과하려고 테스트를
약화시킬 수 없습니다. 각 수정 루프는 최대 다섯 번의 시도로 제한됩니다. 그 뒤에는 멈추고 사람에게 묻습니다.

## 8. 작고 범위가 정해진 작업 단위<Icon name="list-format" class="heading-icon" />

spec은 phase로 나뉩니다. phase 그룹 하나가 issue 하나, pull request 하나이며, 에이전트가 벗어나면 안 되는 작업
범위가 있습니다. 작은 PR은 리뷰하기도 쉽고 버리기도 쉽습니다.

## 9. 모든 단계는 산출물을 남긴다<Icon name="notes" class="heading-icon" />

의도는 spec에, 범위는 issue에, 이력은 pull request에, 실행이 멈춘 이유는 label이나 댓글에 남습니다. 채팅 창이나
누군가의 머릿속에만 있는 것은 없으므로, 새 팀원이나 새 에이전트가 이전 사람이 멈춘 곳에서 이어받을 수
있습니다.
