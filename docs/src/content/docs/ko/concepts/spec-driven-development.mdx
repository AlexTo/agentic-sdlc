**짧게 말하면:** 코드가 생기기 전에 사람과 에이전트가 무엇을, 어떻게, 어떤 순서로 만들지 적어 둡니다. 그렇게
작성된 결과는 코드처럼 리뷰되고 merge됩니다. 그때부터 모든 에이전트 실행이 같은 파일을 읽으므로, 결과는 누가
프롬프트를 어떻게 썼는지에 좌우되지 않습니다.

## 그냥 프롬프트로 하면 안 되는 이유

| 프롬프트 | spec |
| --- | --- |
| 한 사람의 채팅 기록에 있다 | 버전 관리되는 `specs/`에 있다 |
| 작업 시작 전에 아무도 리뷰하지 않는다 | pull request를 거친다 |
| 실행할 때마다 조금씩 다르게 다시 입력된다 | 모든 실행이 한 글자도 다르지 않게 읽는다 |
| 무엇을 만들지는 말하지만, 이유는 거의 말하지 않는다 | 사용자 스토리, 요구 사항, 인수 기준을 명시한다 |

## 문서들

[Speckit](https://github.com/github/spec-kit)은 이 문서들을 한 단계씩 만들어 내는 에이전트 명령과 템플릿
모음입니다.

| 명령 | 작성하는 것 | 답하는 질문 |
| --- | --- | --- |
| `/speckit-constitution` | `.specify/memory/constitution.md` | 프로젝트 전체에서 모든 plan이 지켜야 하는 규칙. 한 번 작성하고, PR로 개정합니다 |
| `/speckit-specify` | `spec.md` | **무엇을, 왜.** 사용자 스토리, 기능 요구 사항, 인수 시나리오. 기술 내용은 없습니다 |
| `/speckit-clarify` | `spec.md` 업데이트 | 최대 다섯 개의 표적 질문, 그리고 spec에 다시 기록된 답 |
| `/speckit-plan` | `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md` | **어떻게.** constitution과 대조해 검사한 기술적 접근 방식 |
| `/speckit-tasks` | `tasks.md` | **어떤 순서로.** phase별로 묶인, 체크할 수 있는 작업 |
| `/speckit-analyze` | 보고서 | 작업이 없는 요구 사항, 요구 사항이 없는 작업, 파일 간의 모순 |

각 기능은 자기 폴더를 가집니다. 예를 들어 `specs/20261116-013307-course-reviews/`입니다.

```d2
direction: right

idea: 한 문단짜리 아이디어
constitution: constitution.md {shape: document}

folder: "specs/<timestamp>-<name>/" {
  style.stroke-dash: 3
  spec: spec.md {shape: document}
  plan: "plan.md\ndata-model.md\ncontracts/" {shape: document}
  tasks: tasks.md {shape: document}
  spec -> plan: /speckit-plan
  plan -> tasks: /speckit-tasks
}

idea -> folder.spec: "/speckit-specify\n/speckit-clarify"
constitution -> folder.plan: Constitution Check
```

## constitution

constitution에는 프로젝트의 타협할 수 없는 규칙이 plan을 대조해 검사할 수 있는 형태로 적혀 있습니다. "a feature
MUST work under `pnpm dev` with no cloud account", "a failing test MUST be fixed in the code, not by weakening
the test" 같은 것들입니다. `/speckit-plan`을 실행할 때마다 **Constitution Check** 섹션을 채우며, 위반 사항이
있으면 그 이유를 밝혀야 합니다.

모든 에이전트가 코드를 작성하기 전에 이를 읽으므로, 에이전트의 결과물을 믿을 수 있게 만드는 규칙은 여기에
둡니다. 전체 예시는 [Discava의 constitution](../../discava/constitution-and-guidance/)을 참고하세요.

## `tasks.md`는 자동화와의 계약이다

Speckit은 `tasks.md`를 사람을 위한 문서로 다룹니다. 이 워크플로에서는 스크립트도 이를 읽어 에이전트가 다음에
받을 작업을 결정합니다. 그래서 형식이 고정되어 있고 모든 PR에서 검사됩니다.

```markdown
## Phase 1: Setup
- [ ] T001 Create the review entity in packages/databases/core-table/src/entities/review.ts

## Phase 3: User Story 1 - Leave a rating (Priority: P1) 🎯 MVP
- [ ] T010 [P] [US1] Unit tests for rating rules
- [ ] T011 [US1] review.upsert procedure
- [ ] T012 (human) Check the layout on a phone-width window
```

phase는 번호가 붙은 제목이고, 작업은 고정된 ID를 가지며 그 자리에서 체크되고, **(human)**은 에이전트가 건너뛰고
리뷰어에게 남기는 작업을 표시합니다. 전체 규칙은 [레퍼런스: tasks.md 형식](../../reference/tasks-format/)에
있습니다.

## 코드가 아니라 spec을 바꾸세요

동작을 바꿔야 할 때는 spec으로 돌아가 업데이트하고, plan과 tasks를 다시 생성하세요. 새 작업은 아직 쓰지 않은 다음
ID를 받으므로, 자동화가 다른 작업과 똑같이 이를 위한 issue를 엽니다. 대신 코드를 손으로 고치면 spec은 더 이상
제품을 설명하지 못하고, 그것을 읽는 다음 에이전트는 옛 동작을 다시 만들어 냅니다.
