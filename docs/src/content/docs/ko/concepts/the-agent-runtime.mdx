**짧게 말하면:** OpenHands는 여러분의 저장소를 대상으로 예약된 automation 세 개를, 에이전트 역할마다 하나씩
실행합니다. **개발자**는 label이 붙은 issue를 구현하고 실패로 표시된 pull request를 수정합니다. **리뷰어**는
검사가 끝난 pull request를 리뷰합니다. **테스터**는 merge된 각 변경을 배포된 개발 stage에서 테스트합니다. 각각
고정된 프롬프트로 일반적인 코딩 에이전트를 시작합니다. 어느 것도 여러분이 채팅을 열 필요가 없습니다.

## 세 가지 역할

| 역할 | Automation | 시작하는 계기 | 남기는 것 |
| --- | --- | --- | --- |
| **개발자** | GitHub issue to PR | `openhands` label이 붙은 issue, 또는 자기 PR에 붙은 실패한 `software-factory/review` 상태 | `openhands/issue-<n>`의 pull request와 그 수정본 |
| **리뷰어** | GitHub code review | `openhands-review` label이 붙은 PR, 모든 검사가 끝난 뒤 | `✅ APPROVED` 또는 `🔄 CHANGES REQUESTED`로 끝나는 리뷰 |
| **테스터** | GitHub issue tester | 배포 뒤에 열린, `openhands-test` label이 붙은 issue | UI, API, 저장된 데이터에서 얻은 증거를 담아 issue에 남긴 테스트 보고서, 그리고 때로는 작은 수정 PR |

merge까지의 루프를 돌리는 데 저장소에 필요한 것은 개발자 에이전트와 리뷰어 에이전트가 전부입니다. 테스터는
테스트할 배포된 곳이 필요하므로, [자동 배포](../../adopt/deploy/)와 함께 옵니다. 이 저장소의 예제 앱에는 배포가
없으므로, fork는 앞의 둘만 실행합니다.

```d2
direction: right

machine: 여러분의 컴퓨터 {
  style.stroke-dash: 3
  canvas: Agent Canvas {
    i2p: issue에서 PR로
    review: 코드 리뷰
    test: issue 테스터
  }
  dev: 개발자 에이전트
  rev: 리뷰어 에이전트
  tester: 테스터 에이전트
  canvas.i2p -> dev: 구현 또는 수정
  canvas.review -> rev: 리뷰
  canvas.test -> tester: 테스트
}

github: GitHub {
  style.stroke-dash: 3
  issues: issues {shape: page}
  prs: pull requests {shape: page}
  statuses: commit statuses {shape: document}
}

stage: 개발 stage {shape: cylinder}

machine.canvas -> github: 5분마다 폴링
machine.dev -> github.prs: "push, 열기"
machine.rev -> github.prs: 리뷰
machine.tester -> stage: "클릭, 호출, 읽기"
machine.tester -> github.issues: 보고
```

## 구성 요소

| 구성 요소 | 무엇인가 |
| --- | --- |
| **Agent Canvas** | 여러분이 직접 실행하는 OpenHands 앱(`npx @openhands/agent-canvas`). 에이전트 서버, automation 백엔드, 웹 UI를 함께 담고 있습니다 |
| **Agent profile** | 어떤 에이전트를 어떤 모델로 실행할지. profile은 임의의 LLM을 쓰는 OpenHands 자체 에이전트일 수도 있고, ACP(Agent Client Protocol)로 연결한 외부 코딩 에이전트일 수도 있습니다 |
| **Automation** | cron 일정에 따라 실행되는 작은 Python worker. GitHub를 읽고, 무엇을 할지 결정하고, 에이전트 대화를 시작하거나 재개합니다. Agent Canvas 카탈로그에서 설치합니다 |
| **Secret** | GitHub 토큰처럼 이름이 붙은 자격 증명. 대화에는 허용 목록에 있는 secret만 주어집니다 |

## 세 가지 automation

### 개발자: GitHub issue to PR

폴링할 때마다 worker는 감시하는 각 저장소에 대해 다음을 합니다.

1. head 커밋에 `software-factory/review`라는 이름의 commit status가 `failure` 또는 `error` 상태로 붙어 있는
   `openhands/issue-<n>` 브랜치의 열린 PR을 찾습니다. 각 PR에 대해 그 issue의 대화로 **revise** 턴을 보냅니다.
   리뷰, 댓글, 실패한 검사를 읽고, 고치고, 같은 브랜치에 push하라는 것입니다.
2. 트리거 label(`openhands`)이 붙어 있고 아직 PR이 없는 열린 issue를 찾아 **implement** 턴을 시작합니다. clone,
   `openhands/issue-<n>` 생성, 구현, 테스트, push, PR 열기, `openhands-review` label 추가입니다.

각 issue는 안정적인 대화를 가진 하나의 *subject*입니다. revise는 원래 구현과 같은 대화로 가므로, 에이전트는
컨텍스트를 유지합니다.

### 리뷰어: GitHub code review

폴링할 때마다 `openhands-review` label이 붙어 있거나, 자기 계정에 대한 대기 중인 리뷰 요청이 있거나, 열려 있고
draft가 아니며 리뷰 요청도 리뷰도 없는 PR을 찾습니다. 각 PR에 대해 **head 커밋의 모든 검사가 끝날 때까지**
기다린 다음, 바로 그 커밋에 대한 리뷰를 시작합니다. 리뷰는 별도의 줄에 판정을 적어 마무리합니다. `✅ APPROVED`
또는 `🔄 CHANGES REQUESTED`입니다.

<Aside type="caution">
issue-to-PR worker는 실패한 `software-factory/review` 상태를 볼 때만 PR을 수정합니다. 빨간 CI 실행도, 리뷰어의
"changes requested"도 그 자체로는 이 상태를 설정하지 않습니다. 그 빈틈을 메우는 것이 [빠진 glue](../the-missing-glue/)의
두 조각입니다.
</Aside>

### 테스터: GitHub issue tester

앞의 두 automation은 Agent Canvas 카탈로그에서 옵니다. 이것은 직접 작성한 것이며, 작습니다. 카탈로그의 GitHub
helper 위에 얹은 약 백 줄짜리 worker와 프롬프트 파일 하나입니다.

폴링할 때마다 트리거 label(`openhands-test`)이 붙어 있고 workflow 자체의 계정인 `github-actions[bot]`이 연 열린
issue를 찾습니다. 각 issue에 대해 **test** 턴을 시작합니다. stage가 실행 중인 커밋으로 저장소를 clone하고, merge된
pull request가 무엇을 바꿨는지 파악하고, 배포된 스택에서 테스트하고, 결과를 issue에 댓글로 남기는 것입니다.

테스트는 세 부분으로 이루어지며, 세 번째가 이를 페이지를 클릭해 보는 것과 구별해 줍니다.

1. **UI.** 실제 브라우저에서, 테스트 사용자로 로그인해 확인합니다.
2. 그 화면 뒤의 **API.** 테스트 사용자의 토큰으로 호출하며, 거부되어야 하는 경우도 포함합니다.
3. **저장된 데이터.** 동작 하나를 할 때마다 테스터는 변경이 썼어야 하는 것을 읽고 확인합니다. 데이터베이스
   레코드, 저장소의 파일, 검색 인덱스, 그리고 로그입니다. Discava에서는 DynamoDB, S3, OpenSearch,
   CloudWatch입니다.

세 가지 세부 사항이 이를 안전하고 조용하게 유지합니다.

- **issue는 무엇을 테스트할지만 말합니다.** 어떻게 테스트할지(도구, 테스트 사용자, 확인 항목, 보고서)는 컴퓨터에
  있는 automation 자체의 프롬프트입니다. issue를 편집할 수 있는 누구도 이를 바꿀 수 없습니다.
- **다른 누군가가 연 issue는 건너뜁니다.** 그 본문이 에이전트의 지시 사항이 되기 때문입니다.
- **label을 붙일 때마다 테스트 한 번.** label이 붙을 때마다 한 번으로 세므로, 테스터 자신의 댓글이 두 번째
  테스트를 시작하는 일은 없습니다. 다시 테스트하려면 label을 제거했다가 다시 붙이세요.

기본적으로는 아무것도 이런 issue를 열지 않습니다. 배포된 pull request마다 issue를 하나씩 여는 workflow가
[빠진 glue](../the-missing-glue/)의 마지막 조각입니다. Discava의 것은 [merge 후 검증](../../discava/post-merge-verify/)에
있습니다.

## 왜 webhook이 아니라 폴링인가

automation은 폴링하므로(Discava에서는 5분마다, 기본값은 15분마다) Agent Canvas는 공개 URL도 webhook secret도 없는
노트북이나 홈 서버에서 실행할 수 있습니다. 대가는 최대 폴링 간격 하나만큼의 지연인데, 에이전트가 일하는 데 걸리는
시간에 비하면 작습니다.

## 에이전트가 접근할 수 있는 것과 없는 것

개발자 에이전트와 리뷰어 에이전트의 프롬프트는 secret 하나, GitHub 토큰을 지정합니다. 그래서 개발자 에이전트는
issue를 읽고 브랜치를 push할 수 있고, 리뷰어 에이전트는 리뷰를 게시할 수 있습니다. 둘 다 클라우드 접근은 필요
없습니다. 이들이 실행하는 것은 모두 로컬 스택에서 실행됩니다.

테스터는 예외입니다. 배포된 stage에 접근해야 하므로, 개발 계정에 로그인된 클라우드 CLI와 앱의 역할마다 하나씩 둔
테스트 사용자로 일합니다. 프롬프트는 이 CLI를 읽기 전용으로 쓰라고 지시합니다. 테스터는 deploy role을 결코 받지
않으며, 프롬프트는 인프라 변경, 배포, 다른 stage에 손대는 일을 금지합니다. 테스터는 그 자격 증명을 가진 채로
issue와 pull request를 읽으므로, 테스터에게 넘겨지는 모든 것은 먼저 잠기고, 쓰기 권한이 있는 사람만 거기에 댓글을
달 수 있습니다.

그 밖에 에이전트가 절대 하면 안 되는 일과 각 제한을 강제하는 것은
[사람 게이트](../human-gates/#에이전트가-절대-하면-안-되는-것)에 있습니다.

## 에이전트 선택

Discava는 셋 모두 **ACP를 통한 Claude Code**로, 각각 자체 agent profile을 두고 실행합니다. 개발자 에이전트에는
Sonnet을, 리뷰어 에이전트와 테스터 에이전트에는 Opus를 씁니다. 리뷰에 더 강한 모델을 쓰는 것은 의도적입니다.
리뷰어 에이전트는 사람 앞의 마지막 검사이고, 개발자 에이전트가 작성하는 것보다 훨씬 적은 코드를 읽습니다.
테스터가 같은 모델을 받는 것은 그 일도 판단이기 때문입니다. 변경이 무엇을 해야 하는지, 그리고 stage에서 보이는
것과 그 저장소에서 찾은 것이 옳은지를 판단합니다. 어떤 ACP 에이전트든, 또는 임의의 LLM을 쓰는 OpenHands 자체 에이전트든 같은 profile에
연결할 수 있습니다.

각 역할이 실행될 때 쓰는 프롬프트는 [에이전트 프롬프트](../../discava/agent-prompts/)에 있습니다.
