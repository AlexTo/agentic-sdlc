Speckit은 `tasks.md`로 끝납니다. OpenHands는 label이 붙은 issue에서 시작해 pull request에서 멈춥니다. CI는 결과를
보고하고 넘어갑니다. 각 도구는 자기 일을 잘하지만, 어느 것도 다음 도구에 일을 넘겨주지 않습니다. glue가 없으면
넘겨주는 일을 *여러분이* 합니다. 작업을 issue에 복사하고, CI가 빨간색이 된 것을 알아채고, 에이전트에게 고치라고
말합니다.

빈틈과 각 빈틈을 메우는 것은 다음과 같습니다.

| # | 빈틈 | 메우는 것 |
| --- | --- | --- |
| 1 | 완료된 spec을 에이전트의 일로 바꿔 주는 것이 없다 | workflow가 `tasks.md`를 읽고 phase 그룹 하나씩 다음 구현 issue를 엽니다 |
| 2 | 에이전트는 CI가 실패한 것을 모른다 | workflow가 실패한 실행을, 에이전트가 이미 지켜보고 있는 commit status로 에이전트에게 알립니다 |
| 3 | 리뷰어의 "changes requested"가 전달되지 않는다 | workflow가 리뷰어 에이전트의 판정에 대해서도 같은 일을 합니다 |
| 4 | 막힌 에이전트가 끝없이 반복하는 것을 막는 것이 없다 | 두 수정 루프 모두 다섯 번의 시도로 제한되고, label로 횟수를 센 뒤 사람이 이어받습니다 |
| 5 | `tasks.md`는 관례일 뿐이라, 형식이 잘못되면 사슬이 조용히 멈춘다 | PR 검사가 형식을 검증합니다 |
| 6 | UI 변경이 아무도 보지 않은 채 리뷰에 도달한다 | 검사가 e2e 스크린샷을 요구하고, CI가 이를 PR에 올립니다 |
| 7 | 에이전트의 PR을 merge해도 다음 phase가 시작되지 않는다 | 에이전트 브랜치의 merge가 spec이 끝날 때까지 다음 issue를 엽니다 |
| 8 | 에이전트는 클라우드 접근 없이 실제 스택을 실행할 수 없다 | 모든 서비스의 로컬 대체물. 그래서 앱 전체와 e2e 테스트가 자격 증명 없이 실행됩니다 |
| 9 | merge해도 아무것도 배포되지 않는다 | `main`의 초록색 빌드가 스스로 배포하고, 더 이상 최신이 아닌 커밋은 건너뛰며, 프로덕션은 사람을 기다립니다 |
| 10 | 에이전트가 유출된 secret이나 취약한 의존성을 커밋할 수 있다 | 모든 빌드에서, 그리고 각 배포 전에 다시 secret과 의존성 스캔 |
| 11 | merge된 변경을 실제로 실행되는 곳에서 확인하는 사람이 없다 | 배포할 때마다 그 배포에 실린 merge된 PR마다 테스트 issue가 열리고, 테스터 에이전트가 배포된 stage에서 변경을 테스트합니다 |

[Discava의 방식](../../discava/overview/)에서 각 행을 해당 파일과 연결합니다.

## glue 작성 규칙

이 규칙들은 Discava에서 glue를 만들고 고치면서 나왔습니다.

### 프롬프트가 아니라 코드로 결정하기

"다음에 무슨 일이 일어날지"에 대한 모든 결정은 단위 테스트를 갖춘 순수 함수입니다. 어떤 merge가 해당되는지는
`gate.ts`의 `decide()`가, 에이전트를 돌려보낼지는 `planCi()`가 결정합니다. workflow 파일은 이벤트를 스크립트에
연결하기만 합니다. 결정은 GitHub 없이 테스트할 수 있고, 에이전트가 말로 피해 갈 수도 없습니다.

### 상태는 GitHub에 두기

데이터베이스는 없습니다. 시도 횟수는 label(`ci-fix-2`)입니다. phase 그룹에 대한 issue는 본문의 숨겨진
마커(`<!-- agent-issue spec:<folder> group:2 -->`)로 찾습니다. "이미 돌려보냄"은 commit status입니다. 누구나 상태를
볼 수 있고, 사람이 손으로 바꿀 수도 있습니다. 예를 들어 label을 제거해 한 번 더 시도하게 할 수 있습니다.

### 에이전트가 이미 쓰는 언어로 말하기

OpenHands는 이미 head에 실패한 `software-factory/review` 상태가 붙은 PR을 수정합니다. 그래서 glue는 새 트리거를
발명하는 대신 그 상태를 게시합니다. OpenHands를 바꿀 필요가 없습니다.

### 토큰으로는 신뢰할 수 있는 코드만 실행하기

glue workflow는 label, 상태, 댓글을 쓸 수 있는 토큰을 가지고 있습니다. 이들은 pull request가 아니라 **기본
브랜치**를 checkout하므로, 에이전트나 기여자가 작성한 어떤 것도 그 토큰으로 실행되지 않습니다. PR에서 읽어 온
것(브랜치 이름, 본문)은 사용하기 전에 엄격한 패턴과 대조해 검사합니다.

### 에이전트가 읽는 것을 잠그기

공개 저장소의 issue와 pull request에는 누구나 댓글을 달 수 있고, 에이전트는 push할 수 있는 토큰을 가진 채로 그
댓글을 읽습니다. 테스터는 배포된 stage에 대한 접근 권한도 가지고 있습니다. 그래서 에이전트에게 넘겨지는 모든
issue와 pull request는 먼저 **잠기며**, 그러면 쓰기 권한이 있는 사람만 댓글을 달 수 있습니다. issue는 label 없이
열리고, 잠긴 다음, 그제야 label이 붙으므로, 낯선 사람이 아직 댓글을 달 수 있는 동안 에이전트가 이를 가져가는
일은 없습니다. 그리고 issue의 숨겨진 마커는 workflow나 쓰기 권한이 있는 사람이 연 issue일 때만 인정됩니다.

### 멱등하게 만들기

GitHub는 이벤트를 두 번 이상 전달하기도 하고, 사람들은 job을 다시 실행합니다. 모든 스크립트는 행동하기 전에
확인합니다. 같은 그룹에 대한 두 번째 issue는 없고, 같은 커밋에 대한 두 번째 시도도 없으며, 더 이상 head가 아닌
커밋에 대한 실행에는 반응하지 않습니다.

### 사람이 보는 곳에서 크게 실패하기

workflow notice는 아무도 읽지 않습니다. 사슬이 멈추면 pull request에 그렇다고 말하세요. "the next issue was not
opened because these tasks aren't ticked: T014, T015" 같은 식입니다.

네 폴더에 걸쳐 있습니다. 도입하기 전에 읽어 보세요. 오후 한나절이면 됩니다.
