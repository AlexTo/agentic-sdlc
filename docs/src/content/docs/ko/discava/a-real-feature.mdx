이 페이지는 실제 Discava 저장소에서 기능 하나, **강좌 평점과 텍스트 리뷰**를 따라갑니다. 모든 숫자와 링크는
GitHub에서 가져왔습니다. 시간은 UTC이며, 따로 적지 않으면 2026년 11월 18일입니다.

## 아이디어

사람이 작성한 [Issue #279](https://github.com/AlexTo/discava/issues/279):

> Enrolled students leave one 1-5 rating plus an optional text review per course (editable,
> deletable). The course carries an aggregate rating and count, kept consistent through a
> core-table helper. Shown on catalogue cards, the course page and as a search sort/boost. The
> instructor can respond; an admin can remove abusive reviews. One review per student per course
> under concurrency; an average/count invariant in `helpers/invariants.ts`.

## spec

`spec/reviews` 브랜치의 [PR #358](https://github.com/AlexTo/discava/pull/358), `docs(specs): course ratings and written
reviews`: 커밋 14개, 923줄, 모두 `specs/20261116-013307-course-reviews/` 아래에 있습니다.

- `/speckit-clarify`는 물어볼 사람 없이 실행되었으므로, 에이전트가 자기 답을 "Clarifications" 아래에
  기록했습니다. 예를 들면 *"Must a student have made progress before they may review? → No.
  Any student whose enrolment is not dropped may review."* spec PR의 리뷰어는 코드가 생기기 전에 이 중 어느
  것에든 이의를 제기할 수 있었습니다.
- `tasks.md`는 **phase 여덟 개, 작업 36개**로 나왔습니다. phase 1은 첫 번째 사용자 스토리(레코드, 요약, 공유
  writer)이고, phase 2부터 8까지는 각각 자신이 어느 PR인지 적혀 있습니다("core-api review procedures (PR 2)").
  작업 두 개는 **(human)**입니다. 로컬 스택에서의 수동 점검, 그리고 배포된 stage에서의 확인입니다.

11월 15일에 열렸고, `spec-ready` label이 붙었으며, 11월 18일 06:47에 merge되었습니다.

PR 여덟 개, 테스트를 포함해 약 9,700줄입니다. 처음 여섯 개는 여섯 시간 안에 merge되었습니다. phase 7에 대한
에이전트의 PR은 issue가 열리고 열 시간 뒤에 열렸고, 마지막 두 개는 그로부터 90분 안에 merge되었습니다. 각 issue는
이전 PR이 merge되고 약 1분 뒤에 열렸으며, 마지막 PR이 #279를 닫았습니다.

## 사람이 한 일

1. 한 문단짜리 추적 issue를 작성했습니다.
2. spec PR을 리뷰하고 merge했습니다.
3. PR 여덟 개 각각에 대해 설명과 스크린샷 댓글을 읽고 merge했습니다.

누구도 issue를 열거나, 프롬프트를 작성하거나, 오류를 붙여 넣지 않았습니다.

<Aside type="note">
issue는 평범한 Conventional Commit 제목을 요구하지만, 각 PR의 제목은 issue-to-PR automation 자체의 형식인
`[#<issue>]`로 시작합니다. 두 계층이 작동하는 모습을 보여 줍니다. issue의 지시 사항은 글이고, automation의 형식은
코드입니다. 코드가 이기므로, 제목이 중요하다면 검사로 강제하세요.
</Aside>

## 사람에게 남은 것

phase 8의 **(human)** 작업 두 개입니다. 로컬 스택에서의 수동 점검, 그리고 배포된 stage에서의 확인입니다. 마지막
PR은 `tasks.md`에서 두 작업이 여전히 체크되지 않은 상태로 merge되었으므로, 자동화는 이를 기다리지 않았고 다른
어떤 것도 기다리지 않았습니다. 이를 추적하는 것은 [Archive Specs](../spec-to-issue/#완료된-spec-아카이브하기)
workflow입니다. 사람이 두 작업을 모두 체크할 때까지 spec 폴더는 활성 상태로 남습니다.
