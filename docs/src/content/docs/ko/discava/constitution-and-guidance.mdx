Discava의 에이전트는 코드를 작성하기 전에 세 계층의 글을 읽습니다. 각 계층은 맡은 일이 다르며, 규칙 하나는 정확히
그중 한 곳에만 있습니다.

| 계층 | 담고 있는 것 | 바뀌는 때 |
| --- | --- | --- |
| **constitution** | plan이 깨면 안 되는 규칙 | 드물게, PR로, 시맨틱 버전과 함께 |
| **`AGENTS.md`** | 여기서 일하는 방법: 명령, 아키텍처, 관례 | 코드베이스가 바뀔 때마다 |
| **issue 지시 사항** | *이번* 실행에서 행동하는 방법: 범위, 실행할 것, 절대 하면 안 되는 것 | workflow가 바뀔 때 |

## constitution

`.specify/memory/constitution.md`, 버전 1.2.1, 2026년 11월 7일 비준. 원칙 여덟 개이며, 각각 짧은 근거가 붙어
있습니다. 에이전트에게 가장 중요한 것은 다음과 같습니다.

### III. 모든 것이 로컬에서 실행된다

> A feature MUST work under `pnpm dev` with Docker and no AWS account. Any AWS service a feature
> adds MUST get a local stand-in or a documented, justified exception.

이 덕분에 CI가 e2e 테스트를 위해 앱 전체를 실행할 수 있고, 클라우드 자격 증명이 에이전트에게서 멀리 떨어져
있습니다. [로컬 스택](../local-stack/)을 참고하세요.

### IV. 계층화된 테스트: 단위, invariant, end to end

하위 규칙이 다섯 개 있습니다. 그중 두 개가 가장 중요합니다.

- **영향 확인.** plan은 기능이 쓰거나 새로운 방식으로 읽는 공유 레코드를 나열하고, 각각에 대해 이미 이를 다루는
  기존 invariant와 테스트를 반드시 명시해야 합니다. 기능이 레코드의 의미를 바꾸는 경우 plan은 반드시 그 검사들을
  확장해야 하고, `tasks.md`에는 반드시 각각에 대한 작업이 있어야 합니다.
- **테스트는 명세다.** 실패한 테스트는 테스트를 약화시키는 것이 아니라 코드에서 고칩니다. invariant도 테스트로
  칩니다. 전체 규칙은 [신뢰의 계층](../../concepts/layers-of-trust/#테스트는-명세다)에 인용되어 있습니다.

영향 확인이 있는 이유는, 에이전트가 새 검사는 기꺼이 추가하지만 오래된 검사는 좀처럼 다시 보지 않기 때문입니다.
"활성 학생"의 의미를 바꾸는 새 기능은 오래된 invariant의 의미를 조용히 깨뜨립니다.

### V. 단일 테이블 데이터 모델

접근 패턴은 코드보다 먼저 plan에서 설계합니다. 사용자 대상 요청은 반드시 키나 선언된 인덱스를 사용해야 하며, 절대
scan을 쓰지 않습니다. **plan** 단계에서 검사하기 때문에 비로소 효과가 있는 규칙의 좋은 예입니다. 나중에 키를
덧붙이려면 데이터를 마이그레이션해야 합니다.

### VII. 출시 전에는 자유롭게 바꾼다

> Until production is live, routes, APIs and data shapes MUST be changed outright: no redirects,
> deprecated aliases or fallbacks for old data.

이 규칙이 없으면 에이전트는 조심하느라 모든 변경에 호환성 shim을 추가합니다.

### 개발 워크플로 섹션

특별히 에이전트를 위해 작성된 부분입니다.

> Features are implemented by autonomous agents, each on its own branch and pull request, so a task
> list MUST NOT require a local stack, Docker or `pnpm dev`. […] A task that needs a running local
> stack or people MUST be marked `(human)` in `tasks.md`. […] An agent MUST NOT merge, push to
> `main`, edit CI workflows, or weaken a test to make CI pass.

## `AGENTS.md`

Discava의 루트 `AGENTS.md`는 약 110줄입니다. 다음을 다룹니다.

- **명령.** 설치, build, lint, 프로젝트 하나나 파일 하나에 대한 테스트, e2e, 로컬 개발, 배포.
- **아키텍처.** 패키지마다 한 줄: 그것이 무엇이고, 자세한 내용이 어디에 있는지.
- **관례.** 그렇지 않으면 리뷰어가 모든 PR에서 반복할 규칙들입니다. Conventional Commits, ESLint 대신 Biome,
  `helpers/` 폴더 규칙, "버튼에는 텍스트 레이블만 쓰고 화살표 아이콘은 쓰지 않는다", 공유 코드를 두는 위치, 그리고 이름 짓기:
  kebab-case 파일 이름, 백엔드 패키지에서는 `lib/`가 아니라 항상 `helpers/`, `*Writes` 함수는 트랜잭션 항목을
  반환하고 동사로 된 이름의 함수는 자기 I/O를 직접 실행합니다.

패키지 하나에 대한 자세한 내용은 그 패키지 폴더 안의 중첩된 `AGENTS.md`에 있습니다. API, 데이터베이스 패키지,
이벤트, 인프라 등에 대해 일곱 개가 있고, 각각 5~28줄입니다. 에이전트는 그 폴더에서 작업할 때만 해당 파일을
읽습니다. 루트 파일이 패키지마다 한 문단씩으로 커졌을 때 Discava는 자세한 내용을 아래로 옮겼고, 그 뒤로는 매
실행이 건드리지도 않는 패키지에 대해 읽지 않게 되었습니다. 예를 들어 데이터베이스 패키지의 파일은 각 공유 쓰기가
어떤 helper를 거치는지, 그리고 테이블에 쓰는 주체를 바꾸면 `Invariant coverage` 검사가 읽는 맵을 다시 생성해야
한다는 것을 알려 줍니다.

<Aside type="tip">
Discava의 `AGENTS.md`는 리뷰에서 같은 실수를 두 번 잡을 때마다 한 줄씩 자랐습니다. 여러분의 파일도 그렇게
키우는 것이 맞습니다.
</Aside>

## skill

Discava는 React 모범 사례, 웹 인터페이스 가이드라인, 글쓰기 가이드라인을 위한 커뮤니티 skill 세 개를
`.agents/skills/`에 설치합니다(`skills-lock.json`에서 커밋으로 고정). Speckit 명령도 skill로 설치됩니다. skill은
관련 있을 때만 로드되므로, `AGENTS.md`보다 훨씬 자세한 내용을 담을 수 있습니다.

## issue 지시 사항

모든 구현 issue는 Agent Issues 스크립트가 `.github/ISSUE_TEMPLATE/implement-phase.md`에서 복사한 같은 지시 사항으로
끝납니다. 에이전트에게 다음을 지시합니다.

- `AGENTS.md`, constitution, spec 폴더를 먼저 읽는다
- 각 스토리의 테스트를 먼저 작성하고, 각 작업은 그것을 완료하는 커밋에서 체크한다
- 단위 테스트, lint, typecheck, build는 로컬에서 실행하고, e2e와 동시성 테스트는 PR CI에 맡긴다
- 모든 UI 변경에 `screenshot()` 호출을 추가하고, 스크린샷을 **(human)** 작업으로 남기지 않는다
- **(human)** 작업은 건너뛰고 PR 설명에 나열한다
- Conventional Commits를 쓰고, `Closes`가 아니라 `Refs #<parent>`를 쓴다
- 테스트를 약화시키거나, workflow를 편집하거나, merge하거나, AWS 자격 증명에 손대지 않는다
- 막히면 issue에 댓글을 달고 멈춘다

각 항목은 초기 실행이 그 반대로 했기 때문에 있습니다. 예를 들어 `Refs` 규칙은 첫 phase의 PR이 기능 전체의 상위
issue를 닫아 버리는 것을 막습니다. 전체 텍스트는 [도입: 에이전트 가이드](../../adopt/agent-guidance/)에 있습니다.
