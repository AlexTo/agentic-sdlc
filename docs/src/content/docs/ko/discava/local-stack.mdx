빈틈 8: 에이전트는 클라우드 접근 없이 실제 스택을 실행할 수 없고, 여러분은 에이전트에게 클라우드 접근을 주고 싶지
않습니다. Discava의 답은 constitution 원칙 III입니다. 모든 AWS 서비스에는 로컬 대체물이 있고, `pnpm dev`가 Docker로
이들을 모두 시작합니다.

## 로컬에서 실행되는 것

| 서비스 | 포트 | 대체하는 것 |
| --- | --- | --- |
| 학생, 강사, 관리자 포털 | 4201, 4200, 4202 | CloudFront |
| core-api, instructor-api | 2022, 2023 | API Gateway와 Lambda |
| DynamoDB local | 8001 | DynamoDB |
| S3Mock | 9090 | S3 |
| ElasticMQ | 9324 | SQS |
| OpenSearch (Docker) | | OpenSearch Serverless |
| 이벤트 러너 | 2024 | DynamoDB streams와 stream router, MediaConvert (ffmpeg), Transcribe (자리 표시용 트랙), SES (받은편지함 페이지), EventBridge, Scheduler, Cognito triggers |
| 로컬 OIDC 서버 | 9400 | Cognito |

백엔드 코드는 `LOCAL_DEV=true`로 전환됩니다. 공유 설정은 한 패키지(`common-server-utils/local-dev`)에 있으므로,
모든 Lambda가 같은 방식으로 엔드포인트를 결정합니다. 각 대체물은 `packages/tooling/local-dev`의 Nx target이며, 해당
컨테이너를 pull하고 시작합니다.

로컬 로그인 페이지는 고정된 사용자(강사 한 명, 학생 두 명, 관리자 한 명)와 임의의 claim을 위한 "Someone else"
양식을 제공합니다. 비밀번호도, Cognito도 없습니다.

## 누가 실행하는가

**구현 에이전트는 실행하지 않습니다.** 에이전트의 issue는 `pnpm dev`, Docker, e2e 러너를 쓰지 말라고 합니다.
에이전트는 시나리오를 작성하고, **PR CI**가 이를 실행합니다. 각 e2e 샤드가 새 러너에서 자기 `pnpm dev`를 시작합니다.
에이전트의 환경은 단순하게 유지되고, 에이전트가 읽는 결과는 언제나 깨끗한 스택에서 나온 것입니다.

사람은 **(human)** 작업을 위해, 그리고 실패를 재현하기 위해 이를 실행합니다.

## E2E 시나리오

`packages/e2e`에는 사용자 흐름마다 `src/scenarios/*.e2e.ts`가 하나씩 있으며, 공유 helper로 만들어집니다. 공유
스택에서 어떤 순서로 실행해도 안전하게 만드는 규칙은 다음과 같습니다.

- 각 시나리오는 자기 사용자와 고유한 이름의 데이터를 만듭니다.
- 어떤 시나리오도 로컬 데이터를 초기화하지 않습니다.
- worker 하나, CI에서 재시도 한 번, 2분 타임아웃. 흐름은 진도 재계산 같은 백그라운드 작업을 기다립니다.

## 모든 테스트 후의 invariant

`packages/databases/core-table/src/helpers/invariants/`에는 테이블 전체에 대한 검사가 주제별로 파일 하나씩(커리큘럼,
학생 활동, 미디어, 분석 등) 들어 있습니다. "강좌에는 강사가 있다", "학생 활동 수는 그 항목을 사용한 학생 수와
일치한다", "형제 항목의 순서는 고유하다", 그리고 그 밖에 마흔 개가 넘는 검사가 있습니다.

Playwright fixture(`packages/e2e/src/helpers/table-invariants.ts`)가 **모든 e2e 테스트 후에** 이를 실행합니다.
테스트 전에 이미 있던 위반은 기록해 두고 새 위반에만 실패하므로, 오래된 로컬 데이터 때문에 실행이 실패하지
않습니다. 메시지에는 invariant와 문제가 된 레코드의 이름이 나옵니다. 카운터를 잘못 쓰는 에이전트는 세 기능 뒤가
아니라, 그것을 쓴 테스트에서 바로 알게 됩니다.

여러 writer에 걸친 모든 규칙은 모든 writer가 호출하는 공유 helper 하나를 통해 작성되며(예:
`studentActivityWrites`), invariant 하나와 그것을 깨는 테스트 하나를 가집니다.

**Invariant coverage** PR 검사가 이를 정직하게 유지합니다. `core-table`의 `entity-writers.json`은 각 엔터티를, 각
패키지에서 그 엔터티를 쓰는 파일에 연결하며, TypeScript 컴파일러로 코드에서 생성됩니다. `main`과 비교해, 다음의
경우 검사가 PR을 실패시킵니다.

- 엔터티에 기존 패키지 외에 쓰는 패키지가 새로 생긴 경우,
- `core-table` 패키지 밖의 파일이 여러 패키지가 쓰는 엔터티를 쓰기 시작한 경우,
- 새 엔터티가 나타난 경우.

PR이 `helpers/invariants/` 아래에 추가한 줄(테스트와 fixture는 제외)이 그 엔터티 각각이나 `snapshot.enrolments` 같은
`TableSnapshot` 키를 언급하면 다시 통과합니다. `entity-writers.json`이 최신이 아닐 때도 검사가 실패합니다.
pre-push hook이 이를 다시 생성하고, 바뀌었으면 push를 멈추므로, 에이전트는 CI보다 먼저 알게 됩니다.

### 검사 면제하기

검사는 writer 집합이 바뀌었다는 것만 봅니다. 이제 규칙이 그 writer들에 걸쳐 있는지는 알 수 없으므로, 메인테이너가
이를 면제할 수 있습니다. PR에 `no-new-invariant` label을 붙이고 job을 다시 실행하세요.

쓰기가 옮겨지거나 나뉘었지만 새 규칙이 걸려 있지 않을 때 label을 쓰세요. 흔한 경우는 리팩터링입니다. Discava가 API
프로시저에서 helper를 별도 파일로 옮겼을 때, 기존 쓰기가 새 파일에서 나타나 검사에 걸렸지만, 그 쓰기들이 지키는
규칙은 이미 다뤄지고 있었습니다.

기능을 통과시키려고 쓰지는 마세요. 새 writer 때문에 다른 API나 handler가 이제 레코드가 올바르다는 것에 의존한다면,
그 규칙은 모든 writer가 호출하는 `core-table` helper에 들어가야 하고, `helpers/invariants/`에 검사가 있어야 합니다.
label은 에이전트가 아니라 사람이 붙이는 것입니다. 걸려 있는 규칙이 없다고 결정하는 것이 바로 이 검사가 강제하려는
판단입니다.

## 동시성 테스트

`packages/e2e/src/concurrency/`는 두 사용자가 경쟁할 수 있는 쓰기(인증서 발급, 자막 첨부, 분석 카운터)에 대해 같은
순간에 API로 직접 요청을 보냅니다. 같은 e2e job에서 실행됩니다.

## 여전히 배포된 stage에서만 실행되는 것

대체물이 완벽하지는 않으며, `CONTRIBUTING.md`에 정확히 어디서 부족한지 나열되어 있습니다. CloudFront 서명,
MediaConvert의 정확한 출력, 실제 Transcribe, Cognito Managed Login, EventBridge 재시도와 실패 큐입니다. 이에 의존하는
작업은 **(human)** 작업이며, 배포 후 `discava-development`에서 확인합니다.
