## 1. 사람이 spec을 merge한다

기능은 업로드 과제의 채점입니다. 강사가 학생의 과제를 점수와 피드백과 함께 돌려주거나 재제출을 요청하고, 학생은 그
결과를 봅니다.

spec PR인 [#662](https://github.com/AlexTo/discava/pull/662)에는 spec 폴더만 들어 있습니다. spec, plan, 데이터
모델, contract 세 개, 그리고 **phase 8개에 작업 34개**가 담긴 `tasks.md`입니다. 제품 코드는 없습니다. PR 설명에는
에이전트가 spec을 쓰면서 물은 질문 다섯 개와 maintainer의 답이 나열되어 있습니다. 그중 하나는 이렇습니다. 돌려준
점수를 바꿀 수 있는가? 그렇다. 단, 이력을 남기고 학생에게 알린다.

maintainer는 이를 읽고 `spec-ready`를 붙인 뒤 06:40에 merge했습니다. 두 사람 게이트 중 첫 번째입니다. 2분 뒤
자동화가 phase 1~3에 대한 issue를 열었습니다.

> Tasks `T016` to `T017` of `tasks.md`: every task under Phase 4: User Story 2 - Student sees the
> grade and feedback (student portal) (P1). Do not start tasks outside these phases.

작업은 두 개입니다. 피드백 한 라운드를 보여 주고 이전 라운드들을 접힌 목록으로 보여 주는 컴포넌트, 그리고 제출물이

## 4. 리뷰어 에이전트가 진짜 버그를 찾는다

모든 검사가 끝나자 리뷰어 에이전트가 diff를 spec과 대조해 읽었습니다. 모든 것이 초록색이었지만 코드는 여전히
틀려 있었습니다. 에이전트의
[리뷰](https://github.com/AlexTo/discava/pull/683#pullrequestreview-6000171162)에서 옮깁니다.

> **Blocking: after a resubmission, the resubmission request's feedback disappears for the
> student.** The component always takes the newest round out of the "Earlier feedback" list. It
> only displays that round when the status is `resubmission_requested` or `returned`. Once the
> student uploads again, the status goes back to `submitted`, and the request round is hidden.
> This breaks FR-009, SC-007 and User Story 2's independent test [...] The new e2e step never
> checks the page in `submitted` after the resubmit, and no unit test covers `submitted` with a
> non-empty `feedback`, so nothing catches it.
>
> 🔄 CHANGES REQUESTED

쉽게 말하면 이렇습니다. 강사가 "please cite your sources"라고 쓰고, 학생이 새 초안을 업로드하면, 강사의 메모가
학생의 페이지에서 사라집니다. spec은 이전 피드백이 계속 보여야 한다고 말합니다(FR-009). 실패한 테스트는
없었습니다. 그 상태를 들여다본 테스트가 없었기 때문입니다. 리뷰어는 코드를 spec과 비교해서 이를 찾아냈고, 빠진
테스트까지 짚어 주었습니다.

**Agent Review Status**가 `review-fix-1`을 붙였습니다. 3분 뒤 개발자 에이전트가
[수정](https://github.com/AlexTo/discava/pull/683/commits/0bdf55d485d5a5df692d1e8a41ec601499977c03)을 push하고 [무엇을 했는지 설명했습니다](https://github.com/AlexTo/discava/pull/683#issuecomment-7052122523).

> Fixed the blocking finding. The newest round is now shown in full only when the status is
> `returned` or `resubmission_requested`. In any other state every round goes under "Earlier
> feedback", so the request stays reachable after a resubmit. I added a unit test for `submitted`
> with a `resubmission_requested` round, and an e2e assertion right after the resubmit.

리뷰어는 새 head를 읽고, 컴포넌트 테스트를 직접 실행한 뒤(42개 통과)
"No material findings remain. ✅ APPROVED"로
[마무리했습니다](https://github.com/AlexTo/discava/pull/683#pullrequestreview-6000351532).

## 6. merge가 배포되고, 테스트 issue가 열린다

Discava에서는 `main`이 스스로 개발 stage에 배포됩니다. 그 [배포](https://github.com/AlexTo/discava/actions/runs/44833259729)는 10:09에 끝났습니다. 1분 뒤

the grade and feedback (student portal)`을 열었습니다. issue는 무엇을 테스트할지만 말합니다.

> Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
> through the flow with Playwright, then call the APIs behind it and check the stored data.

## 8. 테스터가 issue를 닫는다

확인 항목 32개가 모두 통과했으므로, 보고서는 판정으로 끝났고 테스터는 issue를 닫았습니다.

> **PASS.** The student portal shows the grade and feedback as #681 asks

테스터는 이 PR에서 비롯되지 않은 문제 두 가지도 함께 적어 두었습니다. 누구도 이를 회귀로 오해하지 않게 하기
위해서입니다.

### 테스터가 닫지 않을 때

통과만이 유일한 결과는 아닙니다. 이 PR 바로 앞의 pull request인
[#667](https://github.com/AlexTo/discava/pull/667)은 채점 API를 추가했는데, 그 테스트 issue
[#694](https://github.com/AlexTo/discava/issues/694)는 첫 실행 뒤에도 열려 있었습니다. 확인 항목 29개가 통과했고
하나가 실패했습니다.

> **Verdict: the new grading flow works end to end for submissions made after this deploy. It
> does not work for submissions stored before it.** Those have no `reviewRevision` attribute, so
> an instructor can't open or grade them.

단위 테스트도, e2e 테스트도, 리뷰도 이를 찾아낼 수 없었습니다. 모두 빈 데이터베이스에서 시작하는데, 이 버그는 오래된
데이터가 있는 곳에만 존재하기 때문입니다. stage에는 그런 제출물이 세 개 있었습니다.

테스터는 수정이 작고 분명할 때 수정 PR을 열 수 있습니다. 이번에는 왜 열지 않았는지 [설명했습니다](https://github.com/AlexTo/discava/issues/694#issuecomment-7052102048).

> That is a choice between a migration and tolerant reads, and it changes concurrency conditions
> in two packages, so I haven't opened a fix PR.

그래서 테스터는 멈추고, 두 선택지를 모두 적어 둔 채 결정을 사람에게 넘겼습니다. maintainer는 stage의 레코드 세 개를
backfill했습니다. 테스터는 [확인을 다시 실행해](https://github.com/AlexTo/discava/issues/694#issuecomment-7054905761) 오래된 제출물에 이제 그 필드가 있음을
확인하고 issue를 닫았습니다. 오래된 제출물이 있는 다른 환경에도 같은 backfill이 필요하다는 경고도 함께 남겼습니다.
같은 보고서에 있던 사소한 지적 하나(아무것도 돌려주지 않았는데 "returned"라고 말하는 거부 메시지)는 13줄짜리 수정
[#708](https://github.com/AlexTo/discava/pull/708)이 되었습니다.

<Aside type="tip">
[merge 후 검증](../../discava/post-merge-verify/)은 또 다른 테스트 issue를 따라갑니다. 거기서는 테스터가 실패를
찾아 원인까지 추적했고, 수정 PR도 직접 열었습니다.
</Aside>

## 각 게이트가 잡아낸 것

| 게이트 | 잡아낸 것 | 앞선 게이트가 잡지 못한 이유 |
| --- | --- | --- |
| CI | 스크린샷이 없는 UI 변경 | 개발자 에이전트가 스크린샷은 뒤의 phase에 속한다고 판단했습니다 |
| 리뷰어 에이전트 | 재제출 후 사라지는 피드백 | 그 상태를 다루는 테스트가 없어서 CI는 초록색이었습니다 |
| 테스터 에이전트 (#667에서) | 새 코드가 읽지 못하는 오래된 레코드 | 테스트와 리뷰는 stage에 이미 있는 데이터를 볼 일이 없습니다 |

셋 중 어느 것도 혼자서는 대단하지 않습니다. 각자 다른 둘이 볼 수 없는 것을 봅니다. CI는 규칙을, 리뷰어는 spec을,
테스터는 실행 중인 제품을 봅니다.

## 사람이 한 일

1. spec이 작성되는 동안 질문 다섯 개에 답하고, spec PR을 리뷰하고 merge했습니다.
2. PR #683과 그 스크린샷을 읽고, 승인하고 merge했습니다.

누구도 프롬프트를 작성하거나, 오류 로그를 붙여 넣거나, stage를 손으로 클릭해 보지 않았습니다.
