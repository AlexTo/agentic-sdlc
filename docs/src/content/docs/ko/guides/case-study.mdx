[동작 방식](../how-it-works/)은 루프를 설명합니다. 이 페이지는 그 루프가 실제로 한 번 도는 모습을
[Discava](https://github.com/AlexTo/discava)의 실제 pull request로 보여 줍니다. 학생이 구매한 강좌의 환불을 요청한
뒤에 보는 화면입니다.

모든 인용문, 숫자, 링크는 GitHub에서 가져왔습니다. 시각은 시드니 시간(AEDT, UTC+11)이며, 2026년 11월 25일과
26일입니다.

pull request가 열리고 merge되기까지 수정 라운드 네 번(CI에서 세 번, 리뷰에서 한 번), 사람의 행동 한 번입니다.
그다음 테스터가, 앞선 어느 것도 볼 수 없었던 문제 두 가지를 찾아냈습니다.

## 1. issue

환불을 요청한 학생에게는 Stripe가 처리하는 동안 "Refund requested"가 표시되고, 강좌 페이지는 2초마다 환불이
끝났는지 확인합니다. [#1166](https://github.com/AlexTo/discava/issues/1166)은 거기서 무엇이 잘못되었는지
말합니다.

> While a student's refund is pending, the course page refetches `course.myEnrolment` and
> `payment.myOrder` every 2 s, and never stops. If the refund fails at Stripe or its event never
> arrives, the order stays `paid` with a refund requested, the page keeps polling for as long as
> it is open, and the student isn't told anything has gone wrong.

인수 조건은 두 줄입니다. 폴링은 한도에 이르면 멈춘다. 그리고 Stripe 대체물에서 시뮬레이션한 실패한 환불은 분명한
메시지와 함께 보류 상태를 끝낸다.

이 issue는 spec에서 나온 것이 아닙니다. 학생이 환불을 요청할 수 있게 하는 PR을 리뷰하던 리뷰어 에이전트가 그 PR의
범위 밖의 문제로 제기했고, 그것이 별도의 issue가 되었습니다. (#1166은 사본입니다. 에이전트의 예전 머신 계정이
GitHub에 의해 플래그 처리되어 그 계정이 연 모든 것이 숨겨졌고, 열려 있던 issue는 에이전트가 지금 쓰는 GitHub App이
[다시 열었습니다](../../discava/openhands-setup/#github-app).)

## 2. 개발자 에이전트가 PR을 연다

개발자 에이전트가 issue를 가져가 `openhands/issue-1166`에서 [#1195](https://github.com/AlexTo/discava/pull/1195)를
열었습니다. 변경은 패키지 네 개에 걸쳐 있습니다. 강좌 페이지의 2분 한도와 "Check again" 버튼, Stripe의 환불 실패
이벤트를 처리하는 webhook 핸들러, 실패는 반드시 요청 뒤에 와야 한다는 invariant가 붙은 주문의 `refundFailedAt`
필드, 그리고 강좌 페이지의 "Your refund failed"입니다. 설명은 무엇을 실행했고 무엇을 실행하지 않았는지로
끝났습니다.

> Unit tests cover the helper, the webhook, the invariant and the UI (poll limit, check again,
> failure message). [...] I did not run the e2e tests or try the stand-in control in a browser.

## 3. CI가 세 번 되돌려 보낸다

**`ci-fix-1`: 스크린샷이 없고, 테스트가 없는 줄이 있다.** PR은 학생이 보는 것을 바꿨지만 스크린샷을 찍지 않았기
때문에 [**UI Screenshots**가 실패했습니다](https://github.com/AlexTo/discava/actions/runs/45619342535/job/139224403383).
**codecov/patch**도 실패했습니다. 새 줄에 테스트가 없었습니다. **Agent CI Status**가 `ci-fix-1`을 붙이고 개발자
에이전트를 돌려보냈습니다. 에이전트의 [답글](https://github.com/AlexTo/discava/pull/1195#issuecomment-7164484931)을
보면, 그 과정에서 자신의 첫 시도에 있던 문제도 찾아냈음을 알 수 있습니다.

> **UI Screenshots:** added a `learner-refund` e2e scenario for a failed refund, with
> `screenshot(student, 'refund-failed')`. For this the Stripe stand-in has a new
> `fail-next-refund` control. [...] This replaces the `refund-fail` control from the first push,
> which the scenario could not use, because the stand-in completed the refund before it could
> fail.

**`ci-fix-2`: 자기 것이 아닌 실패.** 다음 실행은 **Checks (build)**에서, 인프라 패키지의 CDK synth 테스트에서
실패했습니다. 에이전트는 로그를 읽고
[이를 위해 코드를 바꾸지 않았습니다](https://github.com/AlexTo/discava/pull/1195#issuecomment-7165688653).

> the one failure was `@discava/infra` `instructor-api-stack.test.ts` [...], which hit its 30s
> timeout while the sibling CDK synth tests in that file took 22–31s. This PR doesn't touch infra
> or anything the stack synthesises [...], so I made no code change for it. The push below
> re-runs the build.

에이전트는 codecov가 아직 보고하던 부분적으로만 테스트된 줄 하나를 커버했고, 그 push로 build가 다시 실행되어
통과했습니다. 이해하지 못한 코드를 바꿔서 실패를 "고치는" 에이전트는, 그 실패가 자기 것이 아니라고 이유와 함께
말하는 에이전트보다 나쁩니다.

**`ci-fix-3`: 자신이 새로 만든 테스트가 틀렸다.** 리뷰 뒤(다음 절) 에이전트는 2분 한도에 대한 e2e 시나리오를
추가했고, 그것이 [**E2E tests (11/12)**](https://github.com/AlexTo/discava/actions/runs/45685812586/job/139458011986)에서
실패했습니다. 5분 뒤 [원인](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172674824)입니다.

> the new `a pending refund stops polling and offers to check again` scenario failed with a
> Playwright strict-mode violation, not a product bug. `getByText('Still being processed')` also
> matched the alert's description ("Your refund is still being processed…"), so it resolved to two
> elements. The page did reach the timed-out state. I now match the title with `{ exact: true }`.

에이전트는 e2e 시나리오를 로컬에서 하나도 실행하지 않았고, 매번 그렇게 밝혔습니다. 시나리오가 처음 실행되는 곳은
PR CI이며, [E2E screenshots 댓글](https://github.com/AlexTo/discava/pull/1195#issuecomment-7163204279)에는 그 실행이
찍은 두 화면이 나열되어 있습니다. `learner-refund/01-refund-failed.png`와
`learner-refund/01-refund-still-being-processed.png`입니다.

## 4. 리뷰어 에이전트가 CI가 찾지 못한 것을 찾는다

head의 모든 검사가 끝나자 리뷰어 에이전트가 diff를 issue와 대조해 읽었습니다. 결제 코드는 맞다고 판단했고, 대상을
좁힌 테스트 361개를 직접 다시 실행했는데도
[merge를 막았습니다](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6063632214).

> 1. **The branch carries another open PR's change.** Commit `e7cb9bc9`, "fix(student-portal):
>    surface completions and progress load errors on start route", is the change from open PR
>    #1188, not part of #1166. [...] Merging this PR would ship #1188's start-route error behaviour
>    under a payments title, before #1188 is reviewed.
> 2. **Live evidence is missing for the "Still being processed" / "Check again" state.** [...] The
>    new timed-out state [...] has only unit tests, and no capture from the running app.
>
> 🔄 CHANGES REQUESTED

첫 번째 지적은 모든 검사를 빠져나가는 종류의 문제입니다. 여분의 커밋은 컴파일되었고 그 테스트도 통과했습니다.
다만 여기에 속하지 않았을 뿐입니다. 에이전트의 checkout이 이미 그 커밋을 가진 branch에서 시작되었던 것입니다. 두
번째 지적은 스크린샷 규칙을 읽는 쪽이 다시 적용한 것입니다. CI는 PR이 스크린샷을 추가했는지 확인하고, 리뷰어는 새
상태마다 스크린샷이 있는지 확인합니다.

**Agent Review Status**가 `review-fix-1`을 붙였습니다. 8분 뒤 개발자 에이전트는 자신의 커밋 네 개를 다른 두 개 없이
`main` 위로 [rebase해 두었고](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172386579), 환불을 보류 상태로
붙잡아 두는 대체물 control과, Playwright의 가짜 시계를 설치해 125초를 빨리 감는 e2e 시나리오를 추가했습니다. 이것이
그 뒤 `ci-fix-3`이 바로잡은 시나리오입니다.

마지막 head에서 리뷰어는 두 지적이 모두 해결되었고 e2e 샤드 12개가 모두 통과했음을
[확인했으며](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066801083), 스크린샷 두 장을 짚었습니다.
"No material findings [...] ✅ APPROVED".

## 5. 사람이 승인한다

11:33에 maintainer가 [승인](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066944326)하고
merge했습니다. 이 PR에서 사람이 한 일은 그것뿐입니다. 그때 maintainer 앞에 놓여 있던 것은 이렇습니다. 무엇을
실행했고 무엇을 실행하지 않았는지 적은 설명, CI가 올린 스크린샷 두 장, 초록색 검사 목록, 그리고 각각 이유가 붙은
네 번의 수정 기록입니다.

## 6. merge가 배포되고, 테스트 issue가 열린다

Discava에서는 `main`이 스스로 개발 stage에 배포됩니다. 이 merge를 담은 [배포](https://github.com/AlexTo/discava/actions/runs/45734764281)는
12:28에 끝났고, 1분 뒤 **Post-merge Verify**가 [#1240](https://github.com/AlexTo/discava/issues/1240)을 열었습니다.
issue에는 PR이 바꾼 배포 파일 12개와, 어떤 종류의 테스트를 할지가 적혀 있습니다.

> Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
> through the flow with Playwright, then call the APIs behind it and check the stored data.

## 7. 테스터 에이전트가 배포된 stage를 테스트한다

테스터 에이전트는 테스트 스위트를 다시 돌리지 않고, Stripe 대체물도 쓰지 않습니다. 배포된 제품을 sandbox 모드의
실제 Stripe와 함께, 사람이 쓰듯이 써 봅니다. 에이전트의
[보고서](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815)에는 모든 단계가 나열되어 있습니다.

1. 테스트 강사로서 API를 통해 $19.99짜리 강좌 두 개를 만들었습니다.
2. 테스트 학생으로서 실제 브라우저에서 로그인하고, Stripe Checkout에서 각각을 구매했습니다. 이때 "refund fails"와
   "refund pending"용 Stripe 테스트 카드를 썼습니다.
3. 강좌 페이지에서 각각에 대해 환불을 요청했습니다.
4. 단계마다 API를 호출하고, DynamoDB의 주문과 수강 등록을 읽고, webhook과 API Lambda의 로그를 읽었습니다.

아래 스크린샷은 테스터가 직접 찍은 것으로, 여기서는 중요한 부분만 보이도록 잘랐습니다.

`refunded`로 표시되고 약 3초 만에 수강 등록이 끝났습니다. 실패는 그 뒤에 일어났고, 그에 대해서는 아무것도 도착하지 않았습니다.
테스터는 그 이유를 찾아 나섰고, 서로 다른 원인 두 가지를 찾아냈습니다(다음 절).

이 stage에서는 실제 Stripe로 환불을 보류 상태로 붙잡아 두거나 실패한 환불을 기록할 수 없었습니다. 그래서 테스터는
배포된 번들의 새 화면을 확인하려고 브라우저에서 `payment.myOrder` 응답을 바꿔 쓰고, 실제 API 응답과 저장된 데이터는
따로 확인했습니다. 한도의 시간도 쟀습니다. "Still being processed"는 보류 중인 환불이 표시되고 **120.2 s** 뒤에
나타났고, 그다음 20초 동안 요청은 없었습니다 (`13-still-being-processed-after-2-minutes.png`):

| 2분 뒤 폴링이 멈춘다 | 120.2 s, 그다음 20 s 동안 요청 0개 |
| "Check again"이 폴링을 다시 시작한다 | 그다음 8 s 동안 요청 4개, 알림은 사라짐 |
| 토큰 없는 `payment.myOrder` | 거부됨: 401 |
| 구매하지 않은 사용자로서의 `payment.myOrder` | 200과 `null`: 다른 사람의 주문은 나오지 않음 |
| 이미 환불된 주문에 대한 `payment.requestRefund` | 거부됨: 412, "No purchase to refund" |

## 8. 테스터가 issue를 열어 둔다

확인 항목 세 개가 실패했고, 그중 두 개는 PR이 예상하지 않은 상태로 끝났습니다.
[판정](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815)입니다.

> **Verdict: the student-facing UI and `payment.myOrder` work as the PR describes. The
> failed-refund path does not work end to end on the deployed stage.**

테스터가 찾은 원인은 두 가지이며, 둘 다 PR의 테스트가 닿을 수 있는 범위 밖에 있었습니다.

1. **stage의 Stripe webhook이 새 이벤트를 받지 못한다.** PR은 `refund.failed`와 `charge.refund.updated`를 이벤트
   목록에 추가했지만, 그 목록은 관리자가 처음 연결할 때만 Stripe로 보내집니다. stage는 6일 전에 연결되었습니다.
   테스터는 그 30분 동안 webhook 호출이 정확히 네 번이었고, 그중 실패에 대한 것은 하나도 없었음을 세었습니다.
2. **실제 Stripe에서는 실패한 환불이 주문이 이미 `refunded`가 된 뒤에 도착한다.** Stripe는 환불이 만들어지자마자,
   보류 중이거나 실패할 환불이라도 `charge.refunded`를 보냅니다. `refund.failed`가 도착할 즈음에는 새 핸들러의
   조건(주문이 아직 `paid`일 것)이 더 이상 성립하지 않아, 핸들러는 조용히 아무것도 하지 않습니다.

   > The student has lost access, hasn't been refunded, and isn't told.

   PR의 e2e 시나리오에 있는 대체물은 환불을 실패시키기 전에 확정하는 일이 없기 때문에, CI는 이 일이 잘 풀리는
   경우만 보여 주었습니다.

테스터는 수정이 작고 분명할 때 수정 PR을 열 수 있습니다. 열지 않은 이유를 설명했습니다.

> Fixing it means deciding how a refund failure after `charge.refunded` should restore the order
> and enrolment, or not treating a `pending` refund as refunded. That goes beyond a small fix, so
> I'm reporting it rather than opening a PR.

stage의 Stripe 연결도 건드리지 않았습니다. 다시 저장하면 첫 번째 원인은 고쳐지는데도 말입니다.
"I didn't do that, because it changes stage configuration." 그래서 issue는 열린 채로 남아 있고, 두 문제와 그 재현
방법, 그리고 사람이 내려야 할 선택지가 적혀 있습니다. 테스터는 stage에 남겨 둔 테스트 데이터와, 이미 다른 곳에서
추적 중인 오류 하나도 함께 적어 두었습니다. 누구도 이를 회귀로 오해하지 않게 하기 위해서입니다.

<Aside type="tip">
[merge 후 검증](../../discava/post-merge-verify/)은 또 다른 테스트 issue를 따라갑니다. 거기서는 테스터가 실패를
찾아 원인까지 추적했고, 수정 PR도 직접 열었습니다.
</Aside>

## 각 게이트가 잡아낸 것

| 게이트 | 잡아낸 것 | 앞선 게이트가 잡지 못한 이유 |
| --- | --- | --- |
| CI | 스크린샷이 없는 UI 변경, 테스트가 없는 줄, 에이전트가 직접 만든 e2e 테스트의 깨진 locator | 개발자 에이전트가 e2e 스위트를 실행하지 않았습니다 |
| 리뷰어 에이전트 | branch에 함께 실려 온 다른 PR의 커밋, 스크린샷이 없는 새 화면 상태 | 여분의 커밋은 모든 검사를 통과했고, CI는 스크린샷이 하나라도 추가되었는지만 확인합니다 |
| 테스터 에이전트 | 새 이벤트를 받지 못하는 webhook 엔드포인트, 실패하는 환불을 처음에는 환불된 것으로 보고하는 실제 Stripe | 대체물은 코드가 기대하는 대로 동작하고, stage의 설정을 보는 테스트는 없습니다 |

셋 중 어느 것도 혼자서는 대단하지 않습니다. 각자 다른 둘이 볼 수 없는 것을 봅니다. CI는 규칙을, 리뷰어는 issue와
branch를, 테스터는 실행 중인 제품과 그 뒤에 있는 실제 서비스를 봅니다.
