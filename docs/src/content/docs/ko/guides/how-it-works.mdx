이 페이지는 기능 하나가 전체 루프를 거치는 과정을 따라갑니다. 각 단계마다 누가 행동하고 무엇을 남기는지
적었습니다.

<p>
  <img alt="에이전트 루프: 사람이 spec을 작성하고 merge하면, 자동화가 issue를 열고, Developer 에이전트가 구현해 PR을 올립니다. 그다음 CI와 Reviewer 에이전트가 각각 최대 다섯 번까지 수정하도록 되돌려 보내고, 마지막으로 사람이 리뷰하고 merge합니다. merge 후에는 변경이 개발 스테이지에 배포되고 Tester 에이전트가 그곳에서 테스트합니다" src="/agentic-sdlc/diagrams/agentic-loop.svg" width="720" />
</p>

실선 빨간색은 여러분이 항상 하는 두 단계입니다. 점선 빨간색은 무언가 잘못됐을 때만 여러분이 하는 일로, merge 후 체크되지 않은 에이전트 task나 stage에서 실패한 테스트입니다. 회색은 스스로 일하는 에이전트나 자동화, 남색은 자동 관문입니다. CI, 그다음 Reviewer 에이전트, 그리고 merge 후에는 Tester 에이전트입니다.

세 에이전트는 OpenHands automation입니다. **개발자**가 코드를 작성하고, **리뷰어**가 이를 리뷰하고, **테스터**가
배포된 뒤에 이를 테스트합니다.

## 단계

| # | 누가 | 무슨 일이 일어나는가 | 산출물 |
| --- | --- | --- | --- |
| 1 | 🧑🤖&nbsp;여러분 + 에이전트 | `/speckit-specify`가 한 문단짜리 아이디어를 spec으로 바꿉니다. `/speckit-clarify`가 최대 다섯 개의 질문을 하고 답을 다시 기록합니다 | `specs/<timestamp>-<name>/spec.md` |
| 2 | 🧑🤖&nbsp;여러분 + 에이전트 | `/speckit-plan`이 *어떻게* 할지 정하고, plan을 constitution과 대조해 검사합니다 | `plan.md`, `data-model.md`, `contracts/` |
| 3 | 🧑🤖&nbsp;여러분 + 에이전트 | `/speckit-tasks`가 phase별로 묶인 순서 있는 작업 목록을 작성합니다. `/speckit-analyze`가 세 파일을 교차 검사합니다 | `tasks.md` |
| 4 | 🧑&nbsp;**여러분** | spec PR을 열고, 코드처럼 리뷰하고, `spec-ready` label을 붙인 뒤 merge합니다 | merge된 spec PR. **사람 게이트 1** |
| 5 | ⚙️&nbsp;자동화 | **Agent Issues** workflow가 `tasks.md`를 읽고 첫 번째 phase 그룹에 대한 issue를 `openhands` label과 함께 엽니다 | 구현 issue |
| 6 | 🤖&nbsp;개발자 에이전트 | 다음 폴링 때 에이전트가 issue를 가져가서, 테스트를 먼저 작성하고, 구현하고, 작업에 체크 표시를 한 뒤 `openhands/issue-<n>`에서 PR을 엽니다 | pull request |
| 7 | ⚙️&nbsp;CI | PR 검사가 lint, 단위 테스트, build, `tasks.md` 형식 검사, e2e 테스트, 스크린샷 검사를 실행합니다 | 검사 결과 |
| 8 | ⚙️🤖&nbsp;자동화 + 개발자 에이전트 | 실행이 빨간색이면 **Agent CI Status**가 PR을 실패로 표시합니다. 개발자 에이전트는 다음 폴링 때 이를 보고 같은 PR을 수정합니다 | `ci-fix-1`부터 `ci-fix-5`까지의 label |
| 9 | 🤖&nbsp;리뷰어 에이전트 | 모든 검사가 끝나면 리뷰어 에이전트가 head 커밋을 리뷰하고 `✅ APPROVED` 또는 `🔄 CHANGES REQUESTED`로 마무리합니다. 후자라면 **Agent Review Status**가 개발자 에이전트를 다시 돌려보냅니다 | 리뷰, 경우에 따라 `review-fix-N` label |
| 10 | 🧑&nbsp;**여러분** | PR 설명과 **E2E screenshots** 댓글을 읽고, **(human)** 작업을 처리한 뒤 merge합니다 | merge된 PR. **사람 게이트 2** |
| 11 | ⚙️&nbsp;자동화 | merge가 **Agent Issues**를 다시 실행합니다. 체크되지 않은 에이전트 작업이 남은 다음 phase의 issue를 열고, 남은 작업이 없을 때까지 6~10단계가 반복됩니다 | 다음 issue, 또는 완료 |
| 12 | ⚙️🤖&nbsp;자동화 + 테스터 에이전트 | `main`이 스스로 배포되는 곳에서: merge가 개발 stage에 올라가면 **Post-merge Verify**가 이에 대한 테스트 issue를 엽니다. 테스터 에이전트가 변경을 클릭해 보고, API를 호출하고, 변경이 데이터베이스, 파일 저장소, 검색 인덱스에 쓴 데이터를 검증하고, 보고합니다 | 테스트 보고서. 통과하면 issue가 닫힙니다 |

12단계에는 배포된 stage가 필요합니다. Discava에는 있습니다. 이 저장소의 예제 앱에는 없으므로, fork는 11단계에서
멈춥니다.

## 여러분이 실제로 하는 일

기능마다 spec을 한 번 작성하고 승인합니다. pull request마다 리뷰를 한 번 하고 merge를 클릭합니다. 루프가
시도 횟수를 다 쓰거나(`ci-fix-exhausted` 또는 `review-fix-exhausted`), 에이전트가 막혔다고 댓글을 남기거나,
변경이 stage에서 실패해서 테스터가 테스트 issue를 열어 둘 때만 일찍 불려 갑니다. 에이전트가 일하는 동안
여러분은 다음 spec을 작성할 수 있습니다.

## 각 구성 요소의 위치

| 구성 요소 | 파일 |
| --- | --- |
| spec 도구 | `.specify/`, `speckit-*` skill, `specs/` |
| 모든 에이전트 실행에 적용되는 프로젝트 규칙 | `.specify/memory/constitution.md`, `AGENTS.md` |
| 에이전트가 받는 issue | `.github/ISSUE_TEMPLATE/implement-phase.md` |
| spec에서 issue로 | `.github/workflows/agent-issues.yml` |
| 완료된 spec을 `specs/_archive/`로 | `.github/workflows/archive-specs.yml` |
| CI에서 에이전트로 | `.github/workflows/agent-ci.yml` |
| 리뷰어에서 에이전트로 | `.github/workflows/agent-review.yml` |
| 검사 | `.github/workflows/pr-checks.yml`, `ui-screenshots.yml`, `ci.yml` |
| 배포에서 테스트 issue로 (Discava만) | `.github/workflows/deploy.yml`, `post-merge-verify.yml` |
| 단위 테스트를 갖춘 glue의 규칙 | `packages/common/scripts/src/agent-*`, `ui-screenshots/` |
| 에이전트 런타임과 각 역할의 프롬프트 | 저장소 밖의 OpenHands Agent Canvas |
