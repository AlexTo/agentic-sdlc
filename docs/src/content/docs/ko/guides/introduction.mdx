이 가이드는 **에이전트가 코드를 작성하고 사람은 두 가지 결정만 내리는** 소프트웨어 라이프사이클을 운영하는
방법을 보여 줍니다. 두 가지 결정은 spec 승인과 결과 승인입니다. 그 사이의 모든 일(issue 열기, 코드와 테스트
작성, CI에 대응하기, 리뷰에 답하기)은 일반적인 GitHub 프로세스를 통해 저절로 진행됩니다. 세 가지 에이전트
역할이 그 일을 합니다. **개발자**, **리뷰어**, **테스터**입니다.

이 워크플로는 AWS 기반의 서버리스 학습 관리 시스템인 [Discava](https://github.com/AlexTo/discava)에서 매일
돌아가고 있습니다. 2026년 11월 14일에 가동을 시작한 뒤 8일 동안, 이 방식으로 스물여섯 개의 기능 spec이
작성되었고, 이를 구현하기 위해 176개의 에이전트 pull request가 merge되었으며, 각각은 에이전트가 작성하고,
고치고, 리뷰했습니다. 같은 기간 동안 main에는 270개의 커밋이 들어갔습니다. 이 모든 것을 메인테이너 한 명이
해냈는데, 그는 정규직으로 일하면서 남는 시간에 가볍게 Discava를 다루는 아빠입니다. 😅

## 짧게 말하면

이미 나와 있는 세 가지 도구가 대부분의 일을 합니다.

| 도구 | 여기서 하는 일 |
| --- | --- |
| [Speckit](https://github.com/github/spec-kit) | 아이디어를 `spec.md`, `plan.md`, `tasks.md`로 바꾸고, 프로젝트 constitution과 대조해 검사합니다 |
| [OpenHands](https://github.com/OpenHands/OpenHands) | 세 가지 에이전트 역할을 역할마다 automation 하나씩으로 실행합니다. 개발자는 label이 붙은 issue를 pull request로 바꾸고, 무언가 잘못되었다는 말을 들으면 이를 수정합니다. 리뷰어는 이를 리뷰합니다. 테스터는 merge된 변경을 배포된 stage에서 테스트합니다 |
| GitHub Actions | 검사를 실행하고, 다른 두 도구 사이의 glue를 담고 있습니다 |

이 도구들은 서로에 대해 알지 못합니다. **이 가이드는 대부분 glue에 관한 것입니다.** 완료된 spec을 개발자
에이전트에, CI와 리뷰어 에이전트를 다시 개발자 에이전트에, 배포를 테스터 에이전트에 연결하는 열한 개의 작고
테스트된 자동화 조각이며, 어떤 것도 끝없이 반복되지 않도록 한도가 걸려 있습니다.

## 대상 독자

- 워크플로 도입 여부를 결정하는 **테크 리드와 스태프 엔지니어**.
  [개념](../../concepts/principles/)부터 시작하세요.
- **직접 해 보고 싶은 모든 분.** [이 저장소를 fork](../fork-this-repo/)한 뒤
  [설정하기](../../setup/before-you-start/)를 따라 기능 하나를 전체 루프에 통과시켜 보세요.
- **제품 저장소에 이를 도입할 엔지니어.**
  [Discava의 방식](../../discava/overview/)을 읽은 뒤
  [여러분의 저장소에 도입하기](../../adopt/overview/)를 읽으세요.
- **매일 이를 사용할 개발자.** [튜토리얼](../../tutorial/the-case/)이 기능 하나를 아이디어부터 merge까지
  따라갑니다.

Git, GitHub pull request, GitHub Actions에 익숙해야 합니다. Speckit이나 OpenHands 사용 경험은 필요
없습니다.

## 이 가이드의 구성

| 섹션 | 답하는 질문 |
| --- | --- |
| **여기서 시작** | 이것은 무엇이고, 기능은 이 안에서 어떻게 움직이는가? |
| **개념** | 왜 이렇게 만들었는가? |
| **Discava의 방식** | 각 빈틈을 정확히 무엇이, 어떤 파일에서 메우는가? |
| **설정하기: fork하고 실행하기** | 예제 앱에서 어떻게 실행하는가? |
| **여러분의 저장소에 도입하기** | 기존 저장소에 각 구성 요소를 어떻게 추가하는가? |
| **튜토리얼** | 작은 기능 하나로 써 보면 어떤 느낌인가? |
| **레퍼런스** | label, 상태, workflow, `tasks.md` 형식, 문제 해결, 용어집 |

## 표기 규칙

- `AGENTS.md`는 저장소 루트에 있는 에이전트 가이드 파일을 뜻합니다. 여러분의 코딩 에이전트가 읽는 이름으로
  지으면 됩니다.
- `<you>/agentic-sdlc`는 여러분의 fork이고, `owner/repo`는 임의의 저장소입니다.
- `@your-scope`는 여러분 워크스페이스의 npm scope입니다. 이 저장소는 `@agentic-sdlc`를, Discava는
  `@discava`를 사용합니다.
- 단계에서 따로 언급하지 않는 한 명령은 저장소 루트에서 실행합니다.
- **(human)**은 에이전트가 해서는 안 되는 작업을 표시합니다. `tasks.md`에서 실제로 쓰이는 표시이기도 합니다.
