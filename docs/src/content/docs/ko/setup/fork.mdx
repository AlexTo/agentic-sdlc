**결과:** Issues와 Actions가 활성화되고, 로컬에 clone되었으며, 검사가 통과하는
나만의 fork.

<Steps>

1. **Fork하고 clone합니다.**

   ```bash
   gh repo fork AlexTo/agentic-sdlc --clone
   cd agentic-sdlc
   ```

2. **fork를 `gh`의 기본값으로 설정합니다.** 그렇지 않으면 `gh` 명령이 여러분의 저장소가 아니라
   원본 저장소를 대상으로 합니다.

   ```bash
   gh repo set-default <you>/agentic-sdlc
   ```

3. **Issues를 켭니다.** GitHub는 fork에서 Issues를 꺼 두는데, 전체 workflow가 issue 위에서 동작합니다.
   fork에서 **Settings → General → Features**를 열고 **Issues**에 체크합니다.

4. **Actions를 켭니다.** fork의 **Actions** 탭을 열고 **I understand my workflows, go
   ahead and enable them**을 클릭합니다. 이렇게 하기 전까지 GitHub는 fork에서 workflow를 실행하지 않습니다.

5. **설치하고 로컬에서 검사를 실행합니다.** CI가 실행하는 것과 같은 검사입니다.

   ```bash
   pnpm install
   pnpm nx run-many --target lint --all
   pnpm nx run-many --target test --all
   pnpm nx run-many --target build --all
   ```

   노트 앱을 실행하려면 (Docker 필요): `pnpm dev`를 실행한 뒤 웹사이트가 출력하는 URL을 엽니다.

</Steps>

## 동작 확인

fork에 **Issues** 탭이 보이고, **Actions** 탭에 workflow 목록이 나타납니다. 로컬에서는 세 개의
`nx run-many` 명령이 통과합니다.

<Aside type="note">
fork에서는 두 가지가 다르게 동작하지만, 어느 것도 workflow를 막지 않습니다. `CODECOV_TOKEN`
secret이 없으면 coverage 업로드 step이 에러를 로그에 남기고 계속 진행합니다. CI의 **Deploy Docs** job은
GitHub Pages를 켜기 전까지 실패합니다 (**Settings → Pages → Source: GitHub Actions**). 무시해도
됩니다.
</Aside>
