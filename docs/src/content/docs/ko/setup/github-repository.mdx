**결과:** fork에 설치된, 에이전트가 동작할 GitHub App. 켜진 Issues와 Actions, workflow가 사용하는 모든
label, 검사가 초록색이고 승인을 받은 pull request만 받는 `main` 브랜치, 그리고 collaborator로 제한된
댓글.

<Steps>

1. **에이전트의 GitHub App을 만듭니다.** 에이전트는 다른 용도로는 쓰지 않는 앱으로 동작하므로, 에이전트의
   pull request와 댓글은 그 앱으로 표시되고, 여러분은 다른 사람의 것처럼 승인합니다. Discava의 앱은
   `alex-coding-agent`입니다.

   [내용이 채워진 **New GitHub App**](https://github.com/settings/apps/new?url=https%3A%2F%2Fgithub.com%2FAlexTo%2Fagentic-sdlc&public=false&contents=write&issues=write&pull_requests=write&workflows=write&checks=read&statuses=read&actions=read)을
   엽니다. 링크가 양식을 채워 주므로, 여러분은 다음만 하면 됩니다.

   - **이름**을 입력합니다. 앱 이름은 GitHub 전체에서 유일해야 하므로, `<you>-coding-agent`를 시도해 보세요.
   - **Webhook → Active**의 체크가 해제되어 있는지 확인합니다. Agent Canvas는 폴링하므로, 여러분의 컴퓨터에
     무언가가 도달할 필요가 없습니다.
   - **Create GitHub App**을 클릭합니다.

   확인하고 싶다면, 링크가 **Repository permissions**에서 선택하는 권한은 다음과 같습니다.

   | 권한 | 접근 | 이유 |
   | --- | --- | --- |
   | Contents | Read and write | 에이전트의 브랜치를 clone하고 push |
   | Issues | Read and write | issue 읽기, 댓글, label |
   | Pull requests | Read and write | pull request 열기, 리뷰, 댓글 |
   | Workflows | Read and write | 이것이 없으면 GitHub는 `.github/workflows/`를 건드리는 push 전체를 거부하는데, `main`의 merge가 그럴 수 있습니다. 에이전트는 workflow를 편집하지 않습니다 |
   | Checks, Commit statuses, Actions | Read-only | 리뷰어는 검사가 끝날 때까지 기다린 뒤 리뷰합니다 |
   | Metadata | Read-only | GitHub가 요구합니다 |

2. **앱의 key를 받고 앱을 설치합니다.** GitHub가 다음에 보여 주는 페이지, 즉 앱의 설정에서:

   - 위쪽 가까이에 있는 번호인 **App ID**를 적어 둡니다.
   - **Private keys**에서 **Generate a private key**를 클릭합니다. 브라우저가 `.pem` 파일을
     내려받습니다. 이것이 유일하게 오래 유지되는 secret입니다. 에이전트는 이것으로 만든 한 시간짜리
     토큰만 보게 됩니다.
   - 사이드바에서 **Install App**을 클릭한 다음 **Install**을 클릭하고, **Only select repositories**를
     선택해 fork를 고릅니다.

   [3단계](../openhands/)에서 App ID와 `.pem` 파일이 필요합니다.

3. fork의 소유자로 `gh`에 로그인한 상태에서, clone한 저장소에서 앱의 이름, 즉 앱의 주소
   `github.com/apps/<app-name>`에 나오는 이름을 지정해 **설정 script를 실행**합니다.

   ```bash
   ./scripts/setup-repository.sh <you>/agentic-sdlc <app-name>
   ```

   fork는 코드를 복사하지만 설정은 복사하지 않습니다. script는 `gh` CLI로 설정을 적용하며, 매번 같은
   상태로 설정하므로 다시 실행해도 안전합니다.

   각 `gh` 명령을 실행 전에 보고 싶다면 먼저 `--dry-run`을 붙이세요. script가 설정하는 것:

   | 설정 | 이유 |
   | --- | --- |
   | Issues와 Actions 켜기 | GitHub는 fork에서 둘 다 꺼 두는데, workflow는 issue 위에서 동작합니다 |
   | label 20개 | [레퍼런스: label](../../reference/labels/)의 모든 label |
   | `main`의 branch protection | pull request, 승인 1개, 오래된 승인 무효화, 그리고 필수 검사 일곱 개: `Checks (lint)`, `Checks (test)`, `Checks (build)`, `Tasks format`, `Invariant coverage`, `E2E tests`, `UI Screenshots` |
   | workflow 토큰은 읽기 전용이고, Actions는 pull request를 열거나 승인할 수 없음 | pull request를 열 수 있는 workflow는 승인도 할 수 있습니다. Archive Specs는 완료된 spec을 `specs/_archive/`로 옮기는 브랜치를 push하고, 내용이 채워진 pull request를 여는 링크와 함께 경고를 남기므로, 여러분이 제출하면 됩니다 |
   | 6개월 동안 상호작용을 collaborator로 제한 | 공개 저장소의 fork는 공개이고, 에이전트는 push할 수 있는 토큰을 가진 채로 자신이 작업하는 것의 모든 댓글을 읽습니다 |
   | Actions에서 GitHub Pages 게시 | CI의 **Deploy Docs** job이 이 사이트를 게시합니다 |
   | repository 변수 `AGENT_APP_LOGIN`을 앱의 bot 로그인 `<app-name>[bot]`으로 설정 | GitHub는 앱의 리뷰에 저장소와의 association을 주지 않으므로, glue는 write 권한이 있는 사람과 이 변수가 지정한 앱의 리뷰어 판정에서만 에이전트를 되돌려 보냅니다 |

   이 보호는 우회를 허용해 두므로, 소유자인 여러분이 spec PR처럼 직접 연 pull request를 merge할 수
   있습니다. GitHub는 이런 PR을 여러분이 승인하도록 허용하지 않습니다.

4. **Actions가 켜져 있는지 확인**합니다. fork의 **Actions** 탭에 아직 **I understand my
   workflows, go ahead and enable them**이 보인다면 클릭하세요. API가 Actions를 켠 뒤에도 GitHub가 이
   클릭을 요구하는 경우가 있습니다.

</Steps>

<Aside type="tip" title="왜 두 번째 계정이 아니라 앱인가">
Discava의 에이전트는 처음에 personal access token을 가진 머신 계정 `discava-bot`으로 일했습니다.
2026년 11월 GitHub가 이 계정에 플래그를 달았고, 그 결과 이 계정의 issue와 pull request 210개 모두가 모든
사람에게서 숨겨졌습니다. 앱의 토큰은 한 시간 뒤 만료되고, 앱이 설치된 저장소에만 닿습니다. classic 토큰(`repo`와
`workflow` scope)을 가진 두 번째 계정도 여전히 동작합니다. script에 대신 그 계정을 지정하면, collaborator로
초대됩니다.
</Aside>

<Aside type="caution">
상호작용 제한은 설정한 뒤 6개월이 지나면 만료되고, 아무것도 경고해 주지 않습니다. 날짜를 적어 두고 그전에
script를 다시 실행하세요. 나중에 클라우드 자격 증명을 가진 테스터 에이전트를 추가한다면, 낯선 사람의 댓글이
테스터에게 닿지 못하게 막는 것이 바로 이 제한입니다.
[누가 댓글을 달 수 있나](../../discava/post-merge-verify/#누가-댓글을-달-수-있나)를 참고하세요.
</Aside>

<Aside type="caution">
`software-factory/review`를 필수 검사에 추가하지 마세요. 이것은 에이전트에게 보내는 신호이며 항상
`failure`로만 게시되므로, 필수로 지정하면 모든 PR이 막힙니다.
</Aside>

## 동작 확인

fork의 **Issues → Labels** 페이지에 label 20개가 나열되고, **Settings → Branches**에
필수 검사 일곱 개가 있는 `main` 규칙이 보이며, **Settings → Moderation options → Interaction limits**에
종료 날짜와 함께 collaborator 전용 제한이 보입니다. **Settings → Secrets and variables → Actions →
Variables**에는 `AGENT_APP_LOGIN`이 보이고, **Settings → GitHub Apps**에는 여러분의 앱이 나열됩니다.
