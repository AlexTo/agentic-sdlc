import { Steps, Aside } from '@astrojs/starlight/components';

**결과:** workflow가 사용하는 모든 label, 검사가 초록색이고 승인을 받은 pull request만
받는 `main` 브랜치, 그리고 collaborator로 제한된 댓글.

<Steps>

1. **label을 만듭니다.** 16개나 되므로 UI보다 script가 더 빠릅니다. clone한 저장소에서
   실행하세요. `--force`는 이미 있는 label을 업데이트하므로 다시 실행해도 안전합니다.

   ```bash
   gh label create spec-ready           --force --description "Merging this spec PR starts the agent"
   gh label create openhands            --force --description "OpenHands implements this issue"
   gh label create openhands-review     --force --description "OpenHands reviews this PR's head"
   gh label create no-ui-screenshots    --force --description "Waives the UI Screenshots check: a UI change with nothing to look at"
   for n in 1 2 3 4 5; do
     gh label create ci-fix-$n          --force --description "CI fix-up attempt $n of 5"
     gh label create review-fix-$n      --force --description "Review fix-up attempt $n of 5"
   done
   gh label create ci-fix-exhausted     --force --description "CI fix-ups used up; a person takes over"
   gh label create review-fix-exhausted --force --description "Review fix-ups used up; a person takes over"
   ```

2. **`main`을 보호합니다.** fork에서 **Settings → Branches → Add classic branch protection
   rule**을 열고 다음과 같이 설정합니다.

   | 설정 | 값 |
   | --- | --- |
   | Branch name pattern | `main` |
   | Require a pull request before merging | 켬, 필수 승인 1개 |
   | Dismiss stale pull request approvals when new commits are pushed | 켬 |
   | Require status checks to pass before merging | 켬, 아래 여섯 개의 검사 |
   | Do not allow bypassing the above settings | 끔 |

   여섯 개의 검사: `Checks (lint)`, `Checks (test)`, `Checks (build)`, `Tasks format`, `E2E tests`,
   `UI Screenshots`. GitHub는 검사가 한 번 실행된 뒤에야 검색창에 보여 주므로, 빠진 것이 있다면
   먼저 아무 PR이나 여세요.

   우회를 허용해 두면, 소유자인 여러분이 에이전트가 여러분의 토큰으로 연 PR을 merge할 수 있습니다
   (아래 주의 참고).

   <Aside type="caution">
   `software-factory/review` 상태를 필수로 지정하지 마세요. 이것은 에이전트에게 보내는 신호이며 항상
   `failure`로만 게시되므로, 필수로 지정하면 모든 PR이 막힙니다.
   </Aside>

3. **Actions가 pull request를 열 수 있게 합니다.** **Settings → Actions → General**을 열고
   **Workflow permissions**에서 **Allow GitHub Actions to create and approve pull requests**에 체크합니다.
   Archive Specs workflow가 완료된 spec을 `specs/_archive/`로 옮기는 PR을 열 때 이 설정이
   필요합니다.

4. **댓글을 collaborator로 제한합니다.** 공개 저장소의 fork는 공개이고, 에이전트는 push할 수 있는 토큰을
   가진 채로 자신이 작업하는 issue와 pull request의 모든 댓글을 읽습니다. **Settings → Moderation options →
   Interaction limits**를 열고 **Limit to repository collaborators**를 6개월 동안으로 선택합니다. 그러면 그 밖의
   누구도 댓글을 달거나, issue를 열거나, pull request를 열 수 없습니다.

   <Aside type="caution">
   이 제한은 설정한 뒤 최대 6개월이 지나면 만료되고, 아무것도 경고해 주지 않습니다. 날짜를 적어 두고 그전에
   다시 설정하세요. 나중에 클라우드 자격 증명을 가진 테스터 에이전트를 추가한다면, 낯선 사람의 댓글이 테스터에게
   닿지 못하게 막는 것이 바로 이 제한입니다.
   [누가 댓글을 달 수 있나](../../discava/post-merge-verify/#누가-댓글을-달-수-있나)를 참고하세요.
   </Aside>

</Steps>

<Aside type="caution" title="계정 하나 또는 둘">
처음 시도할 때는 Discava처럼 에이전트가 여러분 계정의 토큰을 사용해도 됩니다. 하지만 GitHub는
계정이 자신의 PR을 승인하도록 허용하지 않습니다. 그러면 여러분의 승인과 리뷰어 에이전트의 승인은
댓글로 표시되고, 여러분은 저장소 admin으로서 merge합니다. 팀이라면 에이전트에게 write 권한이 있는
별도의 GitHub 계정을 주고, 그 계정의 토큰을 [3단계](../openhands/)에서 사용하세요. 그러면 사람들이
에이전트 PR을 평소처럼 승인할 수 있습니다.
</Aside>

## 동작 확인

fork의 **Issues → Labels** 페이지에 새 label 16개가 나열되고, **Settings → Branches**에
필수 검사 여섯 개가 있는 `main` 규칙이 보이며, **Settings → Moderation options → Interaction limits**에
종료 날짜와 함께 collaborator 전용 제한이 보입니다.
