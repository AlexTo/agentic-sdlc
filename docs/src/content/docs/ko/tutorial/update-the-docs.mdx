**현재 위치:** 🤖 에이전트, 그다음 다시 🧑 사람 게이트 #2. **산출물:** tag를 설명하는 문서.

문서도 코드이므로 (이 사이트는 `docs/`의 MDX입니다), 같은 체인이 문서를 처리합니다.

## 에이전트가 하는 일

task `T007`부터 `T008`까지의 issue를 받으면 에이전트는 다음을 합니다.

1. spec과 phase 1, 2에서 merge된 코드를 읽습니다. spec은 기능이 무엇을 위한 것인지 말하고,
   코드는 기능이 무엇을 하는지 말합니다.
2. 노트 앱 페이지를 업데이트합니다: `tags` attribute, 새 API input과 필터, 그리고 규칙
   (tag 다섯 개, 중복 없음, 대소문자 구분 없음)을 spec에 적힌 그대로 표현합니다.
3. 새 스크린샷을 지어내는 대신 e2e 시나리오의 스크린샷을 재사용하므로, 문서가 앱이 실제로
   하는 일을 보여 줍니다.
4. 문서 사이트를 build하므로, 깨진 링크나 잘못된 MDX는 다른 build 에러처럼 PR을 실패시킵니다.

## 여러분이 확인할 것

- 페이지의 모든 규칙이 `spec.md`의 요구 사항과 일치하나요?
- 문서와 spec이 다르다면 **spec이 우선입니다.** 문서를 손으로 고치지 말고 spec을 바꾸세요.
- 코드가 하지 않는 일이 문서에 적혀 있지는 않나요?

## 이것이 체인에 있는 이유

나중에, 다른 사람이, 기억에 의존해 작성한 문서는 어긋납니다. spec과 merge된 코드에서 생성되고
같은 게이트로 리뷰된 문서는 어긋나지 않습니다. 에이전트 리뷰어는 비용이 적게 드는 두 번째 독자이기도
합니다. 어떤 테스트나 코드로도 뒷받침되지 않는 문서의 주장을 짚어 냅니다.

## 완료

문서 PR을 merge합니다. 남은 에이전트 task가 없으므로 새 issue는 열리지 않습니다. 기능은 한 문장에서
merge된 코드와 문서가 되었고, 여러분은 두 종류의 결정을 내렸습니다: spec 승인과 각 결과의 승인.
