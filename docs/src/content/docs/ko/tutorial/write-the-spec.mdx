**현재 위치:** 🧑 여러분 + 🤖 에이전트. **산출물:** `specs/<timestamp>-note-tags/spec.md`.

spec은 *무엇*과 *왜*를 말하며, *어떻게*는 절대 말하지 않습니다. 여러분이 작성하는 것 중 가장 중요한 것입니다.

<Steps>

1. 브랜치에서 시작합니다.

   ```bash
   git switch -c spec/note-tags
   ```

2. Speckit에게 기능을 설명합니다.

   ```text
   /speckit-specify Users can add up to five tags to a note and filter the note list by tag.
   Tags are case-insensitive and unique per note.
   ```

   Speckit이 user story, 기능 요구 사항, 인수 기준이 담긴
   `specs/<timestamp>-note-tags/spec.md`를 만듭니다.

3. 에이전트가 빈틈을 찾게 합니다.

   ```text
   /speckit-clarify
   ```

   최대 다섯 개의 구체적인 질문을 하고, 여러분의 답을 spec에 다시 기록합니다. 이 기능이라면
   다음과 같은 질문을 예상할 수 있습니다.

   - 여섯 번째 tag를 추가하면 어떻게 되나요: 거부하나요, 아니면 가장 오래된 것을 버리나요?
   - `Work`와 `work`는 같은 tag인가요? (spec은 그렇다고 말합니다: 저장할 때 소문자로 바꿉니다.)
   - tag 길이에 최댓값이 있나요?

</Steps>

## 좋은 spec의 모습

- 각 user story를 단독으로 테스트할 수 있고, 인수 시나리오는 Given/When/Then으로 작성되어 있습니다.
- 모든 규칙이 요구 사항으로 명시되어 있습니다. 예: *"A note MUST NOT have more than five tags."*
  이 규칙들이 나중에 invariant와 테스트가 됩니다.
- spec에 기술이 등장하지 않습니다. DynamoDB도, tRPC도 없습니다.

<Aside type="tip">
에이전트가 추측하게 두지 말고 명확화 질문에 직접 답하세요. 여러분이 주는 답 하나하나가 코드 속
잘못된 가정을 하나씩 줄여 줍니다.
</Aside>
