import { Steps, Aside } from '@astrojs/starlight/components';

**No final você terá:** um scan do Trivy em todo push na `main`, um workflow Deploy que entrega cada
`main` verde para um stage de desenvolvimento, deploys de produção que esperam por uma pessoa e, se
você quiser, um agent Testador que testa cada mudança mergeada no stage de desenvolvimento.

Este repositório traz os workflows, desligados: o `deploy.yml` só roda à mão ou depois que
`AUTO_DEPLOY_STAGE` é definida, e o `post-merge-verify.yml` só roda depois de um deploy. O app de
notas não tem infraestrutura em nuvem, então a parte a escrever é sua. Os passos falam de AWS e CDK,
como o Discava usa, mas o formato funciona para qualquer cloud.

<Steps>

1. **Adicione um target `trivy`** aos projetos que você quer escanear (o `pnpm trivy` da raiz roda
   `nx run-many --target trivy --all`). O job `trivy` no `ci.yml` copiado o roda em todo push na
   `main`, como um job separado do `build`, para que uma CVE recém-publicada sinalize a `main` sem
   bloquear mais nada. Registre os achados aceitos, um ID por linha, em `.trivyignore`.

2. **Adicione sua infraestrutura** como um app CDK em `packages/infra`, com um stage por ambiente no
   `src/main.ts` dele:

   ```bash
   pnpm nx g @aws/nx-plugin:ts#infra --name=infra
   ```

   O target `deploy-ci` dele é o que o workflow Deploy roda. Os constructs do site de notas já estão
   em `packages/common/constructs`.

3. **Configure acesso à cloud sem chaves** para cada stage: o provedor OIDC do GitHub, uma role de
   deploy confiável apenas para `repo:owner/repo:environment:<stage>`, uma role de execução do
   CloudFormation com um permissions boundary, o bootstrap do CDK, e um environment do GitHub com o
   nome do stage e as variáveis `AWS_REGION`, `AWS_DEPLOY_ROLE_ARN` e `AWS_EXECUTION_ROLE_ARN`. O
   [`scripts/setup-stage.sh`](https://github.com/AlexTo/discava/blob/main/scripts/setup-stage.sh) do
   Discava faz tudo isso para os stages dele; leia-o antes de adaptá-lo. Não guarde access keys.

4. **Copie `.github/workflows/deploy.yml`**, se você não está trabalhando em um fork, e troque o scope
   `@agentic-sdlc/` e o nome do stage padrão. Ele faz checkout do commit que o CI verificou, para cedo
   com um erro claro se `packages/infra` ou as variáveis do environment estiverem faltando, roda o
   Trivy, faz o synth e só faz deploy se o commit ainda for o último da `main`. Essa verificação de
   atualidade fica *dentro* do slot de concurrency do job, então ela reflete a `main` logo antes do
   deploy, mesmo que a execução tenha esperado atrás de outra.

5. **Ative os deploys automáticos** para o stage de desenvolvimento. Em **Settings → Secrets and
   variables → Actions → Variables**, adicione uma variável de repositório `AUTO_DEPLOY_STAGE` com o
   nome do seu stage de desenvolvimento.

6. **Proteja a produção.** Em **Settings → Environments**, abra o environment do seu stage de
   produção e adicione **Required reviewers**. Para fazer deploy, abra **Actions → Deploy → Run
   workflow** e informe o stage de produção. O job então espera a aprovação.

7. **Adicione o agent Testador**, se você quiser que cada mudança que sai no deploy seja testada
   (lacuna 11). Deste repositório você já tem a cola dele (`post-merge-test/` no passo 5), o template
   de issue dele (passo 4) e o `.github/workflows/post-merge-verify.yml`, que abre uma issue de teste
   para cada pull request que uma execução do Deploy colocou no stage de teste. Ele testa em
   `TEST_STAGE`, uma variável de repositório cujo padrão é `AUTO_DEPLOY_STAGE`.

   Do lado do OpenHands, adicione um agent profile `tester` e uma automation que faz polling de
   issues com o label `openhands-test`. Não há template de catálogo para ela. O worker do Discava e
   o prompt dele estão descritos em
   [Configuração do OpenHands](../../discava/openhands-setup/#testador-github-issue-tester) e em
   [Os prompts dos agents](../../discava/agent-prompts/#testador). Dê ao Testador:

   - uma CLI de cloud autenticada na conta de desenvolvimento, com o mínimo de acesso que os testes
     exigem
   - um usuário de teste por papel no seu app, guardados como secrets do OpenHands
   - um navegador que ele consiga controlar, como o Playwright com Chromium

   <Aside type="caution" title="Repositório público? Limite os comentários aos colaboradores antes">
   O Testador lê issues, pull requests e os comentários deles enquanto tem essas credenciais em mãos. Se
   o seu repositório é público, o comentário de um estranho pode levar instruções a ele.
   O `scripts/setup-repository.sh` limita as interações aos colaboradores, por no máximo seis meses,
   então rode-o de novo antes que o limite acabe. Mantenha também o trancamento em
   `helpers/conversation-lock.ts`, mantenha o "como testar" no próprio prompt da automation em vez de
   na issue, e nunca o aponte para um stage cujos dados importam.
   </Aside>

</Steps>

## Confira se funcionou

Faça o merge de qualquer PR. O CI roda, depois o **Deploy** começa sozinho com o stage de
desenvolvimento. Rode o CI de novo manualmente em um commit mais antigo: o Deploy registra
`Skipping deploy: no longer main's latest commit` e não entrega nada.

Com o Testador configurado: depois desse deploy, o **Post-merge Verify** abre uma issue trancada
com o título `test(post-merge): verify #<pr> …` e o label `openhands-test`. Em até um poll, o
Testador começa, e o relatório dele aparece como um comentário na issue.

<Aside type="note">
Nenhum agent faz deploy, e nenhum vê essas roles. O Desenvolvedor e o Revisor só precisam do token
do GitHub. O acesso do Testador à conta de desenvolvimento é separado da role de deploy, que só é
assumida por um workflow rodando a partir da `main`, no environment do stage.
</Aside>
