import { Steps, Aside } from '@astrojs/starlight/components';

**No final você terá:** um scan do Trivy em todo push na `main`, um workflow Deploy que entrega cada
`main` verde para um stage de desenvolvimento, deploys de produção que esperam por uma pessoa e, se
você quiser, um agent Testador que testa cada mudança mergeada no stage de desenvolvimento.

Os detalhes deste passo são específicos do Discava (AWS, CDK), mas o formato funciona para qualquer
cloud. O app de notas de exemplo deste repositório não tem deploy, então copie do
[`deploy.yml` do Discava](https://github.com/AlexTo/discava/blob/main/.github/workflows/deploy.yml).

<Steps>

1. **Adicione um target `trivy`** aos projetos que você quer escanear (o `pnpm trivy` da raiz roda
   `nx run-many --target trivy --all`). Adicione o job `trivy` ao `ci.yml`, como neste repositório.
   Mantenha-o como um job separado do `build`, para que uma CVE recém-publicada sinalize a `main` sem
   bloquear mais nada. Registre os achados aceitos, um ID por linha, em `.trivyignore`.

2. **Configure acesso à cloud sem chaves.** Na AWS, o `scripts/setup-stage.sh` do Discava cria, por
   stage: o provedor OIDC do GitHub, uma role de deploy confiável apenas para
   `repo:owner/repo:environment:<stage>`, uma role de execução do CloudFormation com um permissions
   boundary, e as variáveis do environment do GitHub (`AWS_REGION`, `AWS_DEPLOY_ROLE_ARN`,
   `AWS_EXECUTION_ROLE_ARN`). Use a federação OIDC da sua cloud para GitHub Actions do mesmo jeito.
   Não guarde access keys.

3. **Adicione o workflow Deploy**, disparado pela conclusão do CI na `main` e manualmente:

   ```yaml
   on:
     workflow_run: { workflows: [CI], types: [completed], branches: [main] }
     workflow_dispatch:
       inputs: { stage: { type: string, required: true } }

   jobs:
     deploy:
       if: ${{ github.event_name == 'workflow_dispatch' ||
               (github.event.workflow_run.conclusion == 'success' && vars.AUTO_DEPLOY_STAGE != '') }}
       environment: ${{ inputs.stage || vars.AUTO_DEPLOY_STAGE }}
       concurrency: { group: 'deploy-${{ inputs.stage || vars.AUTO_DEPLOY_STAGE }}', cancel-in-progress: false }
       steps:
         - uses: actions/checkout@<sha>
           with: { ref: '${{ github.event.workflow_run.head_sha || github.sha }}' }
         # init, then: pnpm trivy, configure credentials (OIDC), synth
         - name: Check commit is still main's latest
           id: freshness
           if: ${{ github.event_name == 'workflow_run' }}
           run: |
             main_sha="$(git ls-remote --exit-code origin refs/heads/main | cut -f1)"
             if [[ "$main_sha" == "$(git rev-parse HEAD)" ]]; then
               echo "current=true" >> "$GITHUB_OUTPUT"
             else
               echo "::notice::Skipping deploy: no longer main's latest commit"
               echo "current=false" >> "$GITHUB_OUTPUT"
             fi
         - name: Deploy
           if: ${{ github.event_name != 'workflow_run' || steps.freshness.outputs.current == 'true' }}
           run: pnpm nx run @your-scope/infra:deploy-ci "$STAGE/*" --role-arn "$AWS_EXECUTION_ROLE_ARN"
   ```

   A verificação de atualidade fica *dentro* do slot de concurrency, então ela reflete a `main` logo
   antes do deploy, mesmo que a execução tenha esperado atrás de outra.

4. **Ative os deploys automáticos** para o stage de desenvolvimento. Em **Settings → Secrets and
   variables → Actions → Variables**, adicione uma variável de repositório `AUTO_DEPLOY_STAGE` com o
   nome do seu stage de desenvolvimento.

5. **Proteja a produção.** Em **Settings → Environments**, abra o environment do seu stage de
   produção e adicione **Required reviewers**. Para fazer deploy, abra **Actions → Deploy → Run
   workflow** e informe o stage de produção. O job então espera a aprovação.

6. **Adicione o agent Testador**, se você quiser que cada mudança que sai no deploy seja testada
   (lacuna 11). Esta é a peça mais nova, e ela fica no Discava, não neste repositório. Copie de lá:

   - `packages/tooling/agent/src/post-merge-test/` e `src/helpers/`, com o target Nx
     `post-merge-test`
   - `.github/workflows/post-merge-verify.yml`
   - `.github/ISSUE_TEMPLATE/test-deployed-pr.md`, para abrir uma issue de teste à mão

   Depois ajuste o nome do stage (`TEST_STAGE`) e os caminhos que nunca chegam a uma stack com
   deploy (`NOT_DEPLOYED` em `plan.ts`) para o seu repositório.

   Do lado do OpenHands, adicione um agent profile `tester` e uma automation que faz polling de
   issues com o label `openhands-test`. Não há template de catálogo para ela. O worker do Discava e
   o prompt dele estão descritos em
   [Configuração do OpenHands](../../discava/openhands-setup/#testador-github-issue-tester) e em
   [Os prompts dos agents](../../discava/agent-prompts/#testador). Dê ao Testador:

   - uma CLI de cloud autenticada na conta de desenvolvimento, com o mínimo de acesso que os testes
     exigem
   - um usuário de teste por papel no seu app, guardados como secrets do OpenHands
   - um navegador que ele consiga controlar, como o Playwright com Chromium

   <Aside type="caution" title="Repositório público? Limite os comentários aos colaboradores antes">
   O Testador lê issues, pull requests e os comentários deles enquanto tem essas credenciais em mãos. Se
   o seu repositório é público, o comentário de um estranho pode levar instruções a ele. Antes de
   ativá-lo, abra **Settings → Moderation options → Interaction limits** e escolha **Limit to
   repository collaborators**. O limite dura no máximo seis meses, então anote quando renová-lo.

   Mantenha também o trancamento em `helpers/conversation-lock.ts`, mantenha o "como testar" no
   próprio prompt da automation em vez de na issue, e nunca o aponte para um stage cujos dados
   importam.
   </Aside>

</Steps>

## Confira se funcionou

Faça o merge de qualquer PR. O CI roda, depois o **Deploy** começa sozinho com o stage de
desenvolvimento. Rode o CI de novo manualmente em um commit mais antigo: o Deploy registra
`Skipping deploy: no longer main's latest commit` e não entrega nada.

Com o Testador configurado: depois desse deploy, o **Post-merge Verify** abre uma issue trancada
com o título `test(post-merge): verify #<pr> …` e o label `openhands-test`. Em até um poll, o
Testador começa, e o relatório dele aparece como um comentário na issue.

<Aside type="note">
Nenhum agent faz deploy, e nenhum vê essas roles. O Desenvolvedor e o Revisor só precisam do token
do GitHub. O acesso do Testador à conta de desenvolvimento é separado da role de deploy, que só é
assumida por um workflow rodando a partir da `main`, no environment do stage.
</Aside>
