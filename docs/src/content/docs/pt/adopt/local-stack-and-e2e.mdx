import { Steps, Aside, FileTree } from '@astrojs/starlight/components';

**No final você terá:** o `pnpm dev` iniciando o app inteiro com substitutos locais, uma suíte
Playwright que o CI roda em todo PR, screenshots postados no PR, e invariantes verificados depois de
cada teste.

Este é o passo que mais depende da sua stack. É também o que permite ao CI dar ao agent um feedback
real sem credenciais de cloud.

<Steps>

1. **Dê a cada serviço de cloud um substituto local**, iniciado por um target `dev`, para que o
   `pnpm dev` rode tudo. O `packages/tooling/local-dev/` deste repositório sobe o DynamoDB local no
   Docker para a tabela de notas. [Os substitutos do Discava](../../discava/local-stack/#o-que-roda-localmente)
   também cobrem S3, SQS, OpenSearch e Cognito, além de um processo "event runner" que chama os
   mesmos handlers que os gatilhos do Lambda, os streams e o EventBridge chamam na cloud.

   Faça o código de backend alternar por uma única flag (`LOCAL_DEV=true`), com os endpoints em um
   único módulo compartilhado. Liste no seu guia de contribuição o que ainda só roda na cloud, e
   marque as tasks que precisam disso como **(human)**.

2. **Copie o projeto e2e** deste repositório, `packages/e2e/`, e substitua o cenário dele pelos
   seus, um arquivo por fluxo de usuário. O que manter:

   <FileTree>
   - packages/e2e/
     - playwright.config.ts lê `E2E_SHARD` para que a matriz do CI possa dividir a suíte, inicia o `pnpm dev`, um worker, retries só no CI
     - src/helpers/
       - screenshots.ts `screenshot(page, 'name')`, que salva as imagens que o job `e2e` do PR Checks faz upload
       - table-invariants.ts um `test` do Playwright que verifica invariantes depois de cada cenário
   </FileTree>

   Cada cenário cria seus próprios usuários e dados com nomes únicos, e nenhum reseta os dados
   locais, então eles rodam em qualquer ordem. Chame `screenshot` onde uma pessoa olharia, depois de
   um `expect` sobre o que aparece:

   ```ts
   await expect(page.getByRole('heading', { name: 'Reviews' })).toBeVisible();
   await screenshot(page, 'reviews section with three reviews');
   ```

3. **Copie os invariantes** de `packages/notes-table/src/helpers/invariants/` para o pacote dono da
   sua tabela. Para cada regra que abrange registros escritos por código diferente (contadores,
   agregados, ordenação), escreva uma verificação que varre um snapshot dos dados e retorna as
   violações, com um teste unitário que a quebra. O `packages/notes-table/README.md`, em "Rules that
   span records", mostra passo a passo como adicionar uma.

   Os cenários pegam o `test` de `table-invariants.ts` em vez de `@playwright/test`. Depois de cada
   um, ele faz o cenário falhar se a tabela tiver uma violação que não tinha antes. Só violações
   *novas* contam, então dados locais antigos nunca fazem uma execução falhar, e o `expect.poll` dá
   tempo para o trabalho em segundo plano (handlers de stream, recálculos) alcançar.

4. **Gere o mapa de writers e copie o hook de pre-push.** Rode
   `pnpm nx run @your-scope/tooling-agent:entity-writers` e faça commit do `entity-writers.json` que
   ele escreve. Copie o `.husky/pre-push` deste repositório, com o `MAP` e o `PATHS` dele apontando
   para os seus: quando uma branch muda código que poderia escrever na tabela, ele regenera o mapa e
   barra o push se o mapa mudou. O PR check `Invariant coverage` então compara o mapa com o da branch
   base, e segura um PR que adiciona um writer até que os invariantes nomeiem a entidade.

5. **Adicione testes de concorrência** para escritas em que dois usuários poderiam competir: dispare
   as mesmas requisições à API no mesmo instante com `Promise.all`, depois faça asserções sobre o
   resultado e os invariantes.

</Steps>

## Confira se funcionou

```bash
pnpm nx e2e @your-scope/e2e
ls dist/packages/e2e/screenshots/*/
```

Depois abra um PR que muda uma página e adiciona uma chamada `screenshot(`. Quando o PR Checks
termina, o PR tem um comentário com o título **E2E screenshots** que lista a nova imagem em "Added
by this pull request".

<Aside type="tip">
Se o seu app ainda não consegue rodar totalmente local, comece pelo que consegue. Mesmo uma suíte
que cobre só a API e o banco de dados pega a maioria dos erros dos agents. Adicione substitutos um
serviço por vez, e mantenha o resto como tasks **(human)** até lá.
</Aside>
