**A versão curta:** quando algo falha, um workflow marca o commit head do PR com um status de
falha. O worker do OpenHands vê isso no próximo poll e pede à mesma conversa do agent que corrija
o mesmo PR. Cada loop tem um contador em um label, e para em cinco.

## Os dois loops

```d2
direction: right

pr: o agent faz push {shape: page}
checks: PR Checks
review: agent revisor
you: review humano

actions: GitHub Actions {
  style.stroke-dash: 3
  ci: Agent CI Status
  rv: Agent Review Status
}

status: "software-factory/review\n= failure" {shape: document}
worker: "worker issue-to-PR\n(próximo poll)"

pr -> checks
checks -> review: todos terminaram
checks -> actions.ci: falhou
review -> actions.rv: changes requested
review -> you: aprovado
actions.ci -> status: ci-fix-N
actions.rv -> status: review-fix-N
status -> worker
worker -> pr: revisa o mesmo PR
```

| | Loop de CI | Loop de review |
| --- | --- | --- |
| Disparado por | O workflow PR Checks terminando com `failure` ou `timed_out` | Um review no PR escrito pelo agent revisor, terminando em `🔄 CHANGES REQUESTED` |
| Workflow | Agent CI Status | Agent Review Status |
| Labels de contador | `ci-fix-1` … `ci-fix-5` | `review-fix-1` … `review-fix-5` |
| Quando desiste | `ci-fix-exhausted`, mais um comentário | `review-fix-exhausted`, mais um comentário |
| Descrição do status | `CI failed (fix attempt 2 of 5): E2E tests (3/4)` | `Review requested changes (fix attempt 1 of 5): see the review` |

Uma execução que passa não publica nada. O próximo commit começa sem status, então o worker deixa o PR
em paz.

## As verificações antes de mandar o agent de volta

Cada script se recusa a agir a menos que tudo isto seja verdade:

1. A branch é exatamente `openhands/issue-<n>`. Uma branch de segunda tentativa, como
   `openhands/issue-308-2`, nunca é revisada pelo worker, então também não é respondida.
2. O PR está aberto.
3. A execução ou o review é do commit head **atual** do PR. Uma execução mais antiga está obsoleta.
4. Esse commit ainda não foi mandado de volta. Rodar de novo os mesmos checks não pode gastar outra
   tentativa.
5. Para reviews: o review carrega o marcador oculto de execução do revisor e vem de uma conta com
   acesso de escrita, para que uma pessoa citando o veredito não o dispare.
6. Menos de cinco tentativas foram usadas.

O label é aplicado **antes** de o status ser publicado. Se a publicação do status falhar depois disso, a próxima
falha conta mais uma tentativa em vez de repetir esta para sempre.

## Por que cinco

Uma nova tentativa corrige a maioria dos erros: um locator instável, um tipo esquecido, uma regra de lint. As próximas cobrem uma correção
que revelou um segundo problema, ou uma execução de CI e um review que pedem coisas diferentes. Na
quinta falha, o agent geralmente está preso em algo que não consegue ver, e mais tentativas custam
dinheiro sem convergir. O Discava começou com um limite de três e o aumentou para cinco.

Dos primeiros 67 PRs de agent mergeados no Discava, 42 não têm nenhum label de correção (alguns são anteriores aos workflows de correção),
17 precisaram de exatamente uma rodada, e só um rodou um loop até o esgotamento.

<Aside type="caution">
Quando um loop se esgota, leia a última falha antes de corrigir qualquer coisa. Falhas repetidas muitas vezes
significam que a spec ou o plano era ambíguo, e o agent estava tentando atender a duas interpretações ao mesmo tempo. Corrija
a spec e depois deixe o agent tentar de novo.
</Aside>

Para dar ao agent mais uma rodada depois disso, veja
