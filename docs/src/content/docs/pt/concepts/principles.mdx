Tudo neste workflow decorre de um movimento: **tirar o desenvolvedor de dentro do loop e colocá-lo
nas duas pontas.** Pessoas decidem *o que* construir e *se ficou bom*. Agents fazem
tudo o que fica no meio, pelo processo normal do GitHub.

Os princípios estão em ordem de importância. Se você só puder aplicar alguns, comece pelo topo.

## 1. Verificação primeiro: dê ao agent mãos e olhos<Icon name="magnifier" class="heading-icon" />

Um agent que não consegue rodar o app e ver o que construiu está chutando, e todos os outros princípios só
organizam os chutes. Código que compila e passa nos testes unitários ainda pode falhar para o usuário, então o
agent precisa **rodar o que construiu, do back end ao front end**, como uma pessoa faria:

- **Mãos:** subir o app inteiro em uma stack local sem conta de nuvem, chamar a API, fazer login,
  clicar pelo fluxo em um navegador de verdade e disparar o trabalho em segundo plano por trás dele.
- **Olhos:** ler o que volta: respostas, logs, os dados deixados no banco de dados e screenshots
  de cada estado que um revisor gostaria de ver.

O agent não faz isso na própria máquina. Ele escreve os cenários e2e, e o CI os roda em
todo PR contra uma stack local nova. Os resultados, as falhas de invariantes e os screenshots voltam para
o PR, então o agent pega os próprios erros e todo PR chega com evidências.

Construa para isso desde o primeiro dia: todo serviço de nuvem precisa de um substituto local, todo fluxo de usuário de um
cenário e2e e todo estado de UI de um screenshot. Qualquer coisa que o agent não consiga rodar é uma tarefa que uma pessoa precisa
verificar.

## 2. A spec é a fonte da verdade<Icon name="document" class="heading-icon" />

Uma feature começa como `spec.md`, `plan.md` e `tasks.md`, revisados como código. O agent constrói a partir
deles. Para mudar o comportamento, mude a spec e gere de novo o plano e as tarefas. Não corrija o código
à mão deixando a spec desatualizada.

## 3. Os gates automáticos dão o feedback, não você<Icon name="approve-check-circle" class="heading-icon" />

Lint, typecheck, testes unitários, invariantes, testes e2e, testes de concorrência, screenshots e um agent
revisor rodam em todo PR. Um resultado vermelho volta direto para o agent que escreveu a mudança.
Ninguém cola mensagem de erro.

## 4. Pessoas ficam com as duas decisões que importam<Icon name="star" class="heading-icon" />

1. **Aprovar a spec.** Fazer o merge do spec PR com o label `spec-ready` é o sinal de partida.
2. **Aprovar o resultado.** Uma pessoa faz o review final e o merge de cada PR.

## 5. Torne regras e skills determinísticas<Icon name="setting" class="heading-icon" />

Uma regra escrita só no `AGENTS.md` ou na constitution é um pedido. O agent pode deixá-la passar, entendê-la
de dois jeitos ou esquecê-la em uma sessão longa. Sempre que um script puder verificar uma regra, escreva o script, rode-o
em um hook ou em um PR check, e mantenha o texto como explicação. Um check que falha diz ao agent
exatamente o que está errado e onde, pelo mesmo feedback loop de qualquer outro resultado vermelho.

O Discava faz isso em todo lugar:

| Regra em texto | O que a garante |
| --- | --- |
| `tasks.md` segue um formato fixo | O PR check `Tasks format`. Sem ele, uma fase malformada é pulada sem aviso |
| Uma mudança de UI tira screenshots no seu cenário e2e | O check `UI Screenshots` falha se markup ou estilos mudaram e nenhum cenário ganhou uma chamada `screenshot(`. Um mantenedor pode dispensá-lo com `no-ui-screenshots` |
| Uma regra que abrange vários registros precisa de uma invariante | O check `Invariant coverage` reprova um PR que muda quem escreve na tabela principal sem mexer nos checks de invariantes em `helpers/invariants/`. Um hook de pre-push mantém o mapa de escritores atualizado. Um mantenedor pode dispensá-lo com `no-new-invariant` |
| Conventional Commits, nenhum segredo commitado | commitlint em um hook `commit-msg`, `git-secrets` em todo commit |
| Cada passo do Speckit ganha sua própria branch e commit | As skills rodam scripts para isso, a partir dos extension hooks do Speckit, quer o agent se lembre ou não |

Se você escreve a mesma correção em um review duas vezes, provavelmente está faltando um check.

## 6. A cola é código, não prompts<Icon name="puzzle" class="heading-icon" />

O mesmo vale entre os passos. Tudo o que decide *o que acontece em seguida* (qual issue abre,
se o agent volta, quando parar) é um script com testes unitários, rodado por um workflow. Ao agent
só se pede o que exige julgamento: escrever o código e revisá-lo. Um prompt pode ser ignorado. Um
workflow, não.

## 7. Autonomia limitada<Icon name="padlock" class="heading-icon" />

O agent não pode fazer merge, não pode editar workflows, não pode mexer em credenciais de nuvem e não pode enfraquecer um teste
para ficar verde. Cada loop de correção é limitado a cinco tentativas. Depois disso, ele para e pede ajuda a uma pessoa.

## 8. Unidades de trabalho pequenas e delimitadas<Icon name="list-format" class="heading-icon" />

Uma spec se divide em fases. Cada grupo de fases é uma issue e um pull request, com um intervalo de tarefas
do qual o agent não pode sair. PRs pequenos são baratos de revisar e baratos de descartar.

## 9. Todo passo deixa um artefato<Icon name="notes" class="heading-icon" />

A intenção fica na spec, o escopo na issue, o histórico no pull request, e o motivo de uma execução
ter parado em um label ou um comentário. Nada vive só em uma janela de chat ou na cabeça de alguém, então um novo
colega ou um novo agent pode continuar de onde o último parou.
