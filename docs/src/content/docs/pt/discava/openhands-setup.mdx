Os agents do Discava rodam em uma workstation Linux, sob o OpenHands Agent Canvas. Não há deploy do
OpenHands em nuvem nem webhook. Tudo é polling de saída para o GitHub.

## Agent Canvas

Agent Canvas 1.41.0, instalado pelo npm (`@openhands/agent-canvas`) e rodando como um serviço de usuário.
O estado dele fica em `~/.openhands/`: configurações, agent profiles, secrets e o banco de dados SQLite
das automations.

## Configurações de conversa

As configurações que definem como os agents trabalham:

| Configuração | Valor | Por quê |
| --- | --- | --- |
| Agent | ACP, servidor `claude-code` | Um coding agent externo, via Agent Client Protocol |
| Timeout do prompt ACP | 30 minutos | Um turno de implementação é longo |
| Máximo de iterações | 500 | Espaço para uma fase inteira em uma conversa |
| Modo de confirmação | desligado | Sem supervisão. Não há ninguém para confirmar |
| Analisador de segurança | LLM | Os comandos ainda são avaliados quanto a risco |
| Runtime | local | Roda no host, onde Node, pnpm e git já estão |
| Prefixo de branch da worktree | `openhands/` | Toda branch que um agent cria começa com isso. A cola se baseia nele |

## Agent profiles

Um profile por papel de agent:

| Profile | Papel | Agent | Modelo | Usado por |
| --- | --- | --- | --- | --- |
| `developer` | Desenvolvedor | Claude Code (ACP) | Sonnet | GitHub issue to PR |
| `reviewer` | Revisor | Claude Code (ACP) | Opus | GitHub code review |
| `tester` | Testador | Claude Code (ACP) | Opus | GitHub issue tester |

Cada um tem um timeout de prompt de 30 minutos.

## Secrets

Guardados no Agent Canvas (**Settings → Secrets**), por nome:

| Nome | Usado para |
| --- | --- |
| `GITHUB_PERSONAL_ACCESS_TOKEN` | As automations leem o GitHub com ele. As conversas o recebem para clonar, fazer push, abrir PRs, fazer review e comentar |
| `OPENHANDS_AUTOMATION_API_KEY` | A chave própria do backend de automations |
| `DISCAVA_STUDENT_USERNAME`, `DISCAVA_STUDENT_PASSWORD` | O aluno do Testador no `discava-development` |
| `DISCAVA_INSTRUCTOR_USERNAME`, `DISCAVA_INSTRUCTOR_PASSWORD` | O instrutor do Testador |
| `DISCAVA_ADMIN_USERNAME`, `DISCAVA_ADMIN_PASSWORD` | O admin do Testador |

O token do GitHub é um personal access token em `discava-bot`, uma conta de máquina que só as
automations usam. Ela é colaboradora com acesso de escrita, e o token tem acesso de escrita a conteúdo
do repositório, issues, pull requests e workflows.

Os seis secrets `DISCAVA_*` são usuários de teste do Cognito no stage de desenvolvimento, um por papel no
app. O Testador faz login nos portais com eles e obtém tokens de API com eles.

## O que o Testador tem na máquina

O Desenvolvedor e o Revisor só precisam de Node, pnpm, git e `gh`. O Testador também usa:

| Ferramenta | Para |
| --- | --- |
| AWS CLI, autenticada na conta que tem as stacks `discava-development-*` | Encontrar o stage (outputs das stacks), obter tokens do Cognito, ler o DynamoDB, o S3 e os logs do CloudWatch. O prompt dele manda usá-la só para leitura |
| Playwright com Chromium | Controlar os portais com deploy |
| O `tmp/screenshots/` do checkout do Discava | Onde os screenshots dele são salvos, uma pasta por pull request |

<Aside type="caution">
Este é o único lugar em que um agent no Discava trabalha com acesso à nuvem. É por isso que o stage é o
`discava-development`, com dados descartáveis, e que
[só colaboradores podem comentar](../post-merge-verify/#quem-pode-comentar) no que os agents leem. Para uma equipe, dê ao Testador sua própria role só de leitura e
sua própria máquina ou VM.
</Aside>

## As três automations

As duas primeiras foram instaladas a partir do catálogo de automations do Agent Canvas, não escritas à mão. A
terceira é do próprio Discava. O que cada uma faz em um poll está em
[O runtime do agent](../../concepts/the-agent-runtime/#as-três-automations), e o prompt que cada
uma dá ao seu agent está em [Os prompts dos agents](../agent-prompts/).

### Desenvolvedor: GitHub issue to PR

| Campo | Valor |
| --- | --- |
| Template | `github-issue-to-pr` 1.2.4 |
| Repositório | `AlexTo/discava` |
| Label de disparo | `openhands` |
| Prefixo de branch | `openhands/issue` → branches `openhands/issue-<n>` |
| Modo de pull request | Ready for review |
| Secret do token do GitHub | `GITHUB_PERSONAL_ACCESS_TOKEN` |
| Agendamento | `*/5 * * * *`, Australia/Sydney |
| Agent profile | `developer` |

Um turno de revisão diz ao agent para aplicar de novo o label `openhands-review` depois, para que o novo head
passe por review.

### Revisor: GitHub code review

| Campo | Valor |
| --- | --- |
| Template | `github-pr-reviewer` 1.11.2 |
| Repositório | `alexto/discava` |
| Label de disparo | `openhands-review` |
| Revisor solicitado | `all-hands-bot` (não usado na prática: o label faz o trabalho) |
| Novos reviews por varredura | 2 |
| Tom do review | Concise |
| Mantenedores | nenhum |
| Agendamento | `*/5 * * * *`, Australia/Sydney |
| Agent profile | `reviewer` |

Enquanto os checks ainda estão rodando, o Revisor publica um comentário "⏳ Review waiting on checks" e
tenta de novo em uma varredura posterior. Os reviews dele começam com "_This review was posted by an AI agent
(OpenHands)._" e carregam um marcador oculto `<!-- openhands-review-run: <id> -->`.

### Testador: GitHub issue tester

Não há template de catálogo para esta. Ela é um worker de cerca de cem linhas, construído sobre os
mesmos helpers de GitHub e de conversa que os templates do catálogo usam, com o prompt em um arquivo ao lado
dele.

| Campo | Valor |
| --- | --- |
| Template | nenhum: `worker.py`, `prompt.md` e `config.json`, escritos à mão |
| Repositório | `AlexTo/discava` |
| Label de disparo | `openhands-test` |
| Autores de issue | `github-actions[bot]` |
| Prefixo de branch | `openhands/test-fix` → branches de correção `openhands/test-fix-<n>` |
| Novos testes por varredura | 2 |
| Arquivo de prompt | `prompt.md` |
| Secret do token do GitHub | `GITHUB_PERSONAL_ACCESS_TOKEN` |
| Agendamento | `*/5 * * * *`, Australia/Sydney |
| Agent profile | `tester` |

A cada poll, o worker:

1. Lista as issues abertas que têm `openhands-test`, do menor número para o maior.
2. Pula qualquer issue que não foi aberta por um dos **autores de issue**. O corpo de uma issue vira parte do que
   o agent lê, então só as issues do próprio workflow são testadas.
3. Encontra o evento mais recente que aplicou o label. O número da issue e o ID desse evento formam uma
   entrega, então um poll posterior da mesma aplicação do label é ignorado, e os próprios comentários do Testador nunca
   iniciam um segundo teste. Remover e aplicar de novo o label é um novo evento, e portanto um novo teste.
4. Inicia ou retoma a conversa da issue com o prompt, até dois novos testes por poll.

As issues que ele procura são abertas pelo [Post-merge Verify](../post-merge-verify/). Os comentários do
Testador terminam com "_This comment was posted by an AI agent (OpenHands)._".

<Aside title="Uma conta para os agents">
No Discava, o Desenvolvedor, o Revisor e o Testador postam como `discava-bot`, e o mantenedor usa a
própria conta. Assim o mantenedor pode aprovar o PR de um agent normalmente, e dá para ver quais
comentários vieram de um agent. O Revisor e o Desenvolvedor ainda compartilham uma conta, e o GitHub
não permite que uma conta aprove o próprio PR, então o veredito do Revisor é publicado como um review
`COMMENTED`. A cola lê a linha do veredito, não o estado do review, então isso não importa.
</Aside>
