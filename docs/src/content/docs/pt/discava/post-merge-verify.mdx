Lacuna 11: todos os checks antes do merge rodaram contra substitutos locais, e ninguém olha a mudança
onde ela realmente roda. O Discava a fecha com um terceiro papel de agent. Depois de cada deploy no
`discava-development`, um workflow abre uma issue de teste para cada pull request que o deploy levou,
e o **agent Testador** testa essa mudança no stage: os portais em um navegador de verdade, as APIs
como os usuários de teste, e os dados que a mudança gravou.

```d2
direction: down

deploy: "Deploy\n(discava-development)"
verify: "Post-merge Verify\npost-merge-test"
issue: "issue de teste\ntrancada, depois openhands-test" {shape: page}
tester: "agent Testador\n(OpenHands, próximo poll)"
stage: discava-development {shape: cylinder}
report: "relatório na issue" {shape: document}
fix: "PR de correção\nopenhands/test-fix-<n>" {shape: page}

deploy -> verify: concluído
verify -> issue: uma por PR do deploy
issue -> tester
tester -> stage: "Playwright, APIs, AWS CLI"
tester -> report
tester -> fix: "só correção pequena e clara" {style.stroke-dash: 3}
```

## Post-merge Verify

O `.github/workflows/post-merge-verify.yml` roda em `workflow_run`, quando o **Deploy** termina, e
à mão com um número de pull request. Ele faz checkout da branch padrão e roda `post-merge-test`.
As execuções compartilham um grupo de concorrência, então dois deploys próximos não conseguem abrir duas issues para o mesmo
pull request.

O script (`src/post-merge-test/`):

1. **Verifica se a execução fez deploy do stage de teste.** Ele lê os jobs da execução do Deploy. Uma execução cujo
   passo `Deploy` foi pulado (o commit dela não era mais o último da `main`) não fez deploy de nada, e uma execução
   para outro stage não é testada.
2. **Encontra o que o deploy levou.** Um deploy pode conter vários merges, porque um deploy pulado
   deixa o commit dele para o próximo. Então ele pega os commits entre o deploy bem-sucedido anterior
   do stage e este, e o pull request com que cada um foi mergeado.
3. **Decide, por pull request** (`decide()` em `plan.ts`). Nenhuma issue quando:
   - já existe uma para ele (encontrada pelo marcador oculto)
   - ele tem o label `skip-deploy-test`
   - ele não muda nada que entra no deploy: só docs, specs, testes, tooling, CI ou outros arquivos que
     nunca chegam a uma stack
4. **Renderiza a issue** (`renderIssue()`). Ela diz só o que testar.
5. **Abre a issue sem label, tranca e depois aplica o label.** A issue, o pull request que ela testa e as
   issues que esse pull request fecha são todos trancados. Só então o `openhands-test` entra. Se
   algo não puder ser trancado, o label nunca é adicionado e a execução falha, nomeando o que trancar à
   mão.

Rodado à mão com um número de pull request, ele abre uma issue mesmo que já exista uma. É assim que uma mudança
é testada de novo do zero.

## A issue que ele abre

Uma real, a [#654](https://github.com/AlexTo/discava/issues/654):

```markdown
<!-- post-merge-test pr:647 -->

## What to test

- Pull request: #647 (feat(stripe-checkout): a refund takes access away)
- Issue it closes: #646
- Merged as `b4dc4f7…`, deployed to `discava-development` at `b4dc4f7…` ([Deploy run](…))
- Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
  through the flow with Playwright, then call the APIs behind it and check the stored data.

<details><summary>Deployed files it changes (4)</summary>

- `packages/events/src/local/stripe-stand-in.ts`
- `packages/events/src/payments/events/charge-refunded.ts`
- `packages/events/src/payments/stripe-webhook.ts`
- `packages/websites/student-portal/src/routes/learn/$courseId/-components/enrolment-actions.tsx`

</details>
```

O título é `test(post-merge): verify #647 a refund takes access away`: um cabeçalho de Conventional Commit
de no máximo 100 caracteres, para que o Testador possa reutilizá-lo. O tipo é `UI change` quando o pull
request mexe em um portal ou nos componentes compartilhados, e `backend change or fix` nos outros casos.

<Aside type="note" title="O que testar, nunca como">
A issue não tem instruções. Como testar (as ferramentas, os usuários de teste, as verificações, o relatório) é
o próprio [prompt](../agent-prompts/#testador) do Testador no OpenHands, então ninguém que consiga editar uma issue
consegue mudá-lo. O `.github/ISSUE_TEMPLATE/test-deployed-pr.md` é a mesma forma para abrir uma à
mão.
</Aside>

## O que o Testador faz

No próximo poll, a automation `github-issue-tester` pega a issue e inicia o Testador.
O prompt dele tem oito passos:

1. Descobrir o que mudou, a partir do pull request, do diff dele, da issue que ele fecha e da spec dele, e
   anotar o que agora deveria ser verdade.
2. Testar a UI, se houver uma: fazer login na página hospedada do Cognito com o Playwright, clicar pelo
   fluxo, tirar um screenshot em cada passo e olhar cada um deles.
3. Chamar as APIs com o access token de um usuário de teste, incluindo os casos de erro.
4. Verificar os dados armazenados: itens do DynamoDB, documentos do OpenSearch, objetos do S3 e os logs das Lambdas.
5. Usar dados próprios, com nomes `pmt-<pr>-<what>`.
6. Relatar na issue: o que ele testou, uma tabela de cada verificação com aprovado ou reprovado e sua evidência,
   e um veredito.
7. Fechar a issue quando passa. Quando falha, deixá-la aberta com os passos para reproduzir. Abrir um pull request
   de correção só quando a causa é clara e a correção é pequena.
8. Nunca mudar infraestrutura, IAM, usuários ou configuração do stage, fazer deploy, mexer em outro stage,
   editar workflows ou fazer merge.

### Execução 1: bloqueado, e ele diz isso

A mudança encerra a matrícula de um aluno quando o Stripe informa um reembolso. Para testar isso, é preciso haver
um pedido pago para reembolsar, e o stage não tinha conta de pagamento. O Testador não aprovou o teste e
não chutou. O [veredito](https://github.com/AlexTo/discava/issues/654#issuecomment-7033260676) dele foi "blocked, not verified", com a evidência: o
`payment.status` da API de admin respondeu `not-connected`, e a tabela principal não tinha nenhum pedido.

Depois ele verificou o que dava para verificar sem um pagamento: a função do webhook em deploy contém o novo
handler `charge.refunded`, o bundle do portal servido tem a nova tela "You're no longer enrolled",
um aviso de reembolso forjado é recusado com um 400 e não grava nada, e as páginas do curso continuam funcionando
para um curso gratuito. Nove verificações passaram. Ele listou as seis coisas que *não* tinha verificado, e o que
as desbloquearia.

Ele também disse o que não faria. Conectar uma conta de pagamento significa salvar uma chave do Stripe, o que
muda a configuração do stage, e o [prompt](../agent-prompts/#testador) dele proíbe isso. Então ele
deixou a issue aberta para uma pessoa.

### Execução 3: uma compra de verdade

Depois que uma conta do Stripe em modo de teste foi conectada ao stage, o Testador começou do início
do fluxo, porque um reembolso precisa de uma compra. Cada passo abaixo é uma linha do
[terceiro relatório](https://github.com/AlexTo/discava/issues/654#issuecomment-7037624120) dele:

1. Como o instrutor, pela API, ele criou um curso chamado `pmt-647-course`, definiu o preço em
   USD 19,99 e o publicou.
2. Como o aluno, em um navegador de verdade, ele fez login na página hospedada do Cognito, abriu o curso,
   escolheu **Buy now** e pagou no checkout hospedado do Stripe com um cartão de teste.
3. Ele voltou para a página do curso, que dizia "Confirming your payment", e acompanhou três
   coisas: a página, o registro do pedido no DynamoDB e os logs da função do webhook.

A última imagem é igual à primeira, e essa é a falha. O pagamento foi feito, mas
o pedido nunca saiu de `pending`, nenhuma matrícula apareceu, e a página voltou a mostrar
**Buy now**. Nada na tela diz que algo está errado: nenhum erro, nenhuma requisição com falha no
console. O Testador pegou isso porque também leu o registro do pedido e os logs da função,
que mostraram o motivo:

```text
REPORT … Duration: 10000.00 ms … Memory Size: 128 MB  Max Memory Used: 117 MB  Status: timeout
REPORT … Duration: 10000.00 ms … Memory Size: 128 MB  Max Memory Used: 117 MB  Status: timeout
```

O aviso do Stripe de que o checkout foi pago nunca entrou. A função que o recebe estava rodando
com os 128 MB padrão da Lambda, e o cold start dela (as entidades da tabela principal, o AppConfig, o SDK do
Stripe) não terminava dentro do timeout de 10 segundos. Um runtime que deu timeout é descartado, então cada uma das
novas tentativas do Stripe começou fria e falhou do mesmo jeito. O Testador a comparou com a função do
checkout, que tem 256 MB e levou 8,1 segundos para iniciar.

O reembolso em teste nunca foi alcançado. O que o Testador encontrou fica um passo antes dele, e é
pior: no stage com deploy, um aluno podia pagar por um curso e nunca recebê-lo.

### Por que nada pegou isso antes

O defeito é mais antigo que o pull request em teste, e tinha passado por todas as camadas:

- **Os testes unitários** exercitam a lógica do handler, que está correta.
- **Os testes E2E** rodam contra a stack local, onde um substituto faz o papel do Stripe e nada tem limite de
  memória nem timeout de 10 segundos.
- **O agent Revisor** e **a pessoa** leem um diff em que nenhuma configuração de memória aparece, porque
  a linha que falta é o defeito.

Ele só existe onde a função está em deploy. Essa é a lacuna para a qual o Testador existe.

### O PR de correção

A causa era clara e a correção pequena, então o prompt do Testador permitia um pull request.
O [#657](https://github.com/AlexTo/discava/pull/657) é um [commit](https://github.com/AlexTo/discava/commit/854760c3c30a5ceb1ee7c7e52ebd596bef3374f1) que muda
dois arquivos: quatro linhas no construct `StripeWebhookApi` que definem a memória da função como 512 MB,
e um teste de doze linhas que falha sem elas (`Missing key 'MemorySize'`). Ele saiu da
`main` como `openhands/test-fix-654`, e a descrição dele faz referência tanto ao [#647](https://github.com/AlexTo/discava/pull/647) quanto à
[#654](https://github.com/AlexTo/discava/issues/654).

A descrição também é franca sobre o seu limite: "Not verified on a deployed stage. The fix only
takes effect once deployed." (não verificado em um stage com deploy; a correção só vale depois do deploy).

Então o Testador parou. Ele não fez merge e não fez deploy. O [PR Checks](https://github.com/AlexTo/discava/actions/runs/44722377986)
rodou verde, e o label `openhands-review` o entregou ao agent Revisor. O review ficou parado
por quarenta minutos por algo que nenhum agent tinha feito errado: o pull request estava trancado, e o GitHub
não aceita um review em um pull request trancado. Depois que ele foi destrancado, o Revisor o aprovou. É
por isso que o Discava parou de trancar pull requests (veja [Quem pode comentar](#quem-pode-comentar)). Uma pessoa
faz o merge dele, como de qualquer outro. A issue de teste [#654](https://github.com/AlexTo/discava/issues/654) fica aberta até que o próprio reembolso seja testado em um
stage onde os pagamentos são concluídos. O último relatório do Testador lista os dados de teste que ele deixou: o
curso e o pedido `pending`.

Os screenshots ficam na workstation, em `tmp/screenshots/pr-<pr>/` no checkout do Discava. Os
relatórios nomeiam cada arquivo e dizem o que ele mostra. Os quatro acima foram copiados de lá para esta página.

## Quem pode comentar

O Discava é um repositório público, então qualquer pessoa pode comentar nas issues e nos pull requests dele. Os agents
leem esses comentários enquanto têm em mãos um token que pode fazer push, e o Testador também tem acesso à AWS e
as senhas dos usuários de teste. Um comentário é, portanto, um jeito de dar instruções a um agent: uma prompt
injection. Os prompts mandam cada agent tratar o que ele lê como dado, mas um prompt é um pedido,
não uma garantia.

Por isso o Discava mantém os estranhos fora da conversa, de duas formas:

| Camada | O que ela faz |
| --- | --- |
| **Limite de interação** | O **Settings → Moderation options → Interaction limits** do GitHub está configurado como **Limit to repository collaborators**. Mais ninguém pode comentar, abrir uma issue ou abrir um pull request em qualquer lugar do repositório |
| **Issues de agent trancadas** | O Agent Issues e o Post-merge Verify abrem cada issue sem o label, trancam a issue (e, no caso de uma issue de teste, o pull request que ela testa e as issues que ele fecha) e só então adicionam o label. Se algo não puder ser trancado, o label nunca é adicionado e a execução falha. O código compartilhado é `src/helpers/conversation-lock.ts` |

Mais duas regras vêm junto:

- **A confiança nos marcadores depende do autor.** Os workflows encontram suas issues anteriores por um marcador oculto.
  Um marcador só conta em uma issue aberta pelo `github-actions[bot]` ou por alguém com acesso de escrita
  (`src/helpers/issue-author.ts`), então um estranho não consegue travar uma cadeia nem impedir um teste abrindo uma
  issue com um marcador dentro.
- **O Testador testa só as issues do workflow.** A automation dele pula qualquer issue de teste que não tenha sido aberta
  pelo `github-actions[bot]`, e as instruções dele são o seu próprio prompt, nunca a issue.

<Aside type="caution" title="Um repositório público precisa do limite de interação">
Se o seu repositório é público, configure o limite de interação como **só colaboradores** antes de ativar
o agent Testador, e de preferência antes de qualquer agent. Sem ele, qualquer pessoa pode comentar em uma issue
de teste ou no pull request que ela testa, e o Testador lê esse comentário enquanto tem em mãos credenciais
de nuvem e as senhas dos usuários de teste.

O limite dura no máximo seis meses. O do Discava vai até 20 de maio de 2027. Coloque a renovação em uma agenda,
porque nada avisa você quando ele expira. Um repositório privado não precisa dele: só pessoas com
acesso podem comentar ali.

Os comentários escritos antes de o limite ser configurado, ou antes de uma issue receber o label, continuam lá. Leia-os antes
de aplicar o label a uma issue existente à mão.
</Aside>

### Por que o Discava parou de trancar pull requests

Até o [#658](https://github.com/AlexTo/discava/pull/658), um workflow chamado **Agent Lock** também trancava todo pull request que um
agent abria, e qualquer issue em que alguém aplicava à mão um label para um agent. Ele mantinha os estranhos fora, mas
tinha dois custos:

- **O agent Revisor não conseguia fazer o review.** O GitHub recusa um review nativo em um pull request trancado,
  mesmo vindo de uma conta com acesso de escrita. O PR de correção [#657](https://github.com/AlexTo/discava/pull/657) foi trancado às 10:49,
  recebeu o label de review às 10:54, e não teve review nenhum até ser destrancado à mão às 11:34. O
  Revisor o aprovou cinco minutos depois.
- **Os E2E screenshots não podiam ser publicados.** O GitHub também recusa ao token do Actions um comentário em uma
  conversa trancada, então a
  [lista de screenshots](../pr-checks/#ui-screenshots-e-o-comentário-e2e-screenshots) teve de ir para
  o resumo do job.

O limite de interação faz o mesmo trabalho para o repositório inteiro, sem trancar nada em que os
agents precisam escrever. O Agent Lock e o script dele foram removidos, e os quatro pull requests de agent
que ele tinha trancado foram destrancados à mão.

DRY_RUN=true GITHUB_REPOSITORY=AlexTo/discava GITHUB_EVENT_NAME=workflow_dispatch PR_NUMBER=647 \

pull request pelo `gh`, então você precisa estar autenticado.
