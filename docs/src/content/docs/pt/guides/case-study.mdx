[Como funciona](../how-it-works/) descreve o loop. Esta página o mostra rodando uma vez, em um
pull request real do [Discava](https://github.com/AlexTo/discava): o que um aluno vê depois de
pedir o reembolso de um curso que comprou.

Todas as citações, números e links vêm do GitHub. Os horários estão no fuso de Sydney (AEDT,
UTC+11), em 25 e 26 de novembro de 2026.

Da abertura do pull request ao merge: quatro rodadas de correção, três vindas da CI e uma do
review, e uma ação de uma pessoa. Depois, o Testador encontrou dois problemas que nenhum deles
poderia ter visto.

## 1. A issue

Um aluno que pede reembolso vê "Refund requested" enquanto o Stripe o processa, e a página do
curso verifica a cada 2 segundos se ele foi concluído. A
[#1166](https://github.com/AlexTo/discava/issues/1166) diz o que havia de errado nisso:

> While a student's refund is pending, the course page refetches `course.myEnrolment` and
> `payment.myOrder` every 2 s, and never stops. If the refund fails at Stripe or its event never
> arrives, the order stays `paid` with a refund requested, the page keeps polling for as long as
> it is open, and the student isn't told anything has gone wrong.

Os critérios de aceitação dela são duas linhas: o polling para depois de um limite, e um reembolso
que falhou, simulado no stand-in do Stripe, encerra o estado pendente com uma mensagem clara.

Esta issue não veio de uma spec. O agent Revisor a levantou durante o review do PR que permitiu a
um aluno pedir reembolso, como um problema fora do escopo daquele PR, e ela virou uma issue
própria. (A #1166 é uma cópia: a antiga conta de máquina dos agents foi sinalizada pelo GitHub, que
escondeu tudo o que ela tinha aberto, e as issues abertas foram
[abertas de novo](../../discava/openhands-setup/#o-github-app) pelo GitHub App que os agents usam
agora.)

## 2. O agent Desenvolvedor abre o PR

O agent Desenvolvedor pegou a issue e abriu o [#1195](https://github.com/AlexTo/discava/pull/1195)
em `openhands/issue-1166`. A mudança passa por quatro pacotes: um limite de 2 minutos e um botão
"Check again" na página do curso, um handler de webhook para os eventos de reembolso que falhou do
Stripe, um campo `refundFailedAt` no pedido com uma invariante de que uma falha precisa vir depois
de um pedido de reembolso, e "Your refund failed" na página do curso. A descrição terminava com o
que ele tinha rodado e o que não tinha:

> Unit tests cover the helper, the webhook, the invariant and the UI (poll limit, check again,
> failure message). [...] I did not run the e2e tests or try the stand-in control in a browser.

## 3. A CI devolve o PR, três vezes

**`ci-fix-1`: sem screenshots, e linhas sem testes.** O PR mudava o que um aluno vê, mas não tirava
nenhum screenshot, então [**UI Screenshots** falhou](https://github.com/AlexTo/discava/actions/runs/45619342535/job/139224403383).
O **codecov/patch** também falhou: linhas novas não tinham teste. O **Agent CI Status** adicionou
`ci-fix-1` e mandou o agent Desenvolvedor de volta. A [resposta](https://github.com/AlexTo/discava/pull/1195#issuecomment-7164484931)
dele mostra que, no caminho, ele encontrou um problema na própria primeira tentativa:

> **UI Screenshots:** added a `learner-refund` e2e scenario for a failed refund, with
> `screenshot(student, 'refund-failed')`. For this the Stripe stand-in has a new
> `fail-next-refund` control. [...] This replaces the `refund-fail` control from the first push,
> which the scenario could not use, because the stand-in completed the refund before it could
> fail.

**`ci-fix-2`: uma falha que não era dele.** A execução seguinte falhou em **Checks (build)**, em um
teste de CDK synth no pacote de infraestrutura. O agent leu o log e
[não mudou nenhum código por causa disso](https://github.com/AlexTo/discava/pull/1195#issuecomment-7165688653):

> the one failure was `@discava/infra` `instructor-api-stack.test.ts` [...], which hit its 30s
> timeout while the sibling CDK synth tests in that file took 22–31s. This PR doesn't touch infra
> or anything the stack synthesises [...], so I made no code change for it. The push below
> re-runs the build.

Ele cobriu a única linha parcial que o codecov ainda apontava, e o push rodou o build de novo, que
passou. Um agent que "corrige" uma falha mudando código que não entende é pior do que um que diz
que a falha não é dele, e por quê.

**`ci-fix-3`: o próprio teste novo estava errado.** Depois do review (próxima seção), o agent
adicionou um cenário e2e para o limite de 2 minutos, e ele falhou em [**E2E tests (11/12)**](https://github.com/AlexTo/discava/actions/runs/45685812586/job/139458011986).
Cinco minutos depois, [a causa](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172674824):

> the new `a pending refund stops polling and offers to check again` scenario failed with a
> Playwright strict-mode violation, not a product bug. `getByText('Still being processed')` also
> matched the alert's description ("Your refund is still being processed…"), so it resolved to two
> elements. The page did reach the timed-out state. I now match the title with `{ exact: true }`.

O agent não tinha rodado nenhum cenário e2e localmente, e disse isso todas as vezes. A CI do PR é
onde eles rodam pela primeira vez, e o [comentário E2E screenshots](https://github.com/AlexTo/discava/pull/1195#issuecomment-7163204279)
lista as duas telas que a execução capturou: `learner-refund/01-refund-failed.png` e
`learner-refund/01-refund-still-being-processed.png`.

## 4. O agent Revisor encontra o que a CI não podia encontrar

Quando todos os checks do head terminaram, o agent Revisor leu o diff contra a issue. Ele achou o
código de pagamentos correto, rodou ele mesmo 361 testes focados e, ainda assim,
[bloqueou o merge](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6063632214):

> 1. **The branch carries another open PR's change.** Commit `e7cb9bc9`, "fix(student-portal):
>    surface completions and progress load errors on start route", is the change from open PR
>    #1188, not part of #1166. [...] Merging this PR would ship #1188's start-route error behaviour
>    under a payments title, before #1188 is reviewed.
> 2. **Live evidence is missing for the "Still being processed" / "Check again" state.** [...] The
>    new timed-out state [...] has only unit tests, and no capture from the running app.
>
> 🔄 CHANGES REQUESTED

O primeiro ponto é o tipo de coisa que passa por todos os checks. O commit extra compilava e os
testes dele passavam; ele só não pertencia ali. O checkout do agent tinha partido de um branch que
já o tinha. O segundo ponto é de novo a regra dos screenshots, aplicada por quem lê: a CI verifica
que um PR adiciona um screenshot, e o Revisor verifica que cada estado novo tem um.

O **Agent Review Status** adicionou `review-fix-1`. Oito minutos depois, o agent Desenvolvedor
[tinha](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172386579) feito o rebase dos
próprios quatro commits sobre a `main` sem os outros dois, e adicionado um controle no stand-in que
mantém um reembolso pendente e um cenário e2e que instala o fake clock do Playwright e avança 125
segundos. É o cenário que o `ci-fix-3` corrigiu depois.

No head final, o Revisor [confirmou](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066801083)
que os dois pontos estavam resolvidos, que os 12 shards de e2e tinham passado, e citou os dois
screenshots: "No material findings [...] ✅ APPROVED".

## 5. Uma pessoa aprova

Às 11:33, o mantenedor [aprovou](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066944326)
e fez o merge. Foi a única coisa que uma pessoa fez neste PR. O que ele tinha diante de si: uma
descrição que dizia o que foi e o que não foi rodado, os dois screenshots da CI, uma lista de checks
verde e um histórico de quatro revisões, cada uma com o seu motivo.

## 6. O merge entra no deploy, e uma issue de teste é aberta

No Discava, a `main` faz deploy sozinha em um stage de desenvolvimento. O [deploy](https://github.com/AlexTo/discava/actions/runs/45734764281)
com este merge terminou às 12:28, e um minuto depois o **Post-merge Verify** abriu a
[#1240](https://github.com/AlexTo/discava/issues/1240). Ela lista os 12 arquivos em deploy que o PR
mudou e diz que tipo de teste rodar:

> Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
> through the flow with Playwright, then call the APIs behind it and check the stored data.

## 7. O agent Testador testa o stage com deploy

O agent Testador não roda a suíte de testes de novo, e não usa o stand-in do Stripe. Ele usa o
produto em deploy como uma pessoa usaria, com o Stripe de verdade em modo sandbox. O
[relatório](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815) dele lista cada passo:

1. Como um instrutor de teste, pela API, ele criou dois cursos a $19.99.
2. Como um aluno de teste, em um navegador de verdade, ele fez login e comprou cada um no Stripe
   Checkout, usando os cartões de teste do Stripe para "reembolso falha" e "reembolso pendente".
3. Ele pediu o reembolso de cada um na página do curso.
4. Depois de cada passo, ele chamou as APIs, leu os pedidos e as matrículas no DynamoDB, e leu os
   logs das Lambdas do webhook e da API.

separadas (próxima seção).

Neste stage, o Stripe de verdade não conseguia manter um reembolso pendente nem registrar um que

dados armazenados. Ele cronometrou o limite: "Still being processed" apareceu **120.2 s** depois

O relatório tem 22 verificações. Dezessete passaram, incluindo estas:

| Verificação | Resultado |
| --- | --- |
| O polling para depois de 2 minutos | 120.2 s, depois 0 requisições nos 20 s seguintes |
| "Check again" reinicia o polling | 4 requisições nos 8 s seguintes, e o aviso some |
| `payment.myOrder` sem token | Recusado: 401 |
| `payment.myOrder` como um usuário que não comprou | 200 com `null`: nenhum pedido de outra pessoa |
| `payment.requestRefund` em um pedido já reembolsado | Recusado: 412, "No purchase to refund" |

## 8. O Testador deixa a issue aberta

Três verificações falharam, e duas terminaram em um estado que o PR não esperava. O
[veredito](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815):

> **Verdict: the student-facing UI and `payment.myOrder` work as the PR describes. The
> failed-refund path does not work end to end on the deployed stage.**

Ele encontrou duas causas, ambas fora de tudo o que os testes do PR conseguiam alcançar:

1. **O webhook do Stripe do stage nunca recebe os eventos novos.** O PR adicionou `refund.failed`
   e `charge.refund.updated` à lista de eventos, mas essa lista só é enviada ao Stripe quando um
   administrador o conecta pela primeira vez. O stage tinha sido conectado seis dias antes. O
   Testador contou exatamente quatro invocações do webhook na meia hora, nenhuma delas para uma
   falha.
2. **Com o Stripe de verdade, um reembolso que falhou chega quando o pedido já está `refunded`.**
   O Stripe envia `charge.refunded` assim que um reembolso é criado, mesmo um que está pendente ou
   que vai falhar. Quando o `refund.failed` chega, a condição do novo handler (o pedido ainda está
   `paid`) não vale mais, e ele não faz nada, em silêncio:

   > The student has lost access, hasn't been refunded, and isn't told.

   O stand-in no cenário e2e do PR nunca conclui um reembolso antes de fazê-lo falhar, então a CI
   mostrou a versão feliz disso.

O Testador pode abrir um PR de correção quando a correção é pequena e clara. Ele explicou por que
não abriu:

> Fixing it means deciding how a refund failure after `charge.refunded` should restore the order
> and enrolment, or not treating a `pending` refund as refunded. That goes beyond a small fix, so
> I'm reporting it rather than opening a PR.

Ele também não mexeu na conexão do stage com o Stripe, embora salvá-la de novo resolvesse a
primeira causa: "I didn't do that, because it changes stage configuration." Então a issue continua
aberta, com os dois problemas descritos, como reproduzi-los e as escolhas que uma pessoa precisa
fazer. Ele listou os dados de teste que deixou no stage, e um erro que viu e que já estava sendo
acompanhado em outro lugar, para que ninguém o confundisse com uma regressão.

<Aside type="tip">
[Verificação pós-merge](../../discava/post-merge-verify/) acompanha outra issue de teste, em que o Testador
encontrou uma falha, rastreou a causa e, desta vez, abriu o PR de correção.
</Aside>

## O que cada gate pegou

| Gate | O que ele pegou | Por que o gate anterior não pegou |
| --- | --- | --- |
| CI | Uma mudança de UI sem screenshot, linhas sem teste e um locator quebrado no próprio teste e2e do agent | O agent Desenvolvedor não tinha rodado a suíte e2e |
| Agent Revisor | O commit de outro PR pegando carona no branch, e um estado novo de tela sem screenshot | O commit extra passava em todos os checks, e a CI só verifica se algum screenshot foi adicionado |
| Agent Testador | Um endpoint de webhook que nunca recebe os eventos novos, e o Stripe de verdade relatando primeiro como reembolsado um reembolso que vai falhar | O stand-in se comporta como o código espera, e nenhum teste vê a configuração do stage |

Nenhum dos três é esperto sozinho. Cada um olha para algo que os outros não enxergam: a CI para
as regras, o Revisor para a issue e o branch, o Testador para o produto rodando e os serviços reais
por trás dele.

## O que a pessoa fez

1. Leu o PR #1195 e os screenshots dele, aprovou e fez o merge.
2. Próximo passo: decidir o que uma falha de reembolso depois de `charge.refunded` deve fazer, a
   partir das opções que o Testador descreveu.

Ninguém escreveu um prompt, colou um log de erro ou clicou pelo stage à mão.
