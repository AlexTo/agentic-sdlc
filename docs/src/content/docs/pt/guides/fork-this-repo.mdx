Este repositório *é* o workflow: a mesma configuração do Speckit, o template de issue, os PR checks, os
workflows de agent e a cola com testes unitários que o Discava usa, em volta de um pequeno app de notas.

**Faça um fork e você tem a configuração do Discava.** Aponte o seu próprio OpenHands para o fork, escreva
uma spec para o app de notas e ela passa pelo loop descrito em [Como funciona](../how-it-works/).

## O que você recebe

<FileTree>
- AGENTS.md o que todo agent lê primeiro, escrito para o app de notas
- .specify/ templates, scripts e a constitution do Speckit
- .husky/ Conventional Commits, scan de secrets e Biome no commit, mapa de invariantes no push
- scripts/
  - setup-repository.sh labels, branch protection e as outras configurações que um fork não copia
  - agent-app-token.sh gera o token do GitHub App dos agents e o entrega ao Agent Canvas
- .github/
  - ISSUE_TEMPLATE/
    - implement-phase.md as instruções que toda issue de implementação carrega
    - test-deployed-pr.md uma issue de teste para o agent Testador, à mão
  - actions/ configuração de CI compartilhada, o Chromium do Playwright, checks de caminhos alterados
  - dependabot.yml mantém atualizadas as actions fixadas e as dependências
  - workflows/
    - pr-checks.yml lint, testes, build, formato de tasks, cobertura de invariantes, e2e, comentário de screenshots
    - ui-screenshots.yml a regra de screenshots
    - ci.yml checks, Trivy e o deploy da documentação na main
    - agent-issues.yml spec → issue, merge → próxima issue
    - archive-specs.yml spec concluída → PR de arquivamento
    - agent-ci.yml CI vermelho → agent
    - agent-review.yml "changes requested" → agent
    - agent-status.yml os passos que esses dois compartilham
    - deploy.yml main verde → um stage, desligado até você adicionar infraestrutura
    - post-merge-verify.yml PR com deploy → issue de teste para o Testador
    - cache-cleanup.yml os caches de um PR fechado
- packages/
  - tooling/agent/ as regras da cola, com 223 testes unitários
  - tooling/local-dev/ sobe o DynamoDB local para o `pnpm dev`
  - notes-table/ entidade ElectroDB, DynamoDB local, invariantes
  - notes-api/ procedures tRPC
  - notes-website/ React, Vite, TanStack Router, shadcn/ui
  - e2e/ cenários Playwright, o helper `screenshot()`, invariantes depois de cada teste
- docs/ este site
</FileTree>

O app de notas roda inteiramente local (`pnpm dev`, com Docker para o DynamoDB local), então o CI pode
rodar seus testes e2e e o agent nunca precisa de credenciais de nuvem.

## O que você adiciona

Só o que não pode ficar em um repositório:

1. **Configurações do GitHub**: o GitHub App com que os agents agem, e as configurações que um fork
   não copia, que o `scripts/setup-repository.sh` aplica de uma vez.
2. **OpenHands**: Agent Canvas na sua máquina, o `scripts/agent-app-token.sh` mantendo o token do app
   atualizado, e as automations apontadas para o seu fork.

## O que fica desligado até você adicionar

A nuvem. O app de notas não tem infraestrutura em nuvem, então um merge não entrega nada além do site
de documentação. `deploy.yml` e `post-merge-verify.yml` estão no lugar, mas nunca rodam sozinhos:
adicione um app CDK em `packages/infra` e defina `AUTO_DEPLOY_STAGE`, e toda `main` verde sai no
deploy, e então o agent Testador testa o que foi publicado. [Adote: deploy](../../adopt/deploy/) tem os
passos, e [Deploy e segurança](../../discava/deploy-and-security/) descreve o pipeline do Discava.
