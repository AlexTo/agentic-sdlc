**No final você terá:** Issues e Actions ligados, todos os labels que o workflow usa, uma branch
`main` que só aceita pull requests com checks verdes e uma aprovação, comentários limitados aos
colaboradores, e a conta própria dos agents como colaboradora.

Um fork copia o código, não as configurações. O `scripts/setup-repository.sh` aplica todas elas com a
CLI `gh`. Cada passo deixa sempre o mesmo estado, então é seguro rodá-lo de novo.

<Steps>

1. **Crie a conta dos agents.** Os agents trabalham com uma conta própria no GitHub, uma conta de
   máquina que nada mais usa. A do Discava é `discava-bot`. Crie uma. O token dela é o que você cria
   no [passo 3](../openhands/), e os pull requests e comentários dela aparecem com essa conta, então
   você os aprova como os de qualquer outra pessoa.

2. **Rode o script** a partir do seu clone, com login no `gh` como dono do fork, passando a conta
   dos agents:

   ```bash
   ./scripts/setup-repository.sh <you>/agentic-sdlc <agents-account>
   ```

   Adicione `--dry-run` primeiro se quiser ver cada comando `gh` antes de ele rodar. O script:

   | Configura | Por quê |
   | --- | --- |
   | Issues e Actions ligados | O GitHub desliga os dois em um fork, e o workflow roda em issues |
   | 20 labels | Todos os labels em [Referência: labels](../../reference/labels/) |
   | Branch protection na `main` | Um pull request, uma aprovação, aprovações antigas descartadas e sete checks obrigatórios: `Checks (lint)`, `Checks (test)`, `Checks (build)`, `Tasks format`, `Invariant coverage`, `E2E tests`, `UI Screenshots` |
   | As Actions podem abrir pull requests | O Archive Specs abre o pull request que move uma spec concluída para `specs/_archive/` |
   | Interações limitadas aos colaboradores, por seis meses | Um fork de um repositório público é público, e os agents leem todo comentário naquilo em que trabalham enquanto têm em mãos um token que pode fazer push |
   | GitHub Pages a partir das Actions | O job **Deploy Docs** do CI publica este site |
   | A conta dos agents convidada com acesso de escrita | Para que os agents possam fazer push de branches e abrir pull requests |

   A proteção deixa o bypass permitido, então você, como dono, pode fazer merge de um pull request
   que você mesmo abriu, como um PR de spec, que o GitHub não deixa você aprovar.

3. **Aceite o convite** com login feito na conta dos agents.

4. **Confira se as Actions estão ligadas.** Se a aba **Actions** do seu fork ainda mostra **I
   understand my workflows, go ahead and enable them**, clique. O GitHub às vezes pede esse clique
   mesmo depois que a API ligou as Actions.

</Steps>

<Aside type="caution">
O limite de interação expira seis meses depois de configurado, e nada avisa você. Anote a data e
rode o script de novo antes disso. Se você adicionar depois o agent Testador, que tem credenciais
de nuvem, é esse limite que impede o comentário de um estranho de chegar até ele. Veja
[Quem pode comentar](../../discava/post-merge-verify/#quem-pode-comentar).
</Aside>

<Aside type="caution">
Não adicione `software-factory/review` aos checks obrigatórios. Ele é um sinal para o agent, só é
postado como `failure`, e exigi-lo bloquearia todos os PRs.
</Aside>

## Confira se funcionou

A página **Issues → Labels** do fork lista os 20 labels, **Settings → Branches** mostra a regra na
`main` com sete checks obrigatórios, e **Settings → Moderation options → Interaction limits** mostra
o limite só para colaboradores com a data de término. **Settings → Collaborators** lista a conta dos
agents com o papel **Write**.
