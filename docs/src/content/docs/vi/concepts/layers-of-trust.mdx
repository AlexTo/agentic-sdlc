Automation chỉ đáng giá nếu bạn tin được những gì nó tạo ra. Mọi thay đổi đi qua nhiều lớp kiểm
tra. Mỗi lớp thu hẹp những gì đến được lớp kế tiếp: các kiểm tra rẻ, tự động chạy trước và bắt được
nhiều nhất, và chỉ những gì chúng không thể đánh giá mới đến tay một người.

| Cấp | Lớp | Bắt được gì |
| --- | --- | --- |
| **Codebase** | Unit test | Logic nghiệp vụ sai và quy tắc bị phá vỡ |
| | Invariant | Dữ liệu phá vỡ một quy tắc trải trên nhiều bản ghi, được kiểm tra sau mỗi e2e test |
| | Test đồng thời | Race condition khi hai request đến cùng một lúc |
| **Phân tích tĩnh** | Lint, typecheck, build | Lỗi style, kiểu và build |
| | Kiểm tra định dạng tasks | Một `tasks.md` sai định dạng có thể âm thầm làm chuỗi đứng lại |
| | Kiểm tra file sinh ra | Output của lint hoặc build mà agent quên commit |
| **Kiểm chứng** | End-to-end test | Luồng người dùng bị hỏng, trong một trình duyệt thật chạy trên local stack |
| | Ảnh chụp màn hình | Thay đổi UI mà chưa ai nhìn qua |
| **Văn bản hướng dẫn** | Constitution, `AGENTS.md`, skill | Hướng dẫn agent đọc *trước khi* viết, để quy ước được tuân theo thay vì bị bắt lỗi |
| | Agent reviewer | Vấn đề mà không test nào bao phủ, được đọc như một lần review code |
| **Người review** | Review cuối | Bất cứ điều gì các lớp trên không đánh giá được. Luôn có một người merge |

## Kiểm chứng là quan trọng nhất

Trong tất cả các lớp, kiểm chứng là lớp giành được niềm tin của bạn. Unit test, lint và kiểu cho
thấy code nhất quán với chính nó. Chỉ e2e test và ảnh chụp màn hình cho thấy tính năng *hoạt động*,
theo cách người dùng thấy, trên stack thật. Đó cũng là lớp một người có thể kiểm tra nhanh nhất: một
lập trình viên nhìn ảnh chụp màn hình có thể đánh giá một PR trong vài phút, không cần pull nhánh.

Đây là [nguyên tắc 4](../principles/): cho agent tay và mắt. Các kịch bản e2e agent viết là tay của
nó: chúng khởi động toàn bộ stack, đăng nhập, gọi API và bấm qua UI. Kết quả, lỗi invariant và ảnh
chụp màn hình là mắt của nó: chúng cho agent, rồi đến bạn, thấy thay đổi thực sự làm gì.

Vì vậy CI biến nó thành mặc định:

1. Mọi kịch bản e2e cho một luồng UI gọi `screenshot(page, 'name')` ở mỗi trạng thái mà người review
   muốn thấy.
2. CI đăng một comment **E2E screenshots** trên PR, liệt kê các ảnh mà PR thêm vào (tách riêng với
   những ảnh đã có từ trước) và liên kết đến artifact của lần chạy.
3. Check `UI Screenshots` thất bại nếu một thay đổi UI được ship mà không có ảnh chụp màn hình.

cài đặt thông báo:

Người review mở chín ảnh mới và kiểm tra từng trạng thái: trang cài đặt với mọi loại được liệt kê,
một công tắc được lưu, email bị dừng và bật lại, một liên kết hủy đăng ký hợp lệ và một liên kết không
hợp lệ, một lỗi và "thử lại". Mỗi trạng thái đó là một yêu cầu từ spec, được thấy đang hoạt động. Đó
là mục đích của lần review cuối: đánh giá kết quả, không phải đọc từng dòng.

## Văn bản hướng dẫn, code thực thi

Văn bản hướng dẫn (constitution, `AGENTS.md`, hướng dẫn trong issue) rẻ để viết và ngăn được phần
lớn lỗi. Nhưng agent có thể hiểu sai hoặc bỏ qua nó. Nên mọi quy tắc quan trọng đều có thêm một check
sẽ thất bại: "viết e2e screenshots" nằm trong issue template *và* được check UI Screenshots thực thi.
"Giữ `tasks.md` theo định dạng này" nằm trong template *và* trong một PR check.

Khi bạn thêm một quy tắc, hãy hỏi: nếu agent phớt lờ điều này, cái gì sẽ chuyển đỏ?

## Test là một đặc tả

Quy tắc quan trọng nhất trong constitution của Discava:

> A failing test MUST be resolved by fixing the code, unless the spec or plan changes the behavior
> it covers. Weakening an existing test (loosening an assertion, deleting a case, adding `skip` or
> `only`, widening a mock or snapshot) is allowed only when a task names the behavior change that
> justifies it, and the PR description says so.

(Một test thất bại PHẢI được giải quyết bằng cách sửa code, trừ khi spec hoặc kế hoạch thay đổi hành
vi mà nó bao phủ. Làm yếu một test có sẵn chỉ được phép khi một task nêu rõ thay đổi hành vi biện minh
cho nó, và mô tả PR nói như vậy.)

Một agent chịu áp lực phải làm CI xanh, sớm hay muộn, sẽ "sửa" test. Quy tắc này, được lặp lại trong
issue template và được agent reviewer kiểm tra, là thứ giữ cho bộ test còn ý nghĩa.

## Invariant: test cho dữ liệu

Unit test kiểm tra một hàm. E2E test kiểm tra một luồng. Không loại nào nhận ra khi hai tính năng,
được viết trong các PR khác nhau bởi các lần chạy agent khác nhau, để database ở trạng thái phá vỡ một
quy tắc trải trên cả hai. Invariant lấp khoảng trống đó. Chúng là một danh sách kiểm tra trên toàn bộ
dữ liệu, ví dụ "số lượt đánh giá của một khóa học bằng số review hiển thị của nó", chạy sau **mọi** e2e
test. Một invariant bị vi phạm làm thất bại chính test đã gây ra nó.

<Aside type="tip">
Invariant là lớp mang lại nhiều giá trị nhất khi agent viết ngày càng nhiều code. Chúng bắt được
những lỗi đến từ việc hai agent, mỗi bên đều đúng ở phạm vi của mình.
</Aside>
