**完成后你将拥有：** 每个智能体最先阅读的 `AGENTS.md`，以及 `.github/ISSUE_TEMPLATE/` 下的 issue 模板，它们是每个实现 issue 中固定说明的来源。

<Steps>

1. 从这个仓库**复制 `AGENTS.md`**，并为你的项目改写每一节。它是有意写短的：只写智能体每次运行都需要的内容，别的都不写。

   | 小节 | 写什么 |
   | --- | --- |
   | What this is | 一段话：产品、技术栈、monorepo 工具 |
   | Commands | 安装；构建、lint、测试全部项目；只运行一次某个项目的测试（不用 watch 模式）；某个测试文件；`nx affected`；e2e；本地开发 |
   | Architecture | 每个包一条：它是什么、它可以导入什么、每种新代码应该放在哪里 |
   | Conventions | Conventional Commits、格式化工具的名称、辅助函数放在哪里，以及评审者不得不重复说过两次的每一条规则 |

   <Aside type="tip">
   命令这一节最重要。一个找不到“只运行一次某个测试文件”的智能体，会以 watch 模式运行整个测试套件，然后卡住。你列出的每条命令都亲自运行一次，确认它能用。
   </Aside>

   当架构一节超出每个包一行的篇幅时，把每个包的细节移到其文件夹中嵌套的 `AGENTS.md` 里，在根文件中只留一行指向那里。智能体只有在某个文件夹中工作时才会加载那里的嵌套文件，所以一次运行只会读到它需要的细节。这个仓库的 `packages/tooling/agent/AGENTS.md` 就是一个例子；在[第 5 步](../glue-scripts/)中把它和粘合代码一起复制。

   如果你的智能体读取的是另一个名字的文件，比如 `CLAUDE.md`，就让那个文件指向 `AGENTS.md`。这个仓库的 `CLAUDE.md` 以 `@AGENTS.md` 开头，Claude Code 会把它理解为“在这里包含那个文件”。

2. 从这个仓库**复制 `.github/ISSUE_TEMPLATE/`**：给开发智能体用的 `implement-phase.md`，以及给测试智能体用的 `test-deployed-pr.md`（如果你在[第 9 步](../deploy/)中添加了测试智能体）。

   Agent Issues 脚本自己写 issue 的 spec 和范围两节，并在运行时读取 `implement-phase.md` 中 `## Instructions for the agent` 之下的全部内容。这个标题必须一字不差，因为脚本会查找它，找不到就会失败。`#<parent>` 也要原样保留：脚本会把它替换为 spec 的父 issue；如果 spec 没有父 issue，就删掉这一条。

3. **按你的技术栈修改这些说明**：命令、截图辅助函数的路径，以及“cloud credentials”对你来说指什么。

</Steps>

## 检查是否成功

```bash
grep -c '^## Instructions for the agent$' .github/ISSUE_TEMPLATE/implement-phase.md
```

```text
1
```
