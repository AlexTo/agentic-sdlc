import { Steps, Aside, FileTree } from '@astrojs/starlight/components';

**完成后你将拥有：** 一个 `tooling-agent` 项目，带有十个 Nx target 和 223 个通过的单元测试。第 6、7 和 9 步中的 workflow 只调用这些 target。

<Steps>

1. 从这个仓库**整个复制 `packages/tooling/agent/`**。它的 `project.json` 已经声明了 workflow 调用的每一个 target，它的 `AGENTS.md` 会告诉智能体每个文件夹里有什么：

   <FileTree>
   - packages/tooling/agent/src/
     - agent-issues/ spec → issue、`tasks.md` 校验器，以及归档已完成的 spec
     - agent-ci/ 红色 CI → 智能体
     - agent-review/ "changes requested" → 智能体
     - helpers/ 锁定智能体读取的 issue，并区分可信作者与陌生人
     - ui-screenshots/ 截图规则，以及 `E2E screenshots` 评论
     - invariant-coverage/ 哪些代码写入哪个实体，以及新的写入方需要不变式的规则
     - post-merge-test/ 已部署的 PR → 给测试智能体的测试 issue
   </FileTree>

   它们只依赖 Node 内置模块、TypeScript（用于不变式扫描）和 `gh` CLI，由 `tsx` 运行。如果你的 glob 还没有覆盖 `packages/tooling/*`，把这个文件夹加入工作区的 `pnpm-workspace.yaml` 和根 `tsconfig.json` 的 references 中。

2. **重命名 scope。** 在项目的 `package.json`、`project.json` 和 `vitest.config.mts` 中，以及它各个 `main.ts` 文件的注释中，把 `@agentic-sdlc/` 替换为你工作区的 scope。你之后复制的每个 workflow 中也都写着 `@agentic-sdlc/tooling-agent`。

3. **按你的配置修改这些常量。** 加粗的那些指向这个仓库的笔记应用，所以你几乎肯定要改它们。其余的只有在你改动了[概览](../overview/)中的某个决定时才需要改：

   | 常量 | 文件 | 默认值 |
   | --- | --- | --- |
   | **`UI_SOURCE`** | `ui-screenshots/check.ts` | `packages/notes-website/src/` 和 `packages/common/shadcn/src/` 下的 `.tsx`/`.css` |
   | **`WRITER_PACKAGES`**、**`ENTITIES_PACKAGE`** | `invariant-coverage/scan.ts` | 其代码会写入表的那些包，以及存放表实体的包（`notes-table`） |
   | **`WRITER_MAP_PATH`**、**`INVARIANTS_PATH`**、**`HELPERS`** | `invariant-coverage/check.ts` | `packages/notes-table/entity-writers.json`、`packages/notes-table/src/helpers/invariants`、`notes-table` |
   | **`UI_PATHS`**、**`NOT_DEPLOYED`** | `post-merge-test/plan.ts` | 哪些算作值得点一遍的 UI 改动，以及永远不会进入已部署栈的路径 |
   | `SPEC_READY_LABEL`、`AGENT_BRANCH_PREFIX` | `agent-issues/gate.ts` | `spec-ready`、`openhands/` |
   | `AGENT_LABEL` | `agent-issues/issue.ts` | `openhands` |
   | `AGENT_BRANCH`、`REVIEW_STATUS_CONTEXT`、`MAX_CI_FIX_ATTEMPTS` | `agent-ci/plan.ts` | `^openhands\/issue-\d+$`、`software-factory/review`、`5` |
   | `MAX_REVIEW_FIX_ATTEMPTS`、`CHANGES_REQUESTED` | `agent-review/plan.ts` | `5`、`🔄 CHANGES REQUESTED` |
   | `WAIVER_LABEL` | `ui-screenshots/check.ts`、`invariant-coverage/check.ts` | `no-ui-screenshots`、`no-new-invariant` |

   如果你暂时不检查不变式，就把 `invariant-coverage` 文件夹留在原处，并且在第 6 步中不要复制它的 PR Checks job。有些单元测试会读取真实的不变式文件，所以请更新这些测试（在 `invariant-coverage/check.test.ts` 中）或上面的路径。

   <Aside type="caution">
   不要修改 `REVIEW_STATUS_CONTEXT`。`software-factory/review` 是 OpenHands issue-to-PR worker 查找的 status。换成任何其他名称，智能体都永远不会被打回去。
   </Aside>

4. **运行测试。**

   ```bash
   pnpm nx run @your-scope/tooling-agent:test
   ```

</Steps>

## 试一次 dry run

每个智能体脚本都从 `GITHUB_EVENT_PATH` 读取 GitHub 事件，在 `DRY_RUN=true` 时会打印出它的决定，而不是执行它。要重放一个真实的案例，从过去的某次 workflow 运行中保存一份 payload，然后让脚本指向它：

```bash
DRY_RUN=true GITHUB_REPOSITORY=owner/repo GITHUB_EVENT_PATH=./event.json \
  pnpm nx run @your-scope/tooling-agent:agent-ci-status
```

```json
{
  "pullRequest": 470,
  "plan": {
    "action": "send-back",
    "attempt": 1,
    "label": "ci-fix-1",
    "description": "CI failed (fix attempt 1 of 5): E2E tests (4/4)"
  }
}
```
