获得这套工作流最快的方式是 [fork 这个仓库](../../setup/fork/)。本节适用于你无法这样做的情况：你有一个已有的产品仓库，想在其中搭建同样的配置。

每一步都会加入一个从这个仓库复制过来的部件，并说明如何检查。完成后，你的仓库就拥有了 fork 所拥有的一切，然后你从 [2. 配置仓库](../../setup/github-repository/)继续。

<Aside type="tip">
无论如何，先 fork 这个仓库，在笔记应用上运行一遍[你的第一个功能](../../setup/first-feature/)。亲眼看到整个循环跑通一次，会让这里的每一步都容易理解得多。
</Aside>

## 先做这些决定

| 决定 | 默认值 | 何时修改 |
| --- | --- | --- |
| 实现用的触发标签 | `openhands` | 你已经在用这个标签 |
| 分支前缀 | `openhands/issue` | 很少需要。粘合层精确匹配 `openhands/issue-<n>`。如果你修改了它，也要修改 `AGENT_BRANCH` 和 workflow 的条件 |
| 评审标签 | `openhands-review` | 同上 |
| 轮询间隔 | 每 5 分钟 | 你希望降低成本，并且可以等更久（目录中的默认值是 15） |
| 最大修复次数 | 每个循环 5 次 | 很少需要。它是两个 `plan.ts` 文件中的 `MAX_*_FIX_ATTEMPTS` |
| Spec 文件夹编号 | 时间戳 | 只要 spec 作者多于一人，就永远不要改 |

在每条命令和每个复制过来的文件中，把 `@your-scope` 或 `@agentic-sdlc` 替换为你工作区的 npm scope。
