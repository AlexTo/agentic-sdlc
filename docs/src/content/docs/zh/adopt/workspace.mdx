**完成后你将拥有：** 一个带 Nx 和 Biome 的 pnpm 工作区，每个 commit 都强制遵循 Conventional Commits，并且每次提交前都会进行 secret 检查。

粘合层并不需要 Nx。但正是 `nx affected` 让 PR 检查足够快，智能体才能在上面反复迭代，而且每个粘合脚本都作为一个 Nx target 运行。如果你使用别的 monorepo 工具，保留这个思路即可：只运行 PR 影响到的部分，并把每个脚本暴露为一个具名任务。

<Steps>

1. 如果你还没有工作区，**创建一个**。Discava 和这个仓库都是用 Nx Plugin for AWS 创建的：

   ```bash
   pnpm create @aws/nx-workspace your-project --iac=cdk --no-interactive
   ```

   已有的 Nx 工作区也可以。在根目录的 `package.json` 中用 `packageManager` 固定 pnpm 版本，让 CI 和智能体使用同一个版本。

2. 从这个仓库把下面这些文件**复制到你仓库中的相同路径**：

   <FileTree>
   - commitlint.config.js Conventional Commits
   - lint-staged.config.js 对暂存的文件运行 Biome
   - .husky/
     - commit-msg 运行 commitlint
     - pre-commit 先运行 git-secrets，再运行 lint-staged，如果 Biome 改动了任何内容就失败，让智能体重新暂存后再提交
     - prepare-commit-msg Commitizen，供交互式提交的人使用。用 `git commit -m` 提交时它会自动跳过，而智能体正是这样提交的
   - .git-secrets/ pre-commit hook 运行的 git-secrets 脚本
   - .gitallowed git-secrets 放行的模式
   - .github/
     - actions/init-monorepo/ 共享的 CI 配置
     - actions/changed-paths/ “这个 PR 是否改动了这些路径中的任何一个？”，用于跳过 job
     - actions/playwright-setup/ Playwright 用的 Chromium，按版本缓存
     - dependabot.yml 让固定版本的 action 和依赖保持最新
   </FileTree>

   `.husky/pre-push` 留到[第 8 步](../local-stack-and-e2e/)再复制：它检查不变式映射。`init-monorepo` 安装 pnpm（会尝试三次，否则一次 registry 超时就会让智能体白白耗掉一次修复机会）、Node 24 以及可选的 uv，恢复 pnpm 和 Nx 缓存，安装依赖，并为 `nx affected` 设置 `NX_BASE`/`NX_HEAD`。

3. 从这个仓库的 `package.json` **复制根脚本和开发依赖**：`scripts` 块（`AGENTS.md`、CI 和智能体会调用它们），以及 `devDependencies` 中的 `@commitlint/config-conventional`、`commitlint`、`commitizen`、`husky` 和 `lint-staged`。然后：

   ```bash
   pnpm install
   ```

   它的 `prepare` 脚本会安装这些 hook。

4. 在 `.github/actions/playwright-setup/action.yml` 中**修改包的 scope**（`@agentic-sdlc/e2e`），改成你的 e2e 项目的名称。

</Steps>

## 检查是否成功

```bash
git commit --allow-empty -m "not conventional"
```

```text
⧗   input: not conventional
✖   subject may not be empty [subject-empty]
✖   type may not be empty [type-empty]
```

然后 `git commit --allow-empty -m "chore: check hooks"` 会成功。

<Aside type="note">
粘合层写的 issue 标题就是 Conventional Commit 的头部，智能体会把它们复用于自己的 commit 和 pull request。这就是 commitlint 排在最前面的原因。
</Aside>
