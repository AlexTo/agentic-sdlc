人并没有被移出循环。他们被移到了最需要判断力的两个点上，远离中间的等待和打字。

## 关卡 1：批准 spec

spec PR 像代码一样接受评审。**带着 `spec-ready` 标签**合并它，是启动实现的唯一方式。

要关注的内容：

- `spec.md` 是否说出了你真正想要的东西，并且每条规则都以需求的形式写出？
- 每个阶段是否小到可以一次评审完？
- `plan.md` 中有没有你在代码评审中会否决的东西？

### 这现在是主要瓶颈

一旦循环能自己运行，代码评审的量就很小了：每个阶段一个绿色、经智能体批准的 PR。最慢的人工步骤就是
这一步。每个功能都在这里等待，直到有人认可 spec 是对的。

它不必等开发者。`spec.md` 是平实的语言（用户故事、验收场景、功能需求），所以**业务分析师**或
**产品负责人**可以在 spec PR 上评审、评论并批准。按文件拆分评审：

| 评审者 | 阅读 | 关注的问题 |
| --- | --- | --- |
| 产品负责人、业务分析师 | `spec.md` | 这是我们想要的功能吗？规则和边界情况对吗？有没有遗漏？ |
| 工程师 | `plan.md`、`data-model.md`、`contracts/`、`tasks.md` | 设计是否合理？阶段是否小到可以评审？ |

任何能读取仓库的人都可以评论。要让他们的批准计入分支保护，他们需要写权限。

## 关卡 2：批准结果

每个智能体 PR 在 CI 变绿、评审智能体批准之后才会到你手上。你的工作是判断结果，而不是去找问题：

- 阅读 PR 描述：改了什么、涉及哪些任务、还有哪些 **(human)** 任务留给你。
- 查看 **E2E screenshots** 评论，而不是拉取分支。它展示了功能在正常工作。示例见
  [验证最重要](../layers-of-trust/#验证最重要)。
- 完成 **(human)** 任务：在本地栈或已部署的 stage 上做手动检查。
- 合并，或者要求修改。如果想让智能体来改，在你的评审之后加上 `openhands-review` 标签：评审智能体
  会重新评审该 PR，它的 "changes requested" 结论会把开发智能体送回评审修复循环，并用同样的
  `review-fix-*` 标签计数。

在自动部署的情况下，测试智能体随后会在开发 stage 上测试你合并的内容，并在一个测试 issue 上报告。这份
报告出现在关卡之后，而不是之前：它告诉你这个变更在它运行的地方，无论是屏幕上还是它存储的数据中，是否正常工作，而
一份失败的报告需要你来处理。

## 智能体绝不能做的事

| 绝不 | 由什么强制执行 |
| --- | --- |
| 合并，或推送到 `main` | 要求一次批准评审的分支保护。智能体的 token 只用于它自己的分支 |
| 编辑 `.github/workflows/` | constitution 和 issue 指令。评审智能体和人工评审会发现它。粘合 workflow 运行的是默认分支的代码，所以 PR 中被编辑的 workflow 无法改变它们 |
| 为了通过而削弱测试 | constitution（"测试即规格"）、issue 指令、评审智能体 |
| 部署，或更改基础设施 | 没有任何智能体会拿到部署角色。部署使用来自 GitHub environment 的短期 OIDC 角色。开发智能体和评审智能体完全不需要云访问权限。测试智能体只能接触开发 stage，它的 prompt 把它限制为只读，以及它通过应用创建的测试数据 |
| 听从陌生人的指令 | 在公开仓库上，交互限制让只有协作者才能评论、开 issue 或开 pull request。workflow 为智能体开的 issue 也会被锁定。测试智能体只测试由 workflow 打开的 issue，它的指令是它自己的 prompt，而不是 issue |
| 在其任务范围之外工作 | issue 写明了范围。在每个智能体任务都被勾选之前，下一个 issue 不会打开 |
| 无限重试 | 每个循环五次尝试，记在标签里 |

## 你何时会被提前拉进来

| 信号 | 发生了什么 | 怎么做 |
| --- | --- | --- |
| `ci-fix-exhausted` | 经过自动修复后 CI 失败了五次 | 阅读最后一次失败。评论给出指导、自己修复，或者修正 spec。然后[重置循环](../../reference/labels/#重置循环) |
| `review-fix-exhausted` | 五轮之后评审智能体仍在要求修改 | 判断评审智能体是否正确。通常是 spec 有歧义 |
| 智能体在 issue 上发的评论 | 它按照指令，在受阻时停了下来 | 回答它，然后移除并重新加上 `openhands` 标签 |
| 已合并 PR 上的一条评论："the next implementation issue … was not opened" | 该阶段的任务没有全部勾选 | 勾选或完成它们，然后针对该 spec 文件夹手动运行 Agent Issues |
| 一个保持打开的测试 issue，带有一份失败或受阻的报告 | 测试智能体发现已合并的变更在开发 stage 上不能正常工作，或者无法测试它 | 阅读报告。如果它打开了修复 PR 就合并它，或者修复 stage，或者写一个任务。重新加上 `openhands-test` 以再次测试 |

## 生产环境是第三个可选关卡

部署到开发 stage 可以在每次 `main` 变绿时自动进行。部署到生产环境则应该等待一个人，使用 GitHub
environment 上的必需审核者。参见[部署与安全](../../discava/deploy-and-security/)。
