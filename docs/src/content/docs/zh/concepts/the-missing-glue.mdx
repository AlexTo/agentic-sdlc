Speckit 以一个 `tasks.md` 结束。OpenHands 从一个带标签的 issue 开始，到一个 pull request 为止。CI
报告一个结果后就继续往下走。每个工具都把自己的工作做得很好，但没有一个会把工作交给下一个。没有粘合层，
交接就得*你*来做：你把任务复制进 issue，注意到 CI 变红了，再告诉智能体去修。

这些就是缺口，以及填补每处缺口的东西：

| # | 缺口 | 由什么填补 |
| --- | --- | --- |
| 1 | 没有东西把完成的 spec 变成智能体的工作 | 一个 workflow 读取 `tasks.md`，每次为一组阶段打开下一个实现 issue |
| 2 | 智能体不知道 CI 失败了 | 一个 workflow 以智能体本就在监视的 commit 状态，把失败的运行报告回智能体 |
| 3 | 评审者的 "changes requested" 无人理会 | 一个 workflow 对评审智能体的结论做同样的事 |
| 4 | 没有东西能阻止卡住的智能体无限循环 | 两个修复循环都限制为五次尝试，用标签计数，之后由人接手 |
| 5 | `tasks.md` 只是一种约定，所以格式错误的文件会让链条悄无声息地停滞 | 一个 PR 检查验证它的格式 |
| 6 | UI 变更在没有任何人看过的情况下进入评审 | 一个检查要求 e2e 截图，CI 把截图发布到 PR 上 |
| 7 | 合并智能体的 PR 不会启动下一个阶段 | 智能体分支的合并会打开下一个 issue，直到 spec 完成 |
| 8 | 没有云访问权限，智能体就无法运行真实的栈 | 为每个服务提供本地替身，让整个应用及其 e2e 测试在没有凭证的情况下运行 |
| 9 | 合并不会发布任何东西 | `main` 上的绿色构建会自动部署，跳过已经不是最新的 commit，生产环境则等待一个人 |
| 10 | 智能体可能提交泄露的密钥或有漏洞的依赖 | 每次构建都进行密钥和依赖扫描，每次部署前再扫描一次 |
| 11 | 没有人在已合并的变更实际运行的地方检查它 | 每次部署都会为它带上的每个已合并 PR 打开一个测试 issue，由测试智能体在已部署的 stage 上测试这个变更 |

[Discava 的做法](../../discava/overview/)把每一行对应到它的文件。

## 编写粘合层的规则

这些规则来自在 Discava 上构建和修复粘合层的过程。

### 在代码而不是 prompt 中做决定

每个"接下来发生什么"的决定都是一个带单元测试的纯函数：`gate.ts` 中的 `decide()` 决定哪些合并算数，
`planCi()` 决定是否把智能体送回去。workflow 文件只负责把事件连到脚本。你可以在没有 GitHub 的情况下
测试一个决定，而智能体也没法靠说辞绕过它。

### 把状态保存在 GitHub 上

没有数据库。尝试次数是一个标签（`ci-fix-2`）。一组阶段对应的 issue 通过其正文中的隐藏标记找到
（`<!-- agent-issue spec:<folder> group:2 -->`）。"已经送回过"是一个 commit 状态。任何人都能看到
状态，人也可以手动修改它，例如移除一个标签来允许再尝试一次。

### 说智能体已经懂的语言

OpenHands 本来就会修改 head 带有失败的 `software-factory/review` 状态的 PR。所以粘合层发布的是这个
状态，而不是发明一个新的触发器。不需要对 OpenHands 做任何修改。

### 用 token 运行可信代码

粘合 workflow 持有一个可以写标签、状态和评论的 token。它们检出的是**默认分支**，而从不是 pull
request，因此智能体或贡献者写的任何东西都不会带着这个 token 运行。从 PR 中读取的任何内容（分支名、
正文）在使用前都会对照严格的模式进行检查。

### 不让陌生人进入智能体阅读的内容

任何人都可以在公开仓库的 issue 和 pull request 上评论，而智能体在阅读这些评论时持有一个可以推送的
token。测试智能体还持有对已部署 stage 的访问权限。所以在公开仓库上，请把 GitHub 的**交互限制**设为仅限
协作者：其他任何人都不能评论、开 issue 或开 pull request。workflow 为智能体开的 issue 也会被**锁定**：
打开时不带标签，先锁定，然后才加上标签。而 issue 的隐藏标记只有在该 issue 由 workflow 或具有写权限的人
打开时才算数。

不过，不要锁定智能体的 pull request。GitHub 会拒绝在已锁定的 pull request 上提交评审，即使来自具有写
权限的账号也一样，于是评审智能体就无法发布评审。

### 保持幂等

GitHub 会多次投递同一个事件，人也会重新运行 job。每个脚本在行动前都会先检查：同一组不会有第二个
issue，同一个 commit 不会有第二次尝试，对于已经不是 head 的 commit 的运行不做反应。

### 大声失败，并且失败在人会看的地方

workflow 的 notice 没有人读。当链条停滞时，就在 pull request 上说出来："the next issue was not
opened because these tasks aren't ticked: T014, T015"。

本仓库中的粘合层大约是 3,300 行 TypeScript，外加同样多的单元测试，分布在
`packages/tooling/agent/src/` 的七个文件夹中。采用之前先读一读。花一个下午就够了。
</Aside>
