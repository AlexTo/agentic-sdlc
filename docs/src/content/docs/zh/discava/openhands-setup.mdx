Discava 的智能体运行在一台 Linux 工作站上，由 OpenHands Agent Canvas 承载。OpenHands 没有云端部署，也
没有 webhook。一切都是向 GitHub 发起的出站轮询。

## Agent Canvas

Agent Canvas 1.41.0，从 npm（`@openhands/agent-canvas`）安装，并作为用户服务运行。它的状态保存在
`~/.openhands/` 中：设置、agent profile、secret 以及自动化的 SQLite 数据库。

## 会话设置

决定智能体工作方式的设置：

| 设置 | 值 | 原因 |
| --- | --- | --- |
| Agent | ACP，服务器 `claude-code` | 通过 Agent Client Protocol 接入的外部编码智能体 |
| ACP prompt timeout | 30 分钟 | 一个实现轮次很长 |
| Max iterations | 500 | 足够在一个会话中完成整个阶段 |
| Confirmation mode | 关闭 | 无人值守。没有人在那里确认 |
| Security analyzer | LLM | 命令仍会经过风险筛查 |
| Runtime | local | 运行在宿主机上，Node、pnpm 和 git 都已在那里 |
| Worktree branch prefix | `openhands/` | 智能体创建的每个分支都以此开头。粘合层依据它来识别 |

## Agent profile

每个智能体角色一个 profile：

| Profile | 角色 | 智能体 | 模型 | 使用者 |
| --- | --- | --- | --- | --- |
| `developer` | 开发智能体 | Claude Code（ACP） | Sonnet | GitHub issue to PR |
| `reviewer` | 评审智能体 | Claude Code（ACP） | Opus | GitHub code review |
| `tester` | 测试智能体 | Claude Code（ACP） | Opus | GitHub issue tester |

每个 profile 的 prompt 超时都是 30 分钟。

## Secret

按名称存储在 Agent Canvas 中（**Settings → Secrets**）：

| 名称 | 用途 |
| --- | --- |
| `GITHUB_PERSONAL_ACCESS_TOKEN` | 自动化用它读取 GitHub。会话拿到它来克隆、推送、打开 PR、评审和评论 |
| `OPENHANDS_AUTOMATION_API_KEY` | 自动化后端自己的密钥 |
| `DISCAVA_STUDENT_USERNAME`、`DISCAVA_STUDENT_PASSWORD` | 测试智能体在 `discava-development` 上的学生用户 |
| `DISCAVA_INSTRUCTOR_USERNAME`、`DISCAVA_INSTRUCTOR_PASSWORD` | 测试智能体的讲师用户 |
| `DISCAVA_ADMIN_USERNAME`、`DISCAVA_ADMIN_PASSWORD` | 测试智能体的管理员用户 |

GitHub token 是 `discava-bot` 上的一个 classic personal access token。`discava-bot` 是只供自动化使用的
机器账号，是拥有写权限的协作者，token 具有 `repo` 和 `workflow` scope。

六个 `DISCAVA_*` secret 是开发 stage 上的 Cognito 测试用户，应用中的每个角色一个。测试智能体用它们登录
各个门户，并用它们获取 API token。

## 测试智能体在机器上拥有什么

开发智能体和评审智能体只需要 Node、pnpm、git 和 `gh`。测试智能体还会用到：

| 工具 | 用途 |
| --- | --- |
| AWS CLI，已登录持有 `discava-development-*` 栈的账号 | 找到 stage（栈输出）、获取 Cognito token、读取 DynamoDB、S3 和 CloudWatch 日志。它的 prompt 要求它以只读方式使用 |
| 带 Chromium 的 Playwright | 驱动已部署的门户 |
| Discava 检出目录中的 `tmp/screenshots/` | 保存它的截图的地方，每个 pull request 一个文件夹 |

<Aside type="caution">
这是 Discava 中唯一一处智能体带着云访问权限工作的地方。正因如此，stage 才是数据可随时丢弃的
`discava-development`，也才会[只有协作者能评论](../post-merge-verify/#谁可以评论)智能体阅读的内容。对于团队，请给
测试智能体一个它自己的只读角色，以及它自己的机器或虚拟机。
</Aside>

## 三个自动化

前两个是从 Agent Canvas 自动化目录中安装的，而不是手写的。第三个是 Discava 自己写的。每个自动化在一次
轮询中做什么，见[智能体运行时](../../concepts/the-agent-runtime/#三个自动化)，每个自动化交给其智能体的
prompt 见[智能体的 prompt](../agent-prompts/)。

### 开发智能体：GitHub issue to PR

| 字段 | 值 |
| --- | --- |
| Template | `github-issue-to-pr` 1.2.4 |
| Repository | `AlexTo/discava` |
| Trigger label | `openhands` |
| Branch prefix | `openhands/issue` → 分支 `openhands/issue-<n>` |
| Pull request mode | Ready for review |
| GitHub token secret | `GITHUB_PERSONAL_ACCESS_TOKEN` |
| Schedule | `*/2 * * * *`，Australia/Sydney |
| Agent profile | `developer` |

修改轮次会让智能体在之后重新加上 `openhands-review` 标签，以便新的 head 得到评审。

### 评审智能体：GitHub code review

| 字段 | 值 |
| --- | --- |
| Template | `github-pr-reviewer` 1.11.2 |
| Repository | `alexto/discava` |
| Trigger label | `openhands-review` |
| Requested reviewer | `all-hands-bot`（实际上未使用：由标签完成这项工作） |
| New reviews per scan | 2 |
| Review tone | Concise |
| Maintainers | 无 |
| Schedule | `*/2 * * * *`，Australia/Sydney |
| Agent profile | `reviewer` |

当检查仍在运行时，评审智能体会发布一条 "⏳ Review waiting on checks" 评论，并在之后的扫描中再次尝试。它的
评审以 "_This review was posted by an AI agent (OpenHands)._" 开头，并带有一个隐藏的
`<!-- openhands-review-run: <id> -->` 标记。

### 测试智能体：GitHub issue tester

目录中没有这一个的模板。它是一个大约一百行的 worker，建立在目录模板所用的同一套 GitHub 和会话辅助函数
之上，它的 prompt 放在旁边的一个文件里。

| 字段 | 值 |
| --- | --- |
| Template | 无：手写的 `worker.py`、`prompt.md` 和 `config.json` |
| Repository | `AlexTo/discava` |
| Trigger label | `openhands-test` |
| Issue authors | `github-actions[bot]` |
| Branch prefix | `openhands/test-fix` → 修复分支 `openhands/test-fix-<n>` |
| New tests per scan | 2 |
| Prompt file | `prompt.md` |
| GitHub token secret | `GITHUB_PERSONAL_ACCESS_TOKEN` |
| Schedule | `*/2 * * * *`，Australia/Sydney |
| Agent profile | `tester` |

每次轮询时，worker 会：

1. 列出带有 `openhands-test` 的打开 issue，编号最小的排在最前。
2. 跳过任何不是由 **issue authors** 之一打开的 issue。issue 的正文会成为智能体阅读内容的一部分，所以
   只测试 workflow 自己的 issue。
3. 找到最近一次加上该标签的事件。issue 编号加上该事件的 ID 构成一次投递，所以之后对同一次加标签的轮询
   会被忽略，测试智能体自己的评论也永远不会启动第二次测试。移除并重新加上标签是一个新事件，因此是一次
   新的测试。
4. 用 prompt 启动或恢复该 issue 的会话，每次轮询最多两个新测试。

它轮询的 issue 由 [Post-merge Verify](../post-merge-verify/) 打开。测试智能体的评论以
"_This comment was posted by an AI agent (OpenHands)._" 结尾。

<Aside title="智能体共用一个账号">
在 Discava 中，开发智能体、评审智能体和测试智能体都以 `discava-bot` 的身份发帖，维护者使用自己的账号。
因此维护者可以正常批准智能体的 PR，也能看出哪些评论来自智能体。评审智能体和开发智能体仍共用一个账号，而
GitHub 不允许一个账号批准自己的 PR，因此评审智能体的结论以 `COMMENTED` 评审的形式发布。粘合层读取的是
结论那一行，而不是评审状态，所以这没有影响。
</Aside>
