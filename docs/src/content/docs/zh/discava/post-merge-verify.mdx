缺口 11：合并之前的每项检查都是针对本地替身运行的，没有人在变更实际运行的地方看过它。Discava 用第三个
智能体角色来填补这个缺口。每次部署到 `discava-development` 之后，一个 workflow 会为这次部署带上的每个
pull request 打开一个测试 issue，由**测试智能体**在该 stage 上测试这个变更：在真实浏览器中打开门户，以
测试用户的身份调用 API，并检查变更写入的数据。

```d2
direction: down

deploy: "Deploy\n（discava-development）"
verify: "Post-merge Verify\npost-merge-test"
issue: "测试 issue\n先锁定，再加 openhands-test" {shape: page}
tester: "测试智能体\n（OpenHands，下一次轮询）"
stage: discava-development {shape: cylinder}
report: "issue 上的报告" {shape: document}
fix: "修复 PR\nopenhands/test-fix-<n>" {shape: page}

deploy -> verify: 已完成
verify -> issue: 每个已部署的 PR 一个
issue -> tester
tester -> stage: "Playwright、API、AWS CLI"
tester -> report
tester -> fix: "仅限小而明确的修复" {style.stroke-dash: 3}
```

## Post-merge Verify

`.github/workflows/post-merge-verify.yml` 在 `workflow_run` 上运行，即当 **Deploy** 完成时，也可以带着一个
pull request 编号手动运行。它检出默认分支，并运行 `post-merge-test`。所有运行共用一个并发组，所以两次
相隔很近的部署不会为同一个 pull request 打开两个 issue。

脚本（`src/post-merge-test/`）：

1. **检查这次运行是否部署了测试 stage。** 它读取 Deploy 运行的 job。`Deploy` 步骤被跳过的运行（它的
   commit 已不是 `main` 的最新提交）什么都没有部署，而针对其他 stage 的运行不会被测试。
2. **找出这次部署带上了什么。** 一次部署可能包含多次合并，因为被跳过的部署会把它的 commit 留给下一次。
   所以它取出该 stage 上一次成功部署与这一次之间的 commit，以及每个 commit 对应合并的 pull request。
3. **逐个 pull request 做决定**（`plan.ts` 中的 `decide()`）。以下情况不开 issue：
   - 已经有一个针对它的 issue（通过隐藏标记找到）
   - 它带有 `skip-deploy-test` 标签
   - 它没有改动任何会被部署的内容：只有文档、spec、测试、工具、CI 或其他永远不会进入栈的文件
4. **渲染 issue**（`renderIssue()`）。它只说明要测试什么。
5. **不带标签地打开它，锁定，然后加标签。** 这个 issue、它测试的 pull request，以及该 pull request 关闭的
   issue 都会被锁定。之后才加上 `openhands-test`。如果有任何一项无法锁定，标签永远不会被加上，运行会
   失败，并指出需要手动锁定什么。

带着一个 pull request 编号手动运行时，即使已经存在 issue，它也会再打开一个。这就是从头重新测试一个变更
的方式。

## 它打开的 issue

一个真实的例子，[#654](https://github.com/AlexTo/discava/issues/654)：

```markdown
<!-- post-merge-test pr:647 -->

## What to test

- Pull request: #647 (feat(stripe-checkout): a refund takes access away)
- Issue it closes: #646
- Merged as `b4dc4f7…`, deployed to `discava-development` at `b4dc4f7…` ([Deploy run](…))
- Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
  through the flow with Playwright, then call the APIs behind it and check the stored data.

<details><summary>Deployed files it changes (4)</summary>

- `packages/events/src/local/stripe-stand-in.ts`
- `packages/events/src/payments/events/charge-refunded.ts`
- `packages/events/src/payments/stripe-webhook.ts`
- `packages/websites/student-portal/src/routes/learn/$courseId/-components/enrolment-actions.tsx`

</details>
```

标题是 `test(post-merge): verify #647 a refund takes access away`：一个最多 100 个字符的 Conventional
Commit 标题行，这样测试智能体就可以复用它。当 pull request 改动了某个门户或共享组件时，类型是
`UI change`，否则是 `backend change or fix`。

<Aside type="note" title="测试什么，从不说怎么测">
这个 issue 不含任何指令。如何测试（工具、测试用户、检查、报告）是测试智能体自己在 OpenHands 中的
[prompt](../agent-prompts/#测试智能体)，所以能编辑 issue 的人没有一个能改动它。
`.github/ISSUE_TEMPLATE/test-deployed-pr.md` 是同样的表单，用于手动打开一个测试 issue。
</Aside>

## 测试智能体做什么

在下一次轮询时，`github-issue-tester` 自动化会接手这个 issue 并启动测试智能体。它的 prompt 有八个步骤：

1. 根据 pull request、它的 diff、它关闭的 issue 及其 spec，弄清改了什么，并写下现在应该成立的事情。
2. 如果有 UI，就测试 UI：用 Playwright 在 Cognito 托管页面上登录，点完整个流程，在每一步截图，并查看
   每一张截图。
3. 用测试用户的 access token 调用 API，包括错误情况。
4. 检查存储的数据：DynamoDB 条目、OpenSearch 文档、S3 对象，以及 Lambda 的日志。
5. 使用它自己的数据，命名为 `pmt-<pr>-<what>`。
6. 在 issue 上报告：它测试了什么、一张列出每项检查的通过或失败及其证据的表格，以及一个结论。
7. 通过时关闭 issue。失败时让它保持打开，并附上复现步骤。只有在原因清楚且修复很小时，才打开修复 pull
   request。
8. 绝不更改基础设施、IAM、用户或 stage 配置，绝不部署、触碰其他 stage、编辑 workflow 或合并。

### 第 1 次运行：受阻，并且如实说明

这个变更会在 Stripe 报告退款时结束学生的选课。要测试它，必须有一笔已支付的订单可供退款，而该 stage
没有支付账号。测试智能体没有让测试通过，也没有猜测。它的[结论](https://github.com/AlexTo/discava/issues/654#issuecomment-7033260676)是 "blocked, not verified"，并附上了证据：管理员 API 的
`payment.status` 返回 `not-connected`，核心表中没有任何订单。

然后它检查了不需要付款就能检查的东西：已部署的 webhook 函数含有新的 `charge.refunded` 处理函数，门户
提供的包中有新的 "You're no longer enrolled" 界面，伪造的退款通知会被以 400 拒绝并且不写入任何东西，
免费课程的课程页面仍然正常。九项检查通过。它列出了自己*没有*验证的六件事，以及怎样才能解除阻塞。

它还说明了自己不会做什么。连接支付账号意味着保存一个 Stripe 密钥，这会改变 stage 的配置，而它的
[prompt](../agent-prompts/#测试智能体) 禁止这样做。所以它让 issue 保持打开，留给人来处理。

页面又回到了显示 **Buy now** 的状态。屏幕上没有任何东西表明出了问题：没有错误，控制台里也没有失败的
请求。测试智能体之所以发现了它，是因为它还读取了订单的记录和函数的日志，日志说明了原因：

```text
REPORT … Duration: 10000.00 ms … Memory Size: 128 MB  Max Memory Used: 117 MB  Status: timeout
REPORT … Duration: 10000.00 ms … Memory Size: 128 MB  Max Memory Used: 117 MB  Status: timeout
```

Stripe 关于结账已付款的通知始终没能送达。接收它的函数运行在 Lambda 默认的 128 MB 上，它的冷启动（核心表
的实体、AppConfig、Stripe SDK）没能在 10 秒的超时之内完成。超时的运行时会被丢弃，所以 Stripe 的每次重试
都从冷启动开始，并以同样的方式失败。测试智能体把它与结账函数做了比较，后者有 256 MB，启动用了 8.1 秒。

被测试的退款根本没有走到。测试智能体发现的问题在它的前一步，而且更糟：在已部署的 stage 上，学生可能
付了课程的钱却永远拿不到它。

### 为什么之前没有任何东西发现它

这个缺陷比被测试的 pull request 更早，而且它通过了每一层：

- **单元测试**检验的是处理函数的逻辑，而逻辑是正确的。
- **E2E 测试**针对本地栈运行，在那里由一个替身扮演 Stripe，没有任何东西有内存限制或 10 秒的超时。
- **评审智能体**和**那个人**读到的 diff 中没有出现任何内存设置，因为缺少的那一行正是缺陷本身。

它只存在于函数被部署的地方。这就是测试智能体要填补的缺口。

### 修复 PR

原因清楚，修复也很小，所以测试智能体的 prompt 允许它开一个 pull request。
[#657](https://github.com/AlexTo/discava/pull/657) 是一个 [commit](https://github.com/AlexTo/discava/commit/854760c3c30a5ceb1ee7c7e52ebd596bef3374f1)，改动了
两个文件：`StripeWebhookApi` construct 中把函数内存设为 512 MB 的四行，以及一个没有这四行就会失败的十二行
测试（`Missing key 'MemorySize'`）。它从 `main` 分出，分支名为 `openhands/test-fix-654`，它的描述同时
引用了 [#647](https://github.com/AlexTo/discava/pull/647) 和
[#654](https://github.com/AlexTo/discava/issues/654)。

描述对自身的局限也直言不讳："Not verified on a deployed stage. The fix only takes effect once
deployed."（未在已部署的 stage 上验证。修复只有在部署之后才会生效。）

然后测试智能体就停下了。它没有合并，也没有部署。[PR Checks](https://github.com/AlexTo/discava/actions/runs/44722377986)
全部通过，`openhands-review` 标签把它交给了评审智能体。评审因为一件没有任何智能体做错的事停滞了四十
分钟：这个 pull request 被锁定了，而 GitHub 不接受对已锁定 pull request 的评审。解锁之后，评审智能体批准
了它。这就是 Discava 不再锁定 pull request 的原因（见[谁可以评论](#谁可以评论)）。和其他任何 PR
一样，由一个人来合并它。测试 issue [#654](https://github.com/AlexTo/discava/issues/654) 会保持打开，直到退款本身在一个付款能够结算的 stage 上得到测试。
测试智能体的最后一份报告列出了它留下的测试数据：那门课程和那笔 `pending` 订单。

截图留在工作站上，位于 Discava 检出目录的 `tmp/screenshots/pr-<pr>/` 下。报告会写明每个文件的名称，并
说明它展示了什么。上面的四张是为了本页从那里复制过来的。

## 谁可以评论

Discava 是一个公开仓库，所以任何人都可以在它的 issue 和 pull request 上评论。智能体在阅读这些评论时持有
一个可以推送的 token，测试智能体还持有 AWS 访问权限和测试用户的密码。因此，一条评论就是向智能体下达指令
的一种途径：即 prompt 注入。prompt 会要求每个智能体把它读到的内容当作数据，但 prompt 只是一个请求，而不是
保证。

所以 Discava 通过两种方式把陌生人挡在对话之外：

| 层 | 作用 |
| --- | --- |
| **交互限制** | GitHub 的 **Settings → Moderation options → Interaction limits** 设置为 **Limit to repository collaborators**。其他任何人都无法在仓库中的任何地方评论、打开 issue 或打开 pull request |
| **锁定的智能体 issue** | Agent Issues 和 Post-merge Verify 不带标签地打开每个 issue，锁定它（对于测试 issue，还会锁定它测试的 pull request 以及该 pull request 关闭的 issue），之后才加上标签。如果有任何一项无法锁定，标签永远不会被加上，运行会失败。共用的代码是 `src/helpers/conversation-lock.ts` |

随之而来的还有两条规则：

- **标记按作者决定是否可信。** 这些 workflow 通过隐藏标记找到它们之前的 issue。标记只有在由
  `github-actions[bot]` 或具有写权限的人打开的 issue 中才算数（`src/helpers/issue-author.ts`），所以
  陌生人无法通过打开一个带有标记的 issue 来让链条停滞或阻止一次测试。
- **测试智能体只测试 workflow 的 issue。** 它的自动化会跳过任何不是由 `github-actions[bot]` 打开的测试
  issue，它的指令是它自己的 prompt，而绝不是 issue。

<Aside type="caution" title="公开仓库需要交互限制">
如果你的仓库是公开的，请在启用测试智能体之前，最好是在启用任何智能体之前，把交互限制设为
**仅限协作者**。没有它，任何人都可以在测试 issue 或它测试的 pull request 上评论，而测试智能体会在持有
云凭证和测试用户密码的同时读到这条评论。

这个限制最长持续六个月。Discava 的限制到 2027 年 5 月 20 日为止。请把续期写进日历，因为它失效时没有任何
东西会提醒你。私有仓库不需要它：在那里只有拥有访问权限的人才能评论。

在设置限制之前、或在 issue 被加上标签之前写下的评论会保留。在手动给一个已有的 issue 加标签之前，请先阅读
这些评论。
</Aside>

### 为什么 Discava 不再锁定 pull request

在 [#658](https://github.com/AlexTo/discava/pull/658) 之前，一个名为 **Agent Lock** 的 workflow 还会锁定
智能体打开的每一个 pull request，以及任何被人手动加上智能体标签的 issue。它把陌生人挡在了外面，但有两个
代价：

- **评审智能体无法评审。** GitHub 拒绝对已锁定的 pull request 进行原生评审，即使来自具有写权限的账号也
  一样。修复 PR [#657](https://github.com/AlexTo/discava/pull/657) 在 10:49 被锁定，在 10:54 被加上评审
  标签，直到 11:34 被手动解锁之前都没有得到评审。五分钟后，评审智能体批准了它。
- **E2E 截图无法发布。** GitHub 同样拒绝 Actions token 在已锁定的对话上发表评论，所以
  [截图列表](../pr-checks/#ui-screenshots-与-e2e-screenshots-评论)不得不改为写入 job 摘要。

交互限制在整个仓库范围内完成同样的工作，而不需要锁定任何智能体必须写入的东西。Agent Lock 及其脚本已被
移除，它锁定过的四个智能体 pull request 也已被手动解锁。

## 试运行

```bash
DRY_RUN=true GITHUB_REPOSITORY=AlexTo/discava GITHUB_EVENT_NAME=workflow_dispatch PR_NUMBER=647 \
  pnpm nx run @discava/tooling-agent:post-merge-test
```

这会打印出它将要打开的 issue 的标题和正文，而不会创建任何东西。它仍然通过 `gh` 读取 pull request，所以
你需要处于已登录状态。

下一步：[一个真实的功能](../a-real-feature/)。
