[工作原理](../how-it-works/)描述了这个循环。本页展示它在 [Discava](https://github.com/AlexTo/discava) 的一个真实 pull request 上完整跑一遍的过程：学生为已购买的课程申请退款后看到的内容。

每段引文、每个数字和链接都来自 GitHub。时间均为悉尼时间（AEDT，UTC+11），日期是 2026 年 11 月 25 日和 26 日。

从 pull request 打开到合并：四轮修复，三轮来自 CI，一轮来自评审，人只动了一次手。之后测试智能体发现了两个问题，前面这些环节都不可能看到。

## 1. Issue

学生申请退款后，在 Stripe 处理期间会看到 "Refund requested"，课程页面每 2 秒检查一次退款是否完成。[#1166](https://github.com/AlexTo/discava/issues/1166) 说明了这里的问题：

> While a student's refund is pending, the course page refetches `course.myEnrolment` and
> `payment.myOrder` every 2 s, and never stops. If the refund fails at Stripe or its event never
> arrives, the order stays `paid` with a refund requested, the page keeps polling for as long as
> it is open, and the student isn't told anything has gone wrong.

它的验收标准只有两行：轮询在达到上限后停止；在 Stripe 替身中模拟的退款失败会结束待处理状态，并给出清楚的提示。

这个 issue 不是来自 spec。评审智能体在评审那个让学生能申请退款的 PR 时提出了它，作为超出该 PR 范围的问题，于是它成了一个单独的 issue。（#1166 是一个副本：智能体以前用的机器账号被 GitHub 标记，它打开过的所有内容都被隐藏了，那些还开着的 issue 由智能体现在使用的 GitHub App [重新打开](../../discava/openhands-setup/#github-app)。）

## 2. 开发智能体打开 PR

开发智能体领取了这个 issue，在 `openhands/issue-1166` 上打开了 [#1195](https://github.com/AlexTo/discava/pull/1195)。这次改动涉及四个包：课程页面上的 2 分钟上限和 "Check again" 按钮，处理 Stripe 退款失败事件的 webhook handler，订单上的 `refundFailedAt` 字段以及一条"失败必须发生在申请之后"的不变量，还有课程页面上的 "Your refund failed"。描述的结尾写明了它运行了什么、没运行什么：

> Unit tests cover the helper, the webhook, the invariant and the UI (poll limit, check again,
> failure message). [...] I did not run the e2e tests or try the stand-in control in a browser.

## 3. CI 把它退回，三次

**`ci-fix-1`：没有截图，还有没测试的代码行。** 这个 PR 改变了学生看到的内容，却没有截图，所以 [**UI Screenshots** 失败了](https://github.com/AlexTo/discava/actions/runs/45619342535/job/139224403383)。**codecov/patch** 也失败了：新的代码行没有测试。**Agent CI Status** 加上了 `ci-fix-1`，把开发智能体送了回去。它的[回复](https://github.com/AlexTo/discava/pull/1195#issuecomment-7164484931)显示，它在修复途中发现了自己第一次尝试中的一个问题：

> **UI Screenshots:** added a `learner-refund` e2e scenario for a failed refund, with
> `screenshot(student, 'refund-failed')`. For this the Stripe stand-in has a new
> `fail-next-refund` control. [...] This replaces the `refund-fail` control from the first push,
> which the scenario could not use, because the stand-in completed the refund before it could
> fail.

**`ci-fix-2`：不是它造成的失败。** 下一次运行在 **Checks (build)** 中失败，失败的是基础设施包里的一个 CDK synth 测试。智能体读了日志，[没有为此改任何代码](https://github.com/AlexTo/discava/pull/1195#issuecomment-7165688653)：

> the one failure was `@discava/infra` `instructor-api-stack.test.ts` [...], which hit its 30s
> timeout while the sibling CDK synth tests in that file took 22–31s. This PR doesn't touch infra
> or anything the stack synthesises [...], so I made no code change for it. The push below
> re-runs the build.

它补上了 codecov 仍然报告的那一行部分覆盖，这次推送重新运行了构建，结果通过。一个靠修改自己不理解的代码来"修复"失败的智能体，比一个说明失败不是自己造成的、并解释原因的智能体更糟。

**`ci-fix-3`：它自己的新测试写错了。** 评审之后（见下一节），智能体为 2 分钟上限添加了一个 e2e 场景，结果在 [**E2E tests (11/12)**](https://github.com/AlexTo/discava/actions/runs/45685812586/job/139458011986) 中失败。五分钟后，它给出了[原因](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172674824)：

> the new `a pending refund stops polling and offers to check again` scenario failed with a
> Playwright strict-mode violation, not a product bug. `getByText('Still being processed')` also
> matched the alert's description ("Your refund is still being processed…"), so it resolved to two
> elements. The page did reach the timed-out state. I now match the title with `{ exact: true }`.

智能体没有在本地运行任何 e2e 场景；每次它都这样说明。PR CI 是这些场景第一次运行的地方，[E2E screenshots 评论](https://github.com/AlexTo/discava/pull/1195#issuecomment-7163204279)列出了这次运行截取的两个界面：`learner-refund/01-refund-failed.png` 和 `learner-refund/01-refund-still-being-processed.png`。

## 4. 评审智能体发现 CI 发现不了的问题

head 上的所有检查都结束后，评审智能体对照 issue 阅读了 diff。它认为支付相关的代码是对的，自己重新运行了 361 个相关测试，但仍然[阻止了合并](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6063632214)：

> 1. **The branch carries another open PR's change.** Commit `e7cb9bc9`, "fix(student-portal):
>    surface completions and progress load errors on start route", is the change from open PR
>    #1188, not part of #1166. [...] Merging this PR would ship #1188's start-route error behaviour
>    under a payments title, before #1188 is reviewed.
> 2. **Live evidence is missing for the "Still being processed" / "Check again" state.** [...] The
>    new timed-out state [...] has only unit tests, and no capture from the running app.
>
> 🔄 CHANGES REQUESTED

第一点正是那种能通过所有检查的问题。多出来的 commit 能编译，它的测试也通过了；只是它不属于这里。智能体的 checkout 是从一个已经带有这个 commit 的分支开始的。第二点还是截图规则，这次由一个读者来执行：CI 检查 PR 是否添加了截图，评审智能体则检查每个新状态是否都有截图。

**Agent Review Status** 加上了 `review-fix-1`。八分钟后，开发智能体[已经](https://github.com/AlexTo/discava/pull/1195#issuecomment-7172386579)把自己的四个 commit rebase 到 `main` 上，去掉了另外两个，并在替身中添加了一个让退款保持待处理状态的控制项，以及一个安装 Playwright 假时钟、快进 125 秒的 e2e 场景。后来 `ci-fix-3` 修正的就是这个场景。

在最终的 head 上，评审智能体[确认](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066801083)两点都已解决，全部 12 个 e2e 分片都已通过，并点名了那两张截图："No material findings [...] ✅ APPROVED"。

## 5. 一个人批准

11:33，维护者[批准](https://github.com/AlexTo/discava/pull/1195#pullrequestreview-6066944326)并合并。这是人在这个 PR 上做的唯一一件事。摆在他们面前的是：一份写明运行了什么、没运行什么的描述，CI 发布的两张截图，一列全绿的检查，以及四次修订的记录，每次都附有原因。

## 6. 合并的内容被部署，测试 issue 打开

在 Discava，`main` 会自动部署到开发 stage。包含这次合并的[部署](https://github.com/AlexTo/discava/actions/runs/45734764281)在 12:28 完成，一分钟后 **Post-merge Verify** 打开了 [#1240](https://github.com/AlexTo/discava/issues/1240)。它列出了这个 PR 改动的 12 个已部署文件，并说明要做哪种测试：

> Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
> through the flow with Playwright, then call the APIs behind it and check the stored data.

## 7. 测试智能体测试已部署的 stage

测试智能体不会重跑测试套件，也不使用 Stripe 替身。它像人一样使用已部署的产品，用的是 sandbox 模式下的真实 Stripe。它的[报告](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815)列出了每一步：

1. 以测试讲师的身份，通过 API，它创建了两门价格为 $19.99 的课程。
2. 以测试学生的身份，在真实浏览器中，它登录并在 Stripe Checkout 上分别购买了这两门课，使用的是 Stripe 用于"退款失败"和"退款待处理"的测试卡。
3. 它在课程页面上为每门课申请了退款。
4. 每一步之后，它都调用 API，读取 DynamoDB 中的订单和选课记录，并读取 webhook 和 API Lambda 的日志。

在这个 stage 上，真实 Stripe 无法让退款保持待处理状态，也无法记录一次失败的退款。所以，为了检查已部署 bundle 中的新界面，测试智能体在浏览器中改写了 `payment.myOrder` 的响应，然后另外检查了真实的 API 响应和存储的数据。它给上限计了时：待处理的退款显示后 **120.2 s**，出现了 "Still being processed"，之后 20 秒内没有任何请求（`13-still-being-processed-after-2-minutes.png`）：

## 8. 测试智能体让 issue 保持打开

三项检查失败，其中两项停在了 PR 没有预料到的状态。[结论](https://github.com/AlexTo/discava/issues/1240#issuecomment-7180418815)：

> **Verdict: the student-facing UI and `payment.myOrder` work as the PR describes. The
> failed-refund path does not work end to end on the deployed stage.**

它找到了两个原因，都在 PR 的测试能覆盖的范围之外：

1. **stage 的 Stripe webhook 从来收不到新事件。** PR 把 `refund.failed` 和 `charge.refund.updated` 加进了事件列表，但这个列表只在管理员第一次连接 Stripe 时才会发送给 Stripe。这个 stage 六天前就已经连接好了。测试智能体数了一下，那半小时内 webhook 恰好被调用了四次，没有一次是因为失败。
2. **在真实 Stripe 中，失败的退款到达时，订单已经是 `refunded`。** 退款一创建，Stripe 就会发送 `charge.refunded`，即使这笔退款还在待处理或者将会失败。等到 `refund.failed` 到达时，新 handler 的条件（订单仍是 `paid`）已经不成立了，于是它悄无声息地什么也不做：

   > The student has lost access, hasn't been refunded, and isn't told.

   PR 的 e2e 场景中的替身从不在让退款失败之前先把它结清，所以 CI 展示的是这件事一切顺利的版本。

修复小而明确时，测试智能体可以打开修复 PR。它解释了为什么这次没有这样做：

> Fixing it means deciding how a refund failure after `charge.refunded` should restore the order
> and enrolment, or not treating a `pending` refund as refunded. That goes beyond a small fix, so
> I'm reporting it rather than opening a PR.

它也没有动 stage 的 Stripe 连接，虽然重新保存一次就能修好第一个原因："I didn't do that, because it changes stage configuration." 所以这个 issue 保持打开，两个问题、复现方法以及需要人来做的选择都写得清清楚楚。它列出了自己留在 stage 上的测试数据，以及它看到的一个已在别处跟踪的错误，以免有人把它误认为回归。

[合并后验证](../../discava/post-merge-verify/)跟随的是另一个测试 issue：测试智能体在那里发现了一次失败，追查到了原因，并且确实打开了修复 PR。
</Aside>

## 每道关卡拦住了什么

| 关卡 | 它拦住了什么 | 为什么前一道关卡没拦住 |
| --- | --- | --- |
| CI | 一个没有截图的 UI 变更、没有测试的代码行，以及智能体自己的 e2e 测试中一个有问题的 locator | 开发智能体没有运行 e2e 套件 |
| 评审智能体 | 分支上夹带的另一个 PR 的 commit，以及一个没有截图的新界面状态 | 多出来的 commit 通过了所有检查，而 CI 只检查是否添加了某张截图 |
| 测试智能体 | 一个从来收不到新事件的 webhook endpoint，以及真实 Stripe 先把一次正在失败的退款报告为已退款 | 替身的行为正如代码所预期，而且没有测试能看到 stage 的配置 |

这三者单独来看都算不上聪明。每一个都在看其他两个看不到的东西：CI 看规则，评审智能体看 issue 和分支，测试智能体看运行中的产品及其背后的真实服务。

## 人做了什么

1. 阅读了 PR #1195 及其截图，批准并合并。
2. 下一步：从测试智能体写出的选项中，决定 `charge.refunded` 之后的退款失败应该怎么处理。

没有人写 prompt、粘贴错误日志，或者手动在 stage 上点一遍。
