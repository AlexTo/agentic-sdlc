[工作原理](../how-it-works/)描述了这个循环。本页展示它在 [Discava](https://github.com/AlexTo/discava) 的一个真实 pull request 上完整跑一遍的过程：学生查看自己上传的作业的成绩和反馈的页面。

每段引文、每个数字和链接都来自 GitHub。时间均为悉尼时间（AEDT，UTC+11），日期都是 2026 年 11 月 21 日。

从 pull request 打开到合并：54 分钟，两次修复，人只动了两次手。

## 1. 一个人合并 spec

这个功能是给上传类作业评分：讲师把学生的作业连同分数和反馈一起返回，或者要求重新提交，学生则能看到结果。

spec PR [#662](https://github.com/AlexTo/discava/pull/662) 只包含 spec 文件夹：spec、计划、一份数据模型、三份契约和 `tasks.md`，共 **8 个阶段、34 个任务**。没有产品代码。它的描述列出了智能体在编写 spec 时提出的五个问题，以及维护者的回答。其中一个：已经返回的成绩还能改吗？能，但要保留历史，并通知学生。

维护者读完之后，加上 `spec-ready`，在 06:40 合并。这是两道人工关卡中的第一道。两分钟后，自动化为阶段 1 到 3 打开了 issue。

## 2. 开发智能体接手阶段 4

阶段 1 到 3（数据、规则和讲师的 API）以 [#667](https://github.com/AlexTo/discava/pull/667) 提交，在 08:42 合并。08:43，**Agent Issues** workflow 再次读取 `tasks.md`，为下一个还有未勾选任务的阶段打开了 [#681](https://github.com/AlexTo/discava/issues/681)：

> Tasks `T016` to `T017` of `tasks.md`: every task under Phase 4: User Story 2 - Student sees the
> grade and feedback (student portal) (P1). Do not start tasks outside these phases.

两个任务：一个组件，显示一轮反馈和一个折叠起来的早先各轮反馈列表；以及作业页面针对提交可能处于的每种状态所做的改动。

开发智能体在下一次轮询时领取了这个 issue。issue 打开七分钟后，它在 `openhands/issue-681` 上提交了 [#683](https://github.com/AlexTo/discava/pull/683)：先写测试，两个任务都在 `tasks.md` 中勾选，描述里写明了它运行了什么、没运行什么。

## 3. CI 把它退回

描述里还有这样一句：

> No e2e screenshots here: the e2e scenario for this flow is a later phase's task.

这是智能体自己做的判断，对任务列表来说也算一种合理的理解。但仓库有一条规则：改动了用户所见内容的变更，必须附带相应的截图，这样评审的人不用运行应用就能看到界面。这条规则是一项检查，而检查不听理由。lint、单元测试、构建和全部六个 e2e 分片都通过了。[**UI Screenshots** 失败了](https://github.com/AlexTo/discava/actions/runs/44823849814/job/136591295471)。

**Agent CI Status** 加上了 `ci-fix-1`，把开发智能体送回同一个 PR。它带着修复给出的[回复](https://github.com/AlexTo/discava/pull/683#issuecomment-7051758312)：

> The only finding was the failing `UI Screenshots` check (the PR added no `screenshot(` call). I
> added an e2e scenario in `assignment.e2e.ts` where a student sees the resubmission request
> beside the open form, then the returned grade and feedback. It takes a screenshot of each and
> drives the instructor side through the API. I did not run it locally, so PR CI is its first run.

下一次运行全绿，CI 把两张新截图发布在 [**E2E screenshots** 评论](https://github.com/AlexTo/discava/pull/683#issuecomment-7051642662)中。

## 4. 评审智能体发现一个真正的缺陷

所有检查都结束后，评审智能体对照 spec 阅读了 diff。一切都是绿的，代码却仍然是错的。摘自它的[评审](https://github.com/AlexTo/discava/pull/683#pullrequestreview-6000171162)：

> **Blocking: after a resubmission, the resubmission request's feedback disappears for the
> student.** The component always takes the newest round out of the "Earlier feedback" list. It
> only displays that round when the status is `resubmission_requested` or `returned`. Once the
> student uploads again, the status goes back to `submitted`, and the request round is hidden.
> This breaks FR-009, SC-007 and User Story 2's independent test [...] The new e2e step never
> checks the page in `submitted` after the resubmit, and no unit test covers `submitted` with a
> non-empty `feedback`, so nothing catches it.
>
> 🔄 CHANGES REQUESTED

说得直白些：讲师写下 "please cite your sources"，学生上传了新的一稿，讲师的这条批注就从学生的页面上消失了。spec 规定早先的反馈必须保持可见（FR-009）。没有测试失败，因为没有测试检查过那个状态。评审智能体是通过对照代码和 spec 发现它的，还点明了缺少哪些测试。

**Agent Review Status** 加上了 `review-fix-1`。三分钟后，开发智能体推送了[修复](https://github.com/AlexTo/discava/pull/683/commits/0bdf55d485d5a5df692d1e8a41ec601499977c03)，并[说明了它做了什么](https://github.com/AlexTo/discava/pull/683#issuecomment-7052122523)：

> Fixed the blocking finding. The newest round is now shown in full only when the status is
> `returned` or `resubmission_requested`. In any other state every round goes under "Earlier
> feedback", so the request stays reachable after a resubmit. I added a unit test for `submitted`
> with a `resubmission_requested` round, and an e2e assertion right after the resubmit.

评审智能体阅读了新的 head，自己运行了组件测试（42 个通过），并以 "No material findings remain. ✅ APPROVED" [结尾](https://github.com/AlexTo/discava/pull/683#pullrequestreview-6000351532)。

## 5. 一个人批准

09:44，维护者[批准](https://github.com/AlexTo/discava/pull/683#pullrequestreview-6000379398)并合并。这是第二道人工关卡。摆在他们面前的是：一份列出运行了什么、没运行什么的描述，CI 发布的两张截图，一列全绿的检查，以及一条显示发现并修复了一个缺陷的评审记录。这个 PR 有三个 commit、508 行，分布在六个文件中，其中四分之三是测试。

## 6. 合并的内容被部署，测试 issue 打开

在 Discava，`main` 会自动部署到开发 stage。这次[部署](https://github.com/AlexTo/discava/actions/runs/44833259729)在 10:09 完成。一分钟后，**Post-merge Verify** 打开了 [#712](https://github.com/AlexTo/discava/issues/712)，`test(post-merge): verify #683 student sees the grade and feedback (student portal)`。这个 issue 只说明要测试什么：

> Kind: **UI change**. It changes a portal: sign in as the user the change is for and click
> through the flow with Playwright, then call the APIs behind it and check the stored data.

## 7. 测试智能体测试已部署的 stage

测试智能体不会重跑测试套件。它像人一样使用已部署的产品，然后检查存储了什么。它的[报告](https://github.com/AlexTo/discava/issues/712#issuecomment-7054937096)列出了每一步：

1. 以测试讲师的身份，通过 API，它创建并发布了一门课程，其中有一个上传类作业 `pmt-683-essay`，满分 10 分。
2. 以测试学生的身份，在真实浏览器中，它选了课，在托管登录页面上登录，并上传了第一稿。
3. 讲师要求重新提交。学生刷新页面，看到了这个要求，并上传了第二稿。
4. 讲师返回了作业并给出 7 分，随后把成绩改为 8.5 分。每次之后学生都刷新了页面。
5. 每一步之后，它都调用学生的 API，读取 DynamoDB 中的记录和 S3 中的文件，尝试那些应当被拒绝的调用，最后扫描了该 stage 上全部 46 个 Lambda 函数的日志，查找错误。

## 8. 测试智能体关闭 issue

32 项检查全部通过，所以报告以一个结论结尾，测试智能体关闭了 issue：

> **PASS.** The student portal shows the grade and feedback as #681 asks

它还列出了它看到的两件与这个 PR 无关的事，以免有人把它们误认为回归。

### 测试智能体不关闭的时候

通过并不是唯一的结果。这之前的那个 pull request [#667](https://github.com/AlexTo/discava/pull/667) 添加了评分 API，它的测试 issue [#694](https://github.com/AlexTo/discava/issues/694) 在第一次运行之后保持打开。二十九项检查通过，一项失败：

> **Verdict: the new grading flow works end to end for submissions made after this deploy. It
> does not work for submissions stored before it.** Those have no `reviewRevision` attribute, so
> an instructor can't open or grade them.

单元测试、e2e 测试和评审都不可能发现这个问题。它们都从一个空数据库开始，而这个缺陷只存在于有旧数据的地方。该 stage 上有三份提交受到影响。

修复小而明确时，测试智能体可以打开修复 PR。这一次它[解释](https://github.com/AlexTo/discava/issues/694#issuecomment-7052102048)了为什么没有这样做：

> That is a choice between a migration and tolerant reads, and it changes concurrency conditions
> in two packages, so I haven't opened a fix PR.

所以它停了下来，把两个选项都写清楚，把决定留给人。维护者在该 stage 上回填了这三条记录。测试智能体[重新运行了它的检查](https://github.com/AlexTo/discava/issues/694#issuecomment-7054905761)，确认旧的提交现在有了这个字段，然后关闭了 issue，并提醒：其他任何存有旧提交的环境都需要做同样的回填。同一份报告中的一条次要备注（一条在什么都没有返回时却说 "returned" 的拒绝消息）变成了一个 13 行的修复，[#708](https://github.com/AlexTo/discava/pull/708)。

<Aside type="tip">
[合并后验证](../../discava/post-merge-verify/)跟随的是另一个测试 issue：测试智能体在那里发现了一次失败，追查到了原因，并且确实打开了修复 PR。
</Aside>

## 每道关卡拦住了什么

| 关卡 | 它拦住了什么 | 为什么前一道关卡没拦住 |
| --- | --- | --- |
| CI | 一个没有截图的 UI 变更 | 开发智能体认定截图属于后面的阶段 |
| 评审智能体 | 重新提交之后反馈消失 | 没有测试覆盖那个状态，所以 CI 是绿的 |
| 测试智能体（在 #667 上） | 新代码读不了的旧记录 | 测试和评审从来看不到 stage 上已有的数据 |

这三者单独来看都算不上聪明。每一个都在看其他两个看不到的东西：CI 看规则，评审智能体看 spec，测试智能体看运行中的产品。

## 人做了什么

1. 在编写 spec 时回答了五个问题，然后评审并合并了 spec PR。
2. 阅读了 PR #683 及其截图，批准并合并。

没有人写 prompt、粘贴错误日志，或者手动在 stage 上点一遍。
