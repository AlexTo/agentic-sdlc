## 链条没有启动或没有继续

| 症状 | 发生了什么 | 怎么做 |
| --- | --- | --- |
| Spec PR 已合并，但没有 issue | 合并时 PR 没有 `spec-ready` 标签 | 给已合并的 PR 加上 `spec-ready`。Agent Issues 也会在 `labeled` 时运行 |
| Agent Issues 运行了：`No issue created: it is not an agent branch and has no "spec-ready" label` | 同上，或者这个 PR 是人工 PR，按设计会被忽略 | 同上，或用该 spec 文件夹手动运行 Agent Issues |
| Agent Issues 失败：`tasks.md is not in the format the workflow reads` | spec PR 上的格式检查被跳过或被忽视了 | 在一个 PR 中修复 `tasks.md`，然后手动运行 Agent Issues |
| 一条评论：“the next implementation issue … was not opened: an issue for … already exists” | 该阶段的 issue 已存在，但其中有些智能体任务没有勾选 | 如果已完成就勾选，否则把它们做完。然后手动运行 Agent Issues |
| Agent Issues 记录了 `no spec folder with a tasks.md was found` | 已合并的智能体 PR 对应的 issue 没有标记，且该 PR 没有改动 `specs/` 下的文件 | 用该 spec 文件夹手动运行 Agent Issues |
| 最后一个阶段合并后什么也没开 | 正确。剩下的只有 **(human)** 任务，或者没有任务了 | 完成 |

## 智能体没有接手或没有修订

| 症状 | 发生了什么 | 怎么做 |
| --- | --- | --- |
| 已加标签的 issue 一直没被接手 | Agent Canvas 宕机、automation 被禁用，或 token 无法读取仓库 | 检查 `agent-canvas` 是否在运行、automation 是否已启用。查看 automation 最近一次运行的日志 |
| PR 是红的，已加 `ci-fix-1`，智能体却从不修订 | worker 只修订名称恰好为 `openhands/issue-<n>` 的分支（修复 workflow 也会给其他 `openhands/` 分支加标签），或者 issue 已关闭 | 检查分支名。重新打开 issue，或者接手这个 PR |
| 红色运行后没有 `ci-fix-*` 标签 | Agent CI Status 没有运行，或忽略了这次运行（见其 notice） | 打开 Agent CI Status 的运行并阅读 notice，例如 `the pull request has a newer commit than this run` |
| 智能体修订后，没有任何东西评审新的 head | 智能体没有重新加上 `openhands-review` | 手动重新加上 |
| push 被拒绝：`refusing to allow a GitHub App to create or update workflow` | app 缺少 **Workflows** 写权限，而分支改动了 `.github/workflows/`（常常是因为合并了 `main`） | 在 app 的设置中授予该权限，并在安装上接受新权限。下一次轮询会重试。使用 personal access token 时，消息中写的是 token，token 需要 `workflow` scope |
| 所有自动化都失败：`The GitHub credential GITHUB_PERSONAL_ACCESS_TOKEN is unavailable`，或 `401 Bad credentials` | secret 不存在，或者存的是超过一小时的 app token | 检查 `scripts/agent-app-token.sh` 是否仍每 45 分钟运行一次，以及它最近一次运行是否更新了 secret |
| `ci-fix-exhausted` | 五次修复都没能收敛 | 阅读最后一次失败。通常是 spec 或计划有歧义。修正它，移除标签，重新运行 |

## 评审

| 症状 | 发生了什么 | 怎么做 |
| --- | --- | --- |
| “⏳ Review waiting on checks”，但没有评审 | head 上有检查尚未完成，或一直卡在排队中 | 找到挂起的检查。一个永远不会运行的必需检查会永远阻塞评审 |
| 评审写着 `🔄 CHANGES REQUESTED`，却没有 `review-fix-*` 标签 | 评审缺少运行标记、既不是来自有写权限的账号也不是来自 `AGENT_APP_LOGIN` 指定的 app，或者 PR 已经有了新进展 | 阅读 Agent Review Status 的 notice。如果它说评审不是来自维护者或智能体的 app，就把仓库变量 `AGENT_APP_LOGIN` 设为 app 的 bot 登录名 |
| 每次代码评审扫描都以 `HTTP Error 403: Forbidden` 失败 | `github-pr-reviewer` 模板通过 `GET /user` 查询自己是谁，而 GitHub 在这里拒绝 app 的 installation token（`Resource not accessible by integration`） | 给 bundle 打补丁：在 worker 从 `GET /user` 读取登录名的地方（`worker.py` 中的 `github_login`，`main.py` 中的 token 检查），遇到 403 时改用 GraphQL `{ viewer { login } }`，它会返回 `<app-name>[bot]`。用 automation API 上传打好补丁的 bundle（`POST /api/automation/v1/uploads`，然后带上它的 `tarball_path` 调用 `PATCH /api/automation/v1/<id>`） |
| 评审显示为 “Commented” 而不是 “Approved” | 评审智能体用的是开启该 PR 的同一个身份，而 GitHub 不允许自己批准自己 | 这是预期行为：开发智能体和评审智能体共用智能体的 GitHub App。粘合层读取的是结论那一行，而不是评审状态 |

## 检查

| 症状 | 发生了什么 | 怎么做 |
| --- | --- | --- |
| `UI Screenshots` 在重构时失败 | 该规则无法区分可见的改动和不可见的改动 | 维护者加上 `no-ui-screenshots` 并重新运行该检查 |
| 每个 PR 的 e2e job 都要下载 Chromium | 缓存只在 `main` 上保存 | 保留 CI 的 `playwright-cache` job，并使用与 PR Checks 相同的 key |
| `Check for mutations` 在 `main` 上失败 | 有东西生成了 PR 没有提交的文件 | 在本地运行 `pnpm build` 并提交差异 |
| 加标签时出现 `Resource not accessible by integration` | workflow token 能写 issue，但不能写 pull request | 给该 workflow 加上 `pull-requests: write` |

## 合并后测试

| 症状 | 发生了什么 | 怎么做 |
| --- | --- | --- |
| 一个 PR 已部署，却没有测试 issue | 它没有改动任何会被部署的内容（只有文档、spec、测试、工具或 CI），它带有 `skip-deploy-test`，或者 Deploy 运行因为其 commit 已不是 `main` 的最新 commit 而什么都没发布 | 阅读 Post-merge Verify 运行的 notice。如果仍想测试它，用该 PR 编号手动运行这个 workflow |
| 测试 issue 已开出，测试智能体却始终不领取 | 该 issue 没有 `openhands-test` 标签，因为它指向的某个对象无法锁定；或者它是由 automation 不信任的账号开出的 | Post-merge Verify 运行会失败，并指出需要锁定什么。锁定它，然后手动加上标签 |
| 测试智能体已报告，而你想再跑一次 | 每次加标签只测试一次 | 移除并重新加上 `openhands-test` |
| 报告写着 “blocked” | stage 缺少该变更所需的某样东西，例如一个已连接的支付账号 | 修复 stage，然后重新加上标签 |
| PR 上没有 **E2E screenshots** 评论 | 该 PR 已锁定，而 GitHub 拒绝 Actions token 在已锁定的对话上评论 | 阅读 `E2E screenshots` job 摘要中的列表，或者解锁该 PR |
| 评审智能体始终不发布评审，而该 PR 已锁定 | GitHub 拒绝在已锁定的 pull request 上提交原生评审，即使来自具有写权限的账号也一样 | 解锁它。要把陌生人挡在外面，请使用仓库的交互限制，而不是锁定 pull request |

## 部署

| 症状 | 发生了什么 | 怎么做 |
| --- | --- | --- |
| 部署因为某个此前没有任何 stack 创建过的资源而以 `is not authorized to perform` 回滚 | 某个 stack 开始使用一种 CloudFormation 执行角色的策略没有覆盖的资源 | 把这些操作加进 `setup-stage.sh` 并重新运行它。它是幂等的，并会发布策略的一个新版本 |
