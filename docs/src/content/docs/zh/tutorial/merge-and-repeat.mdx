**当前位置：** 🧑 人工关卡 #2。**产出：** 第 1 阶段已合并，第 2 阶段的 issue 已开启。

PR 到你手上时已经是全绿的，并已获得评审智能体的批准。你的工作是判断结果，而不是去找问题。

<Steps>

1. 阅读 PR 描述和 **E2E screenshots** 评论。对于网站阶段，这就是你不用拉取分支也能看到功能的方式：空的标签输入框、一条带三个标签的笔记、应用了筛选的列表、添加第六个标签时显示的错误。

2. 查看智能体列出的 **(human)** 任务，并完成它们。

3. 批准并合并。如果智能体用你自己的 token 推送，GitHub 会把你视为 PR 的作者，不接受你的批准，所以像处理 spec PR 时那样绕过它。

   如果要改为要求修改，就评审这个 PR 并加上 `openhands-review` 标签。评审智能体的结论随后会把负责实现的智能体打回去，同样受五次尝试的上限约束。

</Steps>

## 合并会做什么

**Agent Issues** workflow 看到 `openhands/` 分支上一个已合并的 PR，并读取合并后状态下的 `tasks.md`：

1. **这个阶段的智能体任务都勾选了吗？** 智能体在 PR 中勾选每个任务，就在完成它的那个 commit 中。**(human)** 任务不计入：你已经在第 2 步完成了它们，它们永远不会阻挡链条。
2. **是**：它为下一个阶段开 issue。第 2 阶段（网站）现在会和第 1 阶段完全一样地运行：测试先行、PR、关卡、修复、评审。
3. **否**：什么都不会开，已合并的 PR 会收到一条列出未勾选任务 ID 的评论。勾选或完成它们，然后用 spec 文件夹名手动运行 **Agent Issues**。

只有智能体自己的分支才会推进链条。你自己的 PR 会被忽略。

```text
spec PR merged ─► issue 1 ─► PR 1 merged ─► issue 2 ─► PR 2 merged ─► issue 3 ─► PR 3 merged ─► done
   (you)                       (you)                      (you)                      (you)
```
