**当前位置：** 🤖 智能体，然后再次是 🧑 人工关卡 #2。**产出：** 文档介绍了标签功能。

文档也是代码（这个站点就是 `docs/` 中的 MDX），所以由同一条链条处理。

## 智能体做什么

拿到任务 `T007` 到 `T008` 的 issue 后，智能体会：

1. 阅读 spec 以及第 1、2 阶段已合并的代码。spec 说明这个功能是做什么用的；代码说明它实际做了什么。
2. 更新笔记应用页面：`tags` 属性、新的 API 输入和筛选，以及规则（五个标签、唯一、不区分大小写），措辞与 spec 中的表述完全一致。
3. 复用 e2e 场景中的截图，而不是另造新的，这样文档展示的就是应用真实的样子。
4. 构建文档站点，这样失效的链接或格式错误的 MDX 会像其他任何构建错误一样让 PR 失败。

## 你要检查什么

- 页面上的每条规则是否都与 `spec.md` 中的某条需求一致？
- 如果文档和 spec 不一致，**以 spec 为准。** 修改 spec，而不是手动修改文档。
- 有没有写进文档、但代码并没有做到的东西？

## 为什么它在链条之中

事后由另一个人凭记忆写的文档会逐渐偏离。根据 spec 和已合并的代码生成、并经过同样关卡评审的文档则不会。评审智能体也是一个廉价的第二读者：它会标出没有任何测试或代码支撑的文档说法。

## 完成

合并文档 PR。由于没有剩下的智能体任务，不会再开新的 issue。这个功能从一句话走到了已合并的代码和文档，而你只做了两类决定：批准 spec，以及批准每一个结果。
